上下文工程，究竟在工程化什么？

Weaviate 用六块能力画出一张系统地图；真正的主线，是在每一步决定哪些信息进入模型、哪些状态留在外部、下一步由谁执行。

  • 全链路信息流控制：上下文工程控制的是一次任务里的完整信息流：意图、证据、提示、状态、工具和反馈 怎样进入或离开模型窗口。

《The Context Engineering Guide》是 Weaviate 发布的一本面向 AI 应用开发者的上下文工程手册。它关注一个 AI 系统怎样在任务运行过程中，持续为模型准备正确的信息，并让多轮对话、外部知识、长期状态和工具执行保持连贯。

全书围绕六部分展开：Agent 负责调度整个信息流；查询增强把含糊的用户问题改造成可检索、可执行的意图；检索与切块从大量资料中选出当前所需证据；提示规定任务目标和操作边界；记忆保存跨轮状态；工具把模型的判断变成行动，再把执行结果送回下一轮。

六部分构成了一条完整运行链：理解请求、选择证据、装配上下文、保存状态、调用工具、根据结果继续或停止。手册的核心问题，是如何让模型在每一步只看到当前最有用的信息，同时把暂时不用的状态可靠地留在外部。

02. 模型很强，系统仍可能拿不到正确上下文

真实 AI 产品的常见故障，很少只对应“提示写得不好”。模型可能没拿到公司内部资料，不知道刚发生的业务变化，记不住上一步已经确认的决定，或者在十几个相似工具中选错一个。继续加提示，最多修补当前调用，无法补齐数据、状态和行动接口。

主材料怎样画出上下文工程的边界？ Weaviate 手册系统图聚焦 01

Weaviate 淡彩指南封面把文档、用户请求、历史、记忆、模型和工具放在同一系统图中。

这里说的上下文工程，是对意图、证据、规则、状态和工具结果进行运行时选择与装配，让模型在当前一步拿到足够且相关的信息。

2.1 长上下文的四大核心风险与“注意力预算”

手册把长上下文的风险明确分成四类：

  • 污染 (Pollution) 错误内容被反复复用，形成污染：历史轮次中的推测、未经验证的假设或工具返回的脏数据，被后续多轮推理持续吸纳，导致错误滚雪球式放大。
  • 分心 (Distraction) 无关内容太多，造成分心：过量检索注入的背景碎片和庞杂文档挤占模型注意力，稀释关键提示，致使模型忽略关键指令。
  • 混乱 (Confusion) 相似材料挤在一起，产生混乱：同一实体不同时间段的多个版本记录、相似接口的重复声明，使模型无法准确辨别当前上下文的唯一真值。
  • 冲突 (Conflict) 互相矛盾的规则同时存在，形成冲突：系统全局提示与局部工具约束矛盾，新用户输入与旧上下文设定冲突，导致模型输出不可预测或决策瘫痪。

它们共同说明一个事实：上下文窗口是注意力预算（Attention Budget），容量和质量必须分开管理。

2.2 运行时的四个明确决策

因此，每轮运行都要做四个明确决策：

  1. 留存决策：哪些信息继续留在当前窗口，以支撑当前步骤的高信噪比推理；
  2. 转存决策：哪些状态转存到外部存储并按需取回，避免无谓占用宝贵的注意力空间；
  3. 压缩决策：哪些历史交互可以压缩成结构化摘要，剔除中间冗余讨论；
  4. 预留决策：要为模型的思考计划（Chain of Thought）和最终生成预留多少安全空间。

只盯着“还能塞多少 token”，就会漏掉更关键的预算问题：模型还剩多少注意力来判断下一步。

2.3 六大动作闭环与 Agent 调度职责

一套完整系统会反复经过六个动作：先理解意图，再选择证据，把规则和当前状态装配进窗口，决定是否行动，把必要状态写到外部，最后用结果修正下一轮。 Agent 是这条链路的调度者，查询增强、检索、提示、记忆和工具分别给它提供接口。

手册给 Agent 的具体任务也很清楚：

  • 定期压缩多轮历史；
  • 验证检索结果是否一致可用；
  • 删除过期或无关上下文；
  • 第一次检索失败后改写查询、切换知识库或更换切块策略；
  • 把暂时不用的细节卸载到外部；
  • 只加载当前相关工具；
  • 在多来源互相冲突时完成综合仲裁。

Agent 不替代这些技术，它负责在运行时决定何时使用哪一种。

2.4 故障排查反射弧与定位顺序

这张运行时轨道也给出了一个标准的排错顺序：

  • 回答跑偏：先查意图有没有被误解（入口意图层）；
  • 事实不对：查检索到的证据（证据与切块层）；
  • 反复推翻旧决定：查状态有没有持久化（外部工作记忆层）；
  • 工具用错：查工具合同和选择逻辑（工具定义与鉴权层）。

直接换模型往往跳过了最便宜、最可定位的故障点。

03. 第一步，把用户问题改造成系统能执行的意图

人不会按照数据库字段说话。用户可能只写“这个怎么还是不行”，把三个目标塞进一句话，或者默认系统知道“这批客户”指哪个时间段。入口不澄清，后面的检索、重排和生成都会认真优化一个错误目标。

查询重写、扩展、分解和查询 Agent 处理的是四种不同情况。

重写、扩展、分解和查询 Agent 分别适合什么？ Weaviate 手册系统图聚焦 03

重写处理含糊，扩展提高覆盖，分解处理多目标，查询 Agent 处理跨库和迭代搜索；复杂度与成本依次增加但不构成固定等级。

🎯 系统架构图 3：查询改造四大模式决策象限与工作流
对比重写 (Rewrite)、扩展 (Expand)、分解 (Decompose)、查询 Agent (Query Agent) 的适用场景、核心动作、成本阶梯与工程边界。

3.1 查询重写的三大动作与“双版本”分离

查询重写本身有三个基础动作：

  • 把别扭或省略严重的问题重新组织；
  • 删除会干扰检索的无关背景；
  • 补入目标资料常用的关键词。必要时再把复杂问题拆成子问题。

这里的目标在于为不同环节准备不同形式的查询：给检索器的版本追求匹配，给最终回答的版本保留完整意图，而非单纯润色用户原话。

3.2 复合意图拆解与多源跨库查询 Agent 实例

例如，用户提问：“帮我看看最近客户为什么流失，并找三家最值得回访”，表面是一句话，实际上至少包含三层隐式意图：

  1. 时间范围定义：“最近”指哪一个周期（过去 7 天、过去 30 天还是当季度）？
  2. 业务计算口径：“流失”要按什么口径判断（无登录行为、主动退订还是账户余额清零）？
  3. 排序决策标准：“最值得回访”由历史累计金额、活跃度粘性还是算法预测的挽回概率决定？

系统可以先重写成结构化问题，再把原因分析和客户筛选拆开检索，最后综合。若数据分散在 CRM、工单和通话记录里，查询 Agent 才需要根据各库的 schema 动态决定搜索、过滤和聚合顺序。

3.3 查询 Agent 的三个执行阶段与自愈状态

一个完整的查询 Agent 至少经过三个阶段：

  • 分析阶段 (Analysis)：判断问题类型、需要查询哪些来源（向量库/关系库/工单系统）和前置过滤条件；
  • 执行阶段 (Execution)：动态执行搜索。如果结果缺字段、证据互相冲突或不足以完成任务，它要评估缺口，改写或扩展查询后重试；
  • 可选综合阶段 (Synthesis)：只有证据齐备时，才进入综合回答。

这个循环比“一次搜索后直接生成”更贵，却能把检索失败暴露为可恢复的中间状态。

改造模式 适用场景 Token / 延迟成本 收益与优势 主要风险与副作用
查询重写 (Rewrite) 表达省略、含糊、口语化严重 极低 (1 次轻量调用) 消除歧义，提升单库关键词命中率 若过度删减可能误删用户原始意图约束
查询扩展 (Expand) 关键词覆盖率低、专业术语偏差 低至中 (多路并行) 显著提高召回覆盖，防漏检 语义发散，可能把意图越扩越远导致分心
查询分解 (Decompose) 多目标复合、多步骤因果推理 中等 (多次独立检索) 各击破子目标，保证各维度精度 增加检索调用次数与后续信息综合难度
查询 Agent (Query Agent) 跨多库异构系统、未知探索路径 高 (多轮迭代与反思) 动态调整探索路径，失败可恢复 高延迟、高成本，状态空间大且极难调试

扩展查询能提高召回，但也会把用户意图越扩越远；分解能提高精度，但会增加调用次数和综合难度；查询 Agent 能适应未知路径，同时带来延迟、成本和调试复杂度。选择标准应落在任务上：是否含糊、是否多目标、是否需要跨库、第一次检索失败后是否值得继续探索。

3.4 入口阶段必须留下的三项可检查产物

入口阶段至少要留下三项可检查产物：

  • 规范化意图：一份保留用户原话核心诉求的结构化意图定义；
  • 范围条件：一组不可越过的边界限定（如时间范围、主体 ID、业务口径）；
  • 验收句：一个说明“什么结果算回答完成”的判定标准。

没有这三项，系统很难判断后面是在探索，还是已经跑题。

04. 第二步，只把当前需要的知识送进上下文窗口

意图明确后，系统面临第二个问题：资料远大于窗口，哪一小部分既容易被找到，又带着足够语境？这就是检索和切块真正解决的事。

4.1 检索精度与语境完整度的“甜点区”

切块过小与切块过大，各有致命缺陷：

  • 切得太小：单个片段容易在向量空间精准命中，却可能丢掉主语、前置假设、生效条件和例外条款；
  • 切得太大：语境虽然完整，向量表示却被多个复杂主题平均稀释，检索相似度打折，难以被高分召回。

手册把它画成“检索精度”和“语境完整度”的甜点区 (Sweet Spot)。这个甜点区没有全行业通用数字，它随文档结构、问题粒度和下游任务改变。

4.2 六大切块策略工程特性矩阵

主流切块策略在业界可分为六种形式：

切块策略 推荐分块粒度 适用文档形态 核心优势 技术痛点与局限
固定长度切块 (Fixed-size) 256 ~ 512 Tokens 短小、格式均一的规则文本 计算速度快，极低计算开销 容易在句子中间生硬切断语义
递归切块 (Recursive) 512 ~ 1024 Tokens 通用长文档、技术手册 按段落/换行逐级降级，保留自然语义 对无明显标点的松散文本效果下降
结构/文档切块 (Structural) 按章节/函数自适应 结构清楚的 Markdown / 代码 AST 天然与业务逻辑边界（类/函数/章节）重合 对无结构的纯纯文本无效
语义 / LLM 切块 (Semantic) 动态主题边界 多主题混杂的深度研报、复杂对话 由模型判定主题断点，语境切换极准 切块耗时极长，计算成本昂贵
层级切块 (Hierarchical) 摘要 (大) + 细节 (小) 多层嵌套的长篇专著、法规文档 同时保留全局大纲与微观段落定位 存储开销翻倍，检索需要多层映射
后置切块 (Late Chunking) 全文输入，局部池化 兼顾长程依赖与高精度的前沿场景 使小切片向量提前“看到”整篇上下文 需专用模型支持长上下文单次嵌入

4.3 预切块 (Pre-chunking) 与 后切块 (Post-chunking) 的抉择

方法之外，还要决定何时切：

  • 预切块 (Pre-chunking)：把成本放在离线数据入库阶段，在线查询极快，但分块策略一旦确定便固化死板；
  • 后切块 (Post-chunking)：根据当前具体问题的意图动态处理全文或粗粒度块，极度灵活，但首轮检索与切块显著推高延迟。
文档结构、变化频率和延迟要求怎样共同改变切块方案？ Weaviate 手册系统图聚焦 04

结构清楚优先按文档或递归切块，结构松散优先递归或语义切块；内容频繁变化且可接受额外首轮延迟时考虑后切块，否则优先预切块。

4.4 任务级评测四要素与厂商视角反思

选择之后还要做任务级评测 (Task-Level Eval)。建议准备一小组真实任务集，每题标出必须命中的原始段落，然后严格核验四项指标：

  1. 答案覆盖性：检索出的片段集合有没有完整覆盖生成回答所需的全部信息？
  2. 限定完整性：片段是否带着必要的时间、权限、前置假设等限定条件？
  3. 噪音占比：无关片段占了多少（无关片段过多会直接造成模型分心）？
  4. 溯源保真度：模型给出的最终回答能否逐字逐句回到原文段落？

若只看向量相似度或演示中的一个成功案例，切块策略很容易在换文档后失效。

这也暴露了材料的厂商视角：Weaviate 自然把向量数据库放在中心。生产系统还可能组合关键词检索 (BM25)、关系数据库、文件索引、事件日志和直接工具查询。检索层的目标是拿到可用证据，不是证明某一种存储方式先进。

05. 第三步，用提示和记忆把一次调用接成长任务

检索结果不会自动变成好上下文。系统还要决定任务规则、证据、最近对话、工具说明和输出空间各占多少；哪些细节只在当前步骤有用，哪些状态值得跨轮保存。

5.1 提示作为控制层：输出合同与可审计产物

提示在上下文工程中承担控制层职责：定义目标、边界、工具触发条件、参数格式、返回值和完成标准。

手册介绍了 few-shot、Chain of Thought (CoT)、Tree of Thoughts (ToT) 与 ReAct。真正可迁移的工程部分，是用范例固定输出合同、把复杂任务拆成可检查阶段、让行动结果进入下一轮。

无需要求模型展示私有内部推理；计划、工具参数、执行结果、引用和状态变化已经足够工程审计。

5.2 五层记忆架构与生命周期门禁

记忆则把时间尺度拉长。真实系统不能只有一个单向增长的对话历史，而必须划分为五个清晰层级：

  • 当前上下文窗口 (Current Window Context)：仅保存最近消息和这一步必需的材料，属于临时易失性高频缓存；
  • 工作状态 (Working Memory / Task State)：保存一个多步任务尚未完成的状态、已确认的关键决断与当前待办；
  • 情景记忆 (Episodic Memory)：记录发生过的具体事件、会话交互轨迹与历史案例；
  • 语义记忆 (Semantic Memory)：保存跨任务可复用的稳定事实、专业领域知识与实体属性；
  • 程序记忆 (Procedural Memory)：保存经过实战检验、被证伪与被优化的做事方法与工作流 SOP。

它们的存放位置、写入门和清理门截然不同。

5.3 记忆系统的五大工程问题与“防污染”铁律

“什么都存”会制造另一种遗忘：重要信息被重复、过期和低质量记录淹没。 一个可用的记忆系统至少要回答五个问题：

  1. 谁可以写入？ 必须有明确写入权限控制，避免任何临时中间思考或未经验证的幻觉直接写入长期存储；
  2. 凭什么写入？ 写入需满足确证标准（如人工确认、工具校验通过、成功测试通过）；
  3. 怎样合并冲突？ 当新的业务事实与旧条目矛盾时，需按时间戳、信任权重或语义重消歧进行合并覆写；
  4. 什么时候取回？ 并非每轮全量召回，而是根据当前任务阶段与子目标按需触发针对性检索；
  5. 何时过期或删除？ 设置生存时间 (TTL) 或衰减遗忘曲线，清理失效过时数据。

检索质量和写入质量同样重要；错误记忆被反复取回，会把一次失误扩散成长期偏差。

5.4 任务导向的记忆选型与取回优化

记忆架构必须服从任务：

  • 客服 Agent：更依赖能还原用户交互历史的情景记忆；
  • 财报分析 Agent：更依赖稳定的领域事实与权威财务口径（语义记忆）；
  • 轻量级简单任务：可以先用最近若干轮对话的滑动缓冲区，不必一开始就搭建庞大沉重的长期记忆库。

取回记忆也不能只做一次盲搜。手册给出的改进路径包括：

  1. 先扩大或迭代查询：先依据上下文意图生成候选查询集；
  2. 用重排器 (Reranker)：把真正高度相关的关键记录推到最前面；
  3. 必要时启动查询 Agent：跨多个知识集合或业务表继续搜索；
  4. 结合个性化逻辑：将用户特定业务偏好和交互历史融入最终排序。

能存下来只是第一关，能在正确时刻取回正确一条才是记忆系统的核心能力。

5.5 上下文卸载 (Context Offloading) 的最轻量工程落地

手册把上下文卸载写成“把信息放到窗口外，需要时再取回”。现实中，最轻量的工程实现往往是一份结构化任务状态表：

状态字段 (Field) 工程含义与内容规范 更新时机
target_goal 任务全局终极目标与明确的验收句 任务开始时确立，全局不可变
completed_steps 已执行并已校验通过的历史步骤列表及核心结果摘要 每个工具或子步骤执行成功后追加
confirmed_decisions 用户明确确认的约束参数、业务口径、排他选择 用户给出确定指令或多选定案时写入
pending_issues 当前阻塞点、待验证假设或待用户澄清项 遇到局部异常或歧义时登记，解决后清退
evidence_refs 已定位原始资料的绝对路径、文件偏移或外部 ID 索引 检索召回后记录指针，而非全量文本复制

这份结构化任务状态比保留全部聊天记录更便宜，也更容易在每一轮由模型或系统自动化验证。

连接成功只说明接口可用，无法证明 Agent 会在正确时间、用正确参数、经过正确授权调用它。

6.1 单工具调用 vs 工具链的复杂度跃迁

单个工具调用和工具链是两种完全不同难度的工程级别：

  • 单工具调用：查一次航班，只需在上下文提示中选中该工具、提取城市与日期填好参数、解释返回结果，单步即告终结；
  • 复杂工具链 (Toolchaining)：规划一次周末旅行，可能要依次查询航班、酒店和当地活动，还要把前一步结果转化为后一步的动态时空约束。工具链成倍增加了计划顺序、中间状态累积、局部失败回滚与停止收敛条件。

6.2 可靠工具循环的七个检查点

一个工业级可靠的工具循环，至少包含七个严格的检查点：

  1. 发现可用工具：获取当前已注册的工具集元数据；
  2. 筛掉无关工具：根据当前意图过滤干扰，避免向窗口塞入几十个无关 Schema；
  3. 选择或规划：由模型决策调用哪一个（或哪一组编排）工具；
  4. 构造参数：按照 JSON Schema 格式化参数并补充类型；
  5. 经过授权检查：确认敏感写操作或高危调用已获得权限批准；
  6. 执行并校验 Observation：捕获执行结果，截断超大体积并校验返回值有效性；
  7. 控制转移决策：判断是继续执行下一步、更换重试策略、向用户提问澄清，还是彻底完成停止。

6.3 参数构造陷阱与“错误反馈自愈”闭环

参数构造是最容易被低估的一关。 Agent 即使选对工具，也可能漏掉必填字段、混淆时间单位（秒 vs 毫秒）或生成格式错误的参数。

手册中的例子展示了一个关键的可恢复路径：

首次调用因参数不合格而报错，错误堆栈与校验失败原因作为 Observation 回到上下文窗口，Agent 据此精准读懂错误信息，修正参数格式后再次发起执行。

所谓自我修正（Self-Correction），必须落到“读懂错误—改变参数—重新校验”的可观察过程，不能只写一句“模型会自动反思”。

6.4 工具合同规范与返回体积截断控制

工具描述本身就是注入模型上下文的核心提示词。一个高可靠的工具合同（Tool Contract）必须写清七个要素：

合同要素 规范要求 反模式防范
动词定义 (Verb) 精准动词（如 fetch_order_detail、cancel_subscription） 杜绝多合一的模糊操作词（如 manage_order）
适用范围 (Scope) 清晰声明何时触发、何时绝对不应调用本工具 未声明互斥场景，导致模型在 3 个相似工具间反复摇摆
必填参数 (Required) 明确标注 required 列表及字段含义 全量可选字段导致模型漏传关键业务主键
单位与格式 (Format) 强制限定 ISO8601、分/元、Unix 秒级戳 未限定日期格式致使模型输出 "yesterday" 传给 SQL
返回结构 (Return) 声明结构化 JSON Schema 与关键状态码 非结构化纯文本导致下一步解析逻辑崩溃
错误状态 (Errors) 枚举可自愈错误与不可恢复错误 遇到 404 错误陷入无限重试死循环
调用限制 (Limits) 注明限流 QPS、单次返回分页大小上限 未限分页单次拖出 50,000 条记录塞死窗口

工具返回也要严格控制体积：把几万行日志原样塞回窗口，会让下一步决策被噪声彻底拖垮。保留高信息量摘要、关键核心字段、原始日志存储位置和可复查引用，系统通常更稳。

6.5 MCP 协议的解耦价值与清醒认识

MCP 的真正工业价值在于降低重复适配成本：

  • 传统方式：M 个 AI 应用分别对接 N 个外部系统，最坏需要维护 M × N 组定制化驱动与接口转换；
  • 标准协议：让应用端和服务端各自适配一次标准协议，把连接复杂度彻底收敛为 M + N。

它提高的是模块可组合性，不是调用可靠性。官方规范里的基础原语包括 Resources、Prompts 和 Tools，远不止“给模型接工具”。

它仍然不替应用决定：权限审批、数据边界隔离、并发幂等、指数退避重试和任务停止条件。把 MCP 接通当成 Agent 完成，是把插座装好误当成电器已经安全运行。

6.6 多 Agent 架构的上下文隔离收益与协同成本

多 Agent 同样严格遵守上下文注意力的经济学规律：

  • 收益：专业子 Agent 可以各自带着干净、极简的上下文并行处理窄域任务，主调度 Agent 只接收经过压缩的高信噪比结果，避免单窗口超载；
  • 代价：任务拆分逻辑复杂化、证据回传丢失语境、跨 Agent 状态冲突合并以及共享状态同步变得极其困难。

任务没有明显并行收益时，单 Agent 加清楚的工具合同与显式工作状态，往往比多 Agent Fleet 更容易验证和排错。

5. 行动层 (Action) 强类型参数结构体 + 执行授权审计日志 工具选错、参数格式报错、越权违规 强化工具合同中的动词、Schema 类型、单位与边界描述；完善授权拦截器。
6. 反馈层 (Feedback) 校验通过的 Observation + 停止判定 死循环重试、遇到错误无法自愈、崩溃退出 把错误堆栈结构化注入下一轮窗口驱动自愈；设置硬性最大步数熔断。
