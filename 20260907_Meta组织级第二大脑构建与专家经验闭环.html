一分钟速览与核心问题

📌 核心洞察摘要

1. 隐性经验的本质是决策边界： 专家经验包含适用条件、判断顺序和例外边界；只留下最终结论，AI 仍难以复用。

2. 知识陈述与推理程序分离： Meta 将组织知识与分析流程分开保存，让每个阶段按需读取依据，无需为知识更新重新训练大模型。

3. 反馈编译与双阶段门禁： 专家纠正经过归因、修改、原案重放和回归检查，批准后同时留下更新资产与防退步测试案例。

Meta 写了一篇技术博客，分享他们如何为合规等专业领域构建一个“组织级第二大脑”（Organizational Second Brain）。

它要把领域专家脑子里没有完整写下来的“隐性经验”沉淀下来，让 AI 学会按照内部专家的判断方法开展分析，并且不需要重新微调或训练大模型，就能通过专家的日常反馈持续改进。

这件事要解决的，是企业使用 AI 时一个很实际的问题：文档已经接进去了，为什么做判断时还是得找专家？专家纠正过一次，为什么下次还可能答错？

当下的核心痛点：为什么普通 RAG 无法胜任专业判断？

在合规评估中，找到一条规定，只是工作的开始。真正费时间的是判断：这条规定适不适用于当前产品？公司过去如何处理类似情况？哪些条件必须满足？什么情况需要交给专家决定？

Meta 在合规领域遇到的困难，集中在三个方面。

第一，专家知道怎么判断，但文档没有把“为什么”写清楚

“隐性经验”（Tribal / Implicit Knowledge）包括专家习惯先看什么线索、怎样排列因素的重要性、旧结论在什么条件下有效，以及什么时候应当停止推断、找人讨论。有时专家已经熟练到不会主动解释这些步骤，历史记录便只留下了最终结论。

例如“允许小范围试用”是一条结论，却还没有告诉后来的人：试用面向谁、使用什么数据、出了问题能不能撤回。下面用一组教学规则把这些隐藏条件具体化：只有内部测试、模拟数据、可回退三项同时满足，才进入常规试用评审；其他情况转专项人工评审或补材料。 这是帮助理解的虚构规则，不是 Meta 的内部制度。

⚖️ 教学案例：哪些隐藏条件会改变试用判断？

进入常规试用评审的严苛准则： 内部测试、模拟数据、可回退三项同时满足。这里决定评审路径，常规评审仍需完成，并不等于已批准上线。

教学规则分支：

  • 三项全满足 → 走常规试用评审流程；
  • 已知存在对外开放、真实数据或无法回退 → 转专项人工评审；
  • 尚不能确认数据范围且没有已知排除条件 → 先补材料，绝不猜测条件已满足。

改变试用人数，未必改变评审路径；把模拟数据换成真实用户信息，即使人数不变，也可能需要另一种评审。专家经验里包含的正是这种取舍：什么只是表面相似，什么才会改变判断。

将这些经验写下来，也不只是给旧文档做摘要。摘要可能仍是“项目获准试用”；可复用的知识则要保留适用条件、排除情形、判断依据和未决问题。原文介绍了从文档中离线提炼、再用专家反馈更新的办法，但没有公开完整提炼算法；文档中没有出现、专家也从未表达的经验，不能被默认视为系统已经知道。

第二，大模型懂一般知识，却不知道这家公司采用什么标准

同样一项业务，行业里可能有几种处理方式，但公司已经基于历史经验、业务方向或风险承受能力，确定采用其中一种。

通用模型可以列出几种方案，却不知道公司已经做过这个选择。它给出的建议未必没有道理，但仍需要内部专家重新判断、修改。

缺的就是组织自己的立场（Organizational Stance）：面对这个问题，我们采用什么解释，又有哪些不能越过的边界。 即明确区分通用模型“可以怎么做”（What an organization could do）与企业在自身语境下“应当怎么做”（What an organization should consider doing）。

第三，RAG 能找资料，却不能省掉每次重新梳理判断依据的工作

RAG（检索增强生成）可以在回答前查找相关文档。但检索结果可能同时包含旧项目记录、现行规则和只适用于特殊情况的例外。

如果没有提前整理，AI 每次都要重新判断：哪份材料优先？哪些条件适用？几份资料之间有什么关系？

这既费时间，也容易导致同类问题得出不一致的结论。专家纠正了一次，如果纠正只留在聊天记录中，没有进入知识或流程，下一次分析仍可能重走同一条错路。

所以，Meta 要补上的两项能力很明确：把专家使用的判断条件提前写清楚；把后续纠错真正更新到系统中，并检查更新是否有效。

系统核心设计：支撑第二大脑的四大支柱

Meta 将系统拆成四层，让判断依据、执行步骤、验收标准和反馈更新各有明确职责。

系统层级 核心职责 输入与产出物 解耦收益
1. 知识架构层 (Knowledge) 保存机构采用的权威判断标准、立场、术语定义与准入门槛 200+ 结构化纯文本文件，声明 YAML 依赖图谱 文件结构化，使自动化文本编辑与精确 Diff 成为可能
2. 推理配方层 (Reasoning Recipes) 规定如何分步完成分析，每一步何时加载何种知识 命令式工作流程序，主配方调度子程序，渐进式披露 显式操作程序使故障归因精准，区分知识缺失与流程缺陷
3. 评测框架层 (Evaluation) 自动化质量门禁，阻断退步与破坏性修改 双盲定向重放用例 + 领域全量基准回归测试集 严格门禁拦截副作用，保障每一次系统改动“零回归”
4. 自改进闭环 (Self-Improvement Loop) 将专家自然语言反馈编译为受控的文件修改与测试 多智能体编译补丁、对抗审查、Linter 检查、30秒 PR 落地 无需重新训练模型，专家纠错一次永久生效且持续沉淀

图 1：四大支柱互锁机制——知识提供标准边界，配方规定分析路径，评测拦截潜在退步，闭环将专家自然语言反馈编译为受控文件变更。

这四层相互依赖：知识有明确的文件边界，才能精确修改；分析有明确步骤，才能定位失误；评测决定修改能否通过；改进循环则把结果更新回知识和流程。

支柱 1：知识架构层——把专家每次都要解释的内容，提前整理好

Meta 先对原始文档进行离线处理，提炼其中的组织判断，整理出 200 多个结构化文本文件。

这些文件采用严格的分类法分为四类：

  • 立场文件（Position Files）： 公司对某个问题采用什么解释，适用条件和限制是什么，以及机器可执行的触发条件。
  • 分类与词汇文件（Taxonomy and Vocabulary Files）： 团队使用的术语分别是什么意思，作为全机构唯一的术语定义基准，避免同一个词被理解成不同概念。
  • 路由索引（Routing Indexes）： 根据当前任务的特征，找到适用的规则和分析流程，减少仅凭文字嵌入相似度选资料带来的不可审计性与漂移。
  • 入口检查文件（Gateway Files）： 先判断当前任务是否属于某类专业分析的适用范围，避免一上来就套错规则。

图 2：知识系统采用 YAML Frontmatter 显式维护 triggers、depends_on 与 referenced_by 双向依赖图，为自改进闭环中的影响范围分析与静态 Linter 检查提供图谱基石。

入口检查先回答“当前任务是否属于这个分析范围”；路由再回答“进入之后该使用哪些规则”。一段文字很相似，不代表它适用于当前任务；明确的触发条件让选用依据有据可查。

沿用试用例子，一份可用的知识卡可以写成结构化文本：

KNOWLEDGE-CARD: trial_review_standard.yaml 
组织立场：满足内部测试、模拟数据、可回退，进入常规试用评审。
适用范围：功能试用申请。
排除情形：对外开放、使用真实用户信息，或无法回退。
信息不足：先补齐材料，不猜测条件已经满足。
依据：教学例子中的专家补充说明。
使用者：试用评审流程、材料检查清单。

资料也不必全部塞进 Wiki。Meta 按照信息密度与使用频率严格分工：

  • 高密度 Wiki 知识库： 经常使用的提炼规则、立场与边界，信息密度极高，驻留在结构化文件中。
  • 低密度按需 RAG 检索： 具体产品规格说明书、长篇历史审计细节等，按需通过向量或关键字检索。常用不等于整份文档都要常驻上下文。

支柱 2：推理配方层——把专家的分析方法写成步骤 (Recipes)

有了正确知识，AI 仍可能用错顺序、漏查条件，或者过早下结论。

因此，Meta 另外建立了称为 Recipes 的分析流程，规定先检查什么、在哪一步加载哪些知识，以及什么才算完成分析。

核心架构原则：知识文件告诉 AI“采用什么标准”（What it knows），流程文件告诉 AI“怎样用这些标准完成这次任务”（How it reasons）。 流程引用知识文件，不把领域事实重复写进步骤；知识文件陈述立场，不规定操作程序。

顶层流程根据任务调用不同的子流程，每个子流程负责一个分析阶段。分阶段执行时，每一步只加载当前需要的指令和资料。以教学案例为例，入口阶段先确认是不是试用申请；查标准时拿立场文件；核实条件时再查这次产品的数据范围和回退材料。

💡 渐进式披露（Progressive Disclosure）的技术收益

不采用单次将所有 200+ 知识文件注入 Prompt 的朴素做法，而是由 Recipe 按需串行加载：入口网关 → 对应立场 → 专有证据 → 人工裁决。

实测数据： 该设计直接将每轮对话消耗的 Token 减少约 80%，同时消除了长上下文导致的“迷失在中间”（Lost in the Middle）与注意力衰减，故障归因路径清晰明确。

人机协同：该让专家介入的地方，明确停下来

Meta 强调在合规等高风险领域，AI 不是黑盒替代者，而是专家的力量倍增器。系统保留了两种贯穿全流程的人工介入方式：

  • 检查点（Checkpoints）： 设在预定的分析节点。AI 展示中间判断与引用依据，专家确认后再继续，也可以当场纠正方向。
  • 升级转人工（Escalations）： 用于无法可靠判断的情况，例如必要信息缺失，或者证据在业务上支持多种合理解释。此时系统严禁随意脑补推测，必须原样移交专家定夺。

自进化飞轮：专家纠错编译器与四大自优化阶段

系统真正积累经验的地方，是专家纠正之后发生的事情。一句“这个结论不对”，不能直接变成可靠的知识更新。Meta 把这项维护视为“编译”（A Compilation Problem）：将自然语言反馈转成精确、可检查的文件修改。

⚙️ 编译闭环四大执行阶段深度展开

1. 根因归因（Diagnosis）：到底是缺知识，还是用错了知识？

团队早期尝试按专家说话的形式分类（补充信息算知识，纠正方向算流程），但彻底失败了，因为同一句纠错可能指向不同根因。现在的做法是：系统查看 AI 当时实际加载的全部清单，执行核心可达性判定测试：凭当时拿到的材料，AI 本来能不能得出正确结论？

  • 资料根本没写对应条件 → 知识盲区（Knowledge Gap），补立场文件；
  • 资料已有明确条件却被 AI 漏查 → 流程缺陷（Recipe Flaw），修改排查步骤；
  • 专家自身存在不同解释 → 主观分歧（Ambiguity），交人工研讨。

2. 手术刀式编辑与对抗审查（Surgical Editing & Adversarial Review）

改动尽量小，影响要查清。系统采用双重安全网：

  • 对抗性独立审查 Agent： 在一个全新的空白上下文只看修改 Diff，以“找茬”为使命，专门寻找矛盾和被破坏的历史立场。
  • 确定性静态 Linter 检查： 纯代码程序，硬性拦截失效引用、标识符冲突、文件体积超标和依赖循环等结构性错误。

3. 两阶段防退步测试（Two-Stage Regression Testing）

  • 原案例双盲重放（Targeted Replay）： 重新运行触发纠错的场景。执行 AI 不知正在受测，裁判 LLM 仅看输出与专家原始标准，不知道具体改了哪行文件，杜绝偏见。
  • 全量基准回归测试（Regression Testing）： 运行领域已有的基准测试集。解决“全部转专项虽修好原案，却导致模拟数据常规案例被误杀”的副作用。

4. 资产入库与滚雪球（Landing & Enrichment）

专家以 PR 形式在 30 秒内快速审核并批准落地。批准后产生两份永久资产：

  • 更新后的纯文本知识或配方；
  • 新增进回归测试库的测试用例与标准答案。 保证以后无论如何迭代，模型都不会在同一个坑里跌倒第二次。

  • 单次评估从数天缩短至数分钟： AI 承担了绝大部分繁重繁琐的信息收集与初筛工作，专家精力得以聚焦在真正存在业务分歧与法律模糊地带的高价值决策上。
  • 输出可用性明显提升： 领域专家（SMEs）评价智能体输出“几乎始终有用（useful almost all the time）”，相较早期需要专家通篇大幅推翻重写，形成了本质飞跃。
  • 每轮 Token 消耗约降低 80%： 这一收益主要来自配方驱动的阶段化按需加载，彻底取代了一次性向大模型灌入巨量无关材料的暴力做法。
  • 知识维护与更新显著提速： 自动改进闭环能在几分钟内产出通过双重验证的纯文本补丁，而此前人工排查依赖、协调规则可能耗费数周的工程开发周期。
  • 演化周期中未观察到回归： 每次被批准的修复都会自动将原案例及其标准答案补充到全量回归测试集，为未来的所有更新筑牢了堤坝。
⚠️ 工程实证与严谨性边界声明

这些是 Meta 在内部特定合规领域描述的真实成果。“零回归”特指在已运行的自动化测试集覆盖范围内未出现性能退步，并不等于数学意义上的绝对零故障。任何企业在落地该架构时，必须根据自身业务特点构建高质量的领域评测集。

这套实践给所有正在推进大模型落地的企业提供了一个极其清晰、可落地的工程方向：让 AI 学会专业判断，必须同时具备判断依据、执行方法和验收标准。

企业常见错误做法 Meta 第二大脑破解之道 核心工程本质
只堆砌原始文档库，指望模型通过语义向量匹配“自己悟出来” 离线提炼为 200+ 结构化立场文件，声明明确边界与 YAML 触发规则 知识预提炼与边界明确化，把陈述性事实整理成结构化资产
把所有业务规则塞进一段巨大、混乱的 System Prompt 将流程解耦为可组合的 Recipes，顶层配方调度子配方，阶段化按需披露 命令式流程与陈述性知识彻底解耦，消除注意力衰减
专家在聊天框纠错一次，下次分析同类问题依然答错 专家反馈视作编译输入，经对抗审查与双阶段验证门禁后形成受控 PR 无需重训模型的代码化演进闭环，纠错永久积累

这种体系尤其适合以下特征的企业核心业务场景：

  • 专业经验高度集中： 极少数核心专家把持关键决策，业务经验难以成文扩散；
  • 判断一致性要求极高： 同一类型的产品或业务，绝不允许前后出现标准打架或合规漏洞（如合规评估、财务风险审查、工程安全规范、供应商资质评审等）；
  • 业务通量远超人力负荷： 海量业务申请导致专家沦为“常规问题问答机”，无法聚焦高风险特例。

组织级第二大脑的终极价值，就是让专家花时间纠正一次之后，后续任务能够持久使用这次经验，并以工程化的自检门禁确保它永远不会丢失。
