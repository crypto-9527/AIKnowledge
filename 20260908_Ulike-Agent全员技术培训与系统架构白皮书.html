01 · 产品定位与功能全景

01 产品定位与核心功能全景

Ulike-Agent 不是一个简单的通用 Agent 对话 Demo，也不是散乱的 Python 脚本或模型 API 集合。它是专为企业私有数据构建的企业经营认知与决策运行时（Enterprise Cognition & Decision Runtime）。

核心设计命题：
正确业务语义 × 企业 Know-how × 权限治理 × 证据链 × 可恢复执行。
大语言模型（LLM）在本系统中被严格定位为可替换的无状态推理组件，绝不是业务事实源。业务事实源永远由企业数据资产、语义层模型（MDL）、不可变审计账本与严格权限上下文共同定义。

1.1 传统企业 AI 经营决策的六大痛点与 Ulike 破解之道

① 凭空幻觉与算术捏造 已攻克

痛点：传统 Agent 自由生成 SQL 或心算利润，容易编造假数据与错误加总。
破解：引入 Wren MDL 语义模型约束 NL2SQL，服务端强制基于 DB 富化数据，严禁模型裸算关键数值。

② 指标语义与口径漂移 已攻克

痛点：不同业务线对“GMV”、“净收入”、“毛利率”定义不同，导致模型各执一词。
破解：建立声明式 packs/domains/ 业务包，将 Metric/Entity/Relationship 统一治理与版本化。

③ 越权访问与数据泄漏 强门禁

痛点：普通成员通过 Prompt 注入绕过权限查阅全集团薪酬或财务核心大盘。
破解：服务端上下文可信推导 Org Scope，强制行级数据过滤，浏览器零接触服务秘钥。

④ 粗暴片面的因果归因 核心特色

痛点：将 618 大促后的自然周期回落误判为“产品力暴跌”，给出荒谬调价建议。
破解：设立经营归因四道闸（DTD 对齐、大促 YoY 对齐、正交分解、四态账本校验）。

⑤ 止步看数与割裂执行 闭环治理

痛点：看完分析报告还要切换 ERP 手工调价下工单，信息流与工作流严重断裂。
破解：报告尾部直出结构化 Action Chips，支持一键拉起下游巡检、调价与补货流程。

⑥ 破坏性操作无风控脱轨 L0~L3 门控

痛点：智能体自动执行降价或清仓，引发灾难性资损。
破解：两阶段暂存写（Staged Changes）+ 双重变动幅度硬上限拦截 + L3 人工审批（HITL）。

02 · 核心业务场景与适用条件

02 核心业务场景与适用条件

Ulike-Agent 针对企业内部不同岗位与决策复杂度，清晰划分了四类典型业务落地场景，并建立了严格的准入前置条件与边界约束。

场景 A：日常指标多维即席问数 只读快速链路

典型用户：运营、销售主管、客服管理者。
典型诉求：“查询上周华东大区各品类脱毛仪的退款率排行”、“近 30 天抖音渠道直播间场观与转化率走势”。
执行特征：走 Single Primary Loop 快速流式响应，毫秒级意图判断，生成只读 SQL 并返回图表与数据引用卡片。

适用条件：指标已在 Wren MDL 建模；用户具备对应 Org Scope 权限；只读操作，时延要求 < 3s。
场景 B：大促与季度经营深度归因 深度算子链路

典型用户：品牌操盘手、经营分析师（BI）、财务总监。
典型诉求：“为什么 618 结束后某爆款产品 GMV 环比暴跌 42%？到底哪个环节出了问题？”
执行特征：触发 Sales 场景主链，强制加载归因四道闸，调用 Python 算子完成价量、结构与时空正交分解，产出深度诊断。

适用条件：必须通过 ULIKE_ENABLE_SHADOW_SALES_SCENARIO 授权，强约束先验对齐，支持 Detached Run 脱机计算。
场景 C：管理层交互式自包含研报 一等公民 Report

典型用户：高管会汇报、跨部门经营月会、战略投资人。
典型诉求：自动生成可下钻、可筛选的自包含 HTML 经营白皮书，带下钻图表且断网脱机双击可用。
执行特征：生成标准 Report IR，后端富化真实指标，前端严格沙箱受控挂载，杜绝静态 PDF 无法下钻的弊端。

适用条件：报告中的每一条结论必须带有 Citation 数据溯源，初始渲染禁用脚本，由用户显式点选授权。
场景 D：滞销巡检与受控调价闭环 高危 L3 审批

典型用户：品类运营总监、定价委员会、供应链负责人。
典型诉求：对周转天数超标的滞销批次执行促销折价，或调整渠道采购配额。
执行特征：报告末端直出 Action Chips，触发算子生成不可变 StagedChange 差异单，必须由主管在审批面板 CAS 批准后执行。

适用条件：受限于调价双重安全护栏（永久调价幅度硬上限 + 底价穿透拦截）；必须留存不可篡改的审批收据（Receipt）。
03 · 全栈技术架构与数据流转

03 全栈技术架构与数据流转

Ulike-Agent 采用清晰解耦的分层微服务编排架构，包含主前端 UI 与同源 BFF、Java 编排控制面、Python 数据分析执行面、以及 Wren 语义层全栈。

3.1 核心技术选型深度剖析（为什么这么选？）

选型维度 当前选型方案 被否决的替代方案 架构权衡理由与实证依据
控制面持久化 SQLite Local-first (WAL)
control.db / tool.db		 远程共享 MySQL 实例 / PostgreSQL 1. 消除外部运维耦合与死锁：早期生产 RDS 存在连接池耗尽、超时、且 explicit_defaults_for_timestamp=0 致建表崩溃；
2. 单机独占锁与极速启动：采用 SQLite WAL 模式读写分离，应用启动时自愈补表，毫秒级就绪，完全满足单机控制面的高可靠需求。
语义问数层 Wren MDL 语义建模
Ibis + Qdrant 向量召回		 让 LLM 直连只读库写 SQL (Raw NL2SQL) 1. 口径收敛：业务指标必须通过声明式模型建模，禁止模型自由发散关联表；
2. 安全隔离：通过 MDL 语义中介生成标准化 SQL，彻底消除 SQL 注入风险与跨表笛卡尔积。
服务端双栈 Java 编排 + Python 执行
Spring Boot + FastAPI		 纯 Python 全栈 / 纯 Node.js 全栈 1. Java 控制面的严谨性：擅长处理复杂任务状态机、Detached Run 断线重连、严格的并发锁与持久化审批门禁；
2. Python 工具面的敏捷性：擅长执行 Pandas/NumPy 矩阵运算、数据科学拆解算子与大模型生态集成。
前端与 BFF Open WebUI + 同源 BFF
端口 :3080		 独立维护 Legacy React 前端 (:3000) 1. 交互减法与分层配置：吸收开源 Open WebUI 优秀的成熟交互体系，对普通业务人员隐藏底层复杂运维项；
2. 零密钥泄露：BFF 在同源转发中自动注入后端 Service Keys，浏览器完全与密钥脱钩。

3.2 端到端数据流转全景（从输入到呈现）

  1. 请求入站与凭据剥离：客户端向 Open WebUI 发起请求；BFF 在 /api/ulike/* 校验用户 Cookie，提取可信 userId 与 tenantId，注入托管的 GENIE_API_KEY，转发至 genie-backend:8080。
  2. 三层提示词信封组装 (ContextEnvelope 缓存机制)： 后端拦截器按 Global Static（领域定义） → Session Stable（当前会话约束） → Volatile Tail（动态消息）组装 Prompt，时间戳截断至小时，保证大模型 Prompt 缓存命中率达到 80%+。
  3. 动态预算递减 (Budget Control)： 进入 LLM 前调用 getRemainingBudgetMillis 检查毫秒级预算，OkHttp 请求超时设为剩余预算最小值；若预算耗尽直接抛错阻断，防止级联雪崩。
  4. 意图分流与算子计算： 单点问数路由至 Wren AI Service 查询只读业务库；深度销售异动路由至 genie-tool:1601 触发四道闸先验校验，执行正交价量拆解并组装 Report IR。
  5. 流式响应与脱机托管 (Detached Run)： 后端以 SSE (Server-Sent Events) 流式推送事件，使用本地单调自增序号作为游标；若前端异常断开，后端通过 (ownerId, sessionId, originalRequestId) 三元组继续执行，支持重连后追平日志。
  6. 前端零信任沙箱渲染： 前端接收到 report 消息后，默认置于无脚本沙箱 (sandbox="allow-popups allow-forms") 中进行安全展示；用户显式点选“启用交互”后，方重新挂载 allow-scripts 执行动态图表。
04 · 项目核心思想与能力边界

04 项目核心思想与能力边界

卓越的工程系统不在于它宣称能做什么，而在于它清晰地知道自己坚决不做什么，以及如何在模型不稳定时守住确定性边界。

4.1 核心设计理念

① 契约先于实现 (Contract-First)

所有跨语言（Java/Python/TypeScript）数据交互严格依赖 contracts/ 中的 Golden JSON 与 Schema 验证。任何 DTO 必须加 @JsonIgnoreProperties(ignoreUnknown = true)，消除序列化漂移。

② 失败导向关闭 (Fail-Closed)

无论发生网络抖动、预算耗尽、未配置数据权限还是权限降级异常，系统绝不采用隐式放行的兜底模式，一律采取“拒绝请求、记录审计快照、抛出可诊断异常”的安全闭环策略。

③ 状态不可篡改 (Immutability)

写操作由“草案（Staged Change）→ 审批（Approval）→ 执行（Commit）”三阶段构成。草案一旦生成具有独立指纹，执行端带版本号 CAS 推进，杜绝并发脏写与事后修改。

4.2 经营分析核心纪律：归因四道闸规范

在进行销售异动与经营复盘时，系统通过硬编码拦截器推行“四道闸门控”，彻底杜绝 AI 大模型的无端猜测：

道闸顺序 门控名称 检测原理与数学逻辑 拦截的典型错误案例
第一道闸 DTD 日历对齐闸 (Date-to-Date) 严格校准基期与报告期的自然日历错位、节假日偏移（如中秋/国庆跨周对齐），统一天数基底。 把 31 天月份与 30 天月份对比直接判定为“环比下滑 3.2%”的荒谬结论。
第二道闸 大促 YoY 周期对齐闸 大促脉冲与日常销售具有完全不同的客群心理。以大促爆发日（D0）为原点对齐，而非机械对齐公历日。 把 618 结束后第二周的断崖式回落判定为“日常客单价吸引力丧失”。
第三道闸 正交分解闸 (Mix vs. Level) 利用 LMDI 对数均值指数法，将销售总变动严格正交拆解为价格变动贡献（Price Effect）与销量变动贡献（Volume Effect），两项之和恒等于总差额，无任何残差。 既把销量上升归功于降价，又把降价当作亏损原因的双重矛盾叙事。
第四道闸 四态账本校验闸 (Four-State Ledger) 严格跟踪并分离下单态、支付态、发货态、履约/退款态。统计净 GMV 时必须剔除跨期未决退款。 因大促预售跨期退款延迟入账，导致经营分析把大额退款算入当周坏账。

4.3 治理红线与严厉禁令（工程师高压线与安全防御）

⚠️ 技术团队治理高压线：
  • 严禁模型代执行部署与服务启停：所有 Docker 编排、容器重启、服务更新一律由运维或开发人员在宿主机手动执行，模型与智能体严禁代跑部署脚本。
  • 严禁手写 PASS 自我晋级：代码编译成功、容器健康并不等同于可以切流，必须经过真实机器 Gate、Live 验证与主管签发。
  • 严禁向浏览器泄露内部服务秘钥：GENIE_API_KEY、GENIE_TOOL_API_KEY、ULIKE_BFF_API_KEY 仅驻留服务端 Compose 变量白名单，严禁在前端源码中暴露。
  • 严禁写操作绕过审批门禁：任何涉及改价、配额调整、外发推送的业务动作，必须生成 StagedChange 并挂起等待人工（HITL）确认。

06 · 生产级典型案例效果演示

06 生产级典型实操案例演示

通过三个贯穿业务全流程的真实生产案例，具象化展示系统在“大盘异动复盘”、“行级组织问数”与“受控调价闭环”中的实际效果。

案例一：618 大促后某爆款脱毛仪 GMV 异动深度诊断

业务背景与提问：
业务提问：“618 结束后第二周（W26），Ulike 经典款脱毛仪天猫旗舰店 GMV 环比断崖式下滑 42%（从 600 万元跌至 319 万元），请分析原因并给出建议。”

系统执行过程：

  1. 第一道闸（DTD 对齐）：核验 W25 与 W26 天数基底均为 7 天，排除天数不等影响；
  2. 第二道闸（大促周期对齐）：自动关联去年同期大促后走势（YoY），发现大促次周全行业均值回落 38%，属于典型的大促脉冲后消费力自然透支；
  3. 第三道闸（LMDI 正交分解）： 基期客单价 1200 元、销量 5000 件；报告期客单价 1100 元、销量 2900 件。
    总 GMV 差额为 -281.00 万元。
    正交计算得出：销量变动效应（Volume Effect）贡献了 -242.30 万元（占 86.2%）；价格变动效应（Price Effect）贡献了 -38.70 万元（占 13.8%）。
    结论：业绩下滑的核心因果驱动力在于大促后行业客流自然回落（86.2%），绝非所谓的“价格失去竞争力”！
  4. 第四道闸（四态账本校验）：发货与履约退款率在基期与报告期保持在 7.5%~7.8% 正常波动区间，无跨期延迟退款异常。
  5. 最终交付：输出 Report IR 富交互研报，末端直出 Action Chips：[巡检渠道库存]、[维持当前挂牌价]、[拉起营销老客关怀]，杜绝了盲目进一步降价的错误决策！

案例二：多维组织权限下的销售业绩即席问数

业务背景与提问：
用户身份：华南大区销售总监（所属组织：South_China_Sales）。
提问内容：“查询今年第三季度各区域自营门店的毛利率与客单价对比情况。”

系统安全控制流转：

  • 客户端不传递任何硬编码权限参数；BFF 根据当前登录会话推导 GENIE_PERMISSION_ALLOWED_ORGS = ['South_China_Sales']。
  • 后端向 Wren 发起语义查询，Wren 引擎依据 GENIE_PERMISSION_ORG_COLUMN 自动向 SQL 注入强制过滤谓词：
    WHERE fee_dept IN ('South_China_Sales')。
  • 返回数据仅展示华南大区管辖下的门店明细，其余大区自动隐藏，并附带数据血缘与表权限引证凭据（Citation），彻底防范越权横向渗透。

案例三：滞销库存巡检与受控调价闭环

高风险写操作闭环：
系统通过库存巡检算子发现某冷门批次周转天数已达 145 天（警戒线 90 天），Agent 提议：“将该批次从 1599 元促销降价至 1399 元”。

风控与审批执行流：

  • 双重幅度硬拦截检查：本次降幅为 1599-13991599≈12.5%，低于单次调价上限 15%；且折后价 1399 元高于产品底线保护价 1150 元，护栏规则 PASS。
  • 生成不可变草案：系统创建 StagedChange 实体（含唯一哈希 SHA256 与版本号 CAS），任务状态进入 APPROVAL_PENDING 挂起并持久化至 control.db。
  • 前端审批面渲染：在 Open WebUI 审批组件中呈现高亮的可视化 Diff（原价 1599 → 新价 1399，预估边际毛利 +4.2%）。
  • 人工核准执行：拥有审批权限的主管点击“Approve”，后端 CAS 验证版本一致后落库，生成不可伪造的机器收据（Receipt）存入审计账本。
