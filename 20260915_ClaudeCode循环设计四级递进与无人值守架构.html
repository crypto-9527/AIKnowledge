循环设计：从手动确认到无人值守的四级递进

Anthropic Claude Code 团队给「循环（loop）」下了唯一定义，并把早已存在的五个功能，按自主程度从低到高归位成一个四级坐标系。本文在核验英文一手源的基础上，还原被中文转述稿丢失的四条 Token 治理建议，并把三个定性命题改写为可计算模型。

一分钟速览

  • 循环的唯一官方定义：agent 反复执行一轮轮工作，直到满足某个停止条件。关键区别在于「什么时候算完成」是提前定好、交给系统判断，而不是人一轮轮盯着催。
  • 四级分类：回合制（Turn-based）、目标制（/goal）、时间制（/loop 与 /schedule）、主动式（Proactive），按自主程度从低到高递进。
  • 四个分类维度：谁触发、怎么判断停、用 Claude Code 的哪个功能实现、最适合什么任务。
  • 目标制的核心机制：引入一个独立的评估模型（evaluator）核对条件，Claude 自己不能提前喊「够了就收工」，另可设最多尝试次数上限。

循环的定义与四维坐标系

官方定义只有一句：循环，就是 agent 反复执行一轮轮工作，直到满足某个停止条件。

On the Claude Code team, we define loops as agents repeating cycles of work until a stop condition is met.

这个定义的分量在于后半句：停止条件是提前定好的。一旦停止条件外置，人在循环里的角色就从「每一步的决策者」退化为「停止条件的设计者」——这是整个 Loop Engineering 的支点。

作者按四个维度给循环分类，这四维就是后面每种循环的统一参照系：

① 谁触发
提示 → 手动 → 到点 → 事件
从「你发一句话」到「全程无人在场」
② 怎么判断停
自查 → 评估模型 → 你取消
从 Claude 自己判断，到外部评估者核对
③ 用什么功能
对话 → goal → loop · schedule
到全部原语 + workflows + auto mode
④ 适合什么任务
短 → 可验证 → 周期性 → 反复
从零散短任务到定义清晰的持续工作流
作者明确提醒：不是所有任务都需要复杂循环。从最简单的方案起步，这些模式按需选用。把「设计一个循环」当成默认动作，是这套框架最常见的误用。

第 1 级 · 回合制

这就是你每天在用的默认模式：你发的每一条提示，都开启一个由你亲手引导每一轮的循环。Claude 收集上下文、动手、检查自己的工作、必要时重复、然后回复——官方称其为 agentic loop。

维度取值
谁触发一句用户提示（手动、实时）
怎么判断停Claude 自行判断「已完成」或「需要更多上下文」
用什么功能默认对话；改善手段是自定义验证 skills
适合什么任务不属于固定流程、也不按排期来的短任务
你交出去的是「检查」

怎么让它自查得更彻底

可以把「验证」这一步做强：把你平时手动验收的步骤写成一个 SKILL.md，让 Claude 能端到端地自己检查更多东西。关键是给它能看到、量到、动手的工具或连接器。原文的判断是：

The more quantitative the checks are, the easier it is for Claude to self-verify.

原文给出的 verify-frontend-change 技能要求：任何前端改动，不许只凭「编辑成功」就报完成，得像人类审查者那样走完整流程。

  1. 启动 dev server，在浏览器打开改动的页面。
  2. 直接和改动交互：点按钮、确认状态变化、截图前后对比。
  3. 看浏览器控制台：不能有任何新报错或警告。
  4. 用 Chrome DevTools MCP 跑性能 trace，审 Core Web Vitals。

任一步失败，就修好后从第 1 步重跑，绝不交半成品。

展开：原始 SKILL.md 示例代码 
---
name: verify-frontend-change
description: Verify any UI change end-to-end before declaring it done.
---

# Verifying frontend changes
Never report a UI change as complete based on a successful edit alone.
Verify it the way a human reviewer would:

1. Start the dev server and open the edited page in the browser.

2. Interact with the change directly. For a new control (button,
   input, toggle): click it, confirm the expected state change,
   and screenshot before/after.

3. Check the browser console: zero new errors or warnings.

4. Use the Chrome Devtools MCP, run a performance trace and audit
   Core Web Vitals.

If any step fails, fix the issue and rerun from step 1 — do not
hand back partially verified work.

第 2 级 · 目标制

有时候一轮不够，尤其是复杂任务——agent 在能反复迭代时表现更好。你可以用 /goal 把「什么样才算做完」定义清楚，来延长 Claude 迭代的时间。

核心机制：当你定义了成功标准，Claude 就不用自己去判断「够好了吗」然后提前收工。每次 Claude 想停下来，都有一个独立的评估模型拿着你的条件核对一遍；没达标就把它打回去继续干，直到目标达成、或者到了你设定的尝试次数上限才真正停。

判定权发生了转移
从 Claude 手里拿走，交给一个专门核对标准的评估模型。这也是为什么「确定性标准」特别好使——通过的测试数量、清除某个分数阈值，评估模型能明确打勾，不含糊。反过来，模糊标准（「看起来不错」）会让评估模型与执行模型陷入同样的主观判断，这一级的收益就消失了。

原文示例

/goal get the homepage Lighthouse score to 90 or above, stop after 5 tries.

目标制适合有可验证退出标准的任务；你交出去的是「停止条件」，用的功能就是 /goal。管花销的办法：把完成标准和重试上限都定具体。

第 3 级 · 时间制

有些活儿是周期性的：任务不变，只有输入在变，比如每天早上汇总一遍 Slack 消息。还有些活儿依赖外部系统，最简单的对接办法就是按固定间隔去查一下、根据变化做出反应——比如一个 PR，它可能收到评审意见、也可能 CI 挂掉。

这类工作用 /loop 触发，它会按间隔重跑一句提示。停下来的条件是你取消它、或者活干完了（PR 合并了、队列空了）。

/loop 5m check my PR, address review comments, and fix failing CI

/loop · 本地跑

在你自己的电脑上按固定间隔重跑同一句提示。

你把电脑关了，它就停。适合你人在、临时盯一段的活儿。

/schedule · 搬到云端

用 /schedule 建一个 routine，把这套「定时重跑」搬到云端常驻。

你电脑关了，它照样跑。适合要长期挂着、不受你在不在场影响的活儿。

原文将 /schedule 标注为 research preview。管花销的办法原文写得很直接：Set longer intervals or react based on events rather than time——把间隔设长，或改成「按事件反应」而不是死盯时间。

第 4 级 · 主动式

前面几种原语，加上 auto mode（不用每步停下来问你要不要继续）和 dynamic workflows（动态工作流，研究预览版），能组合成一条处理长期工作的循环。触发它的是事件或排期，全程没有人实时在场。

主动式循环的停止逻辑分两层：每个具体任务达到自己的目标就退出，而整条 routine 本身会一直跑，直到你手动把它关掉。它最适合那种反复出现、定义清晰的工作流：bug 报告、issue 分诊、迁移、依赖升级等等。

五功能叠加结构

1 /schedule　定时触发 — 建一个 routine，每小时检查一次有没有新报告（研究预览版）。

2 /goal　停止条件 — 定义什么算「做完」，配合 skills 说明该怎么验证。

3 skills　校验标准 — 把「怎么算修好」固化成技能，让 Claude 能自查。

4 dynamic workflows　多 agent 编排 — 编排一批 agent 去分诊每条报告、修复、再审查修复结果。

5 auto mode　免人工确认 — 罩在最外层，让整条 routine 一路跑完，不停下来问权限。

完整提示长这样

/schedule every hour: check #project-feedback for bug reports.
/goal: don't stop until every report found this run is triaged,
actioned, and responded to. When fixing a bug, use a workflow to
explore three solutions in parallel worktrees and have a judge
adversarially review them.

翻成大白话：每小时去 #project-feedback 频道查 bug 报告；这一轮找到的每一条，不分诊完、处理完、回复完就别停；修某个 bug 时，用一个 workflow 在三个独立分支（worktree）里并行试三种解法，再让一个裁判 agent 对抗式地互相挑错。

从哪里开始 · 三个自查问题

看你已经在做的活儿，挑一个你是瓶颈的任务，问自己哪一块能交出去：

  1. 你能不能写出这件事的验收检查？
  2. 这件事的目标够不够清楚？
  3. 这活儿是不是按时间表来的？

有了想法就把循环跑起来，观察它在哪儿卡住、在哪儿越界，然后放手去迭代它。

质量保障四条

一个循环的输出质量，取决于它周围那套系统。设计系统时，官方给了四条：

① 保持代码库本身干净

Claude 会照着你代码库里已有的模式和约定走。底子干净，它跟着走出来的东西才干净。

② 给 Claude 一个自查的手段

把「什么样才算好」用 skills 固化成你和团队的标准，让它能端到端检查自己。

③ 让文档触手可及

框架和库的官方文档带着最新的最佳实践，别让它凭旧记忆瞎猜。

④ 用第二个 agent 做代码审查

一个上下文全新的审查者偏见更少，不受主 agent 推理的影响。可用内置 /code-review，或接 GitHub Code Review。

Loops that write code need loops that check it.
写代码的循环，需要检查代码的循环。（原文收尾的对称性原则，中文转述稿未收录）

当某一次的结果不达标，别只停在修好这一次的问题。试着把它固化成规则，去改进整个系统，让后面每一轮迭代都受益。出错时该改的是系统规则，不是这一次的结果。

Token 治理六条

要管住 token，循环得有清晰的边界。原文给出六条可执行清单（中文转述稿仅呈现其中两条，此处按一手源补全）：

#建议原文要点与本文注解转述稿
1 为任务选对原语与模型 Smaller tasks don't need multiple agents or loops. 小任务不必上多 agent 或循环；有些任务可以用更便宜更快的模型。这条是成本量级最大的杠杆之一。 缺失
2 明确成功与停止标准 Be specific about what done looks like so Claude can arrive at the solution sooner (but not too soon). 标准要具体，让 Claude 更快到达解——但也不能太快（过松的标准会让它在未达标时就停）。 缺失
3 大规模前先试点 Dynamic workflows can spawn hundreds of agents. 先在一小块工作上评估用量，再放量。 有
4 确定性工作用脚本 Running a script is cheaper than reasoning through the steps. 例如 PDF skill 可以随附一个填表脚本让 Claude 每次直接跑，而不是每次重新推导代码。 有
5 别比需要的更频繁 Don't run routines more often than you need to. 让轮询间隔匹配被观察对象实际变化的频率。 缺失
6 复核用量 /usage 按 skills、subagents、MCP 拆解近期用量；/goal 不带参数可看当前轮数与 token 用量；/workflows 显示每个 agent 的用量，且可随时停掉某个 agent。 缺失
原文另有一句总结性判断：Your model and effort level choices are among the biggest levers on what a loop costs——模型档位与 effort 彻底性这两个旋钮，是循环成本最大的杠杆之一。这与「选对原语与模型」互为表里。

M2 · 目标制：达标概率与期望轮数

把 /goal ... stop after N tries 建模为截断几何分布：每轮独立地以概率 p 达标，最多允许 N 次尝试。这是「最多尝试次数上限」这个旋钮能带来的唯一可量化收益。

Phit(N)=1− (1−p)N · E[K]= 1−(1−p)Np = ∑k=1N (1−p)k−1 · Δ(N)=p (1−p)N−1

其中 p 为单轮成功率，E[K] 为实际执行的期望轮数，Δ(N) 为第 N 次尝试带来的边际达标概率增量。

M2

② 期望轮数远小于上限。E[K]=2.11 而 N=5，说明「上限」主要作用是给长尾兜底，而非日常开销。真正的成本大头是单轮成功率 p——把 p 从 0.45 提到 0.70，期望轮数降到 1.42，比放松上限有效得多。

M3 · 时间制：轮询延迟与成本的权衡

把 /loop T 建模为一个轮询系统：事件在时间上均匀到达，间隔为 T 的轮询对事件平均延迟 T/2、最坏延迟 T；而日均调用次数为 1440/T。这条权衡没有免费午餐：

Davg=T2 · Dmax=T · Cday(T)= 1440T×c= 720Davg×c

成本与平均延迟成反比：延迟降一半，成本翻一倍。这正是原文「把间隔设长，或改成按事件反应」这条建议的数学根据。

M4 · 脚本摊销：什么时候该写脚本

原文第 4 条建议「确定性工作用脚本，跑脚本比让模型重新推导步骤便宜」。这是一个典型的一次性投入 vs 每次摊销的盈亏平衡问题。设写并调通一个脚本的一次性成本为 S，每次让 Claude 重新推导的成本为 R，每次调用脚本的成本为 V：

Cscript(n)=S+n×V · Cderive(n)=n×R · n*= SR−V 　（要求 R>V）

由该模型得到的结论与边界

① 默认参数下 n* = 14.29，第 15 次转正。也就是说，在你判断这件事会重复做 15 次以上之前，写脚本并不划算。这给出了原文「确定性工作用脚本」这条建议的适用边界：它只对高频重复动作成立，一次性任务写脚本是纯亏损。

② 决定 n* 的是差值 (R − V)，不是 R 本身。把 V 从 60 提到 500（脚本本身很啰嗦），n* 从 14.29 跳到 30.00；而 R 只决定了曲线斜率。所以优化方向是让脚本调用尽可能轻，而不是纠结推导有多贵。

③ 存在不回本的参数域。当 R ≤ V 时（调用脚本比让模型重新推导还贵），n* 发散、永不回本。已对滑块全域扫描：R > V 的组合中，有 40,361 个组合的 n* 超出 40 次观察窗口，此时界面会显式提示「窗口内未回本」，而不是画一条虚假的交叉线。

稳健性检验记录。本模型的三个结论均已做全域参数扫描（S: 1000–40000/500，R: 100–2000/50，V: 0–500/10）。结论 ① 依赖基线假设的 S 与 R 取值，属「形状结论」；结论 ② 与 ③ 是代数恒等结论，不依赖任何参数取值，可安全外推。

落地建议与风险边界

按优先级给出可执行动作，每条附原文或本文的出处。

P0先把「停止条件」写出来，再谈循环

目标制的全部收益来自判定权外置（第 5 节）。如果写不出可量化的退出标准（通过多少测试、清除哪个阈值），那么 /goal 只会把回合制的主观判断原样搬进评估模型，收益归零，成本翻倍。落地动作：为第一个接入循环的任务写一条可自动判分的标准，再启用 /goal。

P0用 /usage、/goal、/workflows 建立成本观测

这是中文转述稿丢掉的第 6 条，也是最容易被忽略的一条。三个命令分别给出：按 skills / subagents / MCP 拆解的近期用量、当前轮数与 token 用量、每个 agent 的用量（且可随时停掉某个 agent）。没有观测就没有治理——在跑第一个长期 routine 之前就把这些命令纳入日常。

P1先小范围试点，再放量到 dynamic workflows

原文口径：dynamic workflows 单次可拉起数百个 agent。结合 M2 模型的饱和曲线，建议的做法是：先取工作量的一个小切片跑通，测出实际的单轮成功率 p，再用 M2 沙盘反解一个合理的最多尝试次数上限，最后才放量。

P1让轮询间隔匹配变化频率

M3 模型显示成本与延迟成反比，且在延迟 < 10 分钟的区间近乎垂直。落地动作：先问「被观察对象实际多久变一次」，按这个周期设 T，而不是默认用 5 分钟。能用事件触发就不要用时间轮询。

P2把高频重复动作脚本化，先算 n*

用 M4 沙盘代入你自己的 S / R / V 估算，只有当 n* 明显小于预期重复次数时才值得写脚本。注意决定 n* 的是 (R − V) 差值——让脚本调用尽可能轻。

P2为循环配一个「检查循环」

原文原则：Loops that write code need loops that check it。落地动作：接入第二个上下文全新的 agent 做审查（内置 /code-review 或 GitHub Code Review），并确保每次结果不达标时把教训固化成规则而非只修本次问题。

风险边界与不适用情形

  • 非确定性目标不要上目标制。评估模型与执行模型同样无法判断「好不好看」，此时 /goal 只会增加轮数与成本。
  • /schedule 与 dynamic workflows 均为研究预览版（原文标注），接口与行为可能在正式版中变化，不要建长期依赖。
  • 主动式循环的停止逻辑是分层的：单个任务达标即退出，但整条 routine 会一直跑到你手动关闭。忘记关掉的 routine 是持续的成本泄漏源。
  • auto mode 免人工确认意味着权限边界被整体放开。在接入写权限、外网访问或生产数据之前，必须先用只读任务验证循环的行为边界。
  • 本文三个模型的参数均为假设值，形状结论可外推，具体数值不可直接引用。
