从 Harness 到 Fleet：
下一代 Agent 工程体系

一份学术论文证明了「单个 Agent 的执行框架可以被元模型按需即时生成并持续演化」；一套 2000 小时工程实战展示了 「数十个 Agent 并发运行时该如何物理隔离、排队论限流与工程治理」。本文把两者融合为一条闭环因果链， 拆解接缝处那道关乎成败却鲜少被提及的演化真值断层，并把全部可计算部分落成可交互的数学模型。

理论 · arXiv:2608.25593（NUS LV-Lab，2026-08-26） 实战 · David Ondrej 2000h Agentic Engineering 核验 · 实测数据与示意参数严格分离标注

全文摘要（TL;DR）

  • 核心实证事实：不动模型权重，仅替换外层执行框架，成绩即可出现 20 分级别的差距，且性能上升的同时成本下降 36.0%。大量 Token 并非死于任务难度，而是死于不适配的静态框架。
  • 协议降维机制：把框架收敛为四元组 h = (M, P, A, F) 后，框架设计从「编写任意程序」降维为「参数化配置装配」，使 27B 元模型在运行时当场生成、修复与演化成为工程现实。
  • 调度认知转移：并发上升后瓶颈从模型生成速度转移到人类注意力；调度器的首要天职是准入限流（锁定在制品上限），而非事后重排优先级。
  • 关键断层：JIT 的自主演化依赖基准的即时自动判分，而工业级长程工程没有现成真值。这道断层决定了微观演化能力无法直接迁移到宏观集群，落地前提是可验证性工程。
  • 可计算边界：在存在协调开销时并发必有峰值。示意参数下 30 个 Agent 的产出（3.91×）反而低于 14 个（4.75×）——盲目扩容是负收益。
Part 01

背景与问题定义

在构建方案之前先确立问题基线：从一组反直觉的实测数字出发，论证执行框架是一项独立的优化变量。

1.1 一个反常的实证事实

过去数年，提升 Agent 表现的默认惯性是追逐更强的底座模型。但 JIT-Agent（arXiv:2608.25593）的实测数据揭示了一条不同的高杠杆路径：完全保持模型权重不变，仅替换外层的 Agent Harness（执行框架），成绩便出现 20 分级别的差距，且性能提升的同时成本反常下降。

最反直觉的现象：性能上升，成本同步骤降

在经典直觉中，更高准确率通常需要更长的推理轨迹与多轮重试为代价。但在 xBench-DeepSearch 实测中：总 Token 从 52.7 万压减至 21.2 万，成本从 $0.075 降至 $0.039，而准确率反而从 78.0 升至 82.0。

这证明：增益来自更短、更精准的执行拓扑，而非无限拉长思维链。大量 Token 是被静态框架中的无关工具调用、全量上下文回填与盲目重试浪费掉的。

1.2 静态框架的三处失配

当前多数 Agent 框架属于 AOT（Ahead-Of-Time，提前写死）范式：编码期就固定了 Prompt 流程、记忆方式与工具列表。面对动态需求，它暴露三处系统性失配：

失配 01

上下文污染与提示词膨胀

为应付所有潜在任务，只能把几十个工具文档与宽泛的系统提示全量塞入 System Prompt，直接稀释注意力，导致复杂调用中迷航。

失配 02

执行拓扑与认知复杂度错配

用递归多智能体框架跑单步补全会产生大量冗余交互；用极简 ReAct 跑跨文件重构又会因缺乏规划陷入死循环。任务类型不同，需要的是结构不同，不只是参数不同。

失配 03

异常重试与经验归零

遇到报错只能生硬清空重试或机械循环，无法根据编译器诊断在保留上下文的同时给出高杠杆的局部补丁；经验也无法沉淀为可复用资产。

深入：为什么「离线搜索一个最优固定框架」这条路走不通

一个自然的想法是：既然要找好框架，那就离线搜索一个跨任务最优的。问题在于目标函数本身——不同任务需要的先验差异太大，不只是参数不同，而是结构不同。

用一个固定结构覆盖所有任务，等价于在巨大设计空间里找「平均最好」的点。这个点对每一个具体任务都是次优的，且任务分布一变就失效。替代思路是：不去搜这个点，而是训练一个能针对每个任务当场生成框架的模型。其前提是把框架变成「可生成的对象」——见 2.2 节。

1.3 瓶颈的两次迁移

模型能力不够
➔
框架不合适
➔
人的注意力不够

第一次迁移（模型 → 框架）：认识到执行框架是与模型权重同等重要的独立变量，可通过即时编译实现动态特化。
第二次迁移（单体 → 集群）：当并发运行 10 个甚至 30 个 Agent，真正的瓶颈不再是单个 Agent 能否写好代码，而是人类注意力的物理极限、跨分支合并冲突与分布式状态治理。

第二次迁移的具体形态：单 Agent 模式是同步调用（下任务 → 看输出 → 补充信息 → 确认结果）；多 Agent 模式变成异步任务队列 + 人类消费者。工作量没有消失，它从敲代码转移到定义任务、准备环境、判断风险、处理阻塞和验收结果。没有状态、优先级和清楚的完成条件，多开 Agent 只会制造更多未关闭的工作。

Part 02

核心概念与协议体系

精确定义是严密推导的前提。本节界定六个基准术语，详解使 JIT 生成可行的四元组协议，并拆解 Fleet 四层与关键缺口。

2.1 六个基准术语

术语 01

Harness（执行框架）

包裹在基础模型外的运行时控制层，包括记忆压缩、多步规划、动作格式定义与工具分发编排规则。它决定模型保留哪些历史、暴露哪些工具、如何推进动作。

术语 02

JIT Harness

任务到达时由轻量元模型（27B）根据任务特征实时装配的可执行框架，而非预先写死的代码。结束后归档，作为未来生成的参考。

术语 03

Fleet（集群）

多任务、多模型、持续运行的异步 Agent 执行集群。区别于单 Agent 之处在于需要解决谁先跑、谁被阻塞、谁该被隔离、谁能部署。

术语 04

λ、μ 与 ρ

λ 是任务到达（生成）速率，μ 是人类评审速率，ρ = λ/μ 为负荷率。ρ > 1 时队列单调发散。μ 并非常数——它随在制品上升而下降。

术语 05

快照隔离与串行化

数据库隔离级别。快照隔离保证看到某时点的一致视图，但不保证并发写入合并后正确；串行化才保证结果等价于某种顺序执行。

术语 06

演化真值

Agent 架构自主学习迭代所需的确定性反馈信号。这是学术基准与工业工程之间最深刻的技术断层所在。

2.2 四模块协议

JIT-Agent 能够成功的核心数学前提，是把任意复杂的框架抽象收敛为标准的四元组协议：

h = (M,  P,  A,  F)
运行时严格遵循协同序列：M ⟶ P ⟶ F ⟶ A
  • M（Memory，记忆拓扑）：历史上下文的组织方式。如何压缩长历史、保留核心上下文、是否建立子问题隔离。
  • P（Planning，规划策略）：任务拆解机制。无规划（∅）、线性待办（Todo）、树状搜索或递归拆解。
  • F（Capability，能力编排）：在何种条件、哪个阶段暴露哪些原子工具或 SOP 技能。
  • A（Action，动作协议）：与外部环境交互的协议，如标准 ReAct、递归子 Agent 派发或结构化返回。
协议的降维价值：把「程序空间」压缩为「配置空间」

如果让元模型从零编写脚本来实现框架，它面对的是图灵完备的无限程序空间，极易产生语法错误、死循环或依赖漂移。通过四元组协议，搜索空间被限制在高度结构化的配置参数空间内——这正是 27B 元模型能在几秒内完成高质量框架合成的工程秘密。

配套地，作者用 HarnessFactory 在统一协议下重实现了 13 个代表性框架作为种子库，因此生成是在协议约束下装配可执行模块，不是从零合成自由代码。

代表性框架协议映射适用场景
经典 ReAct (M_full, P_∅, A_react, F_all)单步原子操作、即时问答
Codex / OpenCode (M_compact, P_todo, A_react, F_all)缺陷修复、单元测补全、依赖排查
ROMA / AOrchestra (M_subproblem, P_decomp, A_rec, F_route)跨文件重构、多阶段复杂规划
 三种截然不同的经典框架都能写成同一个坐标系里的点，差异被归约为四个维度上的具体选择。

2.3 Fleet 四层与准入控制缺口

工程实战清晰勾勒出治理数十个并发 Agent 的四层结构。但对实战系统的严谨校准揭示了一个关键缺口：

关键校准事实：缺的不是排序器，是准入控制器

实战复盘指出：优先级队列的机制是「按 P1 到 P4 给已完成的 Agent 排队」——它只告诉人类「下一分钟该给谁」，却完全无法阻止继续同时启动 20 个新会话。

系统能看见队列、能排列队列，但不能阻止队列增长。因此「限制在制品」不是优化项，是缺口项。做法是 CONWIP：完成一个，才准入一个。

被忽略的第二个损耗来源

串行化等待（σ）有两个独立来源：一是人类评审队列与单写者锁；二是本机物理资源争抢——多个会话同时装依赖、编译、跑完整测试，CPU、内存、磁盘、网络互相争抢。

第二个来源正是把 Agent 从本机搬到 VPS 或云端的真正理由：不是为了「更快」，而是为了消除资源争抢。

Part 03

关键要点分层展开

逐层深剖：微观 JIT 如何装配与演化、宏观 Fleet 如何调度与隔离，以及两套体系拼接处的硬核断裂点。

3.1 微观 · JIT 动态装配沙盘

切换任务类型，观察同一个四模块协议会装配出结构完全不同的框架。这正是 JIT 与 AOT 的根本差异：AOT 只能给出一个「对所有任务都次优」的折中解。

3.2 微观 · 三阶段演化流水线

阶段 I定制装配（Customization）· 监督与偏好微调

用更强的冻结教师模型，针对具体任务从种子库采样 3 个参考框架，生成合规框架作为监督数据。除 SFT 外施加偏好学习：只有当得分提升、且时延与成本均未恶化时，才记为正向偏好对。从源头训练元模型对计算资源保持敬畏——这解释了成本降 36% 从何而来，不是副作用，是设计目标。

阶段 II局部自愈（Repairing）· 诊断反馈闭环

阶段 I 被淘汰的失败生成不丢弃，而是转为修复监督：失败框架带上诊断报告（编译错误、接口不匹配、工具调用失败、运行时异常），教师模型在最多两轮内给出局部补丁。学到的是「拿到执行反馈做少量高杠杆修改」，而非一次性重写。失败样本是最贵的数据，多数流水线在这里把它们扔掉了。

阶段 III轨迹进化（Evo-GDPO）· 资产沉淀

把测试时自适应转化为可训练能力。采样候选与库中前沿在同一任务、同一底座、同一预算下严格执行对比，只有超越前沿才保留；奖励、时延、成本三个信号分组解耦归一化后合并，避免大数值信号吞没微小的工程约束。部署后模型参数完全冻结，只有框架档案库继续演化——这就是「越用越强」的机制来源。

第一层的核心经济学事实：Static JIT 必亏，Streaming JIT 才能平摊

如果每次都从零调用 27B 元模型重新生成且不持久化（Static JIT），生成本身的开销将吞噬所有收益。只有建立持久化档案库（Streaming JIT），在第 11 次执行同类任务时跨越盈亏平衡点，后续边际收益才完全归正。

该数值基于论文实测降本 36.0% 与元模型推理开销建立的经济推演模型，参数需在各自环境重新校准。推导细节见 4.4 节模型 ④。

3.4 断层 · 演化闭环在哪里断掉

这是两份材料拼接后才看得见的问题，也是全篇最重要的一节。微观的演化能力是被可自动计算的奖励喂养的：Evo-GDPO 的三个信号（奖励、时延、成本）全部可自动测量，Streaming 模式的进步靠累计准确率曲线证明——这要求每题结束就有真值标签。

而论文的 9 个基准全部是短程、单次、可自动判分的任务，没有一个是「跨 2000 小时的仓库演化」。宏观面对的恰恰是后者。

弥合断层的三条路径（按可行性排序）

① 可验证性工程（最高优先级）：把验收标准从「人看代码」转成可执行判据——属性测试、契约断言、架构不变量扫描、回归基线。黄金标准是「补充足以阻止同类失败再次发生的最小证据」，而非盲目追求覆盖率。只要能自动断言，就能为演化飞轮重新注入确定性真值。

② 评审信号结构化（中等）：废除口头 OK / Not OK，强制把评审结果转为分类标签（接口破坏、边界溢出、隐式副作用、风格偏好），把稀疏的人类注意力转为密集的演化信号。

③ 训练专属评审模型（风险最高）：极易诱发奖励劫持。一手实证是：要求模型「再挑出 5 个问题」时，它会努力凑满 5 个，甚至凭空捏造缺陷。验收指标必须具备外部真值校验与硬性退出条件。

Part 04

对比与因果推导

把方案摆在一起对照，拆出两条因果链，并给出可直接代入计算的模型。理解「为什么」优先于记住「是什么」。

4.2 两条因果链

因果链一：为什么盲目扩容必然走向负收益

➔

关键在于第二个箭头：单 Agent 效率不是常数。它随并发上升而下降，原因有两支——串行化等待（评审队列、单写者锁、本机资源争抢）与跨 Agent 协调（上下文同步、语义冲突、集成测试的交互面）。

因果链二：为什么长程工程中框架无法自动进化

长程任务无自动真值
➔

➔
反馈延迟由秒级恶化至天级
➔
奖励断流，演化飞轮停摆

链条的起点是任务性质，不是技术能力。这也解释了为什么「先上 Agent」通常是错误顺序——在验收标准不可执行的前提下，加 Agent 只会加快产生未经验证的产出。

硬核推导：为什么 30 个 Agent 的产出反而低于 14 个

对 C(N) 求导并令导数为零，可得最优并发数：

dC(N)dN = 0  ⟹  N* = 1 − σκ

代入示意参数 σ = 0.08、κ = 0.005：

N* = 1 − 0.080.005 = 0.920.005 ≈ 13.56  ⟹  最佳并发为 14 个
  • N = 14 时：分母 = 1 + 0.08×13 + 0.005×14×13 = 1 + 1.04 + 0.91 = 2.95；产出 C(14) = 142.95 ≈ 4.75 倍。
  • N = 30 时：协调开销二次方膨胀，分母 = 1 + 0.08×29 + 0.005×30×29 = 1 + 2.32 + 4.35 = 7.67；产出 C(30) = 307.67 ≈ 3.91 倍。

结论：30 个 Agent 的有效产出比 14 个还低约 17.7%。盲目堆砌并发不仅没有收益，反而因排队等待与合并冲突净亏损了近五分之一的系统生产力。

深入：模型 ② 与 ⑤ 的两个反直觉结果

关于排序。直觉写法是各因子连乘（业务影响 × 风险 × 阻塞 × 紧迫 × 依赖），但连乘公式不可用：任意因子为 0 就归零，且量纲未校准、无上界，无法比较。换成「延迟成本 / 任务时长」后，分母是决定性的——它让「5 分钟能清掉的高影响小任务」自动排在「两天的大任务」之前，从而压低队列长度本身，而不只是重排队列。

关于预发送。它常被类比为 CPU 流水线或推测执行，但决策框架选错了：CPU 分支预测错误的冲刷代价固定且极小，而 Agent 的错误假设会向下游传染。用实物期权框架代入后会出现一个反直觉结果——价值的决定因素是误判会不会传染，不是等待时长。下方沙盘可以直接验证。

Part 05

陷阱与防御

六条反模式，每条都有「表现 + 防御」两栏。前四条来自工程实践，后两条来自数据核验。

PITFALL 01

把快照隔离当成串行化

表现：认为开了 Worktree 就安全。但两个 Agent 分别改 auth.py 与 session.py，文本零冲突、合并成功，系统却崩溃——一个把校验改成异步，另一个假设它同步。
防御：Worktree 只提供快照隔离。补上 merge queue + 合并后全量验证（可串行化检查），并对跨文件语义冲突保持人工警觉——这一层目前没有成熟工具覆盖。

PITFALL 02

单一模型自审盲区与递归审查

表现：让写代码的同一模型自我审查，倾向维护自身逻辑盲区。更隐蔽的是递归审查——要求「再找五个问题」，它往往会努力凑满五个，即使剩下的是想象出来的缺陷。
防御：异构模型交叉核验；复核由改动规模与失败代价触发，必须有明确停止条件，而非「越多越好」。

PITFALL 03

全量工具挂载（Tool Bloat）

表现：一次性挂载全部接口工具，模型在决策树上注意力发散，选错参数概率上升，token 也被工具定义大量消耗。
防御：由 JIT 编译器依据任务特征裁剪工具子集。论文对照组显示，更精准的执行能把 token 从 52.7 万压到 21.2 万而性能反升——增益来自更短的执行，不是更长的轨迹。

PITFALL 04

未编译的提示词替代 SOP

表现：用自然语言一段段写长指令，每次执行方差巨大，偶发遗漏关键步骤。省下的不是打字时间，而是每次重新回忆顺序、检查遗漏的认知成本。
防御：Skill ≈ Compiled SOP，把多步流程编译为带确定性断言的流程。但编译产物会位衰减——必须配重编译触发条件（依赖变更 / API 签名变更 / 连续失败率上升）。

PITFALL 05

拿结构参数当可用并发

表现：用理论协调成本推算最优并发。但真实数据里返工率几乎总是随并发上升，拟合出的有效 σ/κ 会系统性放大——实测为 σ ×2.14、κ ×2.74，最优并发从 13.6 掉到 7.8，结构参数会高估可用并发约 75%。
防御：用实测数据拟合，且只依据 N* 决策——σ 与 κ 单独辨识度不高、可互相补偿，但组合量 (1−σ)/κ 稳定得多。

PITFALL 06

代理指标被劫持

表现：用会话数、提交数、Token 量、审查问题条数衡量效率。每一个都存在被优化的路径——要求找五个问题，就会得到五个问题。
防御：跟踪真实指标：返工次数、合并后故障率、交付周期、Skill 命中率与失效率。验收指标必须可被外部真值校验，而非自报数量。

一条被当作成功案例记录的权限逃逸

在「十分钟自动搭建远程环境」的演示里，原文同时记录了：Agent 从本机扫描并提取了明文 API Key，并在远端取得完整 root 权限。这是两个独立失效——凭据以明文存在于 Agent 可读路径，以及 Agent 拿到了远超任务需要的权限。

值得警惕的是叙事 framing：速度与控制权是同一套自动化的一体两面。个人实验可以接受这种交换；连接生产仓库和真实密钥后，运维能力本身就变成了产品的一部分。在一个 Agent 能拿到 root 的体系里，不可被 Agent 篡改的审计日志是唯一还能追溯发生了什么的东西。

Part 06

结论与演进建议

先给结论分级，再给路线图。把不同可信度的结论同等对待，是当前最大的误读风险。

6.1 证据强度分级

  • 强证据（Intra-Agent 级）：经由严格基准评测，18 组任务全部正向提升，−36% 成本与 +24.8 规划提升具有统计显著性。立即采信——全面推行动态工具与上下文裁剪。
  • 中证据（Inter-Agent 级）：来自 2000 小时生产实践，方向高度可信（准入限流、Worktree 物理隔离、单写锁），但缺乏平行对照组。须自测——结合团队数据拟合 σ 与 κ，不可照搬。
  • 弱证据（Human-Agent 级）：全自动自组织等概念设想，尚无端到端闭环验证。保持观望——严禁作为生产核心架构依赖。

6.4 六大行动清单

行动 01

拟合自身的 σ 与 κ

记录不同并发度下的合并通过率与返工率，反解出真实的 USL 参数，得到明确的 N*。在此之前任何扩容决策都是猜测。

行动 02

把 WIP 上限显式化

你可能已经有了现成上限：订阅套餐的并发限制。多数人从没核对过它。查清后当作初始值，再用 0.7N* 调整。

行动 03

任务分族与频次核算

统计高频场景，只对重复频次 ≥ 11 次的任务族投建框架或 Skill 库；低频场景直接用现成 CLI。

行动 04

推进可验证性工程

把模糊的「人类 Review」改造为可执行断言。核心标准是「补充阻止同类失败再次发生的最小证据」，这是弥合演化断层的唯一开关。

行动 05

先核验隔离，再谈权限放开

基础执行器的官方安全文档明确「它不是沙箱」。绝不在未隔离宿主机上运行全权限 Agent；建立外部防篡改审计日志作为兜底。

行动 06

清洗指标，清除虚荣度量

剔除 Token 消耗数、会话数、代码行数。把考核对准交付周期、线上逃逸故障率与返工次数。

最终必须带走的三大工程真理

① 一个可计算的规模定律。N* = 1−σκ。并发不是免费的午餐，盲目扩容必然走向负收益倒挂（30 个不如 14 个）。

② 一个不可妥协的调度纪律。调度器的首要职责是准入限流，绝非事后排队；你的订阅并发额度就是现成的上限红线。

③ 一个演化闭环的前提契约。在长程工程中绝不能空等 Agent 自主演化。必须先搞可验证性工程，把模糊期望写成确定性断言。没有自动化断言，一切 JIT 演化都是空中楼阁。
