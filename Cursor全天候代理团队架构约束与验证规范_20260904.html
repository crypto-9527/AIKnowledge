一个 24/7 代理团队如何成形：SpaceXAI 工程师 Lauren Tan 把工程判断写进系统

一夜自动合并 20 个 PR 的前面，是 600 多个重构 PR。Lauren Tan 展示了架构约束、CI 机械校验、验证技能与逐级授权怎样组成一支持续工作的全天候代理团队。

Lauren Tan（@poteto） SpaceXAI / Cursor 核心工程师 · 前 Meta React 核心团队 / Netflix 架构师

执行摘要与核心透镜

“我几乎不再看代码了。”Lauren Tan 能这样工作，是因为架构约束、CI 和验证流程已经承担了大量原本需要人类工程师逐行盯住的检查。GrokBot 让她可以组织一组各自拥有身份的独立代理，自己更像管理者一样协调它们。

一、一夜自动合并 20 个 PR，前面是 600 多个重构 PR

Lauren 的主体分享从现场第六分钟开始。她接手的是一套真实运行、又带着绿地项目典型风险的 GrokBot 代码库：原型生成得很快，代码却没有稳定护栏。

📹 想先看完整原始分享吗？

完整工作坊中文字幕版，保留原始画面、声音和英文字幕；中文字幕采用单行大字并贴近原英文字幕。

Lauren 说，她已经很少亲自看代码。某天早上醒来，大约 20 个 PR 已由代理自动合并；上一个月她提交了约 1000 个 PR，当月才到第 12 天，又接近 800 个。

这些数字都来自她的现场自述，公开视频没有附上可独立审计的仓库和 PR 清单。它们可以说明交付规模，却不能直接证明代码价值、缺陷率或普遍生产率。

她还解释了为什么主动让代理拆分任务：单个 PR 可能只有几十行，也可能达到数百乃至上千行，并没有固定上限。她看重的是让每次提交尽量原子化地说明一小块改动，使 Git 历史继续成为理解上下文、回滚改动和定位缺陷的工具，而非做高 PR 数量。一个四万行的大 PR 即使合并成功，也很难回答问题究竟从哪里开始。

真正值得先看的，是这四个数字之间的因果关系。

💡 一夜 20 个自动合并 PR 之前，团队付出了什么？

Lauren 现场自述，建立系统前完成 600 多个重构 PR；系统成熟后曾一夜自动合并约 20 个 PR，上月约 1000 个 PR，当月第 12 天接近 800 个。

20 个自动合并 PR 是输出端，600 多个重构 PR 是基础设施端。中间是一套重新设计过的代码库，单靠更聪明的提示词填不上这段距离。

GrokBot 最初是一个快速生成的绿地应用。速度很快，架构却会自然长成“代理当时最方便怎么做，就怎么做”的样子。每个任务都能局部完成，长期叠加后，目录、依赖、进程和状态管理开始互相缠绕。代理也许还能继续改，人类却越来越难理解和信任它。

Lauren 的选择是为代理重建工作环境。她把这套 Electron 架构叫作 Dune。目标是减少代理每次做决定的数量，让结构替它承担抽象原则。

二、让正确路径成为最短路径：Dune 如何约束代理

Dune 有一个极强的设计判断：代理喜欢走捷径，那就把最短路径设计成正确路径。

这句话比“给 AI 写一份更完整的编码规范”更具体。编码规范要求代理每次都记住、理解并主动服从；架构约束则直接改变它能看到的选项。

🛡️ Dune 怎样让代理更难走错路？

Dune 通过按功能共置代码、隔离 Electron 进程、检查依赖图并禁用代理常滥用的模式，让最短实现路径更接近正确路径。

2.1 第一层：功能物理共置（Colocation）

一个功能的大部分代码放在同一目录，代理不必跨多个共享目录寻找状态、组件和业务逻辑。它只需要识别“我正在改新手引导”，就能把主要工作限制在对应功能目录（如 features/onboarding/）内。这消除了全局状态膨胀与跨目录迷航，将大语言模型的注意力上下文严格约束在当前切片。

2.2 第二层：进程边界硬隔离（Process Boundaries）

Electron 的主进程和渲染进程承担截然不同的职责。计算或 I/O 一旦误入渲染侧，就会和界面绘制抢时间。在 60 FPS 刷新率下，每帧仅有约 16.6 毫秒 预算，任何阻塞性计算越界都会导致界面掉帧与无响应。Dune 强制使用明确的目录结构与导入依赖图检查（Dependency Graph Check），在编译与静态分析阶段物理切断依赖穿越。

2.3 第三层：封禁已知高危模式（Anti-Pattern Banning）

Lauren 采取了两个极其激进但效果显著的做法：

  • 禁止直接使用 useEffect：消除因生命周期混淆引起的重复触发、竞态条件与内存泄漏。
  • 禁止普通代码注释：模型极易将某一次 PR 评审中的临时纠结或历史变更背景写成永久性注释，留下与当前代码演进脱节的噪声。

这些规则未必适合所有团队，但背后的方法论完全可以迁移：找到代理最常走的坏捷径，先问能否通过 API 设计、目录隔离、类型系统或依赖关系，让它在物理层面上根本走不进去。

三、把人工提醒改造成 CI：人的判断如何提前进入系统

代码审查里反复出现的同一句话，是一条尚未被编译进系统的规则。

如果工程师每周都要在 PR 中评论“这个依赖不能从渲染进程引入”、“这里不能直接读共享状态”、“这个功能必须放进自己的目录”，团队其实是在用最昂贵、最慢的方式执行约束：等错误发生，再让人发现。

3.1 人工判断向系统编译的五级迁移阶梯

Lauren 给出了清晰的承载方式迁移路线。人类工程判断从口头语言逐步硬化为机械结构：

人工判断（软约束） 更可靠的承载方式（硬约束） 代理失败时发生什么
“请按这种目录组织功能” 脚手架、固定目录和注册机制 最容易复制的现有模式就是合规模式
“这里不能跨进程导入” 依赖图检查、类型边界 CI 直接报错并阻断合并
“不要再写这种 React 模式” lint 规则或编译器诊断 在提交前得到精确的语法与模式错误
“完成前请运行真实功能” 验证 Skill 和物理完成条件 没有可核验的物证就不能声称完成
“请记住我们的团队习惯” Rules、AGENTS.md、Skills 配置文件 提供上下文指引，但仍可能被遗忘

最后一行至关重要。Rules、Skills 和 BugBot 都有显著价值，但它们本质上是较软的约束。大语言模型代理可能漏读、曲解或在复杂长任务中遗忘上下文。架构、类型系统、编译器和 CI 会给出绝对确定性的机械结果，不能靠一句“我已经遵守”绕过去。

3.2 编译器的机械淘汰价值

Lauren 用 Rust 举了一个具体例子：严格的编译器和借用检查器（Borrow Checker）会在代码审查前淘汰掉整整一大类内存和并发错误。这个例子不要求所有团队改用 Rust，它深刻说明：技术栈本身决定了多少工程判断能在人工介入前被机械执行。

于是，人类并没有退出工程判断。人的工作位置发生了根本性转移：从逐个 PR 重复提醒，移到提前设计接口、错误空间和通过条件。

这种前置设计会消耗早期的重构时间和 token，但回报绝不仅仅属于最强大的前沿模型。边界足够明确后，能力较弱的模型、新加入团队的工程师，甚至不熟悉完整代码库的产品经理和设计师，也能在同一套护栏内安全地贡献代码。

四、验证能力决定并行上限：代理必须能自己运行产品

架构可以让代码更整洁，CI 可以挡住已知坏模式，但两者仍不能证明用户看到的功能真正可用。

Lauren 把验证称为代理工具箱里最重要的能力。这里的“验证”远不止跑单元测试。代理要能够：启动应用，进入用户报告的界面，执行交互操作，复现问题，采集 CPU trace 或 heap snapshot，完成代码修改，再沿着完全相同的路径检查问题是否真正消失。

🔍 代理怎样独立证明一个产品问题已经修复？

代理必须启动真实产品，用功能地图找到入口，复现问题并保存证据，修改后沿同一路径回归，最后留下可检查的完成证据。

4.1 终结“人类转接员”的并发雪崩

如果这条回路缺失任何一段，人类就会沦为极其悲惨的“转接员”：代理写代码，人打开本地开发版本；人发现按钮毫无反应，再复制控制台错误粘贴给代理；代理修改后，人重新点击测试一遍。

一个代理时，人类还能勉强配合；十个代理并发工作时，同一个人会被瞬间彻底堵死。 因此，决定团队能够并发调度多少代理的核心瓶颈，不是模型的吞吐速度，而是代理的独立验证闭环。

4.2 功能地图（Feature Map）：抹平语义断层

功能地图解决的是“代理不知道产品具体长在哪里”的问题。用户报告往往非常模糊：“左侧边栏很卡”或者发一张截图和三个问号；但在代码库里，根本没有任何一个文件叫“用户看到的左侧边栏”。

功能地图从用户视角记录入口、子功能、快捷键、DOM 选择器和代码位置的映射关系，让模糊的问题报告能够精确落地为可操作的执行路径。

4.3 PStack 架构与验证技能规范

这套思路后来沉淀为 PStack。Cursor 官方公开的开源仓库规范保留了完全一致的铁律（参见 Cursor 官方技能 create-verification-skill）：

  1. 从代码库识别用户实际接触的界面与入口；
  2. 为核心功能建立精准的功能地图；
  3. 物理启动应用产品实例；
  4. 驱动至少一个完整功能交互；
  5. 保存录屏、Trace 或快照物理证据；
  6. 清理测试环境并二次核验取证结果真实存在。

没有亲自跑过的验证 Skill，只能算作草稿。

五、Skills 也要被测试：PStack 如何从代理失败中长出来

Lauren 强调，PStack 并不是坐在会议室里先构思出一套宏大的方法论，再把它拆包分装成 Skills。它完全是从观察代理的失败细节中长出来的。

  • 代理没有读取相关代码就自信地下结论 → 提炼出强制先检索物理证据的 Skill；
  • 代理不会操控真实桌面应用 → 研发 Control Glass 与基于像素/界面的验证 Skill；
  • 代理找不到用户口中的功能模块 → 补充用户态功能地图。
⚙️ 一条团队经验怎样变成经过测试的 Skill？

团队先观察代理失败，再把改进写成 Skill，制定评分标准，让不同模型在隔离环境执行，并用回归结果判断 Skill 是否真的改善表现。

5.1 代理的单元测试：Skill 评测体系

Skill 写出来仍未结束。Lauren 把评测理解成“针对代理的单元测试”：

  1. 先为特定任务制定清晰的定量评分标准；
  2. 在隔离目录或 git worktree 中并行启动多个子代理；
  3. 让不同的底层基座模型执行同一项任务；
  4. 由协调代理或独立裁判模型进行交叉评分；
  5. 修改优化 Skill 提示与脚本后重新回归运行，观察是否更稳定地导向预期目标。

5.2 隐蔽评测与防作弊盲测机制

她甚至会给评测目录起极其普通的随机名字，避免代理意识到自己正在参加考试后改变行为策略。如果一条 Skill 只有在代理明确知道自己在被评测时才生效，那么在实际工程中它就是不可靠的。

这确立了团队资产质量的真正分水岭：Skill 的质量不能靠文档字数多寡来证明，而要看第一次接触代码库的弱模型代理能否严格按它完成任务并留存证据。

这套循环从根本上重塑了团队知识的形态。过去散落在资深架构师口头提醒、代码审查评论以及线上事故复盘里的碎片经验，被系统性沉淀为可分发、可执行、可评分且可自动回归的工程软件资产。

六、从本地观察到自动合并：信任必须逐级购买

Lauren 没有建议任何团队在第一天就盲目启动成百上千个云端代理。她的推进节奏恰恰相反：从本地开始，打开工具调用跟踪，仔细观察代理究竟读了什么、漏掉了什么、怎样在细微处失败，再逐步补充架构护栏、验证机制与 Skill。

6.1 Benny 代理：云端桌面独立分诊实践

当本地验证稳定成熟后，工作流才逐步迁移至云端。她举了一个叫 Benny 的自动化代理：

用户错误报告到来后，Benny 在云端启动独立桌面环境，运行 Cursor 应用，使用同一套操控 Skill 尝试自主复现，并进一步比对判断主分支是否其实已经修复了该问题。在现场演示案例中，Benny 确认该缺陷已在主分支修复，它交回的是完整的复现录屏、环境状态与免修改发版建议，而非一句毫无依据的“可能是这里”。

🚪 代理获得自动合并权限前要跨过哪些门？

代理权限从本地观察、受控改动、独立验证、云端执行、错误分诊逐步上升到自动合并；每级都要求更强证据与更短回滚路径。

公开版 Cursor Cloud Agents 的商业实现已高度工程化：每个代理运行在独立的隔离虚拟机中，克隆授权仓库，在独立分支工作，并以 Draft PR 形式交接；网络出口、安全凭据与权限审计均由平台机制保证（可参阅 Cursor 安全说明）。

6.2 自动合并的六大不可动摇准入门槛

自动合并比云端运行跨越了最危险的一道红线。前者关乎代理在何处计算，后者决定代码能否直接污染生产环境主分支。要开放自动合并权限，团队必须实证满足六大准入门槛：

  1. 任务边界高度收敛：改动范围严格受限，禁止跨模块肆意重构；
  2. 架构硬约束机械拦截：如 Dune 架构阻断跨进程依赖与危险生命周期调用；
  3. 代理具备真实运行验证能力：必须能自启应用并留下通过证据；
  4. 失败与排查证据链完整：包括控制台日志、CPU Profile、录屏物证；
  5. 极短的原子化回滚路径：单个 PR 原子化，Git 能够一键干净回滚；
  6. 生产环境全链路可观测监控：上线后异常指标能被即时捕获。

七、PR 数量不是生产率：这套方法能学什么，不能照抄什么

这场分享极易被误读为一套简单的“高效高产秘诀”：多花点 Token、把代码库全量重构一遍、开启自动合并，然后用成百上千个 PR 数量在汇报中炫耀生产率。

PR 数量仅仅记录了改动被切分成了多少份。 一个普通任务可以切分成十个小 PR，十个小 PR 也有可能全都是无足轻重的微小修复。PR 计数从未自动包含缺陷率、返工损耗、回滚成本、用户真实价值以及长期的架构维护负担。

7.1 METR 生产率实验更新的警示

METR 在 2026 年更新其开发者生产率实验时给出了一个极具清醒视角的边界：晚 2025 工具在原始统计数据中确实出现了某种加速迹象，但参与者样本偏差、相对较低的激励报酬以及多人同时并行运行多个代理所造成的精确计时极度困难，让研究团队认为这些数据仅能提供微弱的幅度证据（详见 METR 研究更新）。METR 甚至专门指出：并行代理让“一个特定任务到底消耗了多少人类精力时间”变得前所未有地难以测量。

因此，团队衡量真实的工程生产率必须建立六维综合度量体系：

  • 需求到可验证结果的端到端周期时间；
  • 每项任务的人工介入与转接摩擦次数；
  • 线上缺陷率与紧急回滚频率；
  • 验收证据包的完备度与可追溯性；
  • 提交改动的可逆性与原子化程度；
  • 对业务最终核心指标的实质贡献。

7.2 绿地与棕地代码库改造策略

全新代码库（绿地）与既有历史工程（棕地）绝不能盲目采用相同的改造套路：

  • 全新绿地项目：最容易快速生成，也最容易在缺乏护栏时迅速失控退化。它最适合从第一天起就针对代理设计 Dune 式的进程隔离与物理共置边界。
  • 成熟棕地项目：如果原本就拥有严格的静态类型系统、高覆盖率的自动化测试套件和成熟的分支权限规约，它可能已经比很多杂乱的新项目更适合代理工作。全面推倒重写通常是灾难性的，只有在旧架构完全无法提供机械防御、且重构能够分阶段小步验证时才值得启动。

Lauren 还指出，传统大型科技公司历经多年、为海量水平不一人类工程师构建的框架约定、分支准入与防呆防误设施，恰好能近乎零成本地用来约束代理。代理工程并不是凭空诞生的一门玄学，大量最高效的基础设施，本质上正是人类软件工程严谨经验的复用与转译。

📋 这套方法哪些能复制，哪些不能从个案外推？

可复制的是：架构护栏（Dune）、端到端验证闭环（PStack）、Skill 隔离评测与逐级购买信任。
不可盲目照抄的是：轻率推倒重写既有代码库；绝不能从 PR 数量推导真实代码质量、业务价值与普遍生产率；单机 Token 与过夜成本也必须依据自身团队经济模型独立核算。

一支 24/7 全天候工作的代理团队，从来没有消灭人类的工程判断。它只是把人的判断从深夜疲惫不堪地逐行审查代码，提前搬到了白天设计系统架构、划定错误空间、定义物理完成条件和检查真实证据的地方。
