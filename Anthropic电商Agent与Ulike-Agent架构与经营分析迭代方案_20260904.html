Anthropic 电商 Agent 与 Ulike-Agent 技术架构与经营分析演进方案

目标系统：Ulike-Agent monorepo (Java 控制面 + Python 执行面 + Open WebUI + Wren MDL + Packs 治理) 参照标杆：Anthropic commerce-agents 工业级参考实现 (Apache-2.0) 文档定位：跨架构与经营业务的唯一权威增量演进方案 更新时间：2026-09-04

本文档为 Ulike-Agent 引入工业级生产治理的统合指导纲领。针对此前架构设计与业务分析文档碎片化、视角脱节的痛点， 本方案严格执行“增量累计、辩证取舍、业务闭环”原则，将底层软件工程确定性防御（P 系列）与上层智能经营分析闭环（M 系列） 深度缝合，建立起一套“用代码硬门禁规范模型、用归因四道闸防止妄断、从看数诊断无缝触发治理执行”的全新演进架构。

01 执行摘要：架构围栏与经营闭环的双轮跃迁

1.1 核心问题诊断：从“只读看数开环”迈向“安全决策闭环”

当前 Ulike-Agent 在多服务编排（Backend/Tool/OWUI/Wren）、声明式领域包治理（packs/domains/sales、packs/domains/finance） 与 SQLite 架构收敛上已取得显著成果。然而，深入对照 Anthropic 官方生产级参考实现后，系统暴露出两个根本性割裂：

  • 底层工程层割裂：提示词拼装把动态变量（当前分秒、生成文件列表）直插 System Prompt 前缀，导致大模型 Prompt Cache 100% 击穿，Token 成本虚高且首字延迟（TTFT）严重堆叠；同时外部数据缺乏字符级与 XML 不动点（Fixpoint）围栏，缺乏实体出处（Provenance）硬校验。
  • 经营业务层割裂：现有的智能分析（如 sales-performance-review）产物止步于静态的 Markdown / IR 报告，属于典型的“单向只读开环”。运营在得知大盘异动原因后，依然必须跳出智能体，手动进入各个业务后台执行调价、补货或治理。系统缺乏一套像 Anthropic merchant-agent 那样从归因分析（performance-insights）直接流转到商品治理（catalog）、库存（inventory）、调价（pricing）与营销（marketing）的两阶段暂存提交（Staged Changes）闭环。

1.3 辩证审阅四项核心取舍（兼听、辨伪与订正声明）

① 纠偏“拒收电商语义” 重要订正

早期审查文档误将 commerce-agents 等同于“买家端购物车”，从而写下了“拒收电商语义”的武断结论。事实核验表明：其 Merchant Agent 是一套极其精湛的商家数字化经营操作系统。Ulike 属于时尚消费电子制造与零售品牌，Merchant Agent 的经营归因、库存监控、调价护栏和客群营销模板不仅不应拒收，反而是 Ulike 智能经营分析急需补齐的灵魂业务能力。

② 纠偏“全盘单主循环替代” 双轨制折中

Anthropic 主张纯粹的 Single Primary Loop（单智能体循环），反对 Router-Subagent 级联。辩证采纳结论：对于 Ulike 深度研报、跨多数据源核算的场景（如财务对账、销售季度复盘），Ulike 的声明式 DAG / Planning-Solve 具有高可控性，不宜盲目废除；但在日常单点问答与快速下钻中，应摒弃强制调用 SummaryAgent 的多余开销，建立“普通问答走 Single Loop，重度分析走 DAG Pipeline”的双轨架构。

③ 订正“Ulike 无记忆”误判 事实核查

由于 macOS BSD grep 不支持 \| 导致管道匹配静默失效，前置探查曾误判“Ulike 无记忆模块”。经深入源码核查，Ulike 在 agent/dto/Memory.java 具备完整的会话内消息容器，在 ShadowLedgerMemory 具备验证账本。真正的缺口是：缺乏“跨会话的轻量结构化事实抽取与并发安全沉淀”，需精准补齐。

④ 拒收“三端运行时同构” 明确拒收

Anthropic 将同一套 Agent 逻辑强行同构成 Messages API、Agent SDK 和 Managed Agents 三套适配层，这纯属云厂商为了向客户兜售三款商业化产品线的策略。Ulike-Agent 拥有自主控制的 Java/Python 双栈运行时与统一的 Open WebUI BFF，严禁为了模仿而引入这种高冗余的抽象层，保持单一控制面。

1.4 Ulike-Agent 固有优势与反向领先项清单（守正出奇）

在汲取外部养分的同时，必须保持对自身技术沉淀的清醒自信。以下四项是 Ulike-Agent 的反向领先项，在本次迭代中必须严格捍卫，严禁劣化：

Ulike-Agent 架构防御基准（严禁被外部模式稀释）：
  • 声明式 Packs 治理资产（领先）：packs/domains/ 将领域意图、数据血缘、指标语义与分析算子完全解耦声明。这种治理深度远超 Anthropic 仅依赖 Markdown 的平铺设计。
  • 启动期 Fail-Closed 审批门控（领先）：ApprovalActivationGate 在应用启动阶段即验证持久化 Schema，缺表或配置失配直接阻断启动，杜绝了内存悬空审批在重启时静默丢失的隐患。
  • Shadow 影子双栈验证链（领先）：在向生产切流前，具备完整的 Shadow 评估环境，能对新旧模型、新旧算子的输出进行无感并行跑批与语义一致性对比。
  • 分级风险控制体系（L0~L3）：将写操作细化为只读诊断（L0/L1）、受限配置变更（L2）与重大资金/调价/退款审批（L3），边界清晰，杜绝过度审批或安全失控。

02 架构哲学透视：六大支柱与源码级实证

commerce-agents 的工业级价值不在于几句提示词，而在于确立了一套“用确定性的软件工程围栏约束非确定性大模型”的系统化范式。 这套体系建立在六大支柱之上，每一项都在源码中有极其严谨的算法落点。

2.1 支柱一 · 规则放置四分法（Where a Rule Lives）

工业级系统绝不能寄希望于“在 Prompt 里多说几遍请遵守规则”。Anthropic 确立了软硬边界绝对隔离的四分法：

Prompt 提示词软性指导

仅负责推理意图引导、解释口吻、启发式分析模式与无危害的风格偏好。绝对不承担安全性、资金、权限或不可逆变更的校验。

Code 门禁代码硬性约束

掌控不可逾越的业务红线（单次调价上限、底价保护、补货配额、审批流拦截）。违反者直接由代码层抛出异常阻断，模型无法绕过。

Tools 原子工具执行与隔离

隔离环境副作用，负责只读拉取与原子化变更。工具层执行参数合法性校验并捕获异常，将其收敛为结构化结果回传。

Schemas 契约结构截断

通过 Pydantic / JSON Schema 定义严格的数据载荷，强行截断字段超长输入，在输入进入模型或执行逻辑前做类型阻断。

2.2 支柱二 · 两段式 System Block 与小时级时钟的三断点缓存

长上下文多轮 Agent 最大的成本黑洞是前缀突变导致 Prompt Cache 无法命中。prompt_assembly.py 建立了三断点机制与小时钟隔离：

  • Breakpoint 1（静态文本块）：系统协议、角色设定、领域通用指令，在末尾打上 cache_control: {"type": "ephemeral"}。
  • Breakpoint 2（工具注册表）：所有 Tools 定义一次性冻结，在最后一个 Tool 的末尾打断点。
  • Breakpoint 3（滚动轮次断点）：在多轮对话中，将最新持久化消息的尾部动态移动断点，使得前序多轮历史变成只读 Cache Read。
  • 小时级上下文时钟（Context Clock）：动态时间如果包含分/秒，每次请求前缀都发生变化，缓存必穿透！因此动态时间严格截断至整点（now.replace(minute=0, second=0, microsecond=0)），并作为第二系统文本块（Second System Block）跟在静态块后面。
// 截断到小时的上下文时钟实现（消除分秒对静态缓存前缀的污染）
def context_clock(now: datetime) -> str:
    return now.replace(minute=0, second=0, microsecond=0).isoformat(timespec="minutes")

// 两段式 System 块结构：静态前缀先行，动态上下文随后
def build_system_blocks(static_text: str, context: str) -> list[dict[str, Any]]:
    return [
        {"type": "text", "text": static_text, "cache_control": {"type": "ephemeral"}},
        {"type": "text", "text": context},
    ]

2.3 支柱三 · 结构化输入防御数据围栏（Fencing Pipeline）

外部不可信数据（用户提问、搜索结果、第三方网页、CSV 文本）进入大模型上下文前，必须经过强行净化，fencing.py 确立了四道线性清洗防线：

  1. Unicode NFKC 标准化与不可见控制符清除：过滤零宽字符（\u200B）、双向覆盖（Bidi \u202A-\u202E）、蒙古文元音分隔符、隐形 ASCII 标签等后门。
  2. 伪造轮次边界消除：将数据文本中出现的形如 \n\n(human|assistant|user|system): 的标记替换为 \1\2 -，彻底瓦解试图通过换行伪造对话边界的提示词注入。
  3. XML 标签不动点（Fixpoint）剥离：使用 while True 循环递归移除 <tool_use>、<tool_result>、<system> 等控制标签，直至清洗前后文本完全相同（收敛至 Fixpoint），彻底防御类似 </label</label>> 的嵌套转义注入。
  4. 硬长度截断：对文本设定 max_fenced_chars（默认 12,000 字符），超限强制截断并追加 ...[truncated]，防止超长内容对上下文造成 DoS 挤占。

2.4 支柱四 · 实体出处硬门禁（Provenance Gates）与服务端富化（Enrichment）

在生产环境中，模型最大的风险之一是“伪造不存在的实体 ID”与“在 Markdown 中凭空捏造虚假价格/指标”。

  • 出处守卫（Provenance Gate）：每个 Session 的 RunState 严格维护 seen_ids 集合。任何写操作或参数下发，其传入的 SKU ID、订单号、品类代码必须属于 seen_ids。若模型幻觉出未经查询的实体，Code Gate 立即拦截并将其标记为 held，打回重查。
  • 服务端富化架构（Server-Side Enrichment）：模型只负责做出决策（选择实体 ID + 输出业务理由），卡片上的核心指标、最新单价、库存数、趋势图数据 100% 由后端从权威数据库 JOIN 补齐。模型无法在输出流中凭空修改关键数字，从机制上消除了数据幻觉。

2.5 支柱五 · 两阶段暂存写（Staged Changes）与双重 Guardrail 护栏

涉及调价、补货、营销预算调整等破坏性操作时，严禁单步直接执行。merchant-agent/core/merchant_agent/changes.py 建立了两阶段提交（2PC-like）规范：

阶段操作动作执行主体安全校验与护栏
阶段一 (Stage) 调用 stage_* 工具提出变更草案，生成包含 Before/After/Diff 的不可变变更记录并入库暂存。 AI Agent 执行第 1 次 check_guardrails：校验单次变动条目上限、保护字段不可改、调价幅度未超阈值。超限直接拒绝暂存。
中间态 (Preview) 前端组件渲染可视化差异对比（Diff Card），呈现调价影响面、边际利润变化与风险等级。 前端 UI 人工（运营/店长）或具名 Host 在独立界面肉眼审查对比。
阶段二 (Commit) 点击批准（Approve）或拒绝（Reject），触发执行管道对暂存的草案执行最终落库。 Host 系统 / 人工 执行第 2 次 check_guardrails：防止自暂存至批准期间底表基线数据发生漂移，再次校验通过后原子生效。

2.6 支柱六 · 跨会话结构化记忆沉淀与 purge_generation 并发控制

长程智能体需要记住用户的业务偏好与关键业务目标，但绝不能让记忆抽取阻塞用户响应：

  • 会话后异步抽取（Post-Turn Extraction）：在会话交互关键路径之外，启动后台轻量小模型，基于严格的模板抽取“一年后依然成立且脱离今日琐事”的三类事实：偏好（Preference）、约束（Constraint）、业务上下文（Context）。
  • 代数并发控制（Purge Generation）：为每个租户/用户维护一个单调递增的整数代数 purge_generation。当用户发出“清除我的偏好/重置上下文”时，代数自增。若后台正有耗时的抽取任务在运行，写回前比对代数，一旦发现代数落后立即全量丢弃，彻底杜绝并发脏写。

04 商家 Agent 五大技能深度嫁接：Ulike 智能经营分析的闭环跃迁

merchant-agent 是 Anthropic 为店长与品牌操盘手设计的数字化经营中枢。 它由 performance-insights 统领全盘归因诊断，并通过 catalog-listings、inventory-operations、 pricing-promotions 与 marketing-campaigns 形成直接的治理闭环。 这套设计彻底解决了 Ulike-Agent 经营分析“有诊断、无执行”的硬伤。

4.1 performance-insights：严密归因方法论的体系化注入

在实际业务中，许多所谓的“智能分析”充斥着草率的伪归因（例如看见 GMV 下跌就怪罪于流量下滑，或者将低价品畅销误判为大盘降价）。 performance-insights/SKILL.md 确立了一套硬核的分析师推导纪律：

① 数据快照先行纪律Snapshot First

原则：分析必须始于 get_business_snapshot：获取大盘核心指标、同期对比（compare_to）及预警计数。只有快照无法直接回答的深层问题，才允许触发 query_metrics 下钻。严禁开局直接暴力跑宽表 SQL。

② 比较期选择学 (Comparisons)严防口径错位

原则：周度环比看上周；季节性异动看去年同期；政策或调价前后看变动窗口。硬红线：未完周期（Partial Period）严禁直接与完整周期对比；若今日数据截至 14 点，必须同步截取对比期的前 14 点进行同截面核算，否则强制标注“不完全对比”。

③ 价量与结构漂移分离 (Mix vs Level)数学级硬门禁

原则：大盘均价（客单价）下滑，必须在数学上严格分解为：单品真实降价（Level drop）与低价品销量占比上升造成的结构恶化（Mix shift）。在未下钻品类细分结构（Segment）之前，严禁直接声称“降价导致收入下滑”！

④ 因果时空精准对齐 (Causal Alignment)时空交集校验

原则：候选外部诱因必须严格满足两道闸：时间线吻合（营销停滞、调价或断码发生时间与异动拐点严格一致）且影响范围精准落在该分段内。两项同时满足才称为 Cause；仅时间重合者只允许表述为 Correlation；无数据支持者强制标记为“不可见”。

数学证明：大盘均价变动的 Mix 与 Level 经典分解公式

设大盘由各细分品类 $i$ 构成，基期为 $0$，报告期为 $1$。品类单价为 $P_i$，销量占比为 $W_i$（$\sum W_i = 1$）。大盘平均客单价 $ar{P} = \sum W_i P_i$。则平均单价总变动 $\Delta ar{P}$ 可严格正交展开为： 

ΔP_bar = P_bar_1 - P_bar_0 
       = ∑ (W_i1 * P_i1) - ∑ (W_i0 * P_i0)
       = ∑ W_i0 * (P_i1 - P_i0)    [单品纯价变动贡献：Level Effect]
       + ∑ P_i0 * (W_i1 - W_i0)    [结构漂移变动贡献：Mix Effect]
       + ∑ (W_i1 - W_i0)*(P_i1 - P_i0) [交叉复合交互项：Interaction]

Ulike 在脱毛仪与美容仪业务中常出现“大盘客单价下跌，但核心单品并未降价”的假象，其真实诱因往往是低价配件或便携款销量占比（$W_{low}$）骤增。必须在代码层强制计算上述公式，严禁模型信口开河。

05 架构底座迭代实施详案 (P 系列：P0 ~ P2)

本章针对 Ulike-Agent 底层工程弱点，逐项给出具体的代码修改方案、类设计、包路径与测试验证断言。

5.1 P0 级即刻落地项：结构安全与提示词工程

P0-1 实体出处守卫 (Provenance Gate) P0 · 阻断幻觉实体

问题根因：模型在写类工具或指标钻取中，可能凭空生成不存在的 SKU 编码或订单号，导致后端脏写或无意义 SQL 异常。

实施步骤：

  1. 在 genie-backend/.../RunStateSnapshot.java 中扩展 Set<String> seenIds，在所有只读工具（如查询商品、查询订单、快照工具）返回时，自动解析并提取实体 ID 存入该集合。
  2. 在所有写工具（或生成配置工具）执行前，前置挂载 ProvenanceGate 拦截器。校验入参中的目标实体是否包含在当前会话的 seenIds 内。
  3. 若出现未见实体，不直接抛出系统 500 异常，而是收敛为标准错误返回："Entity ID [xxx] was not observed in current session context. Please read before write." 并标记为 held。
P0-2 提示词静/动分离与小时钟 (Prompt Caching Architecture) P0 · 核心成本与时延降低

问题根因：ReactImplAgent.java 与 PlanningAgent.java 构造 System Prompt 时，直接使用 replace("{{date}}", context.getDateInfo()) 将精确到秒的时间戳和每步都在变动的 {{files}} 插在 System Prompt 前缀，导致 DeepSeek / Claude 的 Prompt Cache 命中率为 0。

实施步骤：

  1. 拆分两段式 System Block：
    • Block 1 (静态段)：包含角色定义、协议契约、Packs 声明式算子骨架。在结尾显式注入 cache_control: {"type": "ephemeral"}。
    • Block 2 (动态段)：放置当前动态文件列表、动态会话状态与小时钟。
  2. 实现 Context Clock 小时钟：将时间严格截断至当前小时： 
    public static String getContextClock() {
    return LocalDateTime.now().truncatedTo(ChronoUnit.HOURS).format(DateTimeFormatter.ISO_LOCAL_DATE_TIME);
}
  3. 在多轮交互中，仅对最后一条已完成消息打滚动断点，确保多轮对话前序 Tool Results 全部命中缓存。
P0-3 工业级输入防御围栏 (Java Fencing Pipeline) P0 · 防注入与控制符安全

问题根因：genie-backend 缺乏底层字符级清洗，搜索结果与用户输入中的不可见控制符、伪造轮次边界可轻易实施越狱。

实施步骤：

  1. 在 genie-backend/src/main/java/com/jd/genie/security/ 新建 FencingPipeline.java；
  2. 使用 Normalizer.normalize(text, Normalizer.Form.NFKC) 实现规范化；
  3. 正则过滤 13 类隐形字符区间（零宽、Bidi、不可见标签字符）；
  4. 正则替换伪造轮次：text.replaceAll("(?i)(\\r?\\n[ \\t]*\\r?\\n[ \\t]*)(human|assistant|system|user)[ \\t]*:", "$1$2 -")；
  5. 循环消除控制标签（Fixpoint 迭代）： 
    String prev;
do {
    prev = text;
    text = TAG_PATTERN.matcher(text).replaceAll("[removed]");
} while (!text.equals(prev));

5.2 P1 级关键迭代项：暂存审批、技能加载与分析委托

P1-4 两阶段暂存写语义 (Staged Changes) 与 ApprovalService 融合 P1 · 审批闭环

方案设计：复用现有的 SQLite agent_approval 表与 ApprovalService。写类工具（调价、修改看板、变更库存规则）严禁直接写库，统一返回 StagedChange 结构（包含 before_state, after_state, diff, change_kind）。在入库暂存与最终批准两个时间节点均执行 check_guardrails，前端 Open WebUI 渲染可视化 Diff 卡片，管理员一键 Approve 触发底层无状态 RPC 提交。

P1-5 Packs 领域技能两层动态按需装配 P1 · 提示词解耦

方案设计：将当前 packs/domains/ 中庞大的 YAML 描述拆分为“轻量元数据声明（常驻静态块）”与“详细场景指令（按需加载）”两层。主 Agent 默认只知晓技能名称与简短摘要，通过类似于 load_skill("sales-deep-attribution") 的机制动态将特定业务指令引入第二系统块，大幅削减默认上下文消耗。

P1-6 受限分析委托 (run_analysis) 与结果瘦身回传 P1 · 上下文减负

方案设计：在 genie-tool/agent_runtime/ 中实现受限分析 Delegate。主智能体遇到“交叉多维对比、品类异动拉动率测算”时，下发计算任务至 Delegate。Delegate 在 Python 沙盒中完成计算，仅向主智能体回传标准格式的 AnalysisResult（精简指标摘要卡片），杜绝将数千行原始时序数组直接打印到主会话历史。

P1-7 跨会话结构化记忆与 purge_generation 代数并发控制 P1 · 长期记忆

方案设计：接入 Open WebUI 异步记忆管道，在主会话完成后异步调用小模型抽取“偏好/约束/业务背景”三类持久事实。在 SQLite / Redis 中为用户维护单调递增的 purge_generation。用户执行“清理记忆”时自增代数，后台异步抽取任务在落库前必须原子比对代数，一旦发现代数不一致即刻丢弃，彻底消除并发写回脏数据风险。

5.3 P2 级深度治理项：延迟削减与长会话治理

P2-8 历史折叠（History Compaction）：当单会话交互超过 5 轮时，自动将前序轮次的详尽 Tool Result 替换为精简摘要或单行回执，释放上下文空间。
P2-9 会话乐观并发控制：引入版本号比对，双端同时修改会话时执行 CAS 检验，杜绝并发覆盖。
P2-10 工具流中执行（Eager Dispatch）：在 LLM 流式输出工具 JSON 的过程中，当首个耗时工具的参数结构闭合时，即刻在后台异步启动该工具执行，与剩余文本生成实现并发并重叠时延。

M0-1 经营分析素养指令注入 (Playbook & Operator 增强) M0 · 防假归因

规则注入：在算子的 evidencePolicy 与系统 Prompt 中强制注入四道纪律：

  1. 基准期对齐闸：严禁未完周期（Partial Period）与完整周期直接比对，必须同截面截取。

1. 告别无谓的复杂性迷信: 用单主循环 + 动态技能加载（Single Primary Loop with Skills）替代层层级联、脆弱不可控的多 Agent 路由；

4. 直通业务闭环: 用 Action Chips 与两阶段暂存审批，打破分析与业务系统之间的高墙，让每一次洞察都能一键跃迁为合规、安全、受控的经营生产力。
