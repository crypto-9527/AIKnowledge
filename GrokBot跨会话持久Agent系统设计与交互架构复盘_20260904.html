Grok Bot 团队复盘：他们如何设计 Grok Bot 的，以便让机器人能够在多个会话之间持续工作

一分钟速览

  • 跨会话责任绑定：Grok Bot 的设计起点是把跨会话责任绑定到稳定的 Bot，而不是继续让一次次 Chat 充当产品主对象。
  • 头像多维表达：头像同时承担身份、六种工作状态和最低限度的进度确认；执行细节只在用户需要时逐级展开。
  • 自治与介入边界：独立电脑、结构化结果和分层协作边界都服务于同一目标：让 Bot 负责执行，让人只在判断与异常时介入。
  • 主动化演进：Routine 把工作的起点从用户 Prompt 扩展到时间、外部事件和另一只 Bot；团队随后继续删除会增加监督负担的界面。

Grok Bot 团队从早期探索到产品上线，连续面对同一个问题：当机器人能够记住此前的工作、跨越多次会话继续负责、在后台使用自己的电脑，并在用户离开后主动开工，产品还应该围绕一段段聊天来组织吗？SpaceXAI 的官方设计复盘《Designing Grok Bot for a world of persistent agents》给出了他们的一组界面取舍。

他们的设计理念有一条清晰的推进线：先把“谁在负责”放到界面中心，再为这个长期负责者补上身份、状态、工作空间、产物与主动触发机制；每增加一种能力，同时删掉一层会诱导用户持续监督的控制界面。

传统 AI 产品默认用户始终在场。人发出 Prompt，看着模型执行，收到回答，一轮会话结束。Grok Bot 团队要设计的对象却会长期存在。它今天接下任务，明天仍应记得上下文；没有新消息时，也可能因为时间或外部事件继续工作。于是，团队必须重新回答四类基础问题。

Q: Grok Bot 团队如何把一次性对话改造成持续负责的 Agent 系统？
核心解答：设计先把谁在负责放到中心，再为 Bot 补上身份、状态、工作空间、产物和主动触发；Agent 能力逐层增加，人的监督界面逐层退出。

起点：机器人要跨会话负责，聊天记录就不再是主角

聊天列表适合保存一次次问答，却不适合保存一项持续责任。一次对话解决后会被新会话往下推；隔一周再回来，用户通常重新开一个窗口。对于只回答眼前问题的模型，这种行为完全合理。对于理应认识用户、记得之前的工作并继续负责的 Agent，它却会把同一件事切成互不相连的历史记录。

Grok Bot 团队在开场原型中展示了另一种关系：侧边栏里不是“昨天的对话”“上周的对话”，而是 Kenny、Justin、Luke、Tyler 等不同 Bot。每个名字旁边直接出现最新进展或等待确认的事项，例如全员会议材料需要批准、销售引荐已经写好、收件箱还剩两封要回复。用户回来时先看到“谁在负责什么”，再进入与这名负责者的对话。

这成为后续设计的判断基准。只要 Bot 要跨天延续工作，产品的主对象就必须稳定存在；否则所谓记忆、自动化和工具都只能挂在一堆会不断下沉的会话上。

第一步：把产品的基本单位从 Chat 换成 Bot

持久 Agent 背后有模型、上下文窗口、系统提示、沙箱、连接器、权限和自动化等大量技术对象。全部暴露出来，用户就得先理解系统架构，才能交代一项工作。团队先做了一次概念压缩，只留下五个必须被用户理解的对象：

对象 (Entity) 在产品中的职责 (Responsibility)
Bot 持续存在的 Agent，拥有身份、记忆、运行环境和工具
Chat 用户与某只 Bot 沟通的窗口
Prompt 提供上下文或指令；可只用一次，也可保存为 Skill，或由 Routine 自动触发
Tool 让 Bot 通过软件、API、连接器、Shell 或电脑读取信息并采取行动
Artifact Bot 创建或修改的文档、设计、代码、数据等持久结果

五个对象中，团队最终选择 Bot 来组织产品。Bot 有名字、头像和角色称谓，记得与用户的对话，拥有自己的电脑与工具。第二天回来，用户面对的仍是同一个负责者。Chat 没有消失，只是从主界面的组织单位退回为与 Bot 沟通的入口。

Q: 为什么持续型 Agent 的主界面对象应该从 Chat 变成 Bot？
核心解答：聊天历史按一次次请求和时间排列；Bot 名册按持续责任排列，把身份、记忆、工具、电脑、例行任务和当前状态绑定到同一负责者。

这个调整改变了侧边栏回答的问题。聊天历史回答“我聊过什么”，Bot 名册回答“谁在负责”。一旦工作需要跨越多次会话，第二个问题才是用户首先需要确认的事。

第二步：让用户一眼认出它是谁、正在做什么

Bot 变成长期对象以后，名册必须同时回答三个问题：这是谁？它在做什么？我现在需要知道多少？Grok Bot 团队把三道题都集中到头像与它周围的一小块界面里。

为了让几十只 Bot 既容易区分、又像来自同一个系统，团队试过首字母、Emoji、像素画、水彩、黏土、Noritake 风格线稿、剪影和 identicon 等多套视觉系统。水彩和黏土有个性，但缩到侧边栏尺寸后细节过重；更简单的系统能融入界面，却容易让不同 Bot 看起来可以互换。最终方案保留统一的简单几何结构和富有表情的眼睛，再通过受控变化与配件形成差异。

头像随后承担了第二项任务：表达生命周期。团队列出六种状态——Idle、Working、Waiting、Blocked、Thinking、Done。Bot 接到工作时先作出响应，开始执行后进入更明显的运动；等待外部条件或需要帮助时，动作再次变化；完成后恢复稳定。状态不再需要额外的一排徽章，用户看同一个视觉对象就能同时识别身份与进度。

Q: 同一个 Bot 头像怎样表达从待命到完成的完整生命周期？
核心解答：Bot 头像依次表达待命、工作、等待、受阻、思考与完成六种状态，并在完成后恢复稳定。

第三项任务是控制执行细节的可见度。标准的“三个跳动圆点”信息太少，用户无法判断 Bot 仍在工作还是已经卡住；持续展示完整活动日志又会把人拉回监工位置。团队的用户研究显示，人们追问更多细节，主要是想确认 Bot 还在工作、方向没有跑偏。最终界面先用头像运动给出最低成本的确认；需要进一步检查时，悬停才显示当前动作。

Q: 执行过程应该默认展示多少，用户担忧时又怎样逐级展开？
核心解答：界面先显示 Bot 仍在工作，再按需显示当前动作，最后才展开完整活动日志。

这里形成了第一条完整的设计路径：稳定头像负责“是谁”，动作状态负责“是否仍在推进”，按需出现的当前动作负责“方向是否正确”。信息量随着用户的担忧逐级增加，默认界面保持安静。

第三步：电脑归 Bot 使用，人只保留查看与接管权

每只 Grok Bot 都有自己的电脑，可以浏览网页、处理文件和运行软件。团队很快遇到一个反直觉的问题：电脑画面越醒目，产品越像远程桌面，用户越容易把时间花在观看和操控上。

他们比较了四种布局：浮窗容易打开，却会遮住对话；并排视图持续暴露执行过程，鼓励用户盯着看；模态窗口适合短暂查看，却把 Bot 的工作空间变成一次打断；全屏给电脑足够空间，但会完全挤走对话。四种方案都没有解决所有权问题——界面仍在暗示这是一台需要用户照看的电脑。

Q: 为什么浮窗、并排、模态和全屏都不足以解决 Bot 电脑的所有权问题？
核心解答：浮窗遮挡对话，并排诱导持续观看，模态造成打断，全屏挤走对话；四者都暗示电脑仍由用户管理。

最终方案把介入拆成三层：

  • Status：电脑运行时，标题栏图标变成紫色；用户只知道工作区正在使用。
  • Preview：需要上下文时，打开固定侧栏观察工作，不离开当前对话。
  • Takeover：Bot 碰到必须由人处理的问题时，用户全屏接管，完成操作后再把控制权交还。

Status 还可以按需展开 Bot 的当前动作。于是，三层介入按信息量拆成四级检查路径：状态、当前动作、预览、接管。

Q: 用户怎样从最低成本的状态确认，逐级深入到完整接管？
核心解答：默认先由头像状态确认 Bot 仍在工作，需要时查看当前动作，再打开工作区预览；只有 Bot 需要帮助时才进入全屏接管。

三层访问把“随时可检查”和“必须持续围观”分开。Bot 电脑还拥有随时间变化的壁纸，早晨更亮、夜间更暗。这个细节不是单纯装饰，它帮助用户把工作区理解为 Bot 自己的环境，而不是自己桌面的远程镜像。

第四步：让答案长成可以直接使用的界面

早期 Grok Bot 几乎用散文回答所有请求：五天天气被写成一段话，一组任务也由文字逐项描述。信息可能没有错，重新整理日期、状态、负责人和下一步操作的负担却回到了用户身上。

团队因此把“信息的形状”视为答案的一部分。适合解释的内容继续用文字；需要比较、扫描或直接操作的内容改用内联卡片和组件。邮件组件同时呈现收件人、主题、正文，以及发送和放弃按钮。创建 Routine、修改设置、向另一只 Bot 发消息等动作，则可以作为系统事件直接进入对话时间线。

Q: 为什么天气、任务和邮件不该全部被压成一段自然语言？
核心解答：天气以数据卡片呈现，任务以状态列表呈现，邮件以包含收件人、主题、正文和发送动作的组件呈现。

时间线由此不再只有自然语言。对话、系统事件、交互对象和可视化共享同一段上下文。用户既能看到双方说了什么，也能确认动作是否真的发生、结果处于什么状态、下一步是否需要自己处理。Artifact 也因此不只是一个附件，而是把聊天里的承诺变成可检查成果的界面单位。

第五步：给多只 Bot 划清能力、记忆与协作边界

用户创建多只 Bot 后，系统需要解决两组相反的需求：浏览网页、处理文档和发送邮件等能力应当复用；法律、财务、设计等角色的长期上下文又不能混成一大块记忆。

Grok Bot 最终让能力与上下文遵循不同边界：

  • Tools 与 Skills 属于账户层，多只 Bot 可以共享通用能力。
  • Memory 与 Routines 属于 Bot 层，长期知识和持续职责跟着具体角色走。
  • Group Chat 属于共同任务，跨角色项目只共享完成协作所需的上下文。
Q: 多只 Bot 的通用能力、长期记忆与项目共享上下文分别应该放在哪里？
核心解答：Tools 和 Skills 在账户层复用；Memory 和 Routines 跟随具体 Bot；Group Chat 提供项目共享上下文；协调 Bot 处理日常路由，只把需要判断的事项交给用户。

一些用户还会建立类似 Chief of Staff 的协调 Bot，把方向交给它，由它调度多个专业角色。团队考虑过仪表盘、任务分派板和显式交接控件，但这些界面会把路由工作重新交给用户。最终方向是让协调 Bot 处理日常分发，只在需要判断时把人叫回来。

这一步决定了多 Agent 究竟是一个团队，还是六个需要分别照看的聊天窗口。能力可以广泛共享，角色记忆保持隔离，共同项目只交换必要事实，人的注意力才不会被日常搬运耗尽。

第六步：让工作由时间、事件或另一只 Bot 主动启动

一个 Bot 即使能记住过去，只要每次都等用户发 Prompt 才开始，仍然没有真正承担持续责任。Routine 让用户预先定义一项长期工作，在时间到达或事件发生时自动唤醒 Bot。

触发器覆盖固定时刻、工作日、每周和每月周期，也包括 GitHub 的 Issue、PR、Push、检查失败与工作流事件，Slack 的新消息和表情反应，以及项目管理工具中的状态变化。另一只 Bot 同样可以发起工作。Prompt 仍能启动会话，但不再垄断工作的起点。

Q: 没有新的用户 Prompt 时，工作怎样继续并在需要时把人叫回来？
核心解答：工作可以由用户 Prompt、时间、外部事件或另一只 Bot 启动；Routine 唤醒 Bot，结果写回时间线，只有异常或判断需要用户介入。

团队最初把 Routines 放在次级设置里，后来将它移进 Bot 的主界面。原因很直接：既然主动工作是核心能力，用户就必须看到哪些持续职责正在运行、最近执行了什么、结果留在哪里，以及哪个异常需要处理。对话时间线于是也成为一份责任记录，既容纳人发起的请求，也容纳无人在线时发生的工作。

记忆让 Bot 第二天还认识这项工作，Routine 让它第二天能够自己继续。跨会话持续工作需要两者同时成立。

收尾：删掉会把用户重新变成管理员的界面

复盘的最后，团队写到项目后期的大量工作其实是删除：窗口与面板控制、电脑视图选项、Agent 元数据都被压缩或拿掉。他们还设置了约 50 只 Bot/账户、6 只 Bot/群聊的实际上限。每个决定都接受同一个测试：它是否帮助用户委派，还是只增加一个需要管理的对象？

沿着这条标准回看，前面的设计选择并非一组孤立功能。Bot 名册建立稳定责任；头像让进度可见；按需披露减少查日志；独立电脑把执行留给 Bot；结构化组件让结果可直接使用；分层边界降低多 Bot 协调成本；Routine 让工作无需等待下一条 Prompt。它们共同服务于同一件事：用户离开以后，责任、上下文和工作仍然能够继续。

这份官方复盘没有证明 Grok Bot 已经能在所有场景可靠地承担长期任务。它给出的价值是一套具体的产品判断：如果界面仍以一次会话为中心，如果用户还要不断追问进度、翻看完整日志、搬运上下文并手工触发下一步，那么机器人即使具备更强模型能力，也还没有在产品层面成为一个跨会话工作的长期负责者。
