核验方法说明

原稿为第三方分析稿。本次核验直接抓取 Human-Agent-Society/reef 主分支的 pyproject.toml、LICENSE、recipes/README.md、recipes/gepa/examples/aime/README.md、recipes/openclawrl/README.md、recipes/skillclaw/README.md 与仓库 API 元数据，逐条比对原稿断言。凡一级源未确认者，一律标注为「未独立核验」，不作推断填补。

Part I一分钟速览

  • 多数 Agent 在部署后停止学习，原因不是线上没有经验，而是推理记录、反馈、训练与版本发布彼此断开。
  • Reef 用 Serve、Observe、Grow、Commit 把请求变成可归因经验，再生成模型或 Harness 候选；只有通过评测的版本才能回到服务。
  • Recipe 把 SAO、OpenClaw-RL、TTT-Discover、SkillClaw 和 GEPA 等方法接到同一底座；scenario 隔离记录与版本，但学习方法由部署配置决定。
  • Reef 可以先作为不训练的记录代理接入外部模型，再逐步启用学习；闭环能控制更新，却不能替团队保证反馈和评测目标正确。

一个 Agent 每完成一次真实任务，都会留下极有价值的经验：用户纠正了什么，工具为什么失败，哪条执行路径得到了高分，哪种结果真正解决了问题。可多数推理服务器在返回答案后就把这些信号丢掉了。模型上线的那一刻，也成了它停止学习的那一刻。

麻省理工学院（MIT）的 Ao Qu 与 Human-Agent-Society 团队，开发了一个专门解决这道断点的项目——Reef。Reef 要改变的就是这件事：把线上推理、经验记录、候选更新、评测和版本发布接成一条长期运行的闭环，让推理服务器不只负责「回答」，还负责让 Agent 持续学习和自我改进。

这套系统要解决的并不是某一种训练算法，而是持续学习缺失的工程底座：从真实流量中取得可信经验，决定该更新模型还是外层运行框架，再阻止未经验证的变化直接污染线上服务。Reef 把这个更宽泛的目标称为 continual self-improvement。它允许系统反复从经验中改善，但并不等同于已经实现了能够自行制造下一代系统的递归自我改进（RSI）。

Part I部署后的 Agent 为什么停止学习

传统大模型的生命周期是一条单向流水线：收集数据 → 训练模型 → 离线评测 → 部署上线 → 响应请求。训练系统关心参数如何变化，推理系统只关心如何稳定返回结果，两边在部署时被切开了。

Agent 让这个切口变得越来越昂贵。一次长任务包含多轮对话、工具调用、中间状态、执行结果和用户反馈，它们共同回答了三个关键问题：系统当时看到了什么、做了什么、结果到底好不好。这类经验比通用离线语料更贴近真实需求，却常常没有稳定路径回到学习系统。

另一个问题是，Agent 的行为并不只由模型权重决定。提示词、记忆、Skill、工具权限和编排逻辑都会改变最终结果。工具选错、上下文组织失控或规则写坏时，继续训练模型可能既昂贵又无效；真正该改的对象可能在模型外面。

所以，持续学习需要同时打通两条断点：

  • 推理不再是终点。 线上轨迹、执行结果、用户反馈和环境奖励要成为下一轮学习的输入。
  • 模型不再是唯一的更新对象。 权重与 Harness——也就是负责上下文、记忆、Skill、工具和编排的外层系统——都要进入同一套演化与版本控制流程。

问题因此从「再接一条训练管道」变成了「怎样管理一个不断产生经验、候选和新版本的在线系统」。

到这里，Reef 与站内两篇解读正好接上：Harness 工程继续展开「模型外面还有什么可以优化」，OpenAI 的 ARC-AGI-3 复盘则把 Harness 对结果的影响放进一个具体实验。Reef 补上的下一步，是让这些改动能够从线上经验中持续产生，经过评测，再安全进入下一版服务。

Part I一次请求怎样变成下一次更新

Reef 把一次学习循环拆成四步：Serve、Observe、Grow、Commit。Serve 处理请求并留下记录，Observe 把后续反馈对回具体交互，Grow 用符合条件的经验生成候选，Commit 只把通过评测的候选发布为新版本。

一次线上请求怎样变成下一版 Agent 的学习材料？

请求经过推理生成 record receipt，反馈与 record 绑定，learning recipe 生成模型或 harness 候选；候选通过评测后发布为新版本，供下一次请求使用。

这四步能够连续运转，依赖三项端到端能力：

必须掌控的对象要解决的问题缺失后的结果
经验把反馈精确关联到一次请求、上下文和实际版本样本无法归因，训练数据很快失真
整个 Agent同时识别模型与 Harness 中可变化的部分行为变化无法定位，更新对象选错
版本发布评测候选并控制它何时替换线上版本坏更新直接污染服务，旧任务还可能覆盖新版本

先把经验和反馈对上号

Reef 首先是一台推理服务器。它接受 OpenAI 的 /v1/chat/completions 和 Anthropic 的 /v1/messages 请求体；应用无需另造一套调用协议。区别在于，每次响应会多返回一个 x-reef-agent-record-id，相当于这次推理的收据。

用户评价、测试结果或环境奖励出现后，应用再调用 /reef/report，用这张收据指出反馈对应哪次交互：

Python · 反馈归因调用response = reef.post(
    "/v1/chat/completions",
    headers={"x-reef-scenario": "support-agent"},
    json={"model": model, "messages": messages},
)

receipt = response.headers["x-reef-agent-record-id"]

reef.post(
    "/reef/report",
    json={
        "score": 0.0,
        "feedback": "没有处理空 token 的情况",
        "references": [receipt],
    },
)

这一步解决了持续学习最基础的归因问题：一条反馈究竟在评价哪次推理、哪组上下文和哪个 Agent 版本。Reef 所说的 stateful inference 不只是保存聊天历史，还包括保存结构化推理记录、反馈引用、scenario、artifact 版本和样本新鲜度。

统一的记录层还能处理多轮 session 拼接、重复样本和 off-policy staleness。后者衡量一条经验来自多旧的策略，以及它是否还适合训练当前版本。不同 scenario 隔离各自的记录和版本；Recipe 则由部署配置选定，请求只能指定 scenario，不能临时切换学习方法。

再决定该改模型，还是改 Harness

模型负责语言、推理和生成，Harness 负责把能力组织成可靠行动。模型再强，也补不上错误的工具权限和混乱的上下文；Harness 再精巧，也无法凭空创造模型没有的能力。Reef 因此把两者都做成可以产生候选、接受评测和发布版本的 learning surface。

  • 模型侧： Recipe 异步消费符合条件的记录，训练出 checkpoint 或 LoRA 候选。模型训练后端基于 Slime 适配；候选获准后，可通过 NCCL 同步权重并热更新推理引擎，不必停止服务。
  • Harness 侧： Recipe 根据执行轨迹、反馈与评测任务修改规则、提示词、记忆、Skill、工具或编排树。Cordis 承担 Harness 演化后端，新版本以可安装 artifact 交付；交互式客户端可选择更新或跳过。

Reef 所说的整个 Agent 究竟包括哪些可演化对象？

Reef 同时支持模型权重和 harness 两类更新；harness 包含提示词、记忆、技能、工具和编排，并可作为可安装版本交付。

「Agent 版本」由此不再只是一个模型名称。一次请求用了哪套权重、哪版规则、哪组 Skill 和工具，都可以进入可追踪的版本链。模型和 Harness 也不必一起变化：Recipe 可以只更新某一侧，甚至只训练一个引导模型，把负责执行的外部模型保持冻结。

最后只让通过评测的候选进入服务

持续更新最大的风险，是系统把噪声、个人偏差或奖励漏洞学进去，最后越学越差。Reef 严格区分「新候选」和「正在服务的版本」：Recipe 先生成候选，评测插件再比较候选与现有版本。候选被拒绝，线上服务保持不变；评测异常，流程关闭，准备中的更新不会被发布。

候选更新什么时候能替换正在服务的版本？

经验记录生成候选，候选被拒绝时线上版本保持不变；通过评测后才写入 artifact、加载 serving state 并发布新版本。

只有评测明确通过，Reef 才会提交 artifact、加载新的 serving state，并推进 release。模型 checkpoint、LoRA、Harness tree 和 routing policy 都可以被版本化；Git 与 Git LFS 负责保存这些对象。

每个 scenario 维护自己的追加式 release chain。发布者推进 release head 时，必须声明自己看到的旧 head；如果另一项任务已经发布了更新，compare-and-swap 会拒绝这次过期提交，避免较老的训练任务覆盖较新的版本。

这套门控能保证更新按规则进入服务，却不能替团队定义「什么叫更好」。评测集太窄、反馈带有偏差或指标容易被钻空子时，严密的版本链只会更可靠地执行错误目标。

Part I不同学习方法怎样共用一套底座

Learning Recipe 决定「怎么学」，公共底座负责记录、批处理、评测和发布。在线强化学习、测试时训练、提示词优化和 Skill 演化虽然算法不同，都可以归结为三个配置问题：

  1. 信号从哪里来？ 环境 reward、用户反馈、测试结果、下一状态，还是评审模型的判断？
  2. 经验怎样取得？ 被动等待真实任务，还是主动探索、搜索和自博弈？
  3. 最终改什么？ 模型权重、引导模型、规则、Skill pool，还是整个 Harness tree？

看起来完全不同的自我改进方法，怎样被装进同一套基础设施？

SAO 和 OpenClaw-RL 被动接收任务或用户信号并更新模型；TTT-Discover 主动探索环境奖励并更新模型；SkillClaw 等方法从失败、轨迹或执行结果演化 harness。

Reef 已经把多种路径装进同一套接口：

Recipe经验与信号主要更新对象
SAO连续任务由测试或 verifier 给出分数模型权重
OpenClaw-RL从用户交互的下一状态中提取可利用信号，不要求显式报告模型权重
TTT-Discover围绕同一问题反复尝试，用环境 reward 保留更优解模型权重
Guidance-TTT对代码搜索结果打分，执行模型保持冻结引导模型权重
SkillClaw / Harness Evolve从失败流量、执行轨迹和评测任务中产生 Skill 或规则候选Skill pool 或 Harness tree
GEPA从失败样本中反思并改写规则，在小批次与完整验证集上筛选规则、Skill 等 Harness 组件

OpenClaw-RL 的示例把一名模拟学生的 72 道 GSM8K 作业连续送给个人 Agent，用「经过多少轮交互才能符合学生偏好」衡量适应速度。TTT-Discover 走的是另一条路：它围绕 Packing 32 等可评分问题不断尝试，用环境奖励保留更有效的解法。两者一个从连续交互中被动学习，一个在单个问题上主动搜索，却共享相同的记录与版本底座。

GEPA 进一步说明，持续学习不必等同于更新权重。它从失败流量中选择一个 Harness 组件，让更强的反思模型提出改写，再用小批次和完整验证集逐层筛选。Reef 的 AIME 2025 验证在两个随机种子上分别从 26.67% 提升到 46.67%、从 24.00% 提升到 36.00%。这只有两个种子，说明实现能够跑通并产生候选改进，不能证明它在不同任务上都稳定优于其他方法。

接入也不必从训练开始。Basic Recipe 只记录请求、不学习：可以用一个 Reef 进程代理外部 HTTP 模型，无需本地 GPU；也可以连接本地 SGLang，但不启动训练。团队可以先验证请求、收据、反馈和版本链是否可靠，再决定是否开启权重或 Harness 更新。

需要注意，reef-infra 的 PyPI 包提供核心基础设施，Cookbook Recipe 保存在源码仓库中，并不随 wheel 一起分发。运行这些方法需要源码 checkout 和各自的依赖；模型训练通常还需要满足文档要求的 GPU 环境，Skill 或 Harness 演化则存在不依赖 GPU 的路径。

Part IReef 真正改变了什么

Reef 把 Agent 开发中的三个分离系统接到了一起：推理服务开始积累可归因经验，模型与 Harness 共享版本边界，训练结果必须经过评测和发布控制才能回到线上。

这意味着，训练不再只是周期性产出一个 checkpoint。Observe 决定哪些反馈可信且仍然新鲜，Grow 负责提出变化，Commit 决定变化能否成为下一版服务。持续学习因此成为一项长期的 release engineering，而不是一次离线实验。

最适合这套架构的，是任务会重复出现、结果能够被测试或相对可靠地评分、团队也愿意维护回归评测和 artifact 生命周期的场景。只有零散主观反馈、没有稳定评测面时，接上闭环只会更快地积累不确定性。

Reef 采用 Apache-2.0 许可证，要求 Python 3.10 以上；artifact 与 checkpoint 功能依赖 Git LFS。它提供了让 Agent 在真实服务中「边做边学」的控制平面，但最终学到好习惯还是坏习惯，仍由反馈信号、学习方法和评测质量决定。

Part III门控统计功效模型

Reef 的 Commit 门控本质是一个假设检验问题：候选与在位版本在同一评测集上的得分差异，是否足以拒绝「两者无差别」的原假设。这一定性判断可以被精确量化，并直接给出「多大的评测集才配得上多强的结论」。

双比例 z 检验

设候选在 n2 题上答对 x2 题，在位版本在 n1 题上答对 x1 题，合并比例 p̄ = (x1 + x2) / (n1 + n2)。检验统计量为：

z = p^2 − p^1 p¯ (1−p¯) ( 1n1 + 1n2 )

据此对四组 AIME 运行逐一计算（n1 = n2 = 150）：

对比Δz双侧 pα = 0.05 下显著
seed 0 · upstream 前后（47 → 64）+11.33 pp+2.03290.0421显著
seed 0 · method 前后（40 → 70）+20.00 pp+3.59430.000325显著
seed 1 · upstream 前后（40 → 61）+14.00 pp+2.56560.0103显著
seed 1 · method 前后（36 → 54）+12.00 pp+2.26780.0233显著
seed 0 · 跨臂终点直比（64 vs 70）+4.00 pp+0.69680.4859不显著
seed 1 · 跨臂终点直比（61 vs 54）−4.67 pp−0.83120.4058不显著
结论一：单臂结论可信，跨臂结论不可信

四个「演化前 → 演化后」的自身对比全部通过 α = 0.05 显著性检验——这支持「GEPA 式 harness 演化在 AIME 类任务上确实带来提升」这一命题。但两个跨臂对比的 p 值分别为 0.486 与 0.406，远未显著且符号相反。因此可支持的表述是「演化有效」，不可支持的表述是「Reef 实现优于上游 GEPA」。

最小可检出差异与所需样本量

给定显著性水平 α 与检验功效 1 − β，双比例检验在每臂题数 n 下可检出的最小差异为：

MDE = ( z1−α/2 + z1−β ) · 2p¯(1−p¯) n

取 α = 0.05（双侧）、power = 0.80、p̄ ≈ 0.45，每臂 150 题时的 MDE 为 16.09 pp。也就是说，在现有评测规模下，只有约 16 个百分点以上的差异才可能被稳定检出；而已观测到的跨臂差异为 +4.00 pp 与 −4.67 pp，比 MDE 小一个数量级。

基线噪声的二项解释

一个更具诊断价值的观察：frozen 列四次运行得分分别为 47、40、40、36（满分 150），尽管它衡量的是完全相同的种子提示在完全相同的 150 题上的表现。均值 27.17%，单次二项标准差为：

σ = p(1−p) n = 0.2717×0.7283 150 ≈ 3.63 pp

四次独立正态抽样的期望极差约为 2.059σ = 7.48 pp，而实测极差为 11/150 = 7.33 pp，比值 0.981。这意味着：

结论二：基线离散度完全由二项抽样噪声解释

同一提示在同一测试集上 7.33 pp 的波动，与纯二项噪声预测的 7.48 pp 几乎完全吻合（偏差 1.9%）。换言之，无需引入任何系统性差异即可解释观测离散度——这是采样噪声本身，而非方法差异。其直接后果是：seed 1 上 method 声称的 12.00 pp 提升，仅比纯噪声极差（7.33 pp）高出约 1.6 倍，任何单次运行的读数都不应被当作稳定值。仓库自己也写下了同一判断：「The means are across seeds because one run of this search has no stable number to report.」

发布链 CAS 自阻塞模型

Reef 每个 scenario 维护追加式 release chain，推进 head 时必须声明所见旧 head，若期间已有其他任务发布，compare-and-swap 会拒绝该次提交。这一保护机制的代价可以精确建模。

设候选生成速率为 λ（个/天），评测通过率为 p，一次训练/验证窗口时长为 D（天）。发布事件近似为速率 ρ 的泊松过程，则一个通过评测的候选在其窗口内不遭遇他人发布的概率为 e−ρD。稳态下发布速率满足定点方程：

ρ = λ p e−ρD ⟺ ρ = W(λpD) D

其中 W(·) 为 Lambert W 函数（主枝）。由此得到三项可直接决策的指标：

η = ρλp = e−ρD dρd⁡ln⁡λ = 1D · W1+W
  • η（算力利用率）：通过评测的候选中最终真正进入服务的比例，1 − η 即被 CAS 丢弃的浪费。
  • 边际弹性 dρ/d ln λ：候选生成速率每提升 1%（对数尺度）带来的发布速率增量，衡量加算力的边际收益。

取 p = 0.30、D = 0.5 天作为基线（此二值为演示基线假设，非 Reef 实测值）：

结论三：发布链存在对数饱和，堆算力会自我抵消

由于 W(x) ≈ ln x − ln ln x，发布速率对候选生成速率呈对数增长。上表中 λ 从 1 提升到 100（100 倍算力），发布速率仅从 0.263 提升到 4.020（15.3 倍），而算力利用率从 87.68% 崩塌到 13.40%——86.6% 的通过评测候选被 CAS 丢弃。这意味着在长训练窗口（D 大）或高发布频率的场景下，单纯提高学习强度不仅收益递减，还会把大量 GPU 时间烧在被版本链作废的候选上。真正的调节旋钮是 缩短 D（更快的评测与更小的训练粒度），而非加大 λ。

经验漏斗与陈旧衰减

Reef 的闭环吞吐由最窄一环决定。从一次线上请求到一条可用于训练的有效样本，需连续通过五道闸门，任意一环收紧都会等比削减下游：

Neff = R · c · a · (1−d) · w¯

其中 R 为日请求量，c 为反馈上报覆盖率，a 为归因成功率，d 为重复样本率，w̄ 为 off-policy staleness 加权因子。若采集窗口为 W 天、经验半衰期为 T1/2 天，样本权重按 w(t) = 2−t/T1/2 衰减，则窗口内均匀年龄样本的平均权重为：

w¯ = 1W ∫0W 2−t/T1/2 dt = T1/2 W⁡ln⁡2 ( 1 − 2−W/T1/2 )

该模型的工程含义十分直接：采集窗口 W 相对半衰期 T1/2 越长，平均样本权重越低；当 W = T1/2 时 w̄ ≈ 0.7213，当 W = 4T1/2 时 w̄ 降至 0.3381，当 W = 8T1/2 时进一步降至 0.1796。Reef 之所以要记录并暴露「样本新鲜度」，正是因为它是这个漏斗中唯一能被基础设施直接观测、却最容易被忽视的一项。

Part V接入路径与陷阱

  1. 先当记录代理，再开学习。 用 recipes/basic/external-provider.yaml 起一个 Reef 进程代理外部 HTTP 模型，无需 GPU。核心依赖仅 aiohttp / huggingface_hub / pyyaml / reef-client。先验证四件事：请求是否被完整记录、receipt 是否稳定返回、feedback 能否正确归因、版本链是否可追溯。
  2. Git LFS 是硬前置。 git lfs install 必须在 clone 之前完成，否则 artifact 与 checkpoint 功能不可用。这是部署文档中最容易被跳过的第一步。
  3. Recipe 需要源码 checkout。 Cookbook recipe 不随 wheel 分发，uv pip install reef-infra 之后仍需 git clone 才能运行任何学习方法。
  4. 先算评测规模，再谈结论。 用沙盘 A 反解当前评测集对应的 MDE。若真实期望差异低于 MDE，任何「候选胜出」都只是噪声排序，此时加严门控阈值比加严评测更有害。
  5. 调节 D 而非 λ。 按沙盘 B，提高候选生成速率会被 CAS 自阻塞吃掉；缩短训练与验证窗口、减小批次粒度才是真正提升发布吞吐的旋钮。
  6. 监控漏斗的最窄一环。 按沙盘 C，端到端有效率是多环节连乘。反馈上报覆盖率通常是第一瓶颈——它不属于 Reef 的能力范围，而是宿主应用是否愿意调用 /reef/report。

Part V闭环不能替你做的事

三条边界

一、闭环不定义「更好」。 评测集过窄、反馈带偏差、指标可被钻空子时，严密的版本链只会更可靠地执行错误目标。

二、闭环不产生因果结论。 单次运行的读数受二项噪声支配（frozen 基线在相同提示相同题集上有 7.33 pp 波动）。「候选胜出」不等于「方法更优」，除非评测规模达到 MDE 要求且跨种子符号稳定。

三、 continual self-improvement ≠ RSI。 Reef 允许系统从经验中反复改善，但这不是能够自行制造下一代系统的递归自我改进。它优化的是给定任务族内的表现，不扩展能力边界本身。
