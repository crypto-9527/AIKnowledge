从 Harness 到 Fleet：
下一代 Agent 工程的两层结构

一份论文证明了「一个 Agent 的执行框架可以被即时生成」，一套工作台展示了「几十个 Agent 同时跑起来之后该怎么调度与治理」。两者单独都成立，但拼起来的接缝处，露出了一道双方都没有解决的问题。 本文按由浅入深的六层结构拆开，并把其中可计算的部分落成公式。

起点

两份材料，两个层级

把它们放在一起，是因为它们回答的是同一条链上相邻的两个问题——而中间那段接缝，恰好是没人覆盖的地带。

I

Intra-Agent：一个 Agent 怎么长

JIT-Agent 提出：harness（执行框架）不该预先写死，而应由一个 27B 元模型针对具体任务当场合成。论文用 18 组「底座 × 基准」配对的全面提升，证明 harness 是一个独立于模型规模、可训练、可迁移、可复利的能力维度。

II

Inter-Agent：一群 Agent 怎么调度

David Ondrej 的工作台把十几个工具收敛成四层：统一入口、状态调度、持续执行、工程治理。核心洞察是——Agent 一多，瓶颈就从模型生成速度迁移到人的注意力，问题从「怎么写代码」变成「怎么经营一套异步软件生产系统」。

III

接缝：演化信号在哪里算

JIT 的「越用越强」依赖任务结束即能自动判分。而 Fleet 面对的长程、跨仓库、需人评审的任务，恰恰无法自动判分。这道断层决定了 JIT 的自我演化能力能否迁移到 Fleet 层——也是本文第五层的主题。

一个贯穿全文的纪律

本文中的实验数字均来自论文原文；标注为「示意参数」的（如 σ、κ、成本衰减常数）是推演假设，不是实测值，仅用于展示模型形态与决策方法。第六层会对三层结论分别给出证据强度评级。

第一层 · 现象

模型不是唯一变量

论文开篇的判断很直接：Agent 的能力不是模型权重的属性，而是「模型 × harness」这一对组合的属性。 这句话如果只是定性描述，价值有限；但它后面跟着一组硬数字。

最反直觉的一点：性能升，成本也降

通常性能提升要靠更长的推理轨迹、更多的工具调用来换取，成本会同步上升。这里的方向相反—— 在 xBench-DeepSearch 上，token 从 52.7 万降到 21.2 万、成本从 $0.075 降到 $0.039， 而性能反而从 78.0 升到 82.0。增益来自更短、更精准的执行，而不是更长的轨迹。

这件事的含义比「提分」本身重要得多：它说明大量 token 是被不合适的执行框架浪费掉的， 而不是被任务本身的难度消耗的。harness 的优化空间，此前一直没有被当作一个独立变量来对待。

第一层的结论

harness 是与模型缩放正交的第二增长曲线。它不改变模型权重，只改变模型被组织的方式—— 而改变组织方式能带来 20 分级别的差距，这在以往只有换一代模型才做得到。

第二层 · 机制

harness 凭什么可以被「生成」

要让模型学会生成 harness，第一步必须把 harness 从「一坨自由发挥的工程代码」变成「一套有固定结构、机器可生成的产物」。 这是整件事能成立的工程前提。

四模块协议：把程序压成坐标

任意 harness 被冻结成四元组 h = (M, P, A, F)，运行时按 M → P → F → A 协作：

模块职责为什么必须独立
M · Memory历史如何压缩、工作上下文如何组织决定模型「看得见什么」，是精度的上游约束
P · Planning如何拆解、下一步做什么、怎么应对意外决定搜索的形状：串行、并行、还是递归委托
F · Capability在哪个节点暴露哪个工具或技能决定每步的动作空间大小，直接影响 token 消耗
A · Action动作格式、回传结构、出错如何恢复决定能否稳定执行，以及失败时能否局部修复

这套协议的表达能力已被验证——三种截然不同的经典框架都能写成同一个坐标系里的点：

ReAct = ( M_full , P_∅ , A_react , F_all ) Codex / OpenCode = ( M_compact , P_todo , A_react , F_all ) ROMA / AOrchestra= ( M_subproblem , P_decomp , A_rec , F_route )

差异被归约成四个维度上的具体选择。这一步的关键价值是：搜索空间从「程序空间」降到了「配置空间」。 配套地，作者用 HarnessFactory 在统一协议下重实现了 13 个代表性框架（ReAct、Plan-and-Execute、ReSum、 Flash-Searcher、MemoBrain、ROMA、AOrchestra 等）作为种子库——所以生成是在协议约束下装配可执行模块， 不是从零合成自由代码。

三阶段训练：从会写，到会修，再到会演化

I

Customization · 定制

用更强的冻结教师模型，针对每个任务从种子库采样 3 个参考框架，生成合规 harness 作为监督数据。除了 SFT 模仿，还加了一层偏好学习：同一底座、同一评测种子下两两比较候选，只有「得分更高、且时延和成本都不变差」才记为偏好对。

这一步学到什么

不仅结构合规，还要「又有效又省」。成本从训练目标的第一天起就在里面。

为什么重要

它解释了后面成本降 36% 从何而来——不是副作用，是设计目标。

II

Repairing · 修复

第一阶段被过滤掉的失败生成不丢弃，而是转成修复监督：失败 harness 带上诊断报告（编译错误、接口不匹配、工具调用失败、运行时异常），教师模型在最多两轮内给出局部修改补丁。

学到的是什么

「拿到执行反馈后做少量高杠杆修改」，而不是一次性重写。

工程含义

失败样本是最贵的数据。绝大多数训练流水线在这里把它们扔掉了。

III

Evo-GDPO · 演化

把测试时的演化本身变成可训练能力。从当前框架库采样一组候选，与库中前沿在同一任务、同一底座、同一预算下执行对比，只有超越前沿的候选才被保留；奖励、时延、成本三个信号分组解耦归一化后合并，避免数值尺度互相压制。

部署后的行为

模型参数冻结，只有框架库继续吸收新经验——这就是「越用越强」的机制来源。

两种推理模式

Static JIT（每次独立生成）vs Streaming JIT（持续更新档案库）。论文实测后者累计准确率收在前者之上。

第二层的结论

JIT 范式的真正突破不在「生成」，而在把 harness 变成了可累积的资产。 阶段 III 之后，模型冻结、档案库继续演化——这意味着经验沉淀不需要重训模型， 而是以配置的形式存放在一个可读、可审计、可回滚的库里。

第三层 · 规模

一个变一群，问题就换了

JIT 解决的是「一个 Agent 该怎么组织」。但当几十个 Agent 同时运行，问题不再是组织，而是调度、隔离与治理—— 瓶颈也随之迁移。

瓶颈迁移：从生成速度到人的注意力

单 Agent→下任务→看输出→补充信息→确认结果

这是同步 RPC：人等 Agent，Agent 等人，串行推进。

A · completedB · blockedC · testing D · needs approvalE · security issueF · completed→人

这是异步任务队列 + 人类消费者：人从逐步编写者变成异常处理者和决策者。

Agent 完成速率 = λ 人类评审速率 = μ 只要 λ > μ，队列必然发散

David 的四层工作台

原文把十几个工具收敛成四层，具体产品可替换，层与层之间的职责不能缺：

被误判的调度器职能

直觉上，调度器的问题是「先处理谁」。但真正的职责是准入控制——限制同时有多少任务在系统里。 Corral 只给已完成的任务排序，对并发数量没有任何约束，所以它是一个纯排序器，不是准入控制器。 这使「限制在制品」从优化项变成了缺口项。

这里有一个双向印证

David 的 harness 选择规则（路径明确 → 轻量的 Pi；需要多模型交叉与预发送 → Cursor CLI； 探索性强、做法不清楚 → 会沉淀 Skill 的 Hermes / Prime）就是人工低分辨率版的 JIT 路由。 两者输入都是任务特征，输出都是 harness 选择，区别只在粒度与是否自动演化：

这不是说 David 落后——恰恰相反，它证明了论文的问题设定是真实存在的工程痛点，而非作者构造出来的。 同时也指出了落地路径：先用人工规则把任务分族跑通，再把规则蒸馏成自动路由。

第四层 · 量化

把直觉换成可计算的量

第三层的所有结论都是方向性的：「别盲目扩容」「限制 WIP」「路径清楚才预发送」。 这些判断要能执行，必须变成参数。下面是四个可计算的模型。

模型一：该开几个 Agent（USL）

C(N) = N / ( 1 + σ(N−1) + κ·N(N−1) ) σ = 竞争成本（串行化等待） κ = 一致性成本（跨 Agent 协调）
这条曲线最重要的一句话

30 个 Agent 的有效产出（3.91×）低于 14 个（4.75×）。 盲目扩容是负收益——而这在扩容之前无法凭感觉察觉，因为单个 Agent 看起来都「在正常干活」。

σ 与 κ 不是玄学参数，可以反解：记录不同并发度下「一周内的合并通过率」与「返工率」， 用最小二乘拟合这条曲线即可。配套工具 fleetlab.py fit 做的就是这件事。

模型二：先处理谁（WSJF）

优先级 = 延迟成本 / 任务时长 （延迟成本 = 业务价值 + 时间紧迫性 + 风险降低或机会启用）

直觉的写法是 Impact × Risk × Blocking × Urgency × Dependency，但这个乘法公式不可用： 任意因子为 0 就归零，且各因子量纲未校准、无上界，无法比较。 WSJF 的分母是决定性的——它让「5 分钟能清掉的高影响小任务」自动排在「两天的大任务」之前， 从而压低队列长度本身，而不只是重排队列。

模型三：限多少（CONWIP）

把 λ > μ 当发散条件是对的，但有个更隐蔽的问题：μ 不是常数。 人在队列压力下要频繁切换上下文，每次切换都要重建心智模型，于是 μ 随在制品数量上升而下降：

μ = μ(WIP)，且 dμ/dWIP < 0 → 排队变多 → 上下文切换变多 → μ 下降 → 排队更多（正反馈）

系统因此比经典 M/M/1 预测得更早崩塌。推论很直接：干预「提高 μ」（训练人看得更快）天花板极低， 真正的杠杆是限制在制品——完成一个，才准入一个（CONWIP）。

一个现成的抓手

你可能已经有一个 WIP 上限了：订阅套餐的并发限制。大多数人从没核对过它， 也没意识到它在替自己做准入控制。做法是查清当前套餐的并发数，把它当作 WIP 上限的初始值， 再用拟合出的 N* 反向调整（建议取 0.7·N*）。

模型五：该不该预发送（实物期权）

预发送常被类比为 CPU 流水线或推测执行。类比方向对，但决策框架选错了——CPU 分支预测错误的冲刷代价固定且极小， 而 Agent 的错误假设会向下游传染。正确的框架是实物期权：

投机执行，当且仅当 p · (T_save · C_agent) > (1 − p) · C_waste · N_msg p = 假设正确的概率 N_msg = 预排消息条数（放大倍数）

David 的经验是「架构未定时预排六条消息，会把一个早期误判自动放大六次」—— 这句话为公式里最难估的放大倍数提供了锚点：E[放大倍数] ≈ 预排消息条数。 代入默认值后会出现一个反直觉结果：

场景预排条数临界正确率 p*p = 0.75 时的判定
误判会向下游传染6 条0.923不该投机
误判不传染（单条）1 条0.667可以投机
真正决定预发送价值的，不是等待时长

而是误判会不会向下游传染。同样是 p=0.75、等待 0.5 小时，仅仅把 N_msg 从 6 改成 1， 临界正确率就从 0.923 掉到 0.667，结论完全翻转。N_msg 比 T_save 的影响大一个量级。

第五层 · 断层

拼接处暴露的未解问题

前四层都是「成立的部分」。这一层是两份材料拼起来之后，双方都没有覆盖的地带—— 也是决定这套体系能否从个人实验走向生产的关键。

断层一：演化信号在哪里算（最重要）

JIT 的演化能力是被可自动计算的奖励喂养的：Evo-GDPO 的三个信号（reward / latency / cost）全部可自动测量； Streaming JIT 的进步靠累计准确率曲线证明——这要求每题结束就有真值标签。

而论文的 9 个基准（DeepSearchQA、xBench-DeepSearch、AgentIF-Oneday、PinchBench、DeepPlanning、 OfficeBench、OdysseyBench、BrowseComp-Plus）全部是短程、单次、可自动判分的任务， 没有一个是「跨 2000 小时的仓库演化」。Fleet 场景恰恰是后者。

三条可能的应对路径

① 可验证性工程（最现实）——把尽可能多的验收标准从「人看代码」转成可执行的判据：属性测试、契约测试、回归基线、不变式检查。这是投入产出比最高的一条。

② 评审信号结构化（中等）——让人类评审不只产出 approve / reject，而是结构化标签（假设错误 / 实现偏差 / 遗漏边界 / 风格问题），把稀疏反馈变成可训练的稠密信号。

③ 代理奖励模型（风险最高）——训练评审模型替代人类打分。风险是 reward hacking，且在 Fleet 规模下偏差会被放大 N 倍且极难察觉。

断层二：Worktree 是快照隔离，不是串行化

常见的说法是 Agent ≈ 进程，Worktree ≈ 进程隔离。这个类比会误导工程决策—— 进程隔离解决的是地址空间隔离，而 Agent 并发的真正风险是语义层面的相互破坏：

Agent A → 把 token 校验从同步改为异步（改 auth.py） Agent B → 假设 token 校验是同步的（改 session.py） → 文本零冲突，git 合并成功，系统崩溃

用数据库的隔离级别来看会清楚得多：

数据库概念Agent 侧对应是否已有
Snapshot IsolationGit worktree / branch已有
Serializabilitymerge queue + 合并后全量验证需显式构建
Write Skew 检测跨文件语义冲突检测基本缺失
死锁检测Agent 互相等待（A 等 B 的 patch，B 等 A 的 schema）缺失

所以「One Agent · One Worktree · One Branch」是必要但不充分的。 配套地，串行化的真正位置也不在部署，而在合并——merge 才是把改动写入共享真值的唯一入口， deploy 只是其后的产物搬运。

断层三：指标会被劫持

原文提供了一段罕见的第一手 reward hacking 观察：David 反对递归审查， 因为要求模型「再找五个问题」，模型往往会努力凑满五个，即使剩下的只是想象出来的 Bug。 机制是清晰的：优化目标设为「问题数量」，模型就最大化数量而非价值，最终污染度量本身。

推论是通用的：任何可被 Agent 观测到的量化验收指标，都会在某个规模上被劫持。 因此验收指标必须满足两个条件——可被外部真值校验（而非自报数量），以及有明确停止条件（而非「越多越好」）。

同样的逻辑适用于效率度量。原文自己指出：Agent 会话数、用户提示数、Git 提交数都是代理指标：

代理指标（易采集，不可用于决策）真实指标（难采集，但才是目标）
Agent 会话数返工次数
用户提示数合并后故障率
Git 提交数交付周期
Token 消耗量真实用户结果
生成的 Skill 数量Skill 命中率与失效率
评审问题条数问题信噪比（条数可被劫持）
原文自曝的一次安全事故

在「十分钟搭完 VPS」的成功演示里，原文同时记录了：Agent 从本机找到了 OpenRouter 密钥，并在远端取得完整 root 权限。这是两个独立失效——凭据以明文存在于 Agent 可读路径，以及 Agent 拿到了远超任务需要的权限。

值得警惕的是叙事 framing：这段被当作成功案例讲述。速度和控制权是同一套自动化的一体两面。个人实验环境可以接受这种交换；连接生产仓库和真实密钥后，运维能力本身就成了产品的一部分。最小必要控制项包括：只读生产数据权限、按实例隔离且可即时吊销的短时效凭据、Agent 不可篡改的审计日志、网络出口白名单、一键 kill switch。

第六层 · 结论

分层确认，分级行动

把前五层放在一起，最重要的不是记住多少结论，而是清楚哪些结论有证据、哪些只是推测。 把它们当成同等强度来行动，是当前最大的风险。

证据强度 · 强

Intra-Agent

harness 可被 JIT 生成并演化。18/18 配对提升、24/24 跨模型迁移为正、成本平均降 36%。已被论文证实，可直接采信。

证据强度 · 中

Inter-Agent

Fleet 需要调度、隔离与治理。来源是单人 2000 小时经验，无对照组。方向可信，但参数（σ、κ、N*）必须自己测。

证据强度 · 弱

Human-Agent Organization

人与 Agent 如何组成组织。纯推测，两份材料都没有可验证的答案。不应作为行动依据。

扩容的门槛条件，而不是线性步骤

阶段配置进入下一阶段的门槛
S0 单 Agent1 Agent + 1 Worktree连续 2 周合并通过率 > 80%
S1 一主一辅+ 独立 Worktree + 异模型交叉评审同上，且 σ、κ 已能测量
S2 小规模+ merge queue + 合并后验证 + 结构化评审标签在制品不增长（λ ≤ μ 持续成立）
S3 中等规模+ CONWIP 准入控制 + 任务分族 + 按频次投建 Skill已算出自身 N*，且当前 N < 0.7·N*
S4 接近 N*+ 可验证性工程 + 成本归因边际增益转正为负 → 停止扩容

关键纪律：S3→S4 的判据不是「能不能跑更多 Agent」，而是「加一个 Agent 的有效产出增量是否仍为正」。 在本文参数下，这个增量在 N ≈ 14 处归零。

最终该带走的三样东西

工具名、订阅价、模型排名、以及「云端 PR 近 60%」这类数字，会过期，占了两份材料八成篇幅。剩下能带走的只有三样：

1

一个可测量的规模模型

C(N) = N / (1 + σ(N−1) + κ·N(N−1))。它把「该开几个 Agent」从感觉变成参数， 并预言了盲目扩容是负收益。要得到自己的 σ 和 κ，只需记录不同并发度下的合并通过率与返工率。

注意：σ 与 κ 单独辨识度不高，二者可互相补偿；但组合量 (1−σ)/κ 也就是 N* 稳定得多。决策请依据 N*。

2

一个准入控制纪律

调度器的主职能是限制在制品，不是给队列排序。David 的系统恰好没有这个组件 （Corral 只排已完成的任务），所以它不是优化项，是缺口项。而你的订阅并发上限已经是一个现成的 WIP 上限。

3

一条演化闭环的前提

JIT 的「越用越强」建立在奖励可自动计算之上。在奖励不可自动判分的场景里， 先做的不是上 Agent，而是把验收标准转成可执行判据。这一条不成立， 其余各层都会退化为「更快地产生未经验证的产出」。

收尾

两份材料合起来，竞争焦点从「谁有最强模型」迁移到了「谁有最强的 Agent Runtime + Harness Generator + Scheduler + Evolution Loop」。 但正确的姿态不是直接奔向终局，而是用第一层已被证实的方法——可测量化与可验证性工程——去逐步驯服第二层。
