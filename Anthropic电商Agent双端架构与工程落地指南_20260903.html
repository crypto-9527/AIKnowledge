Anthropic 开源了一套可运行的 AI 电商 Agents 参考实现，覆盖顾客购物和商家运营两端。项目包含 Shopping Agent、Merchant Agent、十个领域 Skills、四个行业示例、三种运行方式和一个 Claude Code 插件。

这套代码实现了模型循环、领域流程、业务工具、结构化界面、长期记忆、安全审批和 Evals。模型理解目标、选择工具并组织结果；企业系统提供目录、库存、价格、订单、权限和支付；Harness 管理模型循环、状态、工具执行、流式输出和安全限制。采用方需要接入自己的业务系统，并补充生产认证、业务授权、欺诈控制、支付和合规。

Anthropic 称，使用 Claude 购物 Agent 的零售商，购物车金额最高增加 35%，消费者完成购买的可能性提高 60%。Anthropic 未公布客户样本、基线、实验方法或时间窗口，因此这两个数字不能视为平均收益或部署承诺。

核验提示 · 这两个数字的准确出处

「+35% / +60%」不在工程深析博文中，而出现在 2026-09-02 的发布博文：“Retailers running shopping agents on Claude have seen carts up to 35% larger and shoppers 60% more likely to complete a purchase.”

二手媒体报道将其归于 Anthropic 平台产品负责人 Angela Jiang 的口述，口径为「某一家未具名伙伴」的 30–35%，而非跨客户平均。详见 一手事实核验。

这套参考实现包含什么

Commerce Agents 仓库 包含以下内容：

  • 两个 Agent：Shopping Agent 与 Merchant Agent。
  • 十个 Skills：两类 Agent 各五个，覆盖搜索、购买研究、规划、客服、个性化、经营分析、商品、库存、定价促销和营销活动。
  • 四个可运行行业示例：零售、旅行、电信和娱乐票务。每个示例都有消费者前台和商家后台。
  • 三种运行方式：Messages API、Claude Agent SDK 和 Claude Managed Agents。
  • 七个本地 Python 包、八个 Web 应用、共享后端接口、前端组件、测试和部署脚本。
  • 一个 Claude Code 插件，提供搭建 Agent、增加业务流程、编写 Evals 和审查现有 Agent 的命令。

仓库要求 Python 3.11+ 和 Node 22。配置凭据后，一条命令即可启动零售示例；参数可以切换到商家后台或同时启动两端：

python scripts/run_demo.py retail
python scripts/run_demo.py retail --merchant
python scripts/run_demo.py retail --all

Claude Code 插件提供 /scaffold-commerce-agent、/add-commerce-flow、/author-commerce-evals 和 /review-commerce-agent。这些命令会根据采用方的技术栈、业务系统和现有 Agent 生成或审查实现。

一次任务怎样从请求走到业务结果

用户请求、当前页面和账户信息先进入主 Agent。高频规则由 system prompt 提供，低频但复杂的流程按需从 Skills 加载。主 Agent 再调用带类型的业务工具，后端返回目录、库存、价格、订单或经营数据，Harness 执行工具、保存状态并强制安全限制，客户端最终渲染商品卡、行程、比较表或变更预览。

模型、prompt、skill、tool、业务后端、UI 与 Harness 各自负责什么？

Commerce Agent 责任栈：模型负责判断，skills 提供流程，tools 暴露接口，后端拥有事实与规则，Harness 控制状态和权限，客户端呈现。

图 3 · 六层责任栈与一次请求的流向

这条链路对应六类代码：

  1. 1Core：定义角色、状态、工具合同、安全 gates、grounding 和长期记忆。
  2. 2Skills：保存按需加载的领域流程。
  3. 3Runtime：处理模型循环、工具执行、流式事件、会话状态和错误。
  4. 4Backend interface：连接目录、库存、价格、订单、经营数据和企业权限系统。
  5. 5Presentation tools：生成带类型的商品卡、行程、套餐比较、图表和变更预览。
  6. 6Examples 与 tests：展示行业扩展方式，并测试正常、拒绝和边界行为。

工具应调用企业已有的搜索、排序、库存、履约、促销和分析系统。search_products 应接收已经排序的结果，模型只负责根据用户目标选择和解释。固定业务规则应留在上游系统或后端接口中，不应在 Agent 工具里重复实现。

工具返回值会直接进入模型上下文，因此只应保留模型决策所需字段。大量图片 URL、内部元数据和无关字段会增加 token 成本并降低模型定位关键信息的能力。错误结果也应给出下一步要求，例如“查询库存时必须提供 product ID”，而不是只返回 403。

不同模型、Skills、运行时和前端可以在这些接口上独立替换。业务事实、账户权限、交易限制和支付继续由现有系统管理。

Presentation Tool 把 UI 定义成带类型的工具调用。模型调用 present_products、present_itinerary 或 present_plan_comparison；服务端校验并补全参数；客户端按固定组件渲染。工具参数要与屏幕布局一致，历史消息才能保留“左边第三个”对应的对象。

为什么只用一个主 Agent

参考架构使用一个主 Agent 持有会话状态，没有前置 intent router，也没有为每个业务域配置一个独立 subagent。购物车、用户偏好、历史消息和待批准变更都留在同一个会话中。频繁交接会复制或压缩状态，增加 token、延迟和约束丢失风险。

Anthropic 表示，在若干企业部署的比较中，“一个 Agent 加 Skills”的质量持续高于单一大 prompt 和多 subagent 方案，成本和延迟通常也更低。Anthropic 未公开这组比较数据，采用方仍需用自己的流量和 Evals 验证。

原文逐字核验（工程深析博文）

“In our comparisons across several enterprise deployments, a single agent with skills consistently has outperformed both the one-prompt-for-everything design and the subagent design on quality, and often at a lower cost and latency per task.”

关于交接代价：“Each handoff can cost several times the tokens and adds seconds of latency.” —— 原文未提供具体倍率与秒数，故本文不对该数字做二次量化。

Subagent 适合两类任务：一类是深度研究等边界明确、会产生大量中间材料的任务，主 Agent 只接收压缩结果；另一类是已有独立合规责任的专业 Agent，例如药房或金融服务 Agent，由 handoff 将整段对话交给它处理。

增强 · 原文补充（原文未含）

delegation 与 hand-off 的分界

工程深析博文对两者给出了明确区分，这是原消化稿未展开的一层：区别在于会话的所有权。

hand-off（交接）

领域 Agent 成为用户的直接对话方，用自己的循环把任务做完。适用于已有独立合规面的专业 Agent（药房、金融服务）。

delegation（委托）

编排者保留会话所有权，领域 Agent 在单轮内被调进调出，每次交换都会退化。适用于窄而自包含的任务（如 deep-research subagent）。

高频规则放在 system prompt，长尾流程放在 Skills。Anthropic 给出的起点是：约三分之一以上流量会使用的规则可以放进 prompt。安全和法律规则、品牌限制、过敏信息等关键事实应始终放进 prompt。若当前页面等信号已经能确定所需 Skill，Harness 可以在第一次模型调用前直接注入，省去一次加载 Skill 的模型轮次。

原文逐字核验 · 三分之一阈值

“A good starting point is that anything relevant to a third or more of your traffic, whether anticipated before launch or observed in production, goes in the system prompt, and the rest goes in skills.”

同时原文明确：Skills 应作为 tool result 加载，不应追加到 system prompt——“skills should be loaded as tool results rather than appended to the system prompt. The skill body then lands in the conversation prefix and is cached along with it.”

怎样缩短响应时间并降低成本

任务总耗时等于多轮模型生成、工具执行和往返时间之和。模型单轮输出更快，不代表完整任务更快；规划能力较弱的模型可能需要更多轮次。

参考实现使用以下方法降低完整任务耗时：

  • 预载当前页面、账户和高概率相关信息，减少额外查询。
  • 在同一轮并行调用彼此独立的商品搜索、政策查询或指标读取。
  • 工具参数完整后立即执行，不等待模型结束整轮输出。Anthropic 表示这曾将数秒间隔缩短到几百毫秒。
  • 提示模型优先输出最慢工具的调用参数。
  • 逐步渲染组件和简短进度信息。
  • 同时衡量任务完成率、grounded accuracy、p50/p99 延迟和单个完成任务成本。

Anthropic 估计典型 commerce 界面响应包含约 500–700 个输出 token；不流式显示时，用户可能等待五秒以上才能看到内容。这是经验值，部署方需要测量自己的链路。

增强 · 原文补充（原文未含）

图 6 · 缓存三段结构与最常见的失效原因

工程深析博文将一次请求按变更频率划分为三段，与原文的排序结论一致，但给出了更精确的机制表述。

Skills 应作为 tool result 加入消息历史，不应追加到 system prompt。缓存断点也要随会话向前移动：每轮把最新断点放到最新用户消息之后，使累计历史和长工具结果可以继续命中缓存。时间戳或当前页面如果放在 system prompt 顶部，会使后续前缀每轮失效。

按当时的 Claude 定价，缓存读取约为新输入的十分之一，缓存写入约为 1.25 倍，第二次复用即可覆盖写入溢价。Anthropic 称，其较好的 commerce 部署缓存命中率为 90%–99%，约 100K token 时缓存读取快 1.5–2 倍。实际结果取决于请求结构和缓存前缀是否稳定。

增强 · 原文补充（原文未含）

工程深析博文另给出一个原消化稿未提及的关键参数：面向消费者的大流量场景应使用默认的 5 分钟缓存过期（“the cheapest, default 5 minute cache expiration”）。同时提供了自检方法——读取 turn_complete 的 cache_read_input_tokens，第二轮若为 0，说明前缀发生了变化。

模型与 effort 应通过完整 Eval suite 比较。Anthropic 建议把 Opus 作为分析型 Merchant Agent 的 sweep 起点，把 Sonnet 作为延迟更敏感的 Shopping Agent 起点。每个候选模型都应根据失败用例调整 prompt，再比较质量下限、延迟和每个完成任务的成本。更强的模型可能因减少复杂请求的轮次而获得更低的 p90/p99 延迟。

原文逐字核验 · 模型选择

“We recommend starting at Opus for merchant agents, whose tasks are analysis-heavy, and Sonnet for consumer agents, where latency weighs more.”

成本口径：“Measure cost per completed task rather than per model call, since a cheaper model that needs more turns, or fails more often, is not cheaper.”

尾部延迟：“a more intelligent configuration sometimes wins on latency (most commonly on p90 and p99) despite slower tokens, because it plans its tool calls better and needs fewer rounds on the most complex requests.”

怎样处理记忆、写操作和上线风险

Agent 跨会话运行时，需要长期记忆、代码级安全限制和可重复评测。

会话结束后再写入长期记忆

长期记忆保存在企业数据库中。每条记录包含短 key、短 value、类别、来源会话和更新时间。商家侧按具体操作人存取，并继续执行原有权限。

写入由会话结束后的异步 extractor 完成。它只读取最近一轮的用户和助手文本，不读取工具返回，避免把商品描述或恶意评论写成用户事实。Anthropic 的内部 commerce memory Eval 显示，这种方式的事实召回比主 Agent 在前台调用保存工具高 13%；Anthropic 未公开这套评测集。

用 Snapshot Evals 固定失败用例

怎样把多轮 Agent 的失败变成可重复的一轮测试？

快照评测流程：构造状态和模拟后端，运行一轮，检查最终业务状态、工具参数和用户界面。

模拟用户适合发现未知失败。已发现的失败应转成 Snapshot Eval，用固定状态重复运行。多数用例应检查最终状态和渲染结果，不应固定模型采用的具体路径。

用例需要同时覆盖正常与拒绝行为：每个“应该执行”配一个“应该拒绝”，每个“应该追问”配一个“信息已足够，应直接行动”。测试状态还应包括冗长或矛盾历史、用户提示注入、数据面提示注入、跨用户数据访问、空结果、超时、UI 组件、内部 ID 泄露和跨多个业务能力的请求。Anthropic 建议每个用户 flow 从 50–100 个用例开始。

多团队如何发布更新

沙盘 1 · 缓存经济性：命中率多少才开始省钱

SANDBOX 01Prefix Caching 盈亏平衡反解

Anthropic 只给了三个单价系数（读取 1/10、写入 1.25×、第二次复用回本）和一个目标区间（90–99%）。本沙盘用这三个系数反解出缓存真正开始省钱的最低命中率，并给出会话维度的累计成本比。所有系数均来自原文，无虚构价格。

盈亏平衡命中率 h*21.74%
本会话累计节省—
本会话省下 token 当量—
推导（系数均取自原文）：设新鲜输入单价为 1，缓存读取 0.10、缓存写入 1.25。 命中率 h 下的每轮期望系数 c(h) = 0.10h + 1.25(1−h)，稳态节省率 S(h) = 1 − c(h) = 1.15h − 0.25。 令 S(h) = 0 得

沙盘 2 · 前缀错位的代价：时间戳放错位置有多贵

SANDBOX 02Volatile 段位置失效模型

原文只说「时间戳放错位置会让整段上下文失去缓存」，没有给量级。本沙盘用可缓存三段模型把它算成 token 数：把 volatile 段从末尾挪到最前，缓存命中前缀从 G+S 塌缩为 0，代价按 0.9·(G+S) 每轮线性累积。

错误排序：可缓存前缀0
每轮额外 token 当量—

推导：请求按变更频率分为 G（跨 session 字节一致）、S（session 内稳定）、V（每轮变化）三段。
每轮额外代价 = (1 − 0.10) · (G + S) = 0.9 · (G + S)

口径声明：token 当量为相对度量（以新鲜输入单价为 1），不含输出 token 与批处理折扣；首轮写入溢价未计入，故为稳态保守估计。

沙盘 5 · 评测覆盖与复现成本：为什么失败要转成 Snapshot Eval

SANDBOX 05用例规模与缺陷复现经济学

原文给了两条硬指标（每 flow 50–100 用例、「应该执行」配「应该拒绝」）和一条方法论（已发现的失败转成 Snapshot Eval）。本沙盘把第二条量化：一个偶发缺陷，靠多轮在线复现要跑多少次才能稳定抓到，而快照评测为什么是 1 次。

Snapshot Eval（构造固定状态，n=1 即确定捕获） 多轮在线复现（概率性） 当前 n
推导：设缺陷在单次运行中出现的概率为 q，运行 n 次至少捕获一次的概率
P(n) = 1 − (1 − q)n  ·  期望运行次数 E[n] = 1q
失败发生在第 k 轮时，一次在线复现要重放 k 轮；Snapshot Eval 直接构造状态、只跑 1 轮，故成本比
复现成本比 = kq
默认参数（k=5, q=0.15）：期望运行 6.7 次、每次 5 轮，合计约 33 轮；快照 1 轮，成本比约 33×，且捕获概率从「跑 6 次约 62%」变为「确定性 100%」。

参数口径：q 与 k 为用户可调假设，代表你自己链路上的偶发缺陷特征，非 Anthropic 数据。F 与 C 的默认值取自原文建议区间（每 flow 50–100 用例）。「正负例配比」按原文「每个『应该执行』配一个『应该拒绝』」折算为 1:1。

与原文的一致性提醒：原文强调「多数用例应检查最终状态和渲染结果，不应固定模型采用的具体路径」——快照的价值在于固定输入与判定，而不是固定推理轨迹。
