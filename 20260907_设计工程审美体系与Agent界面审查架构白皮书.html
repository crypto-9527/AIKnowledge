基于 @jakubkrehel 工业级 Skills 的可计算约束、只读审查协议与三态裁决自动机形式化推演

Section 01

一、执行摘要与核心论点：从 Vibe Coding 到设计工程可计算度量

在以大语言模型驱动前端生成与自主 Agent 协作（Agentic Engineering）的新时代，软件界面研发正经历一场深层次的范式断裂。以往的 AI 辅助界面开发过度依赖所谓的“感觉驱动（Vibe Coding）”与主观审美隐喻，导致模型在生成与修改代码时陷入三大顽疾：其一，随意编造或更改调色板与圆角，破坏设计系统的内在数学规律；其二，在代码变更评审中越权重写、大包大揽，引入未感知的无障碍（Accessibility）断层；其三，凭主观好恶提出缺乏实证依据的泛泛意见，模糊了缺陷与项目设计特性的边界。

由波兰资深设计工程师 Jakub Krehel（@jakubkrehel，设计工程杂志 Interfaces 主理人）开源的 Interface Skills 体系（github.com/jakubkrehel/skills），在工业界首次为 AI Agent 确立了“领域知识与只读审查双层解耦”的高严谨性工程范式。该体系收录了 6 个领域知识 Skill（以 better-* 为前缀）与 5 个流程审查 Skill，构建了一套“证据优先（Evidence, Not Taste）、只读不越权（Read-only by Default）、分工严密隔离（Strict Ownership Boundaries）”的闭环准则。

✦ 核心架构公理：设计工程不是艺术品味，而是可计算约束

“审美经验”在传统软件工程中常被误解为主观感性，但优秀的数字化界面在物理底层全部由精确的离散数学、光学几何与认知心理学定律所主导：同心圆角由共形方程决定、排版字阶由几何级数模比决定、色彩可读性由感知亮度与相对对比度决定、无障碍操作由状态机焦点环决定。代码审查的核心是验证可计算约束是否闭合，而非向开发者推销模型的个人品味。

1.1 系统架构全景图：知识层与流程层的清晰解耦

在 jakubkrehel/skills 中，最关键的设计哲学是“知识归知识，流程归流程”。领域 Skill（Domain Skills）提供纯粹的度量常数、最佳实践与缺陷判定准则；流程 Skill（Process Skills）则负责定义审查作用域、提取证据、调度领域专家、合并报告并作出裁决，严禁流程工具自行发明或修改设计准则。

1.2 体系三大运行铁律

① 证据优先 (Evidence, Not Taste)

审查者的职责是识别客观缺陷，而非推行个人审美偏好。项目文档明示的代码规范不能作为违背物理原则的豁免证，但模型也绝不能将与自身偏好不同的圆角、间距或品牌语气标记为缺陷。每条缺陷必须给出具体代码行号 file:line 与实际运行环境证据。

② 只读不越权 (Read-only by Default)

审查过程严格只读，禁止模型在审查阶段未经授权直接篡改源码。Git 检视必须使用只读 git fetch 与临时隔离 git worktree，严禁执行 git checkout 或 git stash 扰乱开发者的本地未提交改动。

③ 严格边界 (Zero Overlap)

每个领域 Skill 都有极其清晰的职责终点：better-accessibility 管键盘焦点与语义，better-typography 管字阶与截断，better-colors 管感知对比度。遇交叉问题归口于底层根因，单点单报，绝不交叉重复。

Section 02

二、6 大领域知识 Skill 体系化深度剖析（The 6 Domain Knowledge Skills）

6 个 better-* Skill 构成了工程化界面的底层知识基座。它们对现代前端的每项物理细节都给出了精确的数值常量、几何方程与失效边界。

2.1 better-ui：表面深度、同心圆角与微交互工程学

界面的“质感（Polish）”并非来自华丽的特效堆砌，而是源自对数十个微小几何与感知规律的严格遵循。better-ui 锁定了以下核心工程准则：

  • 同心圆角法则（Concentric Border Radius）： 当一个带有圆角的卡片内嵌套另一个带有圆角的元素时，若两者圆角半径相同，在对角线方向就会产生明显的视觉厚度不均匀与边缘挤压感。其严格的几何共形方程为：
    Router = Rinner + Padding
    若内层圆角 Rinner = 4px，内边距 Padding = 8px，则外层圆角必须严格设置为 12px。
  • 光学对齐优于几何居中（Optical Alignment over Geometric Centering）： 纯数学的几何居中在面对不对称图形（如播放器三角形图标、带箭头的按钮、带图标的输入框）时会呈现肉眼可辨的“下坠”或“偏左”。必须在几何中心基础上，沿视觉质心反方向进行光学微调（通常为 1~2px 的 Padding 补偿）。
  • 阴影表达高程，边框表达结构（Shadows for Elevation, Borders for Structure）： 为了表达卡片的浮起深度，应使用多层透明度递进的 box-shadow，避免使用单层粗重黑影；边框（Border）仅用于传达结构隔离、分割线以及被选中的焦点状态。
  • 可中断动画与交错入场（Interruptible Motion & Stagger）： 高频交互状态切换必须使用 CSS Transition（可随时被下一次鼠标动作中断），而非关键帧动画（Keyframes）；非频繁的整页入场展示，将语义块切分为独立单元并施加约 100ms 的交错延迟（Stagger），提升视觉阅读引导。
  • 微交互触觉反馈（Scale on Press）： 可点击按钮在按压激活态（:active）应使用精确的 transform: scale(0.96) 赋予瞬时触觉按压感（低于 0.95 会显拖沓夸张，高于 0.98 则感知微弱）。
  • 主题切换闪烁瞬时抑制（Suppress Transitions on Theme Switch）： 当用户在深色模式与浅色模式之间切换时，全页面数十种属性若同时触发 transition，会导致视觉模糊与颜色拖影。正统实践为：注入 *, *::before, *::after { transition: none !important; }，强制执行一次 DOM 回流（Reflow），并在下一动画帧（requestAnimationFrame）移除该样式。
  • 单 SVG 资源状态着色： 图标必须采用 fill: currentColor 或 stroke: currentColor，通过父级 CSS 变量与文本颜色控制悬停与禁用状态，严禁为 Hover 状态引入第二套 SVG 资源。

2.2 better-typography：排版尺度、角色化行高与文本截断度量

文本是产品界面的核心信息载体。排版设计是克制的艺术：合理的字阶比例、舒适的阅读行高以及自适应的边界控制。

  • 调和字阶体系（Modular Type Scale）： 拒绝随意手写无序的像素字号。严格采用几何倍率字阶（如 Major Third 1.250、Minor Third 1.200），定义清晰的语义级字号：text-sm (12.8px)、text-base (16px)、text-md (20px)、text-lg (25px)、text-xl (31.25px)。标题字号必须随语义级别严格单调递减。
  • 角色化行高衰减模型（Line-Height by Role）： 大标题由于字号较大，笔画内部留白充足，行高必须收紧至 1.1 ~ 1.2，防止折行后标题松散分离；正文长段落由于阅读停留时间长，行高必须保持在 1.5 ~ 1.6。铁律：任何折行达到 3 行以上的卡片描述文本，行高绝对不能低于 1.4。
  • 现代文本换行控制四重奏：
    CSS 属性声明适用场景与核心职责禁止滥用边界
    text-wrap: balance 短标题平衡排版，自动均衡多行文本宽度，避免末行出现孤零零单个短词。 严禁用于超过 6 行的长文本，会引发昂贵的布局计算回流。
    text-wrap: pretty 段落描述文案，阻止段落最后一行遗留单一独立单词（Widow）。 严禁用于极窄固定宽度容器。
    overflow-wrap: break-word 防御长 URL、超长 Token 或未加连字符的外文词汇撑破容器边界。 与 hyphens: auto 配合使用效果更佳。
    white-space: nowrap 徽标（Badge）、状态标签、单行动作按钮，绝不允许折行撕裂。 必须保证容器具备足够的弹性或横向保护空间。
  • 动态数据表格等宽数字（Tabular Numbers）： 普通西文字体的数字大多为比例字体（Proportional Figures，如数字 1 比数字 8 窄得多）。在计时器、行情看板、股票价格与统计报表等动态变动场景下，会导致容器宽度疯狂横向抖动。必须强制声明 font-variant-numeric: tabular-nums。
  • 行宽舒适度限制（Measure: 60~75 CPL）： 人眼在水平扫视过长的文本行后，换行时难以精准定位下一行的开头。长篇正文行宽必须硬性限制在 60~75 个字符（约 500~680px）。
  • 移动端 Safari 16px 缩放防御： iOS Safari 规定，当用户聚焦的 <input> 字体小于 16px 时，浏览器会自动强行放大整个视口，造成界面破碎。针对移动端输入框，基础字号必须锚定在 16px（桌面端降级为 14px）。

2.3 better-colors：OKLCH 感知均匀色彩空间与 Token 拓扑

色彩系统是数字产品中最容易产生技术债务的领域。better-colors 确立了“色彩是色阶（Ramps），而非散乱色值”的核心理念。

  • OKLCH 色彩空间的代际优势： 传统 sRGB 与 HSL 存在致命缺陷——色相与感知亮度严重耦合（例如 HSL 下同样的 Lightness 50%，黄色显得极其刺眼，蓝色却极暗）。OKLCH 实现了真正的感知均匀性（Perceptual Uniformity）：色相（H）变化时，感知亮度（L）完全水平独立，色阶计算更加均匀可信。
  • 双层 Token 命名隔离架构：
    Primitive Token (--blue-500) → Semantic Role Token (--color-accent-solid) → Component Usage
    组件代码中严禁直接使用 Primitive 色值。组件只能绑定具备明确业务职责的 Semantic Token。这是保障暗色模式一键切换的唯一正确工程路径。
  • 单视口单一主色律（One Primary Action per View）： 当纯色填充被用来表达最高优先级操作时，一个视口内只能有一个主要动作按钮（Primary Action）使用该强调色，同级按钮必须保持中性灰。按钮背景填充强调色在全房间内都一眼可辨；若仅在文本上使用强调色，会让人误以为是超链接。
  • 真实渲染层对对比度实测（Rendered Pair Contrast）： 严禁孤立测量文本的前景色与页面底色，必须测量文本与紧邻其正后方的真实背景层（含透明度混合与卡片底色）。必须达到 WCAG 2.1 AA 级（普通文本 4.5:1，大字/UI 组件 3.0:1）或 AAA 级（7.0:1）。
  • 渐变插值空间精准选取： 默认的 sRGB 渐变在两色过渡处往往会衰减发灰；in oklab 能提供极其平滑自然的明度过渡；in oklch 会沿着色相环外圈扫描过度，适合创造鲜艳的高饱和度视觉焦点。

2.4 better-accessibility：平台原生优先与全键盘闭环

无障碍工程（A11y）不是事后打补丁，而是界面的骨骼。better-accessibility 明确指出：使用 Web 平台原生能力，90% 的无障碍问题无需额外代码即可解决。

  • 原生元素绝对优先（The First Rule of ARIA）： 使用 <button> 承载动作，使用 <a href> 承载页面导航与链接跳转，严禁出现 <div onClick>。真正的 <a> 必须支持 Cmd/Ctrl+Click 在新标签页打开以及鼠标中键点击。没有 ARIA 远好过错误的 ARIA。
  • 可见焦点环独立通道（Visible Focus Rings via :focus-visible）： 样式必须定义在 :focus-visible 上而非粗暴的 :focus，确保键盘操作者能看见清晰的焦点指示，而鼠标点击者不被多余边框打扰。严禁使用 outline: none，除非提供了至少 2px 且与周围背景形成高对比的明确替换焦点环。
  • 全键盘操作流与 Roving Tabindex： 任何鼠标可触发的路径，键盘必须 100% 可达。遵循 W3C ARIA APG 规范：Escape 关闭浮层；复合组件（如菜单栏、Tab 栏）内部通过方向键（Arrow Keys）移动焦标，仅当前激活项具备 tabindex="0"，其余全部置为 tabindex="-1"。
  • 弹窗焦点捕获与还原（Trap & Restore Focus）： 模态弹窗打开时，底色背景必须添加 inert 属性隔绝焦点，首选控制项自动获取焦点；模态弹窗关闭时，焦点必须精确恢复到先前的触发源按钮。
  • 触控热区极值标准（Touch Target Size）： WCAG 2.5.8 AA 基线要求最小点击热区为 24×24px；移动触控推荐 44×44px，桌面端推荐 40×40px。当视觉图标较小时，必须使用 ::after 伪元素向外扩张透明点击热区，并设置 pointer-events: none 阻断装饰层阻挡点击。
  • 严禁单维度色彩传达状态： 成功、警告、失败等状态信息，绝不能只通过红绿颜色表达，必须冗余配备文字标签、图标或下划线，以照顾色觉障碍用户。

2.5 better-layout：空间成组律与自适应弹性系统

布局是在用户阅读任何字词之前，向大脑传递层次结构的第一语言。

  • 空间成组律（Group with Space, Not Lines）： 格式塔心理学表明，留白比线条更能优雅地区分内容。组间距（Inter-group Gap）必须至少是组内距（Intra-group Gap）的 2 倍以上（例如组内元素间距 8px，组与组之间至少 16px~24px），否则视觉分组将退化为噪声。
  • 全量采用逻辑属性（Logical Properties）： 淘汰物理方向命名（margin-left、padding-right），全面改用 CSS 逻辑属性（margin-inline-start、padding-inline-end）。在面对 RTL（如阿拉伯语、希伯来语）国际化排版时，界面能够无缝镜像翻转而无需重复维护样式。
  • 渐进式隐藏与边缘线索（Hint at Hidden Content）： 横向滚动容器在视口边缘绝不能正好卡死在单个卡片的边界处，必须让下一个卡片在右侧边缘露出 16~32px 的“窥视线索（Peeking Cue）”，明确暗示用户此处可继续滚动。
  • 内容驱动断点与容器查询（Container Queries）： 摒弃机械硬编码的 768px/1024px 设备断点，断点应当由内容组件何时产生视觉拥挤来决定。优先使用 @container 让组件基于自身容器宽度进行自适应折叠。

2.6 better-writing：工程化产品微文案规范

清晰而简短胜过聪明，一致胜过丰富。最好的错误信息是优化交互设计，让错误根本无法发生。

  • 直呼受众与消除推诿： 指导文案中使用“你（You）”，而非第三人称“用户（The user）”。在系统错误中，严禁出现推卸责任或故作幽默的“哎呀！出错了（Oops! Something went wrong）”，应冷静给出明确事实与排查指引（如“无法保存。请检查网络连接后重试”）。
  • 动词先行按钮（Verb-first Buttons）： 按钮标签必须以动词开头表明操作后果：“发送（Send）”、“保存草稿（Save draft）”、“删除项目（Delete project）”。绝不使用轻浮的“OK!”或毫无上下文的单纯“是/否”。
  • 全流程单一词汇表（Consistent Vocabulary）： 多步流程严禁混用同义词。如果入口叫“开始使用（Get started）”，后续推进必须统一使用“继续（Continue）”或“下一步（Next）”，完成统一使用“完成（Done）”，禁止在不同步骤间随机切换。
  • 前进型空状态（Empty States Pointing Forward）： 空状态绝不是冷冰冰的一句“暂无数据”。一个合格的前进型空态必须包含三个要素：说明此处是什么 + 解释有什么价值 + 提供唯一的下一步行动按钮（如“暂无项目。项目用于统一归档任务与文档。[创建新项目]”）。
Section 03

三、5 大审查流程 Skill 运行机制与编排协议（The 5 Process & Workflow Skills）

如果说 6 大领域 Skill 是界面物理世界的度量宪法，那么 5 大流程 Skill 则是保证这套宪法在真实开发与代码审查中不走样、不失控的审判与验证管线。它们各自声明职责的明确终点，通过协议级配合消除了大模型在代码审查中常见的越权与噪音。

3.1 better-interface：跨学科审查总编排器

better-interface 是所有跨学科全屏审查的总入口。它本身不拥有任何具体的领域准则，其唯一拥有的就是编排权、严重度统一度量衡与终审裁决权。

  • 严格审查时序管道： 审查必须按照从骨骼到肌理的严密顺序逐次执行：
    1. accessibility → 2. layout → 3. writing → 4. typography → 5. colors → 6. ui
    这种顺序确保了基础的可访问性断层与布局塌陷优先暴露，不会被后续精致的视觉圆角或微交互动效所掩盖。若某个拥有者 Skill 在本地未安装，该领域直接标记为 Not reviewed 并指明缺失工具，严禁模型凭记忆脑补规则。
  • 统一严重度标尺（Unified Severity Scale）：
    • HIGH：阻断关键任务流、误导用户认知、遮挡内容或控制项、引发数据丢失风险，或触发系统性重复崩溃。
    • MEDIUM：显著损害界面理解效率、自适应性、视觉层级或一致性。
    • LOW：孤立的视觉打磨点，对核心任务流无实质影响。
  • 13 类升级触发器（Escalation Triggers 铁律）： 一旦 owning skill 确认命中以下 13 种红线场景之一，严重度无条件直接判定为 HIGH，绝不允许因为发生该问题的组件较小而被降级折中：
    编号Escalation Trigger 触发场景违规机理与潜在危害
    T1可交互控制项缺乏可访问名称（No Accessible Name）读屏软件无法朗读，视障用户完全无法操作。
    T2键盘可聚焦控件无可见焦点指示器（No Visible Focus Ring）键盘用户失去当前屏幕焦点位置感知。
    T3指针可达但键盘完全不可达的操作路径彻底破坏 Web 平台全键盘操作基线。
    T4动效或自动播放内容忽略 prefers-reduced-motion引发前庭觉障碍用户的晕眩与生理不适。
    T5在 320px 宽度或 200% 缩放下内容发生重叠截断或不可达违反 WCAG 响应式重排（Reflow）底线。
    T6正文或控制项文本实际渲染层对对比度未达标在非理想光照或低对比屏幕下完全不可读。
    T7单独依赖颜色承载系统状态或操作含义色盲与色弱用户无法辨识成功与危险。
    T8破坏性危险操作无确认弹窗、无撤销手段或无醒目标识造成不可逆的用户核心数据丢失灾难。
    T9文本截断后用户没有任何途径查看完整文本信息永久丢失（缺失 Tooltip 或展开项）。
    T10内容或控制项隐藏在滚动边缘外且无任何视觉窥视线索用户完全不知道右侧或底部存在隐蔽内容。
    T11错误提示信息未告知用户具体的恢复路径用户陷入卡死状态，不知道如何修正输入。
    T12语义颜色违背其既定含义（如在非危险动作使用危险红）造成严重的心理恐慌与预期不一致。
    T13状态变更仅由动画表达，动画结束后无任何静态线索残留动效未播放或错过动画时用户无法确认状态。
  • 单一根因合并与 15 条硬上限（Cap of 15 Findings）： 相同根因引起的全局问题必须合并为单条缺陷报告，并在 Location 栏列出所有受影响的代码文件。单次审查最终报告严禁超过 15 条缺陷，防止海量细碎建议瘫痪工程开发；若触碰触发器过多导致排队溢出，优先保留 Trigger 缺陷，并在报告末尾明确声明被 Cap 排除的低优先级项数量。
  • 终审裁决（Verdict: Block vs Approve）： 只要剩余报告中存在任何一条 HIGH 缺陷，最终裁决强制为 BLOCK；无 HIGH 缺陷时方可给出 APPROVE，并将 MEDIUM/LOW 项作为待办清单交付。

3.2 interface-review：代码变更级审查与爆炸半径分析

interface-review 的核心定位是审查变更（Change），而非全量代码库（Codebase）。开发者发起的提问本质是：“我的这次修改有没有让界面变得更糟？”。

  • 严谨的 Diff 作用域解析： 自动解析 git merge-base origin/<default-branch> HEAD 与当前工作区的实际改动。如果工作区干净且与主干基线一致，严禁模型自行偷懒退化去审查 HEAD~1..HEAD（上一个提交很可能是别人合并的 Merge Commit）。必须明确告知开发者“未检测到变更”，并主动询问审查目标。
  • 爆炸半径（Blast Radius）拓扑展开法则： 改动的文件只是证据，其渲染的消费面才是真正的审查对象。拓扑展开遵循：
    • 默认 1-hop 展开：直接 import 或调用已改动文件的父级消费者界面；
    • 核心原语 2-hop 展开：当改动涉及全局设计 Token、主题配置或最底层的 Button/Input 原语时，允许进一步展开 2-hop，但最多审查 5 个典型消费面，超出部分必须在报告中声明截断。
  • 严格审读 Diff 的 - 侧删除行（Deleted Signals）： 代码回归往往发生在被无意删除的代码中。重点扫描删除行中的 aria-* 属性、焦点处理、键盘监听、prefers-reduced-motion 与文案标识。若无对等替换，直接标记为严重的回归缺陷。
  • 三态缺陷分类状态机（Defect Triad）：
    分类标签严格判定依据在报告与裁决中的地位
    Introduced 本次代码变动全新引入的界面缺陷。 计入 15 条上限；若严重度为 HIGH，直接触发 BLOCK 裁决。
    Regression 本次修改破坏或移除了先前原本正确的功能（如删除了焦点环）。 计入 15 条上限；若涉及触发器，无论改动多小均直接升级为 HIGH 触发 BLOCK。
    Pre-existing 缺陷虽然位于改动文件的临近行，但系历史遗留代码，本次 Diff 并未修改它。 独立于 15 条 Cap 之外，且永远不参与 BLOCK 裁决（最多列出 3 条作为开发提醒，防止一次小修改演变成老旧代码的历史债务大审计）。
  • 工作区绝对只读（Never Mutate the Working Tree）： 审查过程中严禁执行 git checkout、git switch 或 git stash。需要运行预览时，必须创建独立的临时工作区 git worktree add /tmp/review-xxx，并在完成后立即清理。

3.3 break：组件极限场景高压沙盒

一个只针对快乐路径（Happy Path）构建的组件，在真实多变的用户生产内容面前往往脆弱不堪。break 专注于“单组件极限生存性压测”。

  • 单次单组件原则：“设置页面”不是一个组件，表单中的“用户名输入框”才是一个组件。单次运行只对一个明确的叶子组件加压。
  • 推导真实可达场景（Scenarios Inferred from Props）： 根据组件的真实入参类型动态推导测试用例：
    • 字符极值：60 字符不含空格的长字符串（URL、UUID）；
    • 数据极值：0 项数据（空态）、1 项数据、999+ 项溢出数据；
    • 视口极值：320px 超窄容器与 100% 满宽容器并排渲染；
    • 国际化极值：德文/俄文伪本地化文案（长度通常膨胀 30%~50%）。
  • 单次加载视觉呈现（Look Once, Observe Rather Than Judge）： 在一个干净的独立临时路由（Client-side scratch route）中，将真实组件用各种极限 Props 并列排列一次性渲染。“只观察，不评判”：记录诸如“文本超出卡片右边界 18px”、“空数据时呈现纯白无提示”，并将故障归口指派给对应的 better-typography 或 better-writing。

3.4 variant：单轴受控变体探索

与全盘重构或随机生成不同，variant 遵循“构建截然不同的解答，而非同质的色调（Different answers, not different tints）”。

  • 单轴隔离原则：必须在单一主轴上探索（结构 Structure、密度 Density、视觉强调 Emphasis、字阶 Type、语气 Voice 五选一），其余维度严格保持基线一致。
  • 不可逾越的底线防御（The Floor Every Variant Clears）： 任何生成的变体方案，在进入比选器前必须 100% 通过 better-interface 的 Escalation Triggers。无障碍支持、全键盘操作、焦点可见性是硬性门槛，绝不允许用牺牲可用性来换取所谓的“视觉酷炫”。
  • 宿主环境无侵入挂载： 将 3 个候选变体挂载在真实页面上，通过 URL 查询参数 ?variant=quiet 进行实时翻页切换。输出得失权衡矩阵（Trade-offs Matrix），罗列各方案在空间利用率与视觉记忆点上的代价，模型绝不代替人类擅自挑选优胜者。

3.5 explain-interface：三级证据链逆向工程解构

当开发者询问“某知名网站上的这个渐变/动效/磨砂质感到底是怎么做出来的”时，explain-interface 彻底根除了 AI 凭空捏造虚假 CSS 代码的恶疾。

  • 严格的三级证据链（The Three Evidence Tiers）：
    证据层级定义与获取渠道严谨表述范例
    Measured (实测值) 从浏览器 DevTools 或像素直接采样读取的计算样式。100% 可复现。 filter: blur(50px)、border-radius: 12px
    Derived (推导值) 由实测数据经由数学几何公式推导出的复合规律。 “4 个颜色停靠点在 0% 到 100% 均匀等距分布”、“容器比视口宽 56px”
    Inferred (推论) 关于作者设计意图的主观判断，明示不作为客观事实。 “将尺寸向外过溢是为了防止模糊边缘露陷”、“使用弹性过渡是为了模拟触感”
  • 按绘制顺序解构图层栈（Layer Stack in Paint Order）： 现代 Web 视觉特效几乎绝不是单一 CSS 属性，而是一组复合图层栈。必须按渲染树底层到顶层的顺序拆解：底层过溢容器 → 伪元素低透明度渐变 → 高斯滤镜扩散 → 顶层 backdrop-filter 磨砂毛玻璃。
  • 解释感知机制而非单纯抄录代码： 指出每个图层在人类视网膜与大脑中所承担的感知职责（如为什么 85% 的透明度变化集中在前 300ms，而剩余 15% 拖长至 1200ms），让开发者真正习得可迁移的感知设计机制。
Section 04

四、数学物理形式化与设计工程可计算模型（Mathematical Formalization）

将界面设计从不可控的定性语言转化为可验证的软件工程，核心在于将其抽象为数学可计算模型。本章对 Interface Skills 的五大核心几何与拓扑命题完成形式化推导。

4.1 模型 1：同心圆角几何共形方程（Concentric Border Radius Equation）

考虑嵌套矩形几何体，内层矩形四个角具有圆弧半径 Rinner，外层矩形包围内层并具备均匀内边距 Padding = P。建立局部角点极坐标系：

Router = Rinner + P

反模式推导：固定圆角的几何畸变与曲率失真：若外层错误地采用了与内层相同的圆角半径（即令 Rwrong = Rinner），在对角线 45° 方向上，内层角点圆弧与外层角点圆弧之间的实际物理距离 D45 为：

D45 = √2 · ((P + Rinner) − Rwrong) + (Rwrong − Rinner) = √2P

而在正交方向（水平与垂直方向），两者的边缘距离恒为 P。因此，对角线方向与正交方向的间隙比率畸变为：

Distortion Ratio = D45P = √2 ≈ 1.4142    (+41.42% 视觉突触挤压)

这种多出 41.4% 的空间间隙会在人的视网膜中心凹形成强烈的“转角肿胀与厚度骤变”假象。只有当 Router = Rinner + P 时，法向间距在所有角度 θ ∈ [0, π2] 上严格恒等于 P，达成共形保角映射。

4.2 模型 2：调和模比字阶与行高衰减场（Modular Type Scale & Line-Height Field）

字阶系统遵循以基准字号 S0（通常为 16px）与固定模比比率 r（Ratio）构成的离散等比数列：

Sk = S0 · rk,    k ∈ {−2, −1, 0, 1, 2, 3, 4}

其中模比 r 取自经典调和音阶比率：Minor Third (1.200)、Major Third (1.250)、Perfect Fourth (1.333)、Golden Ratio (1.618)。字阶对应的推荐行高（Line-Height, LH）并非线性增长，而是呈现出与字号成反比的非线性衰减场：

LH(S) = LHmin + (LHmax − LHmin) · exp(−λ · S − S0S0)

工程标定参数：LHmin = 1.15（大标题极限收紧），LHmax = 1.60（正文极佳呼吸感），衰减特征常数 λ ≈ 0.85。该模型严密解释了为什么字号越大行高倍数必须越小，而正文段落必须放宽至 1.5 以上。

4.3 模型 3：OKLCH 空间色度投影与 WCAG 相对对比度方程

在 CIE 国际标准中，sRGB 颜色分量 CsRGB ∈ [0, 255] 到绝对线性发光强度分量 Clinear 的反伽马校正变换方程为：

Clinear = CsRGB255 · 12.92,    若 CsRGB255 ≤ 0.03928 (CsRGB / 255 + 0.0551.055)2.4,    若 CsRGB255 > 0.03928

界面的相对感知亮度（Relative Luminance, L）由人类视网膜长/中/短波视锥细胞的光谱吸收灵敏度权重决定：

L = 0.2126 · Rlinear + 0.7152 · Glinear + 0.0722 · Blinear

任意渲染前景色亮度 L1 与背景色亮度 L2（设定 L1 > L2）的 WCAG 2.1 相对对比度比率 CR 严格定义为：

CR(L1, L2) = L1 + 0.05L2 + 0.05 ∈ [1.0, 21.0]

合规阈值分界线：

  • WCAG 2.1 AA 级普通正文：CR ≥ 4.5:1
  • WCAG 2.1 AA 级大号文本（≥ 18pt 或 ≥ 14pt 粗体）与 UI 组件边框：CR ≥ 3.0:1
  • WCAG 2.1 AAA 级高标准正文：CR ≥ 7.0:1

4.4 模型 4：代码依赖有向图与变更爆炸半径拓扑算法

定义整个前端应用代码库为有向图 G = (V, E)，其中节点 v ∈ V 表示源文件或模块，有向边 (u, v) ∈ E 表示模块 u 直接依赖/导入（import）了模块 v（即 u 是 v 的上游消费者）。

当本次 Git Diff 修改了模块集合 M ⊂ V 时，变更影响面的爆炸半径（Blast Radius, B）通过图的有向遍历生成：

Hop1(M) = { u ∈ V ∣ ∃m ∈ M, (u, m) ∈ E }
Hop2(M) = { w ∈ V ∣ ∃u ∈ Hop1(M), (w, u) ∈ E },    若 IsPrimitiveToken(M) ∅,    其他情况

为了防止审查作用域发散导致上下文失控，interface-review 引入了拓扑遍历饱和截断算子：

Binspected = TopologicalRank(Hop1(M) ∪ Hop2(M))[0 : 5]

在所有被波及的消费者页面中，按历史访问权重与路由层级排序，严格只审查前 5 个关键消费面，其余消费面标记为未展开，既保证了核心覆盖度，又杜绝了虚假的“全库扫描”幻觉。

4.5 模型 5：三态缺陷裁决自动机（Review Decision Automaton）

将单次审查检出的缺陷全集定义为 D，根据变更归因划分三相不交子集：

D = DIntroduced ∪ DRegression ∪ DPre-existing

最终合并报告集 R 与终审裁决 Verdict 由如下决策状态机确定：

R = SortBySeverity(DIntroduced ∪ DRegression)[0 : 15]
Verdict = BLOCK,    若 ∃d ∈ (DIntroduced ∪ DRegression) 使得 Severity(d) = HIGH APPROVE,    其他情况

核心边界条件保证：DPre-existing（既有存量缺陷）严格被隔离在裁决方程之外（即便存量代码中存在 HIGH 缺陷，也不能阻断当前仅改动了无关行的 PR 合并，最多允许在报告附录展示 ≤ 3 条），彻底打破了传统代码审查中“改一行引发整库背锅”的推诿僵局。

Section 06

六、企业级前端与 Agent 团队落地实践清单（Production Implementation Roadmap）

将 jakubkrehel/skills 接入实际软件工程团队，并非简单地将几个 Markdown 文件拷贝进仓库，而是需要将其融入研发全流程的各个关键门禁（Gateways）。

6.1 三级研发流水线落地 SOP

  1. 本地开发态（Local Coding Phase）： 开发者在修改复杂交互组件后，首先调用 /break <component> 在临时路由对组件进行高压注入，验证长文本与超窄视口是否爆屏；当面临布局或风格探索时，调用 /variant <spec> 在单一主轴生成 3 个变体并挂载于 ?variant=，在人类确认前模型严禁擅自合并代码。
  2. 提交前自检态（Pre-Commit Phase）： 在发起 Pull Request 前，运行 /interface-review。系统自动对比主干分支，提取爆炸半径消费者并识别删除行中的潜在回归。开发者必须清零所有 Introduced 与 Regression 中的 HIGH 级缺陷。
  3. CI/CD 自动化门禁态（Continuous Integration Phase）： 在 GitHub Actions 或 GitLab CI 中，作为只读审查 Agent 自动拉取 PR Diff。如果存在未解决的 Escalation Trigger，自动标记检查未通过并阻止合并，同时输出结构化、不超过 15 条的精准审查报告。

<div onClick={...}> 代替原生按钮 丢失原生键盘 Enter/Space 激活与屏幕阅读器 Role。 始终使用 <button>；页面导航必须使用带合法 href 的 <a>。
全局声明 outline: none 键盘操作者完全丢失当前焦标位置。 使用 :focus-visible 声明至少 2px 且与背景高对比的独立焦点环。
组件直接引用 --blue-500 原始 Token 硬编码基础色阶导致深色主题与换肤彻底失效。 必须通过语义层 Token 映射（如 --color-accent-solid）间接引用。
单屏出现两个以上填充色主按钮 视觉层级竞争，用户无法瞬间捕捉核心行动点。 单个视口内只能有一个填充强调色按钮，次要操作必须保持中性灰。
长文本正文行高设置为 1.2 垂直阅读呼吸感窒息，造成严重视疲劳与跳行。 正文行高强制设为 1.5 ~ 1.6；折行 3 行以上的卡片文案不低于 1.4。
数据表格未设置 tabular-nums 变长数字在数据刷新时引发持续横向抖动。 针对数值统计与行情组件，必须声明 font-variant-numeric: tabular-nums。
移动端输入框字号小于 16px 触发 iOS Safari 视口强行强制缩放，破坏页面布局。 移动端输入框字号保底 16px（桌面端可设为 14px）。
深浅色切换时未抑制 Transition 全页面数十个属性同时过渡，产生浑浊的颜色拖影。 切换瞬时注入 transition: none !important，强制 Reflow 后再移除。
单独依赖色彩表达状态（红绿警示） 色盲/色弱群体无法辨识业务状态。 必须冗余配备文字标签、形状图标或明确的辅助说明。
触控热区小于 24×24px 在触屏设备上极易误触相邻元素。 移动端保底 44×44px，通过透明伪元素 ::after 向外扩展。
空状态仅显示“暂无数据” 认知阻断，用户不知道该功能的作用与入口。 提供前进型空态：说明功能定位 + 阐明核心价值 + 提供唯一步进按钮。
