01 · 不用背模板：四个要素，该填的才填

OpenAI 团队在 learn.chatgpt.com 发布了一份官方提示词指南，讲清楚在 Chat、Work、Codex 三个界面里到底该怎么写提示词。

它的核心是一套四要素框架：目标、背景、输出、边界。你不用背固定语法，也不用每项都填，只写那几个会影响结果的要素就行。

一套原则统一了 Chat、Work、Codex 三个界面的写法，还给 Codex 配了 9 套拆到命令级别的可复制工作流。短任务一句话就够，大任务才补齐要素。

先说清「要什么结果」，别急着列步骤

从你想要的结果说起，把受众和格式一并交代，剩下怎么做的空间留给 ChatGPT 去搜索、比较、调整。流程本身重要时才描述流程。

目标示例 · 一句话说清做什么给谁看

把这些会议记录整理成一份给项目组看的简短更新。把决定和下一步放在最前面。

Turn these meeting notes into a short update for the project team.
Put the decisions and next steps first.

说清结果拿来干嘛，它才知道写多长多细

「输出」这一要素的诀窍是：告诉 ChatGPT 你打算怎么用这个结果，它就能自己选对长度、详略和组织方式。对重要的活，还可以在结尾要求一次终检，比如确认每个行动项都有负责人和截止日期，或者把它没能核实的信息标出来，然后你自己再审一遍。

输出示例 · 三种「说清用途」的写法

做成一页纸摘要，让总监开会前扫一眼就行，决定和下一步放最前面。／
把这些笔记整理成一封跟进邮件，写清决定、负责人和截止日期。／
做一张计划支出对实际支出的对照表，超过 10% 的差额都标出来。

Make this a one-page summary a director can scan before the meeting. Put the decision and next steps first.

Turn these notes into a follow-up email with the decisions, owners, and due dates.

Create a clear table of planned versus actual spending and highlight any difference over 10%.

边界：最容易被忽略的一项

边界是那几条防止 ChatGPT 帮倒忙或擅自动手的指令。判据很简单：当「改错一个细节就会让结果没法用」，或者「某个动作会影响到别人、你想先审一遍」时，就加一条。抓最关键的一两条即可，不用管住每一步。

边界示例 · 四条最常救命的句式

已批准的日期和预算数字保持不变。／
只用我给的资料，缺信息就标出来，别猜。／
建议不要超出给定预算。／
这条消息先做成草稿，别发出去。

Keep the approved dates and budget figures unchanged.

Use only the supplied sources. Flag missing information instead of guessing.

Keep recommendations within the stated budget.

Prepare the message as a draft. Don't send it.

判断要不要加边界

两个触发条件，命中其一就写：① 改错一个细节，结果就没法用；② 某个动作会影响到别人、你想先审一遍。只抓最关键的一两条，不必管住每一步。

02 · 喂对背景：文件、截图、联网搜索、连接的软件

「背景」就是那些会改变结果的信息。原则是只给相关的来源，并说清楚要 ChatGPT 从每个来源里拿什么。有这么几种喂法：

喂法什么时候用
上传文档 / 表格 / PPT / PDF要它总结、比较、改写，或产出可供审阅的文件时
截图 / 示意图 / 图片任务依赖视觉信息时。配一句文字说清具体看图里哪块，别光甩一张图
联网搜索答案取决于最新信息时。要核对结果，就顺带让它给出来源
连接的数据源（Drive / Slack 等）点名去哪找、找什么，不用把每一次检索都描述一遍

连接数据源示例 · 点名去哪找、要什么

用 Drive 里最新的项目计划，加上项目 Slack 频道里相关的决定和进展，做一份状态更新。

Use the latest project plan in Drive and relevant decisions and updates from the project's Slack channel to prepare a status update.

两层偏好要分清

连接数据源要装对应插件，能不能用取决于你的套餐和工作区设置。想指定某个插件，在输入框打 @ 挑就行。

还有一层要分清：每次都适用的偏好（默认语气、习惯）放进「设置 > 个性化」的自定义指令里；只对当前这个任务有用的细节，写在这次的提示词里。

03 · 结果不满意不用重写：跟进消息 + 插队还是排队

第一条提示词不用一次到位。看完结果，直接说你要改的那一处，就能补来源、纠方向、换个版本、调详略，不必从头再来。

跟进消息示例 · 改哪里、留哪里、挪到哪里

开头改得更直接，证据部分保留，把建议挪到背景那一节的前面。

Make the opening more direct, keep the evidence, and move the recommendation above the background section.

在 Codex 里还多一层：它正在跑的时候，你也能再发消息，落在哪一轮取决于你怎么发。

打个比方

像点餐时厨师已经开始炒这道菜。喊「steer」是让他现在就改配料，这盘当场按新要求做；喊「queue」是等这盘炒完再上你加的那道。

通道细节
  • 桌面 App 里，默认行为在「设置 > General > Follow-up behavior」里设；排队的消息会显示在输入框上方，可以编辑、重排、发送或删掉。
  • Codex CLI 里，跑的时候按 Enter 是 steer 当前轮，按 Tab 是 queue 到下一轮。
  • 桌面 App 支持语音口述：按住 Ctrl + M 说话，说的内容转成文字进输入框，发送前可以检查修改。

04 · 一个完整例子：把四要素在真实 prompt 里对上号

四要素不是死格子。下面这段真实的完整 prompt，四种颜色标出哪几句是目标、背景、输出、边界，看一遍就知道它们怎么揉进一段话里。

官方完整例 · 四色标注

［目标］为周一的管理层会议做一份一页的项目状态更新。 ［背景］用 Drive 里最新的项目计划，加上项目 Slack 频道里相关的决定和进展。 ［输出］开头先给管理层要拍板的决定和下一步，再总结进展、风险、负责人和截止日期。 ［边界］已批准的日期和预算数字保持不变；有冲突或缺失的信息标出来；任何东西都别发、别发布。 ［边界 · 终检］收尾前，检查每个下一步都有负责人和截止日期。

目标背景输出边界 它覆盖了目标、背景、输出、边界，末尾加了一句终检，但没有把每一步都写死。这就是四要素「按需拼装」的样子。

沙盘 1 · 四要素提示词装配器

四个文本框对应四要素，勾选「终检」会在末尾追加自检句。装配结果为纯文本拼接，不做任何语义改写；字符数与要素覆盖数由输入实时统计。预置模板全部取自官方原文。

收尾前，检查每个下一步都有负责人和截止日期。

05 · 日常提问用 Chat，出成品用 Work

Chat 适合提问、找点子、写草稿、做日常决定，从你要的结果说起，需要时再补细节。Work 适合要动用多个来源或工具、要走多步、要产出较大成品文件的活。下面是官方给的范例，每条都可直接抄改。

Chat：日常提问的四种范例

给外行讲懂一个概念

给一个从没投资过的人解释复利是怎么回事。用一个具体例子，凡是引入的金融术语都解释清楚。

Explain how compound interest works for someone who has never invested. Use one concrete example and define any financial terms you introduce.

起草并限定语气 / 字数的邮件

起草一封友善的邮件婉拒这个邀请，理由是我要出差。控制在 120 词以内，给下次活动留个余地。

Draft a friendly email declining this invitation because I will be traveling. Keep it under 120 words and leave the door open for a future event.

列表格比较选项再给建议

帮一个每年出两次国的人比较这两个手机套餐。用表格列出主要差别，然后推荐一个并说明取舍。

Compare these two phone plans for one person who travels internationally twice a year. Show the important differences in a table, then recommend one and explain the tradeoff.

带约束条件做实际计划

规划五顿工作日晚餐，每顿不超过 30 分钟。不用花生，几顿饭之间尽量复用食材，最后汇总成一份购物清单。

Plan five weekday dinners that take less than 30 minutes. Avoid peanuts, reuse ingredients across meals, and finish with one consolidated shopping list.

Work：出成品的三种范例

把源文件做成给高管看的简报 + PPT

用附件里的季度报告做一份给高管看的简报和一个六页 PPT。读者是管理层。开头先给他们要拍板的三个决定，把报告事实和你的分析分清楚，每个数字标明出自哪个源文件，收尾前检查简报和 PPT 内容一致。

Use the attached quarterly reports to create a leadership brief and a six-slide presentation.

The audience is the executive team. Lead with the three decisions they need to make, distinguish reported facts from your analysis, cite each number to its source file, and check that the brief and slides agree before you finish.

调研并给出带假设和待确认问题的决策备忘录

为一家 50 人的公司调研三个客服平台。用最新资料比较价格、安全、集成能力和迁移成本。给出一份推荐备忘录，附上链接、你的假设，以及签合同前该弄清楚的问题。

Research three customer-support platforms for a 50-person company. Compare pricing, security, integrations, and migration effort using current sources. Deliver a recommendation memo with links, assumptions, and the questions we should answer before signing a contract.

协调一次产品发布的全套材料

为附件里的产品简介做一份发布计划。包含时间表、负责人、依赖项、风险、发布公告草稿、用户 FAQ，以及发布当天的检查清单。生成最终文件前，把还没定的决定标出来。

Create a launch plan for the attached product brief. Include the timeline, owners, dependencies, risks, announcement draft, customer FAQ, and a checklist for launch day. Flag any missing decisions before producing the final files.

用 Work 的建议
  • 先从一个你能审查的小结果起步，控制来源范围、限定日期，把必做的活和可选的润色分开。
  • 方法本身重要时让它先出个计划；发送、发布、改动别人依赖的信息之前，要求先经你批准。
  • 这一版跑通了，再把这套流程复用起来；重复性的活还可以直接从那个任务里设成定时自动执行。

Work 这个界面本身是什么、能干什么活，小互解读站此前已完整解读过一篇，这里不重复展开。

06 · Codex 基本功三件套：读代码、修 bug、写测试

当你想让 ChatGPT 处理代码、代码库或开发者工具时用 Codex。一条好的 Codex 提示词会点明要什么行为、指向相关代码或复现步骤、保住关键约束，并说清怎么验证。下面三套都可直接照抄。

两个背景前提

上下文：IDE 扩展会自动把你打开的文件当上下文；CLI 里要显式写路径，或用 @ 补全、/mention 附文件。

沙盒：Codex 在本地跑命令时被关在一个沙盒里，文件和网络权限受限，一旦要越界（比如访问外网、改沙盒外的文件），得先过你设定的审批策略才放行。

读懂代码库

接手一个陌生服务、想理清某个协议或请求流程时用它。

IDE 版 · 选中代码问数据流

讲清楚请求是怎么在我选中的这段代码里流转的。包含：涉及的每个模块各自负责什么（简要）、哪些数据在哪里做了校验、改动它时要留意的一两个坑。
（验证追问）把请求流程整理成带编号的步骤清单，再列出涉及哪些文件。

Explain how the request flows through the selected code.
Include:
- a short summary of the responsibilities of each module involved
- what data is validated and where
- one or two "gotchas" to watch for when changing this

(验证追问) Summarize the request flow as a numbered list of steps. Then list the files involved.

CLI 版 · @ 提及具体文件问协议细节

（启动 codex 后）我想搞懂这个服务用的协议。读一下 @foo.ts @schema.ts，讲讲它的数据结构和请求 / 响应流程。重点说清哪些字段必填、哪些可选，以及向后兼容的规则。

codex

I need to understand the protocol used by this service. Read @foo.ts @schema.ts and explain the schema and request/response flow. Focus on required vs optional fields and backward compatibility rules.

修 bug

手上有个能复现的坏行为时用它。给一份复现配方、加上你怀疑的文件，比一句高层描述有用得多。

流程：复现 → 定位 → 修复 → 验证

CLI 版 · 复现步骤 + 约束 + 验证一次给全

（启动 codex 后）Bug：在设置页点「保存」，有时显示「已保存」但改动没真正存下来。
复现：1）启动应用 npm run dev；2）打开 /settings；3）切换「开启提醒」；4）点保存；5）刷新页面，开关又弹回去了。
约束：别改 API 的形态；改动尽量小，能加个回归测试就加。先在本地复现这个 bug，再给出补丁并跑一遍检查。
（验证追问）修完后跑一下 lint 加最小的相关测试，把用的命令和结果报给我。

codex

Bug: Clicking "Save" on the settings screen sometimes shows "Saved" but doesn't persist the change.
Repro:
1) Start the app: npm run dev
2) Go to /settings
3) Toggle "Enable alerts"
4) Click Save
5) Refresh the page: the toggle resets
Constraints:
- Do not change the API shape.
- Keep the fix minimal and add a regression test if feasible.
Start by reproducing the bug locally, then propose a patch and run checks.

(验证追问) After the fix, run lint + the smallest relevant test suite. Report the commands and results.

IDE 版 · 打开可疑文件直接问

找出导致「显示已保存但改动没存下来」的 bug。给出修法后，告诉我怎么在界面上验证。

Find the bug causing "Saved" to show without persisting changes. After proposing the fix, tell me how to verify it in the UI.

写单元测试

想精确框定测哪一段时用它。IDE 里选中函数代码后问，CLI 里直接点名函数名。

写测试 · 选中代码 / CLI 点名 两种路径

（IDE，选中函数代码后）给这个函数写个单元测试，沿用其他测试里的写法约定。
（CLI，直接点名函数）给 @transform.ts 里的 invert_list 函数加个测试，覆盖正常路径和边界情况。

(IDE，选中函数代码后) Write a unit test for this function. Follow conventions used in other tests.

(CLI，直接点名函数) Add a test for the invert_list function in @transform.ts. Cover the happy path plus edge cases.

07 · Codex 进阶三件套：截图变原型、边改边看、委托云端

三个更进阶的工作流：把设计截图直接变成能跑的原型、一边改代码一边在浏览器里看效果、把耗时的重构本地定好方案后交给云端跑。

截图变原型

想把设计稿、截图或 UI 参考变成一个能跑的原型时用它。图给的是视觉要求，框架、路由、组件风格这些实现约束还得你写；图上看不到的行为（hover 状态、校验规则、键盘交互）也要用文字补上。

输入

一张设计截图 / UI 参考图，配上你补的实现约束（用什么框架、路由怎么走、组件风格），以及图里看不出的行为说明。

产出

一个能跑的原型：新路由 / 页面 + 需要的小组件 + 一份 README。让 Codex 起开发服务器，告诉你在哪个本地地址能看到。

截图变原型 · 约束 + 产出物一次列清

（启动 codex，拖入截图后）照着这张图做一个新的仪表盘。
约束：用 react、vite、tailwind，代码用 typescript 写；间距、字体、布局尽量贴近原图。
产出：一个渲染这套界面的新路由 / 页面、需要的小组件、一份说明怎么在本地运行的 README.md。
（验证追问）启动开发服务器，告诉我在哪个本地网址 / 路由能看到这个原型。
（IDE 版，贴截图）做一个新的设置页，把附上的截图当作目标界面，沿用本项目其他文件里的设计和视觉风格。

codex

(拖入截图后) Create a new dashboard based on this image.
Constraints:
- Use react, vite, and tailwind. Write the code in typescript.
- Match spacing, typography, and layout as closely as possible.
Outputs:
- A new route/page that renders the UI
- Any small components needed
- README.md with instructions to run it locally

(验证追问) Start the dev server and tell me the local URL/route to view the prototype.

(IDE版，贴截图) Create a new settings page. Use the attached screenshot as the target UI.
Follow design and visual patterns from other files in this project.

边改边看的 UI 迭代

把重构委托给云端

想先用本地上下文设计方案，再把耗时的实现丢给云端并行跑时用它。关键在于：本地定好的方案能带着完整上下文迁到云端。

先在本地 IDE 用 $plan 让 Codex 调查代码、出一份方案，你反复修订到满意。切到云端环境时，Codex 会新建一个云端任务，把已有上下文（含方案和你本地的改动）一并带过去。云端在隔离环境里跑完，直接出 diff，你 review 后可以直接建 PR，也可以拉回本地测。有了方案后还能用 /goal 开 Goal mode，给它设一个持续追踪的长期目标，让它自己往下推进多步。

10 · 沙盘：提交前的要素自检

沙盘 3 · 六项提交前自检

六条判据全部来自官方框架：目标、背景、输出、边界、终检、验证。计数为勾选数量，不做任何加权评分。

  • 目标：说清要什么结果、给谁看，格式一并交代。
  • 背景：点名来源，并说明要从每个来源里拿什么。
  • 输出：说明结果拿来干嘛，让它自己决定长度与详略。
  • 边界：写明不能改、不能动、不能猜、不能发的部分。
  • 终检：要求收尾前自检（负责人 / 截止日期 / 未核实信息）。

11 · 边界与前提：用之前先确认这几件事

硬性前提
  • 连接的数据源要装对应插件，能不能用取决于你的套餐和工作区设置；指定插件在输入框打 @ 挑。
  • Codex 本地跑命令在沙盒内，文件与网络权限受限；越界动作（访问外网、改沙盒外文件）需先过你设定的审批策略。
  • 云端委托任务默认关网，agent 阶段不联网，除非你为该环境显式开了联网。
  • GitHub 侧 review 需先在仓库开启 Codex 的 Code review，才能在 PR 评论区 @ 它。
