OpenAI Codex · Agent Harness 开源深度解读

OpenAI 将 Codex 的底层核心框架 Agent Harness 开源：你可以轻松将 Agent 接入自己的业务系统

OpenAI 把管理上下文、工具调用、沙箱和审批的 Codex 执行底座开放出来。开发者不用从零造 Agent 框架，就能让 Codex 进入现有的看板、工单和业务后台。

一分钟速览

  • Codex 不再只能待在编程插件或聊天框里；它的 Agent 能力可以接进物流后台、工单、报税和监控系统。
  • 用户继续在原来的系统里工作：系统把当前对象和业务状态交给 Codex，重要操作按规则等待人工批准，结果再写回正式记录。
  • 开发团队不用从零搭建上下文记忆、工具调用、沙箱、进度和审批机制，可以直接复用 Codex 已有的开源组件。
  • 开源的是 CLI、SDK、app-server 等执行底座；模型、托管服务、IDE Extension 和 Codex cloud 没有一起开源。
01

OpenAI 这次到底开源了什么

OpenAI 开源了让 Codex 能连续干活的底层框架：Agent Harness。

可以把大模型想成一个聪明的大脑。大脑会思考，却不会自动知道自己正在处理哪张工单，也不会天然记住上一步做到哪里，更不知道该去哪个系统查数据、哪些操作可以直接执行、花钱或改记录前要找谁批准。要让它真正进公司上班，还得配上工作记录、工具箱、门禁和请示流程。Agent Harness 就是这套“上岗系统”。

这次开放带来三件很实际的事：

  • 对开发者：少造一层基础设施。上下文记忆、工具调用、沙箱、进度和审批机制，都可以复用 Codex 已有的开源组件。
  • 对产品：AI 可以进入现有软件。物流后台、工单系统、报税软件和监控看板都可以成为 Codex 的工作界面。
  • 对用户：不用把工作重新搬进聊天框。原系统提供当前对象和业务状态，结果仍回到原来的正式记录。

放进物流后台，它可以是这样：调度员选中一票延误货物，Codex 直接拿到当前状态并调查原因；遇到花钱改订等有后果的动作，系统按规则停下来等人批准。

边界先说清楚：OpenAI 没有把整个 Codex、模型和云服务全部开源。明确开放的是 Codex CLI、SDK、app-server 等 Harness 与接入组件；模型访问、托管服务、IDE Extension 和 Codex cloud 仍是独立部分。准确地说，开发者拿到的是 Codex 的 Agent 执行底座和接入层，不是整套 Codex 的自托管版本。
02

为什么光有模型，还做不成真正的 Agent

一次普通的大模型调用很简单：输入问题，等待回答。可一旦任务从“回答”变成“完成”，缺失的东西会迅速暴露出来。

模型要知道自己正在处理哪个对象；要记得此前做过什么；要读取文件、日志或业务记录；要调用外部工具；要在失败后换一条路线；还要区分哪些动作可以自动执行，哪些动作必须停下来等人批准。任务持续几十分钟甚至跨越多轮时，它还得压缩旧上下文，又不能把早期的重要判断一起忘掉。

Agent Harness 就是负责记住进度、调度工具、限制权限并继续推进任务的执行系统。

QAgent Harness 到底比模型加 Prompt 多了什么？
Harness 让任务在目标和上下文、模型判断、工具或沙箱动作、观察结果和状态更新之间持续循环；关键写操作经过人工审批。ARC-AGI-3 实验中，保留推理状态与上下文压缩把 RHAE 从 13.3% 提到 38.3%，输出 Token 降至约六分之一。

Harness 为什么重要，最直接的问题是：同一个模型换一套运行方式，结果会差多少？OpenAI 给出了一个很有分量、但也很容易被滥用的数字。

在 ARC-AGI-3 这套公共任务集里，Agent 要在陌生的交互环境中持续观察、试错并找出规则，因此能否保住此前的判断和行动历史尤其重要。GPT-5.6 Sol 使用 ARC-AGI-3 官方的通用 Harness 时，RHAE（相对人类行动效率）为 13.3%；改为保留此前形成的 reasoning（推理状态），并用 compaction（把旧上下文压成仍可继续使用的摘要）代替简单丢弃最旧内容后，RHAE 升到 38.3%，输出 Token 数降至原来的约六分之一。

背后的机制并不神秘。丢弃 reasoning，相当于让 Agent 每执行一步都重新理解游戏；滚动截断则会让更早的观察和动作逐渐消失。保留推理让计划能够延续，压缩上下文则让 Agent 在长任务中保住关键认识，而不是简单忘掉最旧的内容。

但这个结果只属于特定模型、特定公共任务集和特定评测指标，不能写成“接入 Codex 后所有 Agent 都会提升三倍”。它说明：模型周围的运行架构，也会影响模型最终能发挥出多少能力。

03

接进业务系统后，三层分别管什么

知道 Harness 是一套“上岗系统”以后，下一个问题就很实际：把 Codex 接进产品后，宿主应用、Codex app-server 和 MCP 分别负责什么？这套架构把责任清楚地切成三层，各管一块。

Q宿主应用、Codex app-server 和 MCP 各自负责什么？
宿主应用掌握当前业务对象、界面、规则和批准权；Codex app-server 维持线程、Agent loop、沙箱和事件流；应用自有 MCP 读取可信记录并暴露业务动作。批准后的变化回写系统并刷新界面。
图 1 · 三层责任切分：宿主应用定义对象与规则，app-server 驱动任务循环，MCP 提供可信数据与受控动作；有后果的写操作经审批门控后回写。

第一层是宿主应用，也就是你原本的物流后台、工单系统或报税软件。用户选择了哪条告警、哪张工单或哪笔订单，当前页面展示了什么状态，业务允许做什么，哪一步需要人类同意，都由它定义。

第二层是 Codex app-server。它接过这些上下文，保存任务进度，驱动 Agent 持续调用工具，并把执行限制在沙箱和审批规则内。产品也能看到过程、随时中断并回应审批请求。

第三层是应用自有的 MCP 服务，可以把它理解成一组专门给 Agent 使用的业务接口。MCP 不是业务数据库本身；Agent 通过它读取权威记录，也可以请求改订、建单、更新状态等业务动作。只有满足宿主应用的规则和审批条件后，动作才真正发生。

完成后的变化还要回到原来的产品界面。Agent 的结论进入正式业务系统，由原系统继续充当最终记录和控制中心。

这套分工解决了 Agent 产品里最容易混在一起的三件事：

  • Codex 负责把任务推进下去；
  • MCP 负责把可信数据和受控动作交给 Codex；
  • 宿主应用负责告诉两者什么重要、什么允许，以及最终结果应该落在哪里。
04

从一次性任务到产品功能，三种接法怎么选

大多数任务用不到 app-server。三种接法可以先用一句话记住：脚本或后台任务用 codex exec，业务代码里调用用 SDK，把 Agent 做成产品功能则用 app-server。

Qcodex exec、SDK 和 app-server 应该怎么选？
codex exec 适合启动后完成并退出的一次性任务；SDK 适合业务代码启动、继续或恢复线程；app-server 适合产品直接管理持久线程、流式事件、中断和审批。
一次性任务
codex exec

适合边界清楚的一次性任务，例如在自动化检查流程里审查代码、定时整理记录，或者在后台批量处理一组输入。它既能返回最终文本，也能输出可供程序继续处理的事件或结构化结果。任务启动、运行、结束，生命周期相对简单。

业务代码调用
Codex SDK

适合由业务代码直接启动和管理 Codex 任务。应用可以开始新任务，也能继续或恢复过去的工作；产品团队不必自己处理 app-server 的底层协议。

产品级集成
Codex app-server

适合把 Agent 直接做成产品功能。应用可以长期保留任务，看到执行过程，随时中断，临时提供工具，并在 Codex 请求时处理审批。

不要把这三种方式理解成“低配、中配、高配”。选择时只看三个问题：任务是否需要持续状态，产品是否需要观察和干预执行过程，Agent 是否要在用户当前界面里完成有后果的业务动作。

如果只是一次后台分析，直接上 app-server 只会增加集成成本；如果 Agent 要长期存在于运营台里，只靠一条 codex exec 命令又很难承载会话、审批和界面同步。

选择哪一层只是实现问题。更大的产品问题是：这些能力最终应该被放进什么界面？答案未必是再造一个聊天框。

05

接入 Agent，不等于再加一个聊天框

产品团队接下来要决定的是：AI 应该放在哪里？OpenAI 的答案是，把 Agent 放进工作本来发生的地方，不要给所有软件统一加一个聊天框。

一个脱离业务系统、拿不到当前上下文的通用聊天框，会把整理现场的麻烦全留给用户：请你先把正在处理的订单、页面状态、业务规则和操作目的重新翻译成一段 Prompt。

用户要重新说明自己正在看哪条记录，把看板上的状态复制给模型，再判断模型建议是否基于最新数据。模型给出方案后，用户还要切回业务系统执行。上下文、分析和动作被分散在两个地方，重要边界也很容易在复制粘贴中丢失。

把同一项工作并排来看，差别不在模型会不会回答，而在上下文由谁整理、业务边界从哪里获得，以及结果最终落在哪里。

Q同一项工作放进聊天框和嵌入业务系统后，真正差在哪里？
在脱离业务系统、拿不到当前上下文的聊天框里，用户需要重新说明当前对象、复制可见状态、解释业务规则，并在获得建议后切回系统执行；嵌入业务系统后，宿主应用向 Agent 提供当前对象和最新状态，配置规则、权限与工具边界，并按宿主规则对有后果的写入请求人工批准，获批后由工具更新正式记录。

所以，仪表盘、工单页、报税表格和安全事件队列不会因为 AI 到来就失去价值。它们早已把干活需要的对象、状态、证据和按钮摆在一起。Agent 更合理的位置，是进入这些界面直接使用已有上下文，省掉用户从空白输入框重新描述现场的过程。

聊天当然不会消失。开放探索、模糊问题和临时分析仍然适合对话。应该放弃的，是把通用聊天框当成所有 Agent 产品的唯一形态。

06

Relay 演示：AI 怎样在物流后台把事情做完

Relay 使用虚构种子数据，不是真实客户系统；它把前面的三层分工和接入方式，落成了一笔完整的物流操作。

QRelay 如何把一次 Agent 分析变成受控的业务闭环？
调度员在 Relay 中选择异常货物，页面提供业务上下文，Codex 经 MCP 读取当前记录并比较方案；重新订舱等写操作必须由人批准，执行后结果回写物流记录并刷新界面。

调度员不是从零写一句“帮我分析物流延误”。他先在异常队列中选择一票货物，再点击“调查延误”或“比较补救方案”。这个点击本身已经交付了业务对象和用户意图，页面则继续提供路线、承诺时间、货值和当前异常等可见上下文。

Codex 随后通过 Relay 的 MCP 工具读取当前运营记录，判断问题发生在哪里，并比较可用方案。分析可以自动进行；但如果下一步是重新订舱、改变业务记录或产生费用，系统就会停下来要求调度员批准。动作获批并执行后，变化重新进入物流记录，业务视图随之刷新。

整个闭环可以压缩成七步：

  1. 选择对象
  2. 注入上下文
  3. 查询权威数据
  4. 调查与比较
  5. 人工批准
  6. 执行业务动作
  7. 刷新正式记录

它比“给聊天框接几个工具”多出来的部分，正是产品设计：什么时候自动交付上下文，哪些工具可用，哪种动作有后果，以及人应该在哪里重新接管决定。

类似模式已经进入不同领域。GitHub 与 JetBrains 把 Codex 放进现有 IDE 工作流；Cisco 在 Cloud Control 的 App Builder 中使用 Codex SDK；Thrive Holdings、Crete 与 OpenAI 则把 Codex 接进报税准备和从业者反馈闭环。

Thrive Holdings、Crete 与 OpenAI 的报税准备试点处理了 7,000 份税表，合作方自报将准备时间缩短了约三分之一。这个数字不是独立第三方评测，但它展示了工作流嵌入的第二层价值：Agent 不只完成一次任务，还能读取生产记录、吸收专家纠正、形成评测任务，再推动下一轮产品改进。

07

最后说清楚：哪些开源了，哪些没有

还有一个容易被误解的边界：Harness 可以嵌入产品，不等于整套 Codex 都能自由自托管。官方开放的边界没有这么宽。

已明确开源没有随 Harness 一起开源
Codex CLI模型本身与模型访问
Codex SDKOpenAI 托管服务
Codex app-serverCodex IDE Extension
openai/codex 仓库，Apache-2.0 许可Codex cloud

开发者拿到的是一套可以查看、修改并接进产品的 Agent 执行底座，以及从一次性任务到深度产品集成的不同入口；并没有因此拿到模型和云端服务的开源实现。

更重要的是，Harness 也不会替产品团队生成业务世界。哪张记录是权威数据，哪些工具可以调用，什么动作必须审批，怎样把结果写回系统，这些仍然必须由宿主应用定义。

所以，OpenAI 帮开发者省掉了搭建 Agent 执行底座 的大量工作；业务产品仍要由团队自己做好。差距最终来自对业务的理解，以及能否把数据、工具、权限和人工判断接成一条可靠流程，让 AI 真正在现有系统里把活干完。
