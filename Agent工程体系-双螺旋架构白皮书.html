从微观 JIT 动态编译到宏观 Fleet 治理：
AI 软件工程双螺旋架构

微观上像 JIT 编译器一样为任务动态特化最小运行时；宏观上像操作系统一样对多 Agent 进行隔离、调度与串行化出关。两条链互相独立，又共享同一条演化反馈。

核心摘要： 效率瓶颈已从「模型生成速度」转移到两处—— 微观的上下文与工具装配失配（Intra-Agent）与 宏观的人类审核带宽雪崩（Inter-Agent）。 微观的解法是四模块协议的即时编译，宏观的解法是准入控制与单写者串行化。 但两者拼接处存在一道断层：演化依赖「可自动判分的奖励」，而真实工程任务给不出这个奖励。 本文所有模型参数均标注来源，示意性假设与论文实测数据严格区分。
Chapter 01

背景与问题定义：生产力的两次迁移

为什么模型越来越快，交付却越来越容易失控？瓶颈不在智力，在系统架构。

过去数年 AI 编码的主流范式是「大模型 + 静态脚手架 + 交互式 Copilot」。 当工程师试图扩展到多 Agent 并发与长流程自主编码时，会系统性地撞上两堵墙—— 它们分属两个不同的层级，却经常被混为一谈。

微观困境 · INTRA-AGENT

静态脚手架的适配失配

一套固定的 System Prompt 要覆盖所有任务类型，只能把全量工具定义与历史记忆都塞进去。 不同任务需要的先验不只是参数不同，而是结构不同——广度搜索要并行展开证据， 终端操作要精简串行循环，代码任务天然由文件系统管理补丁与测试。用一套结构覆盖，只能处处妥协。

宏观困境 · INTER-AGENT

审核带宽雪崩

多个 Agent 并发产出（到达率 λ），而人类的审查吞吐是有限且会随压力下降的（服务率 μ）。 当负荷率 ρ = λ/μ > 1 时，队列单调发散，引发分支漂移与合并冲突。 更隐蔽的是：ρ 接近 1 之前系统看起来一切正常，越过之后没有任何预警地崩塌。

💡
问题迁移的完整路径

瓶颈经历了两次迁移：模型能力 → 执行框架 → 人的注意力。 第一次迁移由论文用数据完成，第二次迁移由工程实践揭示。

第一次迁移的证据是硬的：同一底座只换框架，18 组配对全面提升，规划类任务最高 +24.8 分， 而成本平均下降 36%——这个量级以往只有换一代模型才做得到。

Chapter 02

核心概念与双螺旋系统模型

先对齐语言。六个术语 + 四模块协议，构成后面所有论证的坐标系。

双螺旋协作拓扑（MICRO JIT COMPILER ⟷ MACRO FLEET OS） SYSTEM TOPOLOGY

➔

提取任务特征，动态装配 Harness，准入控制

注意 Harness 横跨入口与执行两层，不属于治理层——这是常见的一处归类错误。

核心术语

1. JIT Harness 编译器

在任务到达的运行时，根据具体任务描述与仓库拓扑，动态生成 Memory 格式、Planning 策略、 工具最小子集与验证断言的轻量运行时容器。对应论文的 27B 元模型。

2. Worktree 即虚拟地址空间

把 Git Worktree 抽象为 Agent 进程的物理隔离「虚拟内存空间」。每个 Agent 在专属分支与独立目录运行， 彻底消除文件写入竞态。它提供的是快照隔离，不是串行化——见第五章陷阱 01。

3. 注意力调度

把人类审查决策建模为有限服务台资源，按优先级排队。 关键修正：调度器的主职能是准入控制（限流），不是排序。 只排序不限流，队列仍会发散。

4. MRSW 单写者锁

多个 Agent 可并发只读分析、单测推导与分支构建；但合入主干与部署时强制获取单写者锁串行执行。 真正的串行点在合并（merge），不在部署——merge 才是写入共享真值的唯一入口。

5. Harness 智能

构建与优化执行框架的能力，三属性：适应性（匹配任务与底座）、 可靠性（可稳定执行、失败可修复）、可演化性（把执行反馈转成更强的未来框架）。

6. λ、μ 与 ρ

λ 是 Agent 任务完成速率，μ 是人类评审速率，ρ = λ/μ 是负荷率。 μ 不是常数——它随在制品数量上升而下降（上下文切换开销）， 因此系统比朴素排队论预测得更早崩塌。

四模块协议：把程序压成坐标

要让模型学会生成框架，第一步必须把它从「一坨自由发挥的工程代码」变成「有固定结构、机器可生成的产物」。 论文把任意框架冻结成四元组 h = (M, P, A, F)，运行时按 M → P → F → A 协作：

模块职责为什么必须独立
M · Memory历史如何压缩、工作上下文如何组织决定模型「看得见什么」，是精度的上游约束
P · Planning如何拆解、下一步做什么、如何应对意外决定搜索形状：串行、并行，还是递归委托
F · Capability在哪个节点暴露哪个工具或技能决定每步动作空间大小，直接影响 token 消耗
A · Action动作格式、回传结构、出错如何恢复决定能否稳定执行，以及失败时能否局部修复
 这套协议的表达能力已被验证：三种截然不同的经典框架都能写成同一个坐标系里的点。
ReAct = ( M_full , P_∅ , A_react , F_all ) Codex / OpenCode = ( M_compact , P_todo , A_react , F_all ) ROMA / AOrchestra = ( M_subproblem , P_decomp , A_rec , F_route )
✓
这一步真正的价值：搜索空间降维

差异被归约成四个维度上的具体选择，意味着搜索空间从程序空间降到了配置空间。 配套地，作者用 HarnessFactory 在统一协议下重实现了 13 个代表性框架作为种子库—— 所以生成是在协议约束下装配可执行模块，不是从零合成自由代码。这是整件事能成立的工程前提。

Chapter 03

关键要点分层展开

微观装配、宏观调度、以及两者之间的断层。每层配一个可交互沙盘。

维度一 · 微观：JIT 动态装配沙盘

切换任务类型，观察同一个四模块协议会装配出结构完全不同的框架。这正是 JIT 与 AOT 的根本差异： AOT 只能给出一个「对所有任务都次优」的折中解。

微观：三阶段训练如何支撑这套装配

阶段 I · Customization 定制

用更强的冻结教师模型，针对每个任务从种子库采样 3 个参考框架，生成合规框架作为监督数据。 除 SFT 外加了偏好学习：同一底座、同一评测种子下两两比较候选，只有「得分更高、且时延和成本都不变差」才记为偏好对。

它学到的不只是结构合规，还有「又有效又省」——这解释了后面成本降 36% 从何而来，不是副作用，是设计目标。

阶段 II · Repairing 修复

第一阶段被过滤掉的失败生成不丢弃，而是转成修复监督：失败框架带上诊断报告 （编译错误、接口不匹配、工具调用失败、运行时异常），教师模型在最多两轮内给出局部补丁。

学到的是「拿到执行反馈后做少量高杠杆修改」，而不是一次性重写。失败样本是最贵的数据， 多数流水线在这里把它们扔掉了。

阶段 III · Evo-GDPO 演化

把测试时的演化本身变成可训练能力。采样候选与库中前沿在同一任务、同一底座、同一预算下对比， 只有超越前沿才保留；奖励、时延、成本三个信号分组解耦归一化后合并，避免量纲互相压制。

部署后模型参数冻结、只有框架库继续演化——这就是「越用越强」的机制来源。 但请注意：这个机制有一个前提，见本页「维度三」。

维度二 · 宏观：排队论与注意力雪崩沙盘

被误判的调度器职能

实践中的状态面板 + 优先级队列能看见队列、能排序队列， 但不能阻止队列增长——它只给已完成的任务排优先级，对并发数量没有任何约束。

维度三 · 断层：演化闭环在哪里断掉

这是两份材料拼接后才看得见的问题，也是全篇最重要的一节。 微观的演化能力是被可自动计算的奖励喂养的：Evo-GDPO 的三个信号（奖励/时延/成本）全部可自动测量， Streaming 模式的进步靠累计准确率曲线证明——这要求每题结束就有真值标签。

而论文的 9 个基准全部是短程、单次、可自动判分的任务， 没有一个是「跨 2000 小时的仓库演化」。宏观面对的恰恰是后者。

🧭
三条应对路径（按可行性排序）

① 可验证性工程（最现实）——把验收标准从「人看代码」转成可执行判据：属性测试、契约测试、回归基线、不变式检查。

② 评审信号结构化（中等）——让人类评审不只产出通过/驳回，而是结构化标签（假设错误 / 实现偏差 / 遗漏边界 / 风格问题）。

③ 代理奖励模型（风险最高）——训练评审模型替代人类打分。风险是奖励劫持，且在 Fleet 规模下偏差会被放大 N 倍、极难察觉。

Chapter 05

典型陷阱与防御

每条都有「表现 + 防御」两栏。前四条来自工程实践，后两条来自数据核验。

PITFALL 01

把快照隔离当成串行化

表现：认为开了 Worktree 就安全了。但两个 Agent 分别改 auth.py 与 session.py，文本零冲突、合并成功，系统却崩溃——一个把校验改成异步，另一个假设它同步。
防御：Worktree 只是快照隔离。补上 merge queue + 合并后全量验证（可串行化检查）， 并对跨文件语义冲突保持人工警觉——这一层目前没有成熟工具覆盖。

PITFALL 02

单一模型自审盲区 · 与递归审查

表现：让写代码的同一模型自我审查，倾向维护自身逻辑盲区。 更隐蔽的是递归审查——要求模型「再找五个问题」，它往往会努力凑满五个， 即使剩下的是想象出来的 Bug。
防御：异构模型交叉核验；复核由改动规模与失败代价触发， 必须有明确停止条件，而非「越多越好」。

PITFALL 03

全量工具挂载 · Tool Bloat

表现：一次性挂载全部接口工具，模型在决策树上注意力发散，选错参数的概率上升， token 也被工具定义大量消耗。
防御：由 JIT 编译器依据任务特征裁剪工具子集。 论文的对照组显示，更精准的执行能把 token 从 52.7 万压到 21.2 万而性能反升—— 增益来自更短的执行，不是更长的轨迹。

PITFALL 04

未编译的提示词替代 SOP

表现：用自然语言一段段写长指令，每次执行方差巨大，偶发遗漏关键步骤。 省下的不是打字时间，而是每次重新回忆顺序、检查遗漏的认知成本。
防御：Skill ≈ Compiled SOP，把多步流程编译为带确定性断言的流程。 但编译产物会位衰减——必须配重编译触发条件（依赖变更 / API 签名变更 / 连续失败率上升）。

PITFALL 05

拿结构参数当可用并发

表现：用理论上的协调成本推算最优并发。但真实数据里返工率几乎总是随并发上升， 拟合出的「有效 σ/κ」会系统性放大——实测为 σ ×2.14、κ ×2.74， 最优并发从 13.6 掉到 7.8，结构参数会高估可用并发约 75%。
防御：用实测数据拟合，且只依据 N* 决策—— σ 与 κ 单独辨识度不高，可以互相补偿，但组合量 (1−σ)/κ 稳定得多。

PITFALL 06

代理指标被劫持

表现：用 Agent 会话数、提交数、Token 量、评审问题条数衡量效率。 这些每一个都存在被优化的路径——要求找五个问题，就会得到五个问题。
防御：跟踪真实指标：返工次数、合并后故障率、交付周期、Skill 命中率与失效率。 验收指标必须可被外部真值校验，而非自报数量。

🔓
一条被当作成功案例记录的权限逃逸

在「十分钟搭完远程环境」的成功演示里，原文同时记录了：Agent 从本机找到了 API 密钥，并在远端取得完整 root 权限。 这是两个独立失效——凭据以明文存在于 Agent 可读路径，以及 Agent 拿到了远超任务需要的权限。

值得警惕的是叙事 framing：速度与控制权是同一套自动化的一体两面。 个人实验可以接受这种交换；连接生产仓库和真实密钥后，运维能力本身就变成了产品的一部分。 在一个 Agent 能拿到 root 的体系里，不可被 Agent 篡改的审计日志是唯一还能追溯发生了什么的东西。

最终该带走的三样东西

① 一个可测量的规模模型。它把「该开几个 Agent」从感觉变成参数，并预言盲目扩容是负收益。

② 一个准入控制纪律。调度器的主职能是限流，不是排序——你可能已经有现成的 WIP 上限了： 订阅套餐的并发限制。

③ 一条演化闭环的前提。在奖励不可自动判分的场景里，先做的不是上 Agent， 而是把验收标准转成可执行判据。这一条不成立，其余都会退化为「更快地产生未经验证的产出」。
