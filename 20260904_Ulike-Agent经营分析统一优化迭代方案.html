02Ulike-Agent 当前真实基线

不能把项目描述成“只会 Markdown 的开环系统”，也不能沿用已经被 main 更新推翻的旧差距判断。当前基线以 main@28250ecf 为源码事实锚点；Runtime/Live 状态仍需独立验证。

!
Production Truth（当前最重要事实）：Dynamic Planner / Operator Registry 已在源码主链完成切换，但仓库 Release Status 仍明确记录：运行中的 Tool/Backend/OWUI 容器未对齐新分析镜像，健康栈仍可能走旧链；Sales Live 仍是 NOT_RUN / NO_GO。因此任何后续“经营诊断效果”都必须先建立在真实 Runtime Fingerprint + Real DB + SALES-001 + Browser/Human Review 之上。

必须保持的优势 / 已有地基

  • Dynamic Analysis：dynamic_dag、maxDepth/maxBranches、Evidence sufficient、Hypothesis validation。
  • Operator Registry：趋势、结构、峰值贡献、生命周期、量价、数据质量等确定性算子。
  • Semantic：Wren + Metric/Entity/Relationship/Rule/Binding，比 MerchantBackend 的薄语义更企业级。
  • Evidence：Claim → Citation → Evidence → ReportIR，已有强因果 Citation 门禁。
  • Governance：Pack/Contract/Lifecycle/Shadow/Live/Production Gate。
  • Control Plane：Task/Run/Event/Approval 持久化、恢复、幂等、CAS。
  • ToolResult Contract：contracts/tool-result/v1 已激活，Java 工具主链已接线；不是“只有 Shadow 才有 Envelope”。
  • Provider 基础：默认 LLM Base URL 指向 DeepSeek，当前默认 function_call_type: struct_parse；DeepSeek 官方 Context Caching 默认开启并返回 cache hit/miss token，可直接用于真实基线度量。
  • Memory 基础：Open WebUI 已存在 turn 后异步 memory review；差距是尚未纳入 Ulike 的 tenant/permission/evidence 治理，而不是代码仓库完全没有记忆能力。

当前真实缺口 / 风险

  • 外部内容 Trust Boundary：search_engine.py 抓取网页后直接 soup.get_text() 写入 doc.content，未发现 commerce 式 NFKC / zero-width / bidi / forged-role / fence pipeline；这是当前最明确的 Runtime 安全缺口。
  • Prefix Stability：Planning/Executor/ReAct 仍在 System Prompt 中渲染 {{files}} 等动态内容；动态产物增长会持续改变前缀。
  • Tool Set Stability：ExecutorAgent.filterToolsByTask 仍按子任务动态过滤工具；应改为 Server-resolved Execution Profile 内稳定，而非“所有工具全局固定”。
  • 缺统一的 OperatingSnapshot / Comparable / Partial-period 经营入口。
  • Sales 归因仍主要是 单数据域内部归因，跨商品/库存/营销/用户/价格证据不足。
  • 缺 Mix vs Level 的通用经营分析算子与触发策略。
  • Evidence 很强，但缺 Run-level Seen-ID Provenance 对 UI/Action 的结构约束。
  • 报告可追溯，但“结论 → 下一步”仍缺统一的 Decision/Handoff Contract。
  • 性能项待实测：Eager Dispatch 尚未成为稳定主链能力；function_call 与 struct_parse 的优劣未形成 Ulike 自身 Eval 证据。
  • 源码主链与真实 Runtime/Browser/Live 仍必须严格区分，不以静态绿色冒充 Production。
最新稿中的一处关键纠偏：“ToolResultEnvelope 只在 Shadow”已被当前 main 推翻；真正应该做的是 Envelope/held/error taxonomy 的跨 Java/Python/Host 一致性收口。相反，“deepsearch 外部内容缺少结构围栏”和“System Prompt/工具集前缀不稳定”仍由当前 main 代码直接支持，应进入最前置改造。
判断：项目现在有两条并行但有先后关系的主线：先完成 Runtime Trust / Context Safety，再把“单域分析能力”升级成“跨域经营诊断能力”。两者不是竞争路线。

五大 Skill 源码思想的完整保留版（不是只留一句话）

1. performance-insights｜经营分析中枢

  • Snapshot-first：先建立 headline / compare-to / alerts / coverage，再决定是否下钻；Snapshot 是动态事实块，不属于静态缓存前缀。
  • Comparison discipline：环比、同比、变更前后、同生命周期阶段按问题选择；Partial Period 必须与匹配部分比较或显式声明不完整。
  • Verify movement before explain：先排除缺口、异常基线、口径变化、部分期，再解释原因。
  • Locate segment：先量化哪一组织/渠道/商品/人群贡献主要变化以及 contribution share。
  • Mix vs Level：平均值变化先区分个体水平变化与组合结构变化；没有细分结构时禁止直接归因。
  • Causal alignment：外部原因至少要求时间吻合 + 影响 Segment 吻合；不满足只能降级为 correlation / lead。
  • Evidence language：Finding / Lead / Not visible；Ulike 进一步扩展为 Finding / Lead / Inconclusive / Rejected。
  • Bounded analysis：长尾多维问题可交给只读 Delegate；完整 series 留 Artifact/Presentation，主循环只拿摘要/shape/ref。

2. catalog-listings｜商品治理

  • 巡检标准化：缺失关键属性、描述薄弱、类目矛盾、关键图缺失。
  • 任何商品属性必须来自商品记录或用户本轮明确输入；“大概率如此”仍是未知。
  • 评论/客服文本保持 Evidence 身份，不直接升级为商品事实。
  • 批量修复先展示 1–2 个样本，确认模式后再分批 Stage；顺手发现的问题不得混入原 Proposal。

Ulike 裁决：先做 Product Evidence Profile + content-quality audit；自动改标题/上下架不进入当前 P0。

3. inventory-operations｜库存与经营简报

  • Daily Brief 并行读取经营快照、库存/履约告警、pending changes 等；“昨天的总结”不是事实源。
  • 排序优先级是 Money at Stake → Decision Window，不按哪个工具先返回排序。
  • 强制压缩为 3–6 项真正需要决策的事项，其余折叠。
  • 滞销明确 Leave / Mark down / Pull 三叉决策，且每条建议必须展示决定性数字。
  • 补货、售罄天数等衍生数字必须可复算，输入与公式可追溯。

4. pricing-promotions｜可行域内定价

  • 先读 Pricing Context：现价、成本/服务端 margin、允许区间、max delta、max discount、demand signal。
  • caps 先说后动；超限请求明确指出上限并给合规候选，不能“先 Stage 试试看”。
  • Margin 只引用服务端结果，不由模型心算；Floor/Protected fields 由 Code Gate 硬拦。
  • 最小动作原则：更小幅度、更窄范围、更短窗口优先；非降价方案可先于降价。
  • 促销 Stage 前必须 Scope + Depth + End Date 完整。

5. marketing-campaigns｜营销与预算

  • Campaign shape = Audience Intent + 单一可测 Objective。
  • Attributed Revenue 是渠道归因口径，不等于真实因果增量；无对照组必须显式声明无法剥离自然转化。
  • 窗口太短/花费太薄时，不强行评判，给出“何时值得再次读取”的日期/条件。
  • 默认总预算固定：建议 A 加码必须说明 B 减码；除非业务明确允许总预算扩张。
  • 问什么 Stage 什么：文案更新不得顺带修改预算，预算调整不得顺带替换文案。

五技能之间真正的关系

不是 5 个平行 Agent：performance-insights 是诊断中枢；Product / Inventory / Pricing / Marketing 是证据域与动作域。它们应该在 Ulike 中体现为 Skill + Operator + Evidence Provider + Action Handoff，而不是会话 Handoff。

因此：经营分析不是“更长的销售报告”，而是“跨域验证经营假设并形成受约束决策候选”的 Runtime。

04经营诊断方法论：统一成一条可执行纪律链

把 Merchant 的分析师素养与 Ulike 的机器算子治理结合起来。方法论负责“为什么选这个分析”，Operator 负责“怎么算”。

1
Scope & Time Resolution

明确组织、指标、业务对象、时间语义、粒度和权限；缺失会改变结论的输入则澄清。

2
Operating Snapshot

先给 headline 指标、基准期、变化、coverage、alert counts、limitations，建立经营基线。

3
Verify Movement

优先排除部分期、缺口、异常基线、口径变化；“异常不成立”就停止归因。

4
Comparable Selection

按问题选择上期/同期/变更前后/同生命周期阶段；Partial 对 Partial，不凭记忆造 Comparable。

5
Locate Segment

先找哪个组织/渠道/品线/商品/人群贡献了主要变化，并量化 contribution share。

6
Mix vs Level

平均值变化必须区分个体水平变化与结构占比变化；没有结构数据时明确“无法区分”。

7
Hypothesis Generation

基于已知证据形成候选原因，不把候选写成结论。

8
Cross-domain Evidence

Marketing / Product / Inventory / Pricing / Customer / Supply 只在它们能验证当前 Hypothesis 时被调用。

9
Causal Triangulation

时间对齐 + Segment 对齐 + 机制方向一致 + 反证检查；不满足则降级为 correlation/lead。

10
Evidence Grade

FINDING / LEAD / INCONCLUSIVE / REJECTED，每级绑定证据或缺口。

11
Goal / Pace & Seasonal Context

只有用户或受治理 Memory 明确给过目标/季节模式时才做 pace report：当前进度、期间已过占比、剩余所需节奏；没有目标绝不补造。判“异常”前允许读取已声明季节模式，但它只是比较上下文，不替代当前 Evidence。

12
Business Impact & Recommendation

量化金额、风险窗口、目标差距；推荐满足目标的最小动作，不越过 DecisionFeasibleSpace。

13
Presentation / Handoff

ReportIR 展示 Evidence；Action Chip 只携带已验证 refs + 参数 + rationale，进入下一工作流。

必须代码化的三组核心经营分析公式

A. Mix / Level / Interaction：设细分 i 的价格/均值为 P_i，权重/销量占比为 W_i：

ΔP̄ = Σ W_i0 · (P_i1 - P_i0)          # Level Effect
    + Σ P_i0 · (W_i1 - W_i0)          # Mix Effect
    + Σ (W_i1 - W_i0)(P_i1 - P_i0)   # Interaction

这类拆解应由 Operator 计算。模型只解释结果，不能把“大盘均价下降”直接写成“降价”。

B. Goal Pace：

required_remaining_pace = (target - achieved_to_date) / remaining_time_units

只有目标来自用户、受治理 Memory 或业务系统时才允许计算；目标缺失时不得编造。

C. Recommendation Ranking：建议采用透明多因素评分，不强制唯一公式：

priority = f(business_impact, evidence_confidence, feasibility, reversibility, decision_window)

其中任何一项都必须可追溯到 Evidence / Constraint；不要把模型的主观偏好当分数。

07 Adaptive Orchestration + Operator-first + Bounded Delegate

这是吸收 Merchant run_analysis 后最重要的边界：高频分析沉淀为 Operator，长尾分析才委托。

Quick Path

  • 简单问数、单一业务快照、单指标比较、一个或少量标准 Operator。
  • 不强制 Planning；不强制 Summary；满足 Result Contract 直接 Finalize。
  • 仍遵守 Semantic / Evidence / Permission / Fence。

Deep Path

  • 多假设、跨域归因、管理层经营复盘、复杂报告。
  • 进入 Dynamic Planner / Hypothesis Ledger；允许 bounded read-only Delegate。
  • 规划是可审计 DAG，不是多 Agent handoff。

走 Operator

  • 算法/公式明确，可确定性实现。
  • 高频重复出现，需要稳定回归。
  • 需要严格 DQ / causal policy / stop condition。
  • 可用标准 Contract 表达输入输出。

例：趋势、峰值、贡献、生命周期、价量、漏斗、库存覆盖、ROI、Mix/Level。

走 Bounded Delegate

  • 长尾、多维、临时组合，Operator 尚未标准化。
  • 需要 ad-hoc SQL / Python，但只读即可。
  • 输入范围、row/byte/time/round budget 可被硬限制。
  • 必须从结构化 submit_analysis 单出口返回。

例：“高复购用户买 A20 后 60 天的第二品类偏好与去年同期差异”。

DIALECTICAL DECISION 采用“双表示”：raw evidence / raw hash 永不修改；只有送入 LLM 的 model_view 做 NFKC、zero-width/bidi/control、forged role、tool/transcript tag、fixpoint fence 清洗与长度 cap。

验收：投毒样本、嵌套标签、Bidi、伪造 assistant/system 轮次、正常中文误伤、hash 可追溯全部进入安全回归。

R1 · Prompt / Context Assembly｜稳定前缀但不牺牲权限

CURRENT-MAIN FACT Planning/Executor/ReAct 仍存在 {{date}} / {{files}} / {{query}} 等动态渲染；文件列表会随执行增长。

DIALECTICAL DECISION 建 ContextEnvelope：Global Static → Session Stable → Volatile Tail。工具集合不是“全系统固定”，而是由服务端基于 tenant/scenario/permission 解析出的 ExecutionProfile 内保持稳定。

验收：静态段字节稳定；同 Profile tool signature 稳定；动态 Snapshot/files 不进入静态块；缓存收益只看真实 provider telemetry。

R2 · ToolResultEnvelope / held taxonomy｜不是从零新建

CURRENT-MAIN FACT 当前 contracts/tool-result/v1 已明确 Java 工具主链接线，Python 为契约消费者；Java/Python 都已有 Envelope 实现。

DIALECTICAL DECISION 后续工作是把 held / blocked / degraded / failed / timeout / security 语义跨 Java/Python/Host 收口，并让 Fencing、Provenance、Guardrail、Approval 共享统一挂载点。

不做：创建第二套 ToolOutcome/Envelope v2 作为平行事实源。

R3 · function_call vs struct_parse｜先 A/B，后切换

CURRENT-MAIN FACT 默认配置仍为 function_call_type: struct_parse，同时 LLM 适配层已经存在 function_call 分支。

VERIFY 不假设原生 tools 必然更好。用同一 Eval 集比较：schema 成功率、工具选择准确率、重试率、输入 token、cache hit/miss、TTFR、端到端完成率。

R4 · Eager Dispatch｜条件式优化

只有当流式解析能可靠识别“完整且唯一”的 tool-call 边界，并且 tool execution 具备幂等/去重保证时才启用。否则提前派发会把性能优化变成重复副作用风险。

验收：TTFR/TTLT A/B、duplicate execution=0、parse retry、取消/超时、多个工具乱序事件。

R5 · Memory / Compaction｜复用 Open WebUI 基础

CURRENT-MAIN FACT Open WebUI 已有 turn 后异步 memory review；真正缺口是 Ulike tenant/permission/retention/delete 语义、业务目标/季节模式事实类型，以及与 ContextEnvelope 的治理集成。

历史压缩前置条件：Provenance/关键状态必须存在 RunState/Evidence 中，而不是只活在早期 tool result 文本里。

11产品体验：经营分析不是“更长的报告”

Merchant Agent 最值得借鉴的产品变化，是让经营分析从被动报告升级为“发现问题 → 解释 → 下一步”。

Operating Attention Digest

首页/晨会入口只展示 3–6 个最重要经营事项，按 Money at Risk → Decision Window 排序：

  1. A20 库存覆盖仅 6.2 天，潜在 GMV 风险…
  2. 抖音 ROI 连续三日低于目标，消耗风险…
  3. AIR3 退款异常，主要集中…
  4. 某供应商延期影响核心 SKU…
  5. 待审批经营提案…

每条都有 Evidence、未知项和唯一 Next Action。

经营分析 Result 最小结构

  1. Takeaway：一句话结论 + baseline。
  2. Key figures：从 Evidence/Run Snapshot enrich。
  3. Hypotheses：Finding/Lead/Unknown/Rejected。
  4. Limitations：Partial period / missing domain / causal boundary。
  5. Business impact：金额/风险窗口/目标差距。
  6. Next actions：1–4 个参数化 Handoff。

现有 Open WebUI 的“营销诊断 / 用户经营 / 商品分析 / 销售复盘 / 供应链 / 经营报告”入口保留；变化在于它们不再是孤立页面，而是同一个 Business Diagnosis Runtime 的不同 Skill / Operator / Evidence Provider。

Scheduled / Headless Digest（只读）

借鉴 Merchant 的 morning digest，但不复制其脚本结构：由 Ulike Task/Run 调度一个只读经营诊断 Run，固定输入“今日最需要决策什么”，读取同一 OperatingSnapshot + Alerts + Pending Approvals，生成结构化 Digest Artifact / ReportIR。定时任务只负责发现与排序，不自动执行写动作；需要动作时只生成 ActionHandoff。

12唯一实施路线图

仍然只有一条路线，但本版将“Runtime Trust / Context Safety”提前为硬前置。每个 Batch 只解决一个层级的问题；安全正确性可与 Runtime Live 验证并行，性能优化不得越级。

Batch 0｜Runtime Truth + Immediate Trust Foundation

硬前置 ① 让 Dynamic Planner 新主链真实运行：镜像/真实 DB/SALES-001/Open WebUI/人工质量复核；② 建立 Runtime telemetry；③ 立即落地 External Content Fence；④ 建立 PromptAssembler 的 Global/Session/Volatile 分层；⑤ 生成 Server-resolved Execution Profile，消除 per-step 工具集漂移；⑥ 记录 DeepSeek cache hit/miss tokens 与 tool-set signature。Batch 0 的出口是“真实跑 + 输入可信 + 可测量”。

Batch 1｜经营诊断内核（产品最高优先）

P0 OperatingSnapshot + period completeness + comparable selection + Mix/Level + ulike-business-performance-insights + HypothesisLedger。目标：把 Sales Analysis Engine 升级为“会验证 movement、会选择 baseline、会管理假设”的 Diagnosis Engine。

Batch 2｜跨域 Evidence + Runtime Trust 收口

P1 Marketing/Product/Supply 首批 Evidence Provider；causal-triangulation；RunProvenanceLedger；Server-side Presentation refs；Result Slimming；ToolResultEnvelope 跨 Java/Python/Host 一致性与 held/error taxonomy。目标：让“原因”跨域可证，让 UI/Action 引用可约束。

Batch 3｜Decision Handoff + Operating Digest

P1 ActionHandoff、recommendation ranking、Business impact、晨会 Digest。只读/无副作用；用真实经营 Case 验证“发现→解释→下一步”产品闭环。

Batch 4｜Controlled Action Runtime

P2 ActionProposal → DryRun → Diff → Approval → revalidate → Execute → Receipt → Outcome Evidence；优先低风险内部动作/配置，高风险价格/预算/外发保持 L3 HITL。Provenance、当前配置重校验、幂等和审计必须先于任何 live write。

Batch 5｜规模化、性能与进化治理

P2+ function_call vs struct_parse A/B；满足前置条件时 Eager Dispatch；Skill Runtime 按需加载；history compaction；Ulike-governed Cross-session Memory；Bad Trace→Snapshot Eval；Business Outcome Learning。

优先级原则

Runtime Truth & Safety
        > Diagnosis Quality
        > Cross-domain Evidence & Provenance
        > Decision Handoff
        > Controlled Write Capability
        > Protocol / Latency / Cache / Memory Optimizations
重要：Batch 0 与 Batch 1 可以在不同工程流并行开发，但任何 Batch 1+ 的“效果结论”都必须建立在 Batch 0 的真实 Runtime telemetry 上；否则只能称 Static Design，不能称收益已验证。

Commerce Agent 六层责任栈

  1. Reasoning：模型做目标理解、权衡、下一步选择。
  2. Procedure / Skill：低频复杂 SOP 按需加载，不承担权限。
  3. Capability / Tool：薄接口连接企业已有系统；不复制排序/库存/价格真相。
  4. Backend / Semantic：事实、规则、权限、凭据留在服务端。
  5. Harness / Gates：会话状态、Fence、Provenance、Caps、Approval、流式事件。
  6. Presentation：模型给引用与注释，服务端校验/enrich，客户端固定组件渲染。

规则归位四分法

  • 单工具参数规则 → Tool Description / Schema。
  • 高频、跨大多数请求的行为规则 → Static System Prompt。
  • 低频复杂流程 → Skill / Playbook，按需加载。
  • 钱、权限、库存、价格、外部输入、不可逆副作用 → Harness / Backend Code Gate。

Ulike 进一步增加：Planner/Operator/Contract/Evidence 是参考实现没有完整表达的治理层，应保留。

三断点与 Context Economy

  • 静态 System 块：部署生命周期内字节稳定。
  • 工具/Schema 块：在可信 ExecutionProfile 内稳定。
  • 滚动历史断点：让长 tool results / prior rounds 尽可能复用前缀。
  • 小时级时间只是参考实现的缓存技巧；Ulike 是否采用取决于业务时间精度，不能让缓存优化篡改事实精度。
  • History Compaction 必须晚于状态外置与 Evidence/Provenance 落地。

Safety Chain

Untrusted Text → Fence/model_view
Read Tool → server-issued IDs / Evidence
Write/Present → Provenance check
Proposal → Guardrail(stage)
Approval → Guardrail(apply, current config)
Execute → Receipt / Audit / Outcome Evidence

held ≠ error：安全门禁应返回可恢复的结构化结果，让模型补读/修正，而不是让整个 Turn 崩溃。

Bounded Delegate 四条边界

  • 只读；无写/Stage/Presentation 权限。
  • SELECT-only / 单语句 / 行数、字符、时间、轮数 Budget。
  • 唯一结构化出口 AnalysisResult。
  • 完整大数据不回主上下文，只回 headline/findings/shape/ref。

Snapshot Eval 的真正价值

  • 断言终态/工具参数/渲染结果，而不是要求模型走固定思维路径。
  • 正负成对：每个应该执行的 Case 都有一个应该拒绝/停止/降级的 Case。
  • 线上事故 1:1 固化成回归资产。
  • CI 只跑核心+安全+邻域，nightly/release 跑全量，降低组合爆炸。
