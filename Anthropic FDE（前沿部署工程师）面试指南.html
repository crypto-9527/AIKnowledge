一分钟速览

  • Anthropic 当前美国 FDE 岗位年薪为 28 万至 32 万美元，买的不是提示词技巧，而是把 Claude 送进客户生产系统的能力。
  • FDE 的完整闭环是发现工作流、划定风险边界、构建、评测、上线，再把现场模式反馈给产品。
  • 面试真正筛的是五种能力能否合在一起：生产代码、Agent 架构判断、评测证据、客户管理和安全工程。

Anthropic 正在招聘一批有些反常的工程师。

他们不只在模型公司内部写代码，还要进入客户的系统，和银行、医疗机构、政府部门及大型企业的团队一起工作。Anthropic 当前美国 FDE 岗位列出的年薪是 28 万至 32 万美元，另有股权。

一家拥有前沿模型的公司，为什么还要花这么高的价格，招聘一批深入客户现场的人？

这份 FDE 面试指南表面上在告诉候选人如何准备招聘流程，真正透露的却是一项更重要的变化：当模型能力越来越强，AI 落地最稀缺的已经不是“会调用模型的人”，而是能把客户混乱的工作流程改造成可评估、可控制、可上线系统的人。

Anthropic 花高价购买的不是提示词技巧，而是把模型能力送过最后一公里的能力。

FDE 到底是什么？

FDE 是 Forward Deployed Engineer，通常译作前沿部署工程师或前线部署工程师。

这个职位最早因 Palantir 出名。它不是传统驻场外包，也不是只画架构图、做演示的售前岗位。FDE 要直接进入客户环境，把一个模糊的业务愿望变成能够运行的生产系统。

Anthropic 把 FDE 放在 Applied AI 团队。官方职责包括在客户系统中构建 Claude 生产应用，交付 MCP servers、sub-agents 和 agent skills，提供企业部署支持，并把反复出现的现场模式反馈给 Product 与 Engineering。

把这个岗位放到当前招聘信息里看，轮廓更清楚：

  • 岗位职责与资格要求：需要生产 LLM 应用经验、扎实的 Python、客户沟通与发现能力、高自主性，以及在企业环境里交付系统的经验；
  • 主要交付物：Claude 应用、MCP servers、sub-agents、Agent Skills，以及可以跨客户复用的部署模式；
  • 当前美国年薪：28 万—32 万美元，另有股权；
  • 工作方式：预计约 25% 的客户现场出差，至少 25% 的时间在办公室；
  • 面试中的 AI 使用：可以用 Claude 准备，但现场面试默认由本人独立完成；assessment 除非明确允许，也不能交给 AI 代写。

这些工作不是互不相干的任务，而是一条首尾相接的路径。

FDE 如何把一次客户项目变成可复用产品能力？

FDE 从客户工作流出发，确定风险边界，构建 Claude 系统，用 eval 验证并推动上线，最后把重复模式反馈给产品和工程团队。

最后一步决定了 FDE 不是普通外包。咨询项目结束后，经验可能只留在报告里；定制开发结束后，代码可能只服务一个客户。FDE 还要继续问：这次解决的问题，能不能变成下一百个客户都能使用的 MCP、Skill、评测套件或产品功能？

FDE 因而也是 Anthropic 的外部产品研发机制。

如果想继续理解企业为什么“用了同一个模型，结果却完全不同”，可以从部署条件而不是模型参数继续往下看。

为什么一家模型公司需要 FDE？

因为“模型很强”和“企业真的能用”之间，隔着一条很宽的鸿沟。

假设一家银行找到 Anthropic，说：“我们想做一个合规 Agent。”这句话听上去目标明确，实际上几乎没有可执行信息。FDE 必须继续追问：

  • 到底是哪一个合规流程？
  • 使用者是调查员、审核员，还是客户经理？
  • 系统只是检索、摘要和起草，还是可以修改记录、发送消息甚至冻结账户？
  • 哪些系统保存权威数据，数据是否完整、及时、可信？
  • 用户权限如何传递给 Claude 调用的工具？
  • 模型答错一次的实际代价是什么？
  • 哪些动作必须由人审批？
  • 上线成功看节省时间、召回率、误报率，还是案件完成率？

真正困难的不是写一句“你是一名资深合规专家”，而是把这些问题落实为身份权限、工具接口、数据过滤、审计记录、评测任务、人工审批和回滚机制。

这也是 Context Engineering 与普通 Prompt Engineering 的差别。Anthropic 对它的定义不只包含提示词，还包括系统指令、工具、MCP、外部数据、消息历史和不断变化的 Agent 状态。模型负责推理，不代表模型应该负责认证、权限过滤、重试、数据校验和高风险动作审批。

评测同样不能只看最后一段回答是否顺眼。Agent 声称“案件已经更新”，真正要检查的是后台记录是否改变、权限是否正确、审计轨迹是否完整。Anthropic 的 Agent eval 框架把完整轨迹与最终环境状态分开，正是因为一句成功声明不等于任务真的完成。

所以 FDE 的工作不是把 Claude 接进企业，而是决定 Claude 在什么边界内、凭什么证据、以什么方式进入企业。

它和几个相近岗位有什么不同？

FDE 容易被误认成软件工程师、Solutions Architect、AI 应用工程师或咨询顾问。它确实吸收了这些岗位的一部分，但主要产出和失败方式不同。

FDE 最难替代的部分，是同时承担生产交付和跨客户模式沉淀。

FDE 与 SWE、Solutions Architect、AI 应用工程师和咨询顾问究竟差在哪？

FDE 同时承担高客户接触和高编码责任，主要产出是客户生产系统与可复用部署模式；它的典型失败是做成无法产品化的一次性定制。

最关键的差别不只是“既懂技术又懂客户”。FDE 还是产品侦察兵。

他站在模型能力与客户现实发生碰撞的地方。哪些工具不好用，哪些权限模型缺失，哪些 Agent 行为难以评估，哪些需求在不同客户那里反复出现，他往往比内部产品经理更早看到。

高级 FDE 与普通项目交付者的分界也在这里。前者会把一次部署提炼成可复用模式；后者可能成功完成一个项目，却让下一位工程师从头再来。

给你一个模糊、敏感、跨系统的企业任务，你能不能在没有完整剧本的情况下，把它变成一个客户敢用的 AI 产品？

五类面试能力为什么必须同时出现？

FDE 面试的五类信号分别证明系统能构建、架构有边界、结果可验证、客户目标被正确收缩、安全控制进入生产；缺少任一项都难以建立客户信任。

1. 你能不能真的写代码

FDE 不是只负责开会、做需求和画架构图。Anthropic 的官方职位要求写得很明确：候选人需要熟练使用 Python，最好还掌握 TypeScript、Java 等语言，并且有交付生产应用的经验。

这轮不应只按 LeetCode 准备。原指南给出的高频题型更接近真实交付：

表 3 · Coding 轮高频题型与真实考察点
题型可能任务真正考察
API 集成拉取分页 CRM 数据，处理限流、超时和异常记录API 基础、错误处理、数据校验
MCP / 工具实现带 metadata filter 的文档搜索工具schema、最小数据返回、工具边界
Eval 脚本计算分类通过率并列出失败样本指标设计、切片与可复现性
Trace 分析找出失败调用、缺失引用和重复循环调试纪律、状态与工具调用理解

可靠性为不稳定 API 加指数退避、超时和结构化错误重试策略、幂等与失败语义

所谓生产能力，不只是实现正常流程。它包括 API、认证、权限、分页、超时、重试、幂等、日志、测试、secrets 管理和异常数据处理。面试官还会观察你是否主动询问输入规模、脏数据、失败后的行为，以及凭什么判定任务成功。

一套稳妥的现场答题顺序是：

  1. 1用自己的话重述任务，确认你没有理解错；
  2. 2询问输入格式、数据规模、认证方式、延迟和异常情况；
  3. 3先定义成功、失败、重试和升级分别返回什么；
  4. 4实现最简单且安全的版本，不提前堆架构；
  5. 5补正常、边界、无权限、重复数据和工具失败测试；
  6. 6说明生产强化方案：日志、观测、secrets、限流、幂等与审计；
  7. 7把这段代码放回客户工作流，解释它和上下游系统怎样连接。

一个普通回答可能是：“我会给企业文档做一个 RAG，再让 Claude 调用搜索工具。”接近 FDE 的回答还要处理：谁执行文档权限过滤？工具失败后如何恢复？哪些数据没有必要进入模型上下文？写操作如何防止重复执行？怎样确认 Agent 声称完成的动作真的改变了后台状态？

比如让你实现一个文档搜索工具，强回答不会马上开写，而会先确认权限由上游还是工具内部执行。即使上游已经过滤，也可以在工具层再次校验 ACL；返回结果只包含模型完成任务需要的字段；测试覆盖空结果、无权限文档、损坏 metadata 和重复 ID。这个过程比“我用了向量数据库”更能证明生产判断。

面试官不是只看代码能不能跑，而是看客户能不能信任这段代码。

2. 你能不能设计 Agent，而不迷信 Agent

成熟候选人不会听到需求后立刻宣布：“我们做一个多 Agent 系统。”

他会先判断，这个任务是否真的需要自主循环；普通工作流加一次模型调用是否已经足够；哪些环节必须由确定性代码负责；哪些判断适合交给 Claude；哪些动作必须由人确认。

这一轮可能让你设计企业客服助手、CRM MCP server、尽调 sub-agents、受监管报告 Skill，或者让你诊断一个在两个工具之间反复循环、不断读取旧数据的 Agent。

“我会优化提示词”已经不是充分答案。候选人必须能讨论上下文选择、工具 schema、结构化输出、身份与权限、状态管理、沙箱、日志、失败恢复和系统复杂度。

遇到完整系统设计题，可以沿着十步框架推进：

  1. 1澄清工作流：谁在什么频率下完成什么任务，失败代价是什么；
  2. 2定义成功指标：正确率、完成率、节省时间、升级率、采用率和安全指标；
  3. 3画出数据与系统：文档、数据库、CRM、API、IAM、所有者和数据新鲜度；
  4. 4划定动作边界：只读、起草、建议、写入和自动执行分别到哪一步；
  5. 5选择架构：Claude、检索、工具、MCP、Skills、sub-agents 与确定性代码如何分工；
  6. 6加入安全控制：认证、最小权限、secrets、PII、数据流与审计；
  7. 7设计 eval：golden tasks、边界样本、trace review、outcome grader 和回归集；
  8. 8设计观测：工具失败、循环、延迟、成本、用户反馈和生产状态；
  9. 9制定上线计划：试点用户、人工审核、通过门槛、扩张条件与回滚；
  10. 10形成产品回路：哪些能力可复用，哪些平台缺口要反馈给 Product 与 Engineering。

一个强答案通常会明确说：认证、权限过滤、重试和数据校验交给确定性代码；Claude 负责需要语义理解与推理的部分；工具只暴露窄接口；高风险写操作要求人工批准。先用一个工作流做试点，查看真实 trace 和 outcome，再决定是否增加 Agent 自主性。

很多时候，最好的 Agent 设计恰恰是删掉不必要的 Agent。

3. 你能不能把“效果不错”变成证据

Agent 最后输出“任务已经完成”，不代表任务真的完成。正确的验证对象可能是数据库中是否出现记录、文件是否正确生成、工单是否进入目标状态，或者用户权限是否真的得到执行。

Anthropic 对 Agent eval 的官方解释区分 task、trial、grader、trace 和 outcome。能力评测回答“系统现在能做到什么”，回归评测回答“它是否还能稳定完成过去已经会做的事”。

评测对象应该检查什么常见误区
Task是否来自真实用户工作流，是否写清成功条件用几个漂亮问题代替任务分布
Trial同一任务多次运行是否稳定一次成功就宣布能力成立
Grader规则、状态检查、人工或模型评分是否适合目标所有结果都交给语言模型主观打分
Trace工具选择、参数、循环、引用和中间状态是否合理只看最终文本，不看失败路径
Outcome数据库、文件、工单和权限状态是否真的正确Agent 说“完成”就算完成
Regression修改模型、工具或上下文后旧能力是否退化只测新功能，不保留历史失败集
增强 · 一手术语校准

Anthropic 官方 eval 术语（逐条对照）

原文表格的中文口径与 Anthropic 工程博客《Demystifying evals for AI agents》的官方定义完全一致。补全官方英文原义后，术语边界更清晰：

表 7 · 官方术语定义（依据 Anthropic Engineering 一手文档整理）
术语官方定义要点易错点
Task单个测试，含明确的输入与成功判定标准（同义：problem / test case）把「几个漂亮问题」当成任务分布
Trial对同一任务的一次完整尝试；因输出存在随机性，需跑多次以获得稳定结果用单次运行推断能力
Grader对 Agent 表现某一维度打分的逻辑；一个 Task 可含多个 Grader，每个含多条断言（checks）全部交给 LLM 主观打分
Transcript
（trace / trajectory）		一次 Trial 的完整记录：输出、工具调用、推理、中间结果与全部交互。在 Anthropic API 中即评测结束时的完整 messages 数组只看最终文本，不查失败路径
OutcomeTrial 结束时环境的最终状态——不是 Agent 说了什么，而是数据库里有没有那条记录Agent 声称“完成”即判定完成

官方原例：一个订机票 Agent 可能在 transcript 结尾说 “Your flight has been booked”，但真正的 outcome 是环境的 SQL 数据库里是否真的存在这条预订记录。原文将此改写为「Agent 声称案件已经更新」的合规场景——语义一致，属本地化改写。

面试中如果被要求为客服 Agent、合规助手或报告生成系统设计评测，可以按六步回答：

  1. 1从真实工作流定义 task，不从“回答看起来不错”开始；
  2. 2用历史案例建立 golden set，再加入缺失数据、冲突来源、无权限和工具失败等边界样本；
  3. 3为不同目标选择 grader：规则校验、状态检查、人工评分或模型评分；
  4. 4同一任务运行多次，区分偶然成功和稳定能力；
  5. 5同时检查 trace 与 outcome：它如何完成，以及后台结果是否真的正确；
  6. 6把失败按类型切片，形成回归集和上线门槛。

指标必须跟任务变化。客服场景可以看解决正确率、引用质量、升级准确率、工具成功率、延迟和用户采用；合规场景还要看证据完整性、政策引用、误升级风险、幻觉事实和审计完整性。高风险写操作不能只靠语言 grader，应该直接检查数据库、文件、工单或权限状态。

所以候选人不能只展示几个成功截图。他必须能回答：系统在哪些真实任务上成功？同一任务重复运行是否稳定？哪类失败最常见？修改模型、工具或上下文策略后有没有退化？最终业务状态是否真的正确？上线阈值由谁决定，没通过时系统如何降级或回滚？

没有 eval，“效果很好”通常只是演示者的感觉。

4. 你能不能管理客户，而不只是服从客户

这项能力从 recruiter screen 就开始被判断。你至少要准备五类问题：为什么 Anthropic、为什么 FDE 而不是 SWE 或 Solutions Architect、最成熟的生产 AI 系统、最难的客户部署，以及你如何理解安全 AI 落地。

弱回答是“我做过 Claude 聊天机器人”“我有客户经验”“我会 Prompt Engineering”。强回答会说清完整链条：客户原本要解决什么工作流，你如何发现真实瓶颈，亲手构建了哪些集成，怎样处理权限与风险，用什么 eval 判断能否上线，最后产生了什么结果或产品反馈。

客户说“我们要在 30 天内向全公司上线自主 Agent”，并不意味着 FDE 的工作是点头，然后拼命赶工。

5. 你能不能让安全进入架构

对 Anthropic 来说，“我认同 AI 安全”不是有效答案。

真正的安全判断要落到最小权限、敏感数据边界、工具调用范围、高风险动作审批、审计记录、上线评测、生产监控、异常升级和回滚机制。

一个医疗 Agent 如果只是帮医生整理文献，和一个可以直接修改患者用药记录的 Agent，不能使用同一套上线标准。能力相同，动作权限不同，风险等级就完全不同。

FDE 需要明确系统可以读什么、可以判断什么、可以写什么，以及在哪一步必须停下来交给人。这才叫安全工程。

这件事更大的意义

Anthropic 设置 FDE，不只是新增了一个高薪岗位。它说明前沿模型公司的竞争正在从“谁的模型能力更强”，延伸到“谁能让模型进入最复杂、最昂贵、最敏感的真实工作流”。

模型能力越来越容易获得，客户环境却不会因此变得整齐：

  • 每家公司都有不同的身份和权限系统；
  • 企业数据普遍残缺、重复、过期或互相冲突；
  • 实际流程和管理层想象的流程经常不是一回事；
  • 安全、法务、IT、采购和业务部门的目标彼此冲突；
  • Agent 的失败往往发生在多个工具和多轮状态之间；
  • 一个成功 Demo 离组织真正采用还有很远。

FDE 的稀缺性来自一种很难标准化的能力：既能深入代码，又能理解组织；既能推动上线，又敢限制自动化；既解决一个客户的问题，又不把公司拖进无底洞式定制开发。

它还承担模型公司的现场学习功能。如果不同客户反复要求相同的权限控制，平台可能缺少统一授权能力；如果多个 Agent 都在同一种工具调用上失败，工具设计可能存在问题；如果某类工作流始终无法建立可靠 eval，产品也许还没有资格承诺自动化。

这些信息从客户现场流回产品和工程团队，才可能变成下一代平台能力。FDE 不是站在产品交付链的末端，而是把交付现场重新接回产品起点的人。

这也是这份面试指南真正透露出的反直觉结论：

AI 越通用，最后一公里反而越需要高水平的人。
不是因为 Claude 不够聪明，而是因为企业现实无法被一个通用提示词自动整理干净。

FDE 就是站在这片混乱里，把模型能力变成可信结果的人。

沙盘 1 · 五维能力自评雷达 增强

原文的核心论断是「面试找的是五种能力能否在同一个人身上闭合」——缺任一项都难以建立客户信任。这个沙盘把「闭合」变成可计算的量：你的自评是唯一输入，所有输出均由公式实时推导，不含任何预置基准值。

S1五维能力闭合度

按 0–5 分为五个维度自评。评的是「能否在面试中拿出可验证证据」，而非自我感觉：0 = 无证据；3 = 有项目但说不清取舍；5 = 有生产结果、有量化收益、有失败复盘。

综合准备度 = 五维均值 / 560.0%
木桶短板—
均衡度 = 1 − 极差/5100.0%
闭合度 = 均值 × 均衡度60.0%

公式与口径：设五维自评 s1..5 ∈ [0,5]。综合准备度 = (Σsi / 5) / 5；极差 = max(si) − min(si)；均衡度 = 1 − 极差/5；闭合度 = 综合准备度 × 均衡度。
防造假声明：本沙盘不输出任何「你的通过率是 X%」之类无源结论——所有数值 100% 由你的滑块经上述公式实时算出，不存在预置基准或经验拟合。

沙盘 2 · 稳定性计算器 增强

原文反复强调「同一任务运行多次，区分偶然成功和稳定能力」。Anthropic 官方给了两个互补指标：pass@k（k 次中至少成功一次）与 pass^k（k 次全部成功）。二者之差，就是从「Demo 惊艳」到「生产可信」之间的那段距离。

S2pass@k 与 pass^k 的剪刀差

拖动单次成功率 p 与尝试次数 k，观察两条曲线的分离速度。面试含义：用 pass@k 讲故事会系统性高估系统可靠性；面向客户的 Agent 活的是 pass^k。

pass@k（至少成功一次） pass^k（全部成功） 当前 k 位置
pass@k（≥1 次成功）—
pass^k（k 次全成功）—
剪刀差 Δ = pass@k − pass^k—
pass@k = 1 − (1 − p)k      passk = pk

定义来源：Anthropic Engineering《Demystifying evals for AI agents》官方给出 pass@k 与 pass^k 的定义。
关键假设（必须显式声明）：上式成立需要「各次 trial 相互独立且单次成功率恒为 p」。真实 Agent 的失败常具有相关性（同一段脏数据、同一个坏工具、同一处权限缺失会连续触发），因此真实的 pass^k 通常优于 pk，而 pass@k 通常劣于 1−(1−p)k。本模型是独立同分布下界 / 上界的基准，不是真实系统的预测值。
面试用法：被问「你们的 Agent 准确率多少」时，反问「你说的是 pass@1 还是连续 k 次的稳定通过率」——这正是原文「Trace / Trial / Outcome」三章要你区分的。

沙盘 3 · 上线门槛样本量反解 增强

原文多次出现「上线门槛由谁决定」「达到什么门槛才能扩大范围」，但从未给出门槛该定在多少。这个沙盘把它变成一个可解的样本量问题：要宣称失败率低于某个上限，你究竟需要多少个连续成功的 trial？

S3上线门槛反解器

设定你能容忍的真实失败率上限 ε 与所需置信水平 C，反解出「必须观察到多少次连续成功」才能做出该断言。

观测 N 次连续成功 ⇒ (1 − ε)N ≤ 1 − C ⇒ N ≥ ln(1 − C) ln(1 − ε)
所需连续成功样本量 N（精确解，向上取整）—
Rule of Three 近似 3/ε—
对应需构建的 golden task 数（N 的 1.5 倍）—

推导：若真实失败率为 ε，则连续 N 次全部成功的概率为 (1−ε)N。要让我们能以置信度 C 拒绝「失败率 ≥ ε」，需 (1−ε)N ≤ 1−C，解得 N ≥ ln(1−C) / ln(1−ε)。
Rule of Three（Hanley–Lippman 近似）：C = 95% 时 N ≈ 3/ε，与精确解高度接近（ε = 5% 时精确解 59，近似 60）。
归属声明：这是通用统计推断，不是 Anthropic 官方口径，Anthropic 官方文档未给出具体门槛数值。此处仅用于把「上线门槛」从感觉变成可谈判的样本量要求。
golden task 倍数说明：×1.5 是本次为便于估算而设的演示参数（考虑边界样本占比），无文献出处，请勿当作行业标准。
