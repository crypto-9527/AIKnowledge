Anthropic 官方指南：教你如何在和 Claude Code 对话的时候节省 Token

一个小修复为什么会拖成长会话？这份指南教你看懂额度花在哪里，并在 /clear、/compact、/rewind 与 Subagent 之间做出正确选择。

⚡ 一分钟速览（Executive Summary）
  • 过程材料累积效应：文件、日志和工具结果进入会话后会跟随后续请求；无关内容进入越早、存活轮数越多，额度负担和判断干扰越大。
  • 诊断与优化优先序：处理会话消耗时，先看跨任务长会话，再看无关上下文，然后检查模型与 Effort 是否过高，最后检查提示缓存是否失效。

1. 只改了几行代码，为什么额度已经掉了一截 成本机制拆解

你让 Claude Code 修一个失败测试。最后的改动可能只有三行；在找到这三行之前，它已经搜索了仓库、打开一批候选文件、跑出几百行测试日志，又在错误方向上试了几轮。

这些过程不会在 Claude 找到答案后自动消失。你每让它继续一次，模型都要再次处理此前积累的系统提示、项目规则、文件、命令结果和对话历史。

⚖️ 传统开发工具 vs 编程 Agent 的成本本质差异

这套成本逻辑和传统开发工具不同。传统编辑器往往免费或按月、按年付费，多修一个 Bug 通常不会增加软件账单；编程 Agent 每完成一个任务都要运行模型推理。

无论最终改了几行，它读入和生成的 Token 都会占用 GPU、TPU 等计算资源，同一个任务也会因为使用方式不同而产生巨大的消耗差异。

开发者面临的三个直接痛点

1. 额度流失快且缺乏归因 !

订阅用户通常只看到使用额度变化，很难把消耗精确对应到某个被读取的文件、某段庞大的测试日志或某次无意义的全局搜索。

2. 会话越长旧信息越难摆脱 ~

缓存可以让重复读取更便宜，但旧内容依然占着有限的上下文窗口，也会把 Claude 的注意力拉回已经无关的方向，增加幻觉风险。

3. 命令虽熟悉但使用时机选错 ?

新任务该用 /clear，同一任务换阶段才考虑 /compact，末尾几轮走偏更适合 /rewind；Subagent 能隔离噪声，但也会产生独立的启动成本。

Anthropic 发布这份指南，就是为了系统回答这些会话管理问题。读完以后，你应该能够判断：当前消耗首先来自长会话、无关上下文、模型与 Effort 过度，还是提示缓存失效；也应该知道什么时候直接给文件、什么时候收短日志、什么时候切断历史，以及什么时候值得把工作交给 Subagent。

实证对比：5 次请求 vs 18 次请求的启示

原文用同一个失败测试画出了两条截然不同的解决路径：

交互路径模式 用户输入策略 Claude Code 执行行为链路 总请求轮次
精准输入路径 直接指出测试文件（如 @utils.test.ts） 直接读取测试和实现 → 提交针对性修改 → 运行验证测试 → 输出简要总结 5 次请求完成
模糊探索路径 仅输入“测试挂了” 全局搜索仓库 → 打开多份候选文件 → 运行全量日志 → 沿错误方向试错多轮 → 最终走到同一修复 18 次请求完成

5 次与 18 次只代表官方测试图中的具体场景，不能直接换算成固定成本倍率。它说明了一件更重要的事：代码改动相同，进入会话的过程材料可能完全不同。指南追求的是让 Token 服务于必要的代码、推理和验证，把无关搜索、噪声输出和跨任务残留尽早切断。

请求链路剖析：真实账单究竟怎样形成

五次请求的路径也解释了账单怎样形成：

  • 第 1 轮：提交系统提示、CLAUDE.md 和任务描述；
  • 第 2 轮：Claude 请求读取测试文件，文件结果追加进会话后再次发送；
  • 第 3~5 轮：接着读取实现文件、提交代码修改、运行测试验证，最后生成简短总结。

每一轮都包含此前的完整会话，但正常追加时，旧的连续前缀可以走缓存读取，只有新工具调用、新文件或新测试结果需要按正常输入价格 Prefill。

核心洞察：一次典型调用可能是数万输入 Token，只生成几百个输出 Token。数万输入并不等于全部按正常输入价重算：每轮费用由历史的缓存读取（0.1x）、新增内容的正常输入价（1.0x）和本轮输出价（5.0x）共同组成。理解这一点，才能看懂为什么少一次无意义搜索、中途少切一次模型，可能比压缩最后几十个字更有价值。

2. 先做这六件事 实操准则

如果暂时不想深入研究底层的 Token 计费机制，可以先按下面六条直接调整日常使用方式：

1. 开局选定模型和 Effort 01

机械修改用够用的模型，模糊故障和架构判断再提高能力与工作深度。尽量不要在长会话中途频繁切换。

2. 把已知范围直接交出 02

给出目标文件、失败测试、期望结果和验证命令；界面支持时，第一次就用 @文件名 引用，省去全局搜索与 Read 探测。

3. 严格控制命令输出 03

只跑相关单测，使用 quiet reporter、错误过滤或 tail，别让几百行成功日志留在后续几十轮历史里。

4. 最近走偏立刻 /rewind 04

发现最后几轮走错时用 /rewind。它从会话末尾裁掉错误分支，前面的缓存前缀仍可能继续保留命中。

5. 开始新任务前 /clear 05

旧任务需要以后找回，可以先 /rename 归档，再清空当前上下文开启新任务，切断历史包袱。

6. 过程吵闹才用 Subagent 06

扫描长日志、完整测试输出和 Git 历史适合隔离；主会话只需要结论时才交出去，小任务交出去反而更贵。

影响排位金字塔：优化力度的优先次序

原文最后一张图把影响顺序排得很清楚：先看长会话，再看上下文过多，然后才是模型或 Effort 超过需要，以及提示缓存失效。这个顺序能避免在细枝末节反复节省，却放任旧任务历史每轮重发的根本性失误。

优先级阶梯 排查维度 核心危害机制 治理举措
第 1 优先 跨任务长会话 历史线性累加，被后续所有无关轮次全量重算与携带 按任务边界执行 /rename → /clear
第 2 优先 无关上下文过多 数万字符命令日志、非必要文件过早常驻上下文 静默命令输出、精确 @文件、优化 CLAUDE.md
第 3 优先 模型与 Effort 过度 机械简单任务调用顶配模型，生成与思考过度消耗 开局设定匹配模型与 Effort，避免中途切换
第 4 优先 提示缓存失效 中途变更加载键或 TTL 过期导致前缀无法命中 0.1x 优惠 保持前缀稳定，了解 5分钟/1小时 TTL 边界

4. 第一优先：别让一个会话装下多个任务 任务边界治理

Claude Code 的每一轮请求都会携带截至当时的完整会话内容。第一项任务留下的文件、日志和工具结果，如果继续留到第二、第三项任务，它们就会在后续请求中重复出现。

会话累积负担 ≈ 上下文累计内容 × 后续存活轮数 × 并发上下文数
注：最后再考虑模型系数、Decode 输出与缓存倍率。此为帮助直观理解的近似工程关系式，非精确账单公式。

原文的三任务示意图呈现了这种严重的线性累积效应：

  • 任务 1 的历史：会被带入后续任务 1、任务 2、任务 3 共三轮；
  • 任务 2 的历史：会被带入后续两轮；
  • 任务 3 的历史：带入一轮。

全部塞进一个长会话时，图中的 Token 总量达到了分会话独立治理方案的 1.9 倍。这个数字只属于图中的测试条件，最值得记住的核心法则是：“旧内容会乘上它之后存活的轮数”。

因此，/clear 应该严格跟着任务边界使用。它的准确时机是准备开始新任务，不必等到上下文快满。需要保留旧会话入口时，先 /rename 再 /clear。

/loop 命令的周期监控陷阱：每次循环都是一轮完整的 API 请求。周期监控如果挂在一个很长的主会话里，会定期全量携带整段历史重新 Prefill；单独开一个干净的新会话，只放循环真正需要的精简材料才合适。

5. 第二优先：别让无关内容过早进入会话 底噪控制工程

会话的初始负担早在第一条任务消息之前就可能形成。工具定义、系统提示、CLAUDE.md 和启用的 MCP 服务都可能进入上下文。新会话可以先运行一次 /context，检查启动时究竟加载了什么；当前用不到的 MCP 服务，可通过 /mcp 检查并关闭。

CLAUDE.md 的准入与修剪边界

长期适用且足够短的项目规则适合放进 CLAUDE.md。只在特定流程使用的长篇说明更适合按需手动加载。判断标准非常简单：常驻内容是否值得在每一轮对话中都出现并消耗额度。

任务描述精度与 @文件名 机制深度剖析

任务描述也决定了 Claude 是否需要重新发现你已经知道的范围：

  • “测试失败了”：会触发全局仓库搜索和候选文件试探；
  • “修复 utils.test.ts”：可以省掉绝大部分搜索；
  • 在支持文件引用的界面里使用 @utils.test.ts：文件还能随第一条消息直接进入上下文，少一次 Read 工具往返调用。

注意文件驻留代价：文件进入会话后会留在那里。@文件名 省掉的是搜索、读取和一次往返，文件本身占用的上下文空间不会因此变小。不要在后续轮次反复 @ 同一个文件，否则可能在历史中附加第二份副本。CLI、Desktop、IDE 和远程环境对文件引用的支持也不完全相同，应以当前界面为准。

命令输出控制与 BASH_MAX_OUTPUT_LENGTH 保护

命令输出通常更容易失控。测试、构建、git log 和调试日志都会像文件一样追加进历史。原文发布时，超过 30,000 字符的输出会被自动写入本地临时文件，只把预览和路径放回上下文；这个阈值可通过环境变量 BASH_MAX_OUTPUT_LENGTH 调整。更常见且更致命的问题是几百行没有触发保护的中等噪声。

使用 Quiet 模式 ✓

例如运行单测时配置 --reporter=dot，将数百行冗余成功信息压缩为点阵，避免无意义日志入库。

错误附近截断与 Tail ✓

仅提取包含 ERROR 或 FAIL 的关键栈帧，使用 tail -n 50 限制行数，切断无价值日志传播。

Hooks 自动改写命令 ✓

可在 Claude Code 中设置 Hook，在高噪声测试或构建命令执行前，由脚本自动拦截并注入精简参数。

7. 第三优先：模型、Effort 和缓存尽量在开局定好 推理参数优化

一次请求的价格受三个核心变量直接影响：模型选择、输入/输出计算阶段以及提示缓存状态。

模型要按完成任务的总成本选择

更大的模型通常有更高的 Token 单价。明确的小修复、机械改名和格式调整，使用够用的模型（如 Haiku）往往更合适；架构判断、模糊故障和跨系统推理，才值得投入更强的能力（如 Sonnet / Opus）。

破除单 Token 价格误区：只看单个 Token 的价格容易产生误判。在困难任务上，小模型可能需要更多搜索、重试和验证，最后仍达不到同样质量，综合总花费反而超过大模型。选择时应该综合比较达到可接受结果所需的端到端总工作量。

Effort 深度调节机制

Effort 会影响模型读多少文件、调用多少工具、验证到什么程度。模型决定能力上限，Effort 调整这一轮愿意投入的工作量。机械任务可以降低 Effort；需要追查和判断的任务则应保留足够深度。

原文还提到 MAX_THINKING_TOKENS=0 可在单次会话中关闭 Thinking（并注明 Fable 5 例外）。这类环境变量和模型行为变化较快，更适合作为经过当前版本确认后的高级设置，不应当成所有会话通用的默认建议。

输入整段读取 (Prefill) 与输出逐字生成 (Decode)

请求先经过 Prefill 阶段：模型读取工具定义、系统提示、CLAUDE.md、消息、文件和命令结果。随后进入 Decode 阶段：逐 Token 生成思考、工具调用和可见回复。

Anthropic 当前列出的主流 Claude 模型中，输出 Token 单价大约是输入的 5 倍。让 Agent 少输出无用客套说明确实有帮助；但长会话里数量规模更大的部分，往往仍是每一轮重新携带的输入历史。

提示缓存（Prompt Caching）自动工作，但不会清走历史

Claude Code 会自动管理提示缓存，不需要用户额外开启。它仍会把完整会话重新发送；请求开头与上一轮保持一致时，服务端可以复用缓存状态：

计费动作类型 相对价格倍率 触发机制与适用条件
缓存读取 (Cache Read) ~0.1x 正常输入价 请求前缀与此前缓存完全匹配时，复用服务端已计算状态
正常输入 (Full Prefill) 1.0x 基准输入价 新追加的文件内容、新工具调用结果或缓存未命中部分
5 分钟缓存写入 (5m Write) 1.25x 正常输入价 首次将新前缀写入缓存池（API Key 默认 TTL 5 分钟）
1 小时缓存写入 (1h Write) 2.0x 正常输入价 长效缓存池写入（Claude Code 订阅场景默认 1 小时）
输出生成 (Decode Output) ~5.0x 基准输入价 模型思考过程（Thinking）与最终生成的回复 Token

前缀连续性约束：缓存要求请求前缀从开头连续匹配。请求通常按 [工具定义] → [系统提示] → [CLAUDE.md] → [对话历史] 的顺序组装。越靠前的部分发生变化，后面需要重新 Prefill 的内容越多。

中途更换模型、更换 Effort、打开 Fast Mode、运行 /compact，或者等到缓存过期后再回来，都可能让相关历史重新 Prefill。opusplan 进入和退出 Plan Mode 时会切换模型，也属于这种情况。原文特别说明，关闭 Fast Mode 回到原状态，在缓存层面没有同样的重算代价。

/model 和 /effort 还会记住上一次选择，新会话不一定回到默认值。因此开局先确认真实配置；需要切换时，优先放在新会话开头或刚执行完 /clear 之后，别等长历史形成后再换。

前缀享 0.1x 读取价
发生了什么：工具结果加在末尾，旧历史继续命中缓存，只有新尾部按完整输入价处理。
深度解析与建议：正常追加是最合算的连续交互模式。只要不频繁切换模型或修剪前部，历史成本可压到最低。

/compact 与 /rewind 的使用时机分水岭

/compact 和 /rewind 也有截然不同的用途：

  • 同一任务进入新阶段、旧细节已经失去价值时，可以用 /compact 把历史重写成摘要；
  • 如果只是末尾几轮走错，优先 /rewind，因为它只裁掉错误分支，前面的长缓存前缀仍可能完整保留；
  • 离开前的主动压缩技巧：准备离开较长时间、回来仍要继续同一任务时，可以在缓存有效期内先 /compact。生成摘要还能利用当前缓存，通常比缓存过期后先完整重读旧会话再压缩更合算。

9. Subagent 适合隔离噪声，不适合所有复杂任务 多 Agent 成本权衡

Subagent 使用独立上下文。它有自己的系统提示、工具和 CLAUDE.md，不会继承主会话的全部历史；任务结束后，通常只有答案或摘要回到主会话，中间读过的日志和尝试不会继续跟随主任务。主会话也只会得到 Subagent 主动写进报告的内容，遗漏的细节不会自动返回。

适用场景（高隔离价值） ✓
  • 扫描数千行冗长构建日志排查错误；
  • 运行全量测试用例并分析海量失败栈；
  • 搜索海量 Git 提交历史定位回归点；
  • 主会话只需要最终结论，不需要过程堆叠。
不适用场景（负收益） ✗
  • 只需读几十行代码的小问题；
  • 中间排查过程也是后续必须保留的决策依据；
  • 交出任务会导致重复读取主会话看过的文件；
  • 频繁创建短生命周期 Subagent 增加启动开销。

代价分析：Subagent 要重新加载自己的启动上下文，可能重读主会话已经看过的文件，还会产生独立的多轮请求。一个只需读几十行代码的问题，交出去往往只会增加开销。

分级模型搭配方案：如果某类高噪声任务会反复出现，可以为它建立专用 Subagent，并明确指定较小、较便宜的模型（如 Haiku 或 Sonnet）。没有单独指定时，它会默认继承主会话当前的模型。这样能控制重复脏活的单次成本，前提仍是主会话只需要最终报告。

核心决策准则：判断时问一句就够——这项工作的中间过程，主会话之后还需要吗？如果只需要结论，而且过程很吵，隔离有极大价值；如果过程本身会成为后续决策依据，就坚决留在主会话。

10. 使用这份指南时，记住四个边界 工程认知边界

边界 1：官方产品指南而非横向竞品对比 01

这是一篇 Anthropic 面向 Claude Code 用户发布的官方实践指南。它能说明产品当前的机制和建议，不能证明 Claude Code 比其他 Agent 工具更省钱或更高效。

边界 2：订阅额度与 API 账单的计费表面 02

订阅用户未必看到逐 Token 金额，但同样的上下文仍会消耗使用额度；API 用户直接面对输入、输出和缓存倍率。底层 Token 消耗机制完全一致。

边界 3：参数与机制随版本动态演进 03

模型、定价、缓存 TTL、界面能力、命令和环境变量都会变化。本文的倍率和操作边界依据 Anthropic 2026 年 8 月发布的文章及当期官方文档。

边界 4：场景倍率属于解释性而非绝对常数 04

5 对 18 次请求、6/1/0 次工具调用和 1.9 倍 Token 都是解释性场景，只适用于各自图中的测试条件，不可直接机械硬套为全局常数。

真正有用的目标，是把 Token 留给任务需要的代码、推理和验证。开局定好模型与 Effort，给出已知范围，收短日志；末尾走偏用 /rewind，换任务用 /clear，高噪声过程才交给 Subagent。这样做不会保证每个任务都更便宜，却能系统性减少会话里最常见的无效负担。
