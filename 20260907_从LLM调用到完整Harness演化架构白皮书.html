核心架构真理： 这篇文章真正要讲的，不是“Agent 比 LLM 多了几个 Tool”，而是：
LLM 本身始终只是一个根据输入上下文生成输出的模型。Agent 的大部分“自主性”，其实来自模型外部不断增厚的运行时系统。这个运行时最终演化成了 Harness。

文章给出的演化逻辑非常清晰：模型每突破一次边界，工程系统就在外面补一层——记不住就加 Context，碰不到世界就加 Tools，一步做不完就加 Loop，历史太长就加 Memory，真实操作有风险就加 Permission/Sandbox，需要恢复和并行就加 Session、Event、Thread、Sub-Agent。

核心总览：LLM 是怎样一步一步“长成” Agent Harness 的

今天的 Agent 系统看起来很像一套小型操作系统：它们管理子 Agent 进程，维护长期记忆文件，通过工具驱动接触外部世界，还要处理权限、隔离、恢复和观测。可它们的起点并不宏大。最初，开发者手里只有一个把输入映射为输出的语言模型。

复杂性并不是一次设计出来的。每当模型试图越过一次调用的边界，系统就必须在模型外面增加一个新部件：模型不知道此前聊了什么，于是出现上下文；模型无法改变世界，于是出现工具；一次工具调用解决不了任务，于是出现循环；上下文装不下历史，于是出现记忆；循环开始产生真实副作用，于是出现权限与沙箱；一个循环不够并行，于是出现子 Agent...

一、从一次模型调用到 Agent

在探讨复杂的 Harness 之前，必须先理清最根本的误解：大语言模型本身并没有“变成 Agent”。最原始的模型始终只是一个输入一段 token、输出另一段 token 的函数。

1.1 LLM：单向映射与无状态认知

最朴素的大语言模型接口可以被看成一个纯函数：输入一段 token，输出另一段 token。它可以在参数中编码世界知识，却不会天然记住某个用户上一轮说过什么，也不知道自己刚刚输出的命令是否被执行。

2020 年，GPT-3 展示了大规模语言模型仅通过文本提示完成多种任务的能力；2022 年底，GPT-3.5 成为 ChatGPT 背后的模型；2023 年 2 月，Meta 发布 LLaMA，推动开放权重模型进入主流研究与本地部署。GPT、LLaMA 以及后来出现的 Claude、Gemini、Qwen 等模型虽然能力不同，但在应用看来仍然共享同一个基本形态：接收上下文，predict next token。

PYTHON: 纯函数形态Pristine LLM
answer = LLM(question)

最初的系统只有一次前向调用。模型负责生成文本，应用只负责把问题送进去、把答案显示出来。模型参数里的知识来自训练；一次对话中的名字、偏好和任务状态，则必须由应用在每次调用时重新提交。模型本身并没有一个不断增长的用户档案，它没有：

  • 永久记忆 (Persistent Memory)：重启或下一次请求时状态重置；
  • 任务生命周期 (Task Lifecycle)：无法跟踪复杂任务的状态跃迁；
  • 工具执行与环境感知 (Tools & Environment)：无法接触操作系统文件、网络和命令行；
  • 权限、沙箱与恢复能力 (Permission & Recovery)：没有任何安全控制边界。

1.2 Q&A Bot：上下文装配层与 Working Memory

Q&A Bot 的第一项工程进步，不是换了一个更聪明的模型，而是在模型前面增加一个上下文装配层（Context Assembly Layer）。它把系统指令、用户当前输入和对话历史拼成一次请求。

在 GPT-3 时代，许多应用仍然把模型包装成单轮问答接口；2022 年 11 月，ChatGPT 把多轮对话带给大众，开发者开始普遍维护 System Prompt、User Prompt 和 Chat History。模型没有突然获得跨轮记忆，是聊天应用在每次请求前重新装配了历史。

PYTHON: 上下文装配Working Context Assembly
working_context = [
    system_prompt,
    recent_chat_history,
    user_prompt
]

answer = LLM(working_context)

Working Memory 不是长期存储，而是这一轮真正提交给模型的全部上下文。

💡
Harness 核心奠基原则：模型看见的一切，都是运行时替它构造出来的。
运行时选择哪些历史进入上下文、哪些指令拥有更高优先级、哪些内容必须被裁剪，都会从根本上改变 Agent 的行为。换言之：
World ──▶ Runtime Filtering / Retrieval / Assembly ──▶ Working Context ──▶ LLM
很多时候，不是模型能力不够，而是 Harness 给模型构造了一个错误的世界。

1.3 ReAct：从单纯生成到闭环行动的 Agent Loop

Bot 只需要回答一次，但 Agent 必须根据行动结果继续决策。2022 年提出的 ReAct 执行架构把推理轨迹与动作交错起来：模型形成下一步意图，执行外部动作，接收 Observation，再把观察送回下一轮推理。

ReAct 论文于 2022 年 10 月公开，并在 ICLR 2023 发表。它把此前分别讨论的 Chain-of-Thought 与外部行动连接成 Thought → Action → Observation 循环。2023 年大量早期 Agent 项目沿用了这一模式，Agent 也由“一种提示词技巧”逐渐变成了一个需要程序持续驱动的执行循环。

Agent 真正的分水岭不是“会思考”，而是建立了 模型 → 动作 → 环境 → 观察 → 模型 的闭环。

PYTHON: ReAct 核心循环Agent Runtime Loop
while not finished:
    response = model(context)
    if response.has_action:
        observation = environment.execute(response.action)
        context.append(response.action, observation)
    else:
        return response.answer
⚠️
关键工程真相：这个 while 循环不是 LLM！
它是模型外面的程序（Agent Runtime）。模型仍然只生成 token，真正负责“继续运行”的是外部程序：它必须解析模型输出、判断任务是否结束、调用真实环境，并把环境反馈重新写回上下文。

1.4 Tool Calling：从脆弱正则到可验证的动作协议

早期 Agent 常让模型输出类似 Search[Wikipedia] 的文本，再由程序用正则表达式解析。这种方式很灵活，但也极其脆弱：格式可能漂移，参数可能缺失，模型还可能把解释文字混进命令，导致解析失败与环境异常。

2022 年的 ReAct 主要依赖约定格式表达动作；2023 年 6 月，OpenAI 发布 Function Calling，工具名和参数开始成为模型 API 的结构化输出；2024 年 11 月，Anthropic 发布 MCP (Model Context Protocol)，进一步尝试标准化 Agent 与外部数据源、工具服务之间的连接。

✦ 结构化 Tool Calling 标准化执行链路
Schema 注册、意图路由、权限校验与结果闭环

文章清晰地将 Tool Calling 拆解为三层架构：

  • Tool Schema： 描述工具名称、用途、参数类型与约束，严密界定模型的“动作空间 (Action Space)”；
  • Tool Router： 根据工具名匹配具体实现，进行参数格式与类型校验，把模型意图转化为确定的可执行程序调用；
  • Tool Result： 携带全局调用 ID、状态码与返回值，保证外部环境观察能精准映射到原始动作。

从这一刻起，Agent 获得了可验证、可路由、可审计的动作协议。随后的 Terminal、Browser、Filesystem、Database 与 MCP，本质上都是 Agent 动作空间的向外扩张。

1.5 Memory：外部持久化与策略分层

Agent Loop 解决了“如何连续行动”，却没有解决“如何跨会话积累”。完整历史会越来越长，而模型的上下文窗口始终有限。系统不得不把记忆拆分成两个独立空间：一个是本轮模型可见的 Working Memory，另一个是外部可持久化、可检索的 Long-term Memory。

2020 年的 RAG 已经清楚地区分了模型参数中的知识与外部可检索知识；2023 年的 MemGPT 又借用操作系统的分层存储思想，在有限上下文与外部存储之间调度信息。此后，记忆从“检索几段文档”逐渐扩展到摘要、用户偏好、会话归档、技能文件和后台知识整理。

记忆分类 (Type) 核心定义与技术承载 典型载体与检索方式 生命周期与失效应对
程序记忆
(Procedural)		 技能 (Skills)、工作流 SOP、工具调用规约与用户定制规则 规则文件、SKILL.md、AGENTS.md、Prompt Templates 版本化管理，随着工程工具迭代显式升级或弃用
语义记忆
(Semantic)		 跨任务稳定事实、概念模型、用户偏好、项目领域知识 本地 Markdown 库、SQLite 关系表、全文索引、轻量向量库 后台定期去重与知识整合，矛盾时以最新确认事实覆盖旧事实
情景记忆
(Episodic)		 某次任务发生了什么、采取了哪些动作、工具结果如何的完整轨迹 会话归档日志 (Session Archive)、Event Rollout、执行快照 长任务基于窗口滑动裁剪，或通过 Compaction Agent 提取关键结论
💡
Memory 的本质不是“加一个向量数据库”！
这里真正困难的不是存储（memory.save()），而是写入与读取策略：什么值得保存？何时保存？保存事实还是过程？什么时候更新？冲突怎么办？旧经验何时失效？哪些信息值得进入本轮 Context？进入多少？错误 Memory 如何纠正？
因此，成熟的 Memory 必然长出 Extract → Filter → Deduplicate → Consolidate → Conflict Resolution → Retrieve → Context Injection 这一整套策略管线。
Memory 本质上首先是一个 Policy（策略治理）问题，其次才是 Storage（存储）问题。

二、当能力变多，Agent 外面出现了 Harness

到这里，系统已经拥有了上下文、循环、工具和分层记忆。然而，一旦 Agent 从 Demo 演示走向承载生产级真实任务，一批极为严苛的工程挑战便随之爆发。

2.1 走向真实工作时的六大工程挑战

2023 年的许多 Agent 原型仍把 Prompt、Loop 和 Tools 混写在一个脚本里；2024 年，MCP 开始统一外部连接协议；到 2025 年，Claude Code 和开源的 Codex CLI 把终端 Agent 推向真实软件工程场景。系统暴露出六大必须在模型外部解决的核心瓶颈：

  • 会话能否恢复 (Session Recovery)： 程序崩溃、进程断开或用户退出后，循环必须从一致的快照精确恢复，不能从零开始；
  • 副作用是否安全 (Side-Effect Safety)： 执行 rm -rf、修改核心生产代码、发起网络通信不能寄托于模型的“自我约束”；
  • 上下文如何压缩 (Compaction & Token Budget)： 长达数十万 token 的长任务轨迹，必须动态保留核心结论并释放窗口空间；
  • 多客户端如何协同 (Multi-Client Protocol)： TUI、IDE 插件、桌面端、Web 仪表盘与 SDK 需要同时连接并观察同一个运行状态；
  • 扩展如何动态装配 (Resource Loader)： 工具、MCP 服务器、Skills、Prompt 模板需要确定性的动态发现与热加载机制；
  • 任务如何高效并行 (Sub-Agent Lifecycle)： 派生的子 Agent 必须拥有隔离的独立上下文、权限范围、运行历史与生命周期。

于是，Agent Loop 不再直接暴露给世界。它被包裹进一个厚重坚固的外部运行时体系——这个负责装配资源、管理会话、约束工具、持久化事件、暴露统一 API 并在多个 Agent 间调度任务的基础设施，就是 Agent Harness。

2.2 Harness 的经典架构定义

“Agent 决定下一步做什么；Harness 决定这一步在什么上下文、权限、生命周期与持久化规则下发生。”

—— 这句话是现代智能体软件工程对 Agent 与 Harness 职责边界最精准的定义。

2.3 操作系统与 Agent Harness 深度映射（16 项对照表）

理解 Harness 最清晰的认知框架，就是将其视作一套以 LLM 为执行核心的小型现代操作系统（Agent OS）。二者在抽象层次上存在高度严整的对偶关系：

传统操作系统 (OS Concept) Agent Harness 对应抽象 (Harness Concept) 核心职责与工程机制
CPU LLM / Decision Engine 认知推理核，负责 next-token 预测与意图决策
Process (进程) Agent / Sub-Agent 具有独立执行目标和上下文边界的执行实体
Process Manager (进程管理器) Thread / Agent Manager 负责 Agent 实例的创建、挂起、销毁与拓扑调度
RAM (内存) Working Context 当前轮次前向计算直接装配的一级工作集
Disk (磁盘持久化) Long-term Memory 外部持久存储（文件、SQLite、向量检索数据库）
Virtual Memory (虚拟内存换页) Context Compaction & Retrieval 超出物理窗口时自动裁剪历史、摘要压缩与动态加载
System Call (系统调用) Tool Calling 从安全用户态陷入外部环境内核的标准请求协议
Driver (外设驱动) Tool Adapter / MCP Server 屏蔽终端、浏览器、文件系统等外部服务差异的标准化协议

Process Log (系统日志与审计) Event Store / Rollout 逐 Step 记录不可篡改的原子事件轨迹与可溯源快照
Scheduler (进程调度器) Agent Scheduler / Cron 决定当前计算配额分配给哪个 Agent/Turn 推进
Fork (进程分叉复制) Sub-Agent / Thread Fork 基于稳定快照复制上下文与状态，派生分支独立探索
Snapshot (系统快照) Session Persistence 任务状态序列化并物化落盘至数据库或文件系统
Crash Recovery (崩溃恢复) Session Resume / Replay 进程重启后从最近稳定检查点还原内存上下文继续执行
Daemon (守护进程) Persistent Runtime 常驻后台，可被时间定时器或外部 Webhook 事件唤醒

三、四大设计哲学与架构空间（Pi / OpenCode / Codex / Hermes）

同一个大语言模型，只是换了一套 Harness，结果到底能差多少？评测数据表明，Harness 的设计差异不仅决定了 Agent 的能力上限，还会直接导致任务成本出现数倍的剧烈分化。

3.1 Harness 设计空间二维象限解析

在 Agent Harness 的工程演化谱系中，并不存在唯一的“最优解”。不同的工业级系统在工程控制粒度（Harness Tax vs. 安全治理）与时间跨度目标（单任务高吞吐 vs. 长期自进化）之间做出了截然不同的权衡：

3.2 Pi：极简主义与最低 Harness 税（Harness Tax）

同一个模型，只是换了一套 Harness，结果能差多少？评测机构 Composio 将 DeepSeek V4 Flash 分别放进 Pi Agent、Prime Agent、Deep Agents 和 Hermes Agent，执行同一批 30 个综合 Agentic Tasks。Pi 的通过率高达 66.7%，而中位任务成本只有 0.012 美元。在这组对比测试中，Pi 完成任务最多，消耗 Token 却最少。

Databricks 的内部基准又把这个问题放进更接近生产环境的坐标系：他们从工程师真实 Pull Request 构造任务，在覆盖 Python、Go、TypeScript、Scala 等语言的数百万行代码库上，比较单任务平均成本和整体通过率。

📊
Databricks 实测关键发现：
  • 在 Pareto 前沿曲线上，Pi 占据了多个主流性能区间；
  • Opus 4.8 搭配 Pi 的 xhigh 设置任务通过率接近 90%，GLM 5.2 搭配 Pi 也进入最高能力梯队；
  • 部分同模型、同推理强度的 Agent 换到 Pi 后，解题质量基本不变，单任务成本却相差两倍以上；
  • 运行追踪证实：Pi 每轮送入模型的工作集上下文约少三倍，以更紧凑的状态、更少的循环轮次完成了任务。

Pi 为什么能一边压低成本，一边把任务做对？
核心在于它坚决不让模型反复阅读无关内容。Pi 默认只暴露四个核心工具：read、write、edit、bash。外部的 Resource Loader 显式装配当前会话启用的指令、Skills 和 Prompt Templates，Session Manager 再利用活动分支和 Compaction 将完整历史投影成极为紧致的 Working Memory。这样一来，每轮请求携带的历史噪声和工具 schema 描述大幅压减，极简主义在此处直接转化为了吞吐性能和财务收益。

⚠️
Pi 的工程代价与安全局限：

3.3 OpenCode：事件驱动的服务与结构化状态投影

在 OpenCode 里，用户在终端或界面看到的一段回复，在底层存储中并不是一整块孤立的文本。一次 Assistant Message 内部被拆解为细粒度的状态零件（Part）：

DATA MODEL: 细粒度状态结构OpenCode Message Anatomy
Assistant Message
├── Reasoning        (模型内部推演思维链)
├── Text             (面向用户的回复正文)
├── Tool             (发起的工具调用请求)
├── Step Start       (执行步骤启动时间点)
├── Step Finish      (执行步骤结束确认)
├── Patch            (实际改动的文件差异补丁)
└── Compaction       (触发的历史压缩摘要)

为什么要把一轮回答拆得这么碎？
因为 OpenCode 保存的对象是 Agent 运行过的全生命周期事件流。只要执行全过程被原子化、结构化地记录下来，客户端意外退出或进程重启便不等于丢失执行现场，恢复 Session 也不再依赖脆弱的“字符重放”。

这套系统始于 Agent Profile。源码中的 Agent.Info 将 Prompt、模型标号、Mode、Permission 策略、单次生成参数与最大步数统一定义在配置对象中：

  • Build & Plan： 作为主 Agent (primary)，直接面向用户需求，二者的本质差异体现在权限边界与工具暴露上；
  • General & Explore： 作为子 Agent (subagent)，由 Task Tool 调度执行，例如 Explore 仅开放只读搜索和有限命令；
  • Compaction / Title / Summary： 作为隐藏后台 Agent，专职负责多轮压缩、动态命名与代码变更汇总。
💡
OpenCode 的运行哲学：
Agent Profile 决定此刻是谁在工作，Session Events 负责留下事实，Compaction 决定哪些过去还要继续被模型看见。
Message 与 Part 的变更驱动 Projector 将数据持久化到 SQLite 中。当长会话逼近上下文窗口极限时，后台 Compaction Agent 汇总早期历史，在预算内保留近期 Turns，旧工具输出被动态折叠裁剪，重构成下一轮的 Working Memory。这套体系是一条确定性的上下文管线，而非脆弱的外挂向量库。

3.4 Codex：安全执行、Thread 生命周期与子 Agent 谱系管理

在 Codex 中，工程设计的重心完全投向了真实计算机环境下的高风险防御与超长任务管理。文章揭示了全篇最具工程含量的分水岭：

核心分水岭：Approval ≠ Sandbox（用户批准不等于沙箱放行）

在 Codex 里，用户点下“允许”，并不等于模型拿到了整台电脑！
Approval Policy 只决定某个动作是否获准尝试执行；Sandbox Policy 仍然严格约束命令可以写到哪里、能否访问网络、可以触碰哪些系统资源。 一次会制造真实副作用的工具调用，必须连续穿透这两道边界！

独立测评项目 OpenBench 在 2026 年 7 月将同一个 gpt-5.6-sol 接入 7 套 Coding Agent Harness，比对各组均完整运行的 42 个深度工程任务：Codex 完成了 31 个（通过率 73.8%），但其中位耗时高达 94.6 秒，单任务平均消耗 117,107 个新 Token，属于全场最重的一档。

这组数据清晰展现了 Codex 的 Harness 成本（Harness Tax）：线程生命周期管理、逐层安全审批、微容器沙箱、事件持久化与多级恢复，在简单任务中体现为可观的开销；但对于必须被审计、随时可能中断/恢复的长程复杂任务，这是唯一具备生产可行性的路径。

✦ Codex 核心协议模型：Thread / Turn / Item 树状体系
App Server 与 Thread Manager 驱动的原子可观察生命周期

支撑这套生命周期的是核心引擎 Thread Manager。在内存中，它通过 HashMap<ThreadId, Arc<CodexThread>> 记录活跃 Thread：

  • 冷热分离调度： Resume 一个正在运行的任务直接复用内存实例，避免启动双重 Agent Loop；冷任务才从 Thread Store 或 Rollout 文件反序列化历史；
  • StepContext 快照隔离： 每次模型采样创建瞬时上下文，冻结当前的 Environment、Capability Roots、MCP Binding 与 AGENTS.md 规则，屏蔽后台并发变动的干扰；
  • Multi-Agent 的真实本质： 子 Agent 绝非在同一 Prompt 上下文里塞入角色扮演对话，而是由 Thread Manager 派生的独立子 Thread（如 Newton、Franklin、Dirac、Peirce 4 个并行实例），拥有隔离的生命周期、沙箱边界与 Rollout 轨迹，结果物化后再回传父任务。

3.5 Hermes：认知自进化与时间驱动的持久运行时

Pi 关注当下任务的轻量高效，OpenCode 关注过程的精确审计，Codex 关注生产级的控制与安全。而 Hermes Agent 则把思考推到了下一个时代：Agent 第二次面对同类任务时，能不能少走一次弯路？

2026 年 8 月发布的专用评测基准 PAST-Bench 构建了 26 个工程场景、共计 204 个跨会话 Episode：早期 Episode 提供偏好或纠错经验，后续 Episode 清空当前上下文，测试智能体的记忆与自适应演进能力。

📈
PAST-Bench 严谨实验结论：
固定 MiniMax-M2.7 底座模型后，Hermes 是基准中唯一在 Memory、Procedural Reuse、Information Gathering 与 Update 四大维度全部取得正向增益的框架，总体综合增益达到 +0.13。
更关键的是机制证据分（Mechanism Evidence Score）：通过审计日志中 Memory 写入、Skill 创建与跨会话读取的完整闭环，Hermes 取得了 0.64 的高分（同取得 +0.13 净收益的 nanobot 仅 0.57），证实收益确系来源于系统化的经验复用，而非模型的随机波动。

自我进化的真谛： 真正的自进化并非在线微调底层大模型的数十亿权重（昂贵且可能导致灾难性遗忘），而是在模型外部构建一个持续提炼认知、自我修正规则与沉淀可执行技能的外部系统。

在此之上，Hermes 引入了 Persistent Runtime：通过内置 Cronjob 与事件监听器，任务可以由“到达特定时刻”或“外部 Webhook 事件”触发，使 Agent 彻底跳出“打开终端才存在的短暂进程”，跃迁为全天候在线的个人操作系统。

4.2 Agent 综合有效性（Agent Effectiveness）量化模型推导

为什么仅仅关注 Prompt Engineering 无法解释现代 Coding Agent 之间巨大的性能落差？文章给出了一个极具启发性的近似关系，我们可以将其进一步形式化为严谨的可计算物理模型：

Agent Effectiveness ≈ Uctx × Gact × Qfb Nnoise × Cloop × Eerr

公式各因子的严格物理意义与工程度量如下：

  • 分子（有效生产力驱动项）：
    • Uctx∈(0,1] 有用上下文密度 (Useful Context Ratio)： 送入模型的 working context 中，直接有益于当前决策的 Token 占比；
    • Gact∈(0,1] 有效动作质量 (Good Actions Probability)： 模型生成的 Tool Call 命中正确工程逻辑且参数合规的概率；
    • Qfb∈(0,1] 环境反馈置信度 (Feedback Quality)： 外部工具与环境返回结果的清晰度、完整度与区分度。
  • 分母（系统损耗与阻尼惩罚项）：
    • Nnoise∈(0,1] 上下文噪声因子 (Context Noise Factor)： 历史对话堆积、无用工具 Schema 暴露对模型注意力机制造成的扰动；
    • Cloop>0 单轮综合循环开销 (Loop Cost & Harness Tax)： 包含 Token 传输消耗、审批挂起等待、沙箱重入时延在内的单步阻尼；
    • Eerr∈(0,1] 环境错误与副作用扩散率 (Error & Side-Effect Impact)： 误删文件、编译失败或越权外联导致的惩罚因子。
⚖️
工程平衡启示：
盲目给模型提供“无限工具”和“海量历史”，会直接推高分母中的 Nnoise；缺乏有效的沙箱与验证，会导致 Eerr 急剧膨胀；而过于笨重迟滞的层层拦截又会使 Cloop 飙升。
优秀 Harness 的首要职责，绝非一股脑把一切推给模型，而是动态精算并调控模型“此刻应该看到什么、可以触碰什么”。

六、全文五大核心结论与架构终极定义

6.1 全文最值得记住的 5 个技术结论

①
LLM、Agent、Harness 是三个完全不同的系统层级：
  • LLM： 是认知推理核与决策引擎（根据输入上下文预测输出）；
  • Agent： 是 LLM 结合了自主闭环控制（Model → Action → Environment → Observation）；
  • Harness： 是让 Agent 能够长期、受控、可审计、安全、可恢复运行的完整外部运行时系统（Runtime System）。
②
Agent 的能力不只取决于模型，而是多维系统的乘积：

Agent Capability = Model × Context Quality × Tool Quality × Loop Design × Memory Policy × Runtime Governance
这正是 Databricks 与 Composio 实验所证明的根本原因：同一个模型换上不同的 Harness，通过率与任务成本能够相差数倍！

③
Context Engineering 已经彻底演进为 Runtime Engineering：
以前研究“Prompt 怎么写”，现在必须研究：什么信息进入上下文？何时进入？历史如何压缩？长期记忆如何门控检索？工具输出保留多久？Skill 什么时候动态加载？ Prompt 只是整个运行时管线中极其轻薄的一层。
④
真正的 Agent 自进化，优先发生在外部 Harness，而非模型权重：
底层大模型的权重可以完全冻结保持不变。通过在模型外部持续沉淀 Experience ──▶ Review ──▶ Memory & Skills ──▶ Policy Evolving ──▶ Better Next Context，以外部认知系统的进化撬动能力的持续跃迁（Hermes 路线）。
⑤
模型越强，外面的 Harness 反而越关键：
当模型能力羸弱时，错误仅仅表现为屏幕上的文字瑕疵；当模型获得执行权限能够真实行动后，一个失误就意味着误删核心代码、损毁数据库、泄露加密凭证或遭受恶意网络渗透。模型越能行动，外面的权限审批、沙箱隔离、事件审计与状态回滚越不可或缺！
