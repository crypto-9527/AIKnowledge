为什么 AI 软件工程师必须拥有一台 Mac，以及 Cognition 如何从存储快照、网络隔离、镜像预制、实时画面和无障碍树，打通苹果原生应用的“开发—运行—验证”完整工程闭环。

发布机构：Cognition Labs 技术实体：Devin / macOS Cloud Workspace 架构层级：五层运行时验证体系 归档时间：2026-09-16 原文出处：Cognition Engineering Blog

核心技术要点 (Executive Summary)

  • 真机运行时闭环：Devin 获得 macOS 云端工作区后，能够构建并运行 iPhone、iPad 与 Mac 原生应用，并能像真实用户一样在模拟器和桌面上操作应用、触发交互、核验状态。
  • NBD 存储快照接驳：针对苹果官方 Virtualization.framework 不支持 vhost-user 的限制，团队开发了网络块设备（NBD）前端，成功接入既有快照后端；关机时存储进程必须完成数据刷盘并保存快照，Hypervisor 才继续资源回收。
  • 用户态网关规避 pf 竞态：放弃 Apple 托管 NAT，采用文件句柄模式直接处理 L2 以太网帧，并在宿主机自建用户态网关处理 ARP 响应与 MAC/IP 合法性校验，彻底规避双边竞相修改 pf 防火墙导致的规则冲突。
  • 离线配置切断模态弹窗：在镜像构建期直接离线挂载虚拟磁盘，注入系统用户并预写入 TCC 隐私权限数据库；开机后再进行在线预热，预先唤醒 Xcode 与 iOS 模拟器，消除运行期的人工干预。
  • 无障碍树语义级操控：借助 Dioxus 开源项目的 accessibility-cli 提取原生控件树，通过稳定句柄发起精确操作，克服传统多模态纯截图方案的高时延与高 Token 开销；同时保留截图通道互补自绘画布。

Cognition 正式宣布为其自主 AI 编程智能体 Devin 推出 macOS 支持，将其自主云端开发工作流从传统的 Web 和 Linux 后端，扩展至 iOS 应用、原生 macOS 桌面程序以及所有深度依赖 Apple 开发工具链的复杂工程项目。

01为什么 Devin 必须有一台 Mac？

编译与启动不能证明运行时行为正确

在传统的自动化编程场景中，智能体通常运行在 Linux 容器中。对于命令行工具或后端服务，智能体可以通过捕获编译器错误、执行单元测试或检查进程退出码来判断代码修复是否成功。但在面向终端用户的图形界面与苹果生态中，面临着两个递进的硬核现实要求：

  • 编译通过与进程拉起不代表业务功能正确：在本地开发中，代码助手很容易根据编译器报错不断修改语法直到构建成功。但对于图形界面应用，单纯代码编译通过、窗口成功拉起完全不等于实际工作，真正的验证在于运行时动态行为与持久化状态还原。
  • 原生应用工具链与验证闭环深度绑定 macOS：苹果生态的原生应用深度依赖 Xcode 构建系统、macOS 图形渲染框架以及专属的 iOS 模拟器（Simulator）；要验证应用在真实运行时的表现，智能体必须拥有一个可以实际运行、交互和核验的原生 macOS 工作区。

以开发一款 iPhone 手机游戏为例，核心需求是：“用户退出游戏后再次打开，游戏必须精准恢复到上次暂停时的状态”。单纯编译通过，无法保证应用生命周期的挂起通知（sceneDidEnterBackground）、序列化落盘以及反序列化还原代码能够正确执行。智能体必须像真实用户一样完成“玩、暂停、退出、重开并验证恢复”的完整闭环。

在云端将这套闭环跑通并不简单。在虚拟机里把 macOS 跑起来只是最浅层的第一步；要让它成为一个自主开发工作区，必须在底层解决数据状态持久化、会话网络安全隔离、开机免人工干预配置，以及人机两端的实时画面与控件操作问题。

五层验证链全景图 (The Verification Stack)

这些关键工程沿着同一条**五层验证链（Verification Stack）**逐层衔接：底层先打通存储快照并管住网络，镜像准备把人工弹窗移出任务时间，实时画面让用户查看和接管运行中的应用，结构化无障碍树则让 Devin 能够查询、操作并检查原生控件。

02存储层设计：用 NBD 协议打通跨会话快照

vhost-user 缺失与 NBD 协议替代

Devin 的云端服务构建在 AWS EC2 Mac 裸金属服务器之上，宿主机通过苹果官方的原生虚拟化框架 Virtualization.framework 运行客体 macOS 虚拟机（Guest VM）。

云端智能体开发的一大核心特征是异步协作：用户给智能体指派任务后无需守在屏幕前，而空闲等待会话也不应一直独占裸金属算力资源。为了让用户在下一次打开会话时能瞬间回到上次的工作现场，底层必须具备极速、可靠的跨会话增量快照机制，保存工程所有编译缓存、DerivedData、模拟器沙盒与修改文件。

对于 Guest 操作系统而言，虚拟磁盘只是底层的原始块设备（Block Device）。在典型的 Linux KVM/QEMU 环境中，Devin 普遍采用 vhost-user 协议将虚拟磁盘的 I/O 委托给宿主机上的独立存储进程。但在 macOS 宿主上，苹果官方的 Virtualization.framework 并未提供 vhost-user 支持。

作为突破口，团队挖掘了苹果框架支持的另一项标准协议——网络块设备（Network Block Device，简称 NBD）。NBD 允许客户端通过本地套接字直接读写块设备数据。团队在原有快照存储系统前端封装了一层 NBD 前端适配层，无需重构底层的快照存储后端（Snapshot Backend），就成功复用了整套分布式持久化架构，客体虚拟机看到的依旧是标准的虚拟磁盘。

虚拟机与快照存储的连接路径

[macOS 客体机内部 (Guest VM)]
应用与文件系统读写 (APFS / Xcode / iOS Simulator)
       ↓
标准虚拟磁盘（块设备块接口）
       ↓
==================== 系统分界线：macOS 宿主机 ====================
Virtualization.framework
       ↓ (NBD 协议 / 本地 Unix Domain Socket)
宿主机快照存储进程（NBD 前端接入原有快照存储引擎）
       ↓
分布式对象/块存储后端（增量快照、分层缓存与持久化归档）

停机生命周期的终结时序保证 (Finalization)

在虚拟化环境中，突发关机或资源强制回收极易导致块设备脏数据未落盘，进而损毁 APFS 元数据或快照镜像。系统建立了一套严格的停机终结时序（Finalization Pipeline）：

虚机退出与快照固化时序

虚拟机状态：   [ 正在运行 ] ──────> [ 断开连接 / 停止 ]
存储进程状态： [ 处理实时读写 ] ──> [ 写入挂起数据 ] ──> [ 快照就绪并上传 ]
虚拟化管理器：                      [ 阻塞等待数据落盘 ] ──> [ 清理回收机器资源 ]

当客体虚拟机由于任务结束或超时断开连接时，Hypervisor 并不会立即回收虚拟机内存与资源句柄，而是由宿主机上的独立存储进程接管：存储进程将内存中所有缓冲的待写数据（Pending Writes）刷新落盘，计算增量差异并向快照系统完成提交。只有当 Hypervisor 收到存储进程发出的 Finalization 确认信号后，才会执行真正的机器销毁与资源释放，确保会话恢复的百分之百完整性。

03网络层控制：自建用户态以太网网关规避防火墙竞态

三种网络模式与 pf 防火墙竞态根因

云端开发工作区对网络边界有着严苛的双向安全要求：一方面，虚拟机必须能够正常访问公共网络下载 CocoaPods、Swift Package Manager 依赖以及 GitHub 代码；另一方面，工作区必须严格阻断对 AWS 宿主机私有元数据服务（IMDS）、宿主机局域网内其他基础设施的横向探测。

苹果 Virtualization.framework 原生提供了三种虚拟机接入网络的方式：

网络接入模式 工作机制 主要优势 工程限制与缺陷
桥接模式 (Bridged) 将虚机以太网帧直接发往宿主机物理网卡 性能高，直接获得局域网 IP 暴露宿主机内网，无法在宿主机实施细粒度会话级流量拦截。
NAT 模式 (Apple NAT) 共享宿主机外部 IP，由 macOS 系统托管地址转换 开箱即用，自动分配 DNS 与网关 致命竞态：系统 Apple NAT 与 Devin 会话控制器竞相修改 pf 防火墙，产生配置覆盖。
文件句柄模式 (File-handle) 通过宿主机本地 Unix Datagram Socket 直接收发原始二层以太网帧 宿主机拥有对每个数据包的绝对控制权 宿主机必须承担二层链路解析（ARP 响应、MAC 校验等）的工程开销。

在裸金属多租户与会话隔离环境中，NAT 模式原本是最直观的选择。但 macOS 底层依赖 包过滤防火墙（pf，Packet Filter）。macOS 系统的 Apple NAT 服务在运行期间会动态重写 pf 规则锚点；而 Devin 自身的安全沙箱与网络策略控制器同样需要实时动态更新 pf 过滤表。两者同时并发操作同一个 pf 引擎，会产生不可调和的规则竞态（Race Condition），导致规则覆盖、连接重置甚至安全策略被静默旁路。

自建用户态以太网网关 (User-space Ethernet Gateway)

为从根源上杜绝竞态，团队放弃了苹果托管的 NAT 方案，果断下潜到底层“文件句柄模式（File-handle attachment）”。该模式下，宿主机与客体机之间通过 Unix 数据报套接字（Datagram Socket）连接，每个套接字数据报严格承载一个原始的二层以太网数据帧（Layer 2 Ethernet Frame）。

这一选择带来的代价是：宿主机无法直接接收标准的三层 IP 包。当 Guest 虚拟机初次尝试对外发包时，必须先在链路层广播 ARP 请求：“局域网网关的 MAC 地址是多少？”如果没有人响应 ARP，虚拟机的网络协议栈就会彻底阻塞。

为此，团队在宿主机上自主开发了一个用户态以太网网关（User-space Ethernet Gateway），承担起二层链路的完整控制：

虚拟机网络数据包往返链路

[ macOS 虚拟机 (Guest VM) ]
       │ 原始以太网数据帧 (Guest MAC → Gateway MAC)
       ▼
[ 宿主机用户态以太网网关 (User-space Ethernet Gateway) ]
  ├── 1. 响应虚拟机的 ARP 物理地址查询（伪装为默认网关响应真实 MAC）
  ├── 2. 严格校验以太网帧的源/目标 MAC 地址合法性（阻断 MAC 欺骗）
  └── 3. 核实以太网载荷中源 IP 地址是否匹配系统预分配租约
       │ 剥除以太网头，放行合法的纯三层 IPv4/IPv6 数据包
       ▼
[ 宿主机虚拟通道接口（Tunnel Interface / utun）]
       │
       ▼
[ 单一归口的 pf 防火墙规则与安全代理服务 ] ──> 审查出网流量并安全直连外网
明确的技术取舍：团队承担了在宿主机端自行解析数据链路层协议（ARP 解析、MAC 帧过滤、IP 校验）的开发代价，彻底避开了系统级 Apple NAT 与 pf 防火墙的规则竞态，并将出网流量完全收敛到单一归口的 Tunnel 虚拟网卡中，统一由会话策略执行精细化出网控制。

04镜像预制与预热：在系统开机前切断权限弹窗

macOS 权限机制与离线磁盘挂载 (Offline TCC DB Injection)

在苹果生态中，一台刚安装完 macOS 原生系统的机器距离开箱即用的自动化工作区存在巨大鸿沟。除了缺少用户账号、Xcode、模拟器运行时之外，自动化面临的最严峻障碍是苹果的 TCC 权限机制（Transparency, Consent, and Control）。

macOS 对屏幕录制（Screen Recording）、辅助功能无障碍控制（Accessibility）、全盘访问等敏感权限设计了严格的系统级确认弹窗。如果把这些授权留到智能体接手任务后动态触发，每一个弹窗都会成为堵死全自动流水线的路障，迫使 Devin 陷入停滞等待人类介入。

permission-dialogs.png · macOS TCC Modal Dialogs
默认 macOS 未处理时频繁出现的权限拦截弹窗：若在任务运行期间弹出，将直接打断 Agent 自动化链条（对应图片资产 /media/devin-gets-a-mac/permission-dialogs.png）。

如果尝试在开机后通过模拟鼠标脚本去点击这些弹窗，不仅极不稳定（弹窗出现时机随机且受系统动画干扰），而且在 macOS 现代化安全机制下，合成事件通常被禁止直接点击隐私确认按钮。

Cognition 的解决方案分为两阶段。第一阶段是离线挂载客体磁盘（Offline Disk Mounting）：在构建全局母盘镜像（Golden Image）时，宿主机直接将客体的 APFS 虚拟磁盘离线挂载到宿主机本地文件系统，直接绕开 macOS 图形界面，写入用户账号配置文件，并直接向系统级与用户级的 TCC.db 权限 SQLite 数据库中插入免弹窗白名单规则，在操作系统开机前就切断所有可能的权限弹窗。

在线预热：Xcode 依赖与 iOS 模拟器冷启消除

并非所有配置都能完全在离线磁盘阶段完成。例如：Xcode 首次启动需要验证许可协议、安装平台 SDK 核心运行时、解压设备支持文件；iOS 模拟器首次拉起需要解包完整的 iOS 运行时文件系统；Spotlight 桌面索引服务会在开机后疯狂消耗 CPU 建立本地文件缓存。

如果将这些留到 Devin 接手后再处理，Devin 将与 macOS 系统庞大的初始化任务争抢 CPU 和磁盘 I/O，导致初次编译或启动耗时成倍增加。因此，构建流水线引入了第二阶段——在线预热（Online Warmup）：

  • 启动预制镜像执行预热脚本：安装完整的开发工具链并预先触发 Xcode 的签名验证与证书配置。
  • 主动唤醒并就绪 iOS 模拟器：调用 xcrun simctl boot 提前拉起目标机型的 iOS 模拟器，等待其内部 SpringBoard 与系统守护进程完全进入可响应状态。
  • 等待系统后台索引平复：等待 Spotlight 文件检索与系统元数据构建完全落盘，并在快照固化前主动停用与开发无关的无用系统后台守护进程（Background Daemons）。

通过“离线预写权限 + 在线预热唤醒”的组合拳，Devin 接手工作区时面对的是一个已经完全就绪、开箱即战的纯净高性能原生环境。

04实时画面：让实时画面保持跟手

ScreenCaptureKit 缓冲竞争与独立副本隔离

在人机协同开发中，不仅 Devin 需要持续检查应用的运行状态，人类开发者同样需要随时观察画面并具备随时介入接管的能力。系统通过标准的 VNC 协议提供全桌面视图，并额外开发了一个单独映射 iOS 模拟器窗口的高保真独立面板。

但在云端视频流工程中，团队遭遇了底层图形框架的缓冲竞争（Buffer Contention）：苹果官方的现代化抓屏框架 ScreenCaptureKit 底层维护了一个容量极其有限的可复用图形缓冲区环（Circular Buffer Pool）。如果服务端为了进行编码或推流分析而长久持有某一帧的指针，就会直接耗尽该缓冲区池，导致后续屏幕帧直接发生硬件级丢弃。

为此，画面采集层设计了零拷贝/快速复制分流机制：一旦从底层捕获到 CMSampleBuffer，系统立即在最快速度内复制一份独立的内存副本送往编码器，并立即将原始硬件缓冲区归还给系统驱动，彻底解放 ScreenCaptureKit 的渲染流水线。

队列积压上限控制与关键帧强制同步 (Keyframe Fallback)

第二个挑战是队列积压问题（Queue Backpressure）。当网络传输出现瞬时波动、或智能体并发高负载导致客户端解码滞后时，视频帧在采集、编码、网络传输与显示任意环节都会发生排队堆积。堆积的结果是致命的：人类或 AI 看到的画面是 3 秒甚至 5 秒前的“旧世界”，产生极强的操作违和感与动作滞后。

为确保画面“时刻跟手”，系统实施了激进的流控策略：

传统简单丢帧策略的缺陷

  • 简单丢弃中间帧会导致解码器因缺少前置参考帧而发生马赛克与画面破损。
  • 若不丢帧强行按序播放，会导致操作延迟随时间线性累积，无法实时对齐最新交互。

Devin 的流控与关键帧恢复策略

  • 对缓冲区队列设置严格的帧数上限（Queue Threshold）。
  • 一旦检测到流落后于预设时限，果断丢弃积压的所有陈旧预测帧（P-Frames）。
  • 立即从最近的关键帧（Keyframe/I-Frame）恢复，或主动向编码器请求生成新的关键帧，瞬间对齐最新物理帧。

05无障碍树：让原生控件可查询

纯多模态截图操作的局限：慢且昂贵 (Slow & Expensive)

在传统计算机视觉操作（Computer Use）智能体方案中，最普遍的做法是纯视觉多模态路径（Screenshot-only Pipeline）：智能体截取整个屏幕的高清图像，将大图输入多模态模型，通过像素坐标推断按钮位置，调用虚拟鼠标点击，操作完成后再次全屏截图核验。

这种纯多模态路径在复杂的苹果原生开发中被证明是极其缓慢且昂贵的（Slow and expensive）：

  • 网络与 Token 开销剧烈膨胀：一次长程测试往往包含数十次点击与滚动，每次传输并解析 2K/4K 高清截图会导致模型推理开销陡增，延迟长达数秒。
  • 像素漂移与定位脆弱：由于 Retina 屏缩放比例、窗口位移或微小动画渲染，视觉模型推断的像素坐标极易发生漂移，容易误触到相邻元素。
  • 不可见状态无法透传：视觉截图中很难精准判断一个控件当前是处于 disabled、hidden 还是可点击状态，语义透明度低。

基于 accessibility-cli 的结构化语义闭环

与网页端智能体借助 DOM 树定位元素同理，macOS 与 iOS 原生操作系统拥有极其强大的底层语义基础设施——无障碍树（Accessibility Tree）。系统将图形界面的所有视图组件组织成一棵具有严格层级关系的结构化语义树，每个节点包含以下核心属性：

  • role（角色）：如 button、textField、scrollArea、window 等。
  • name（名称）：控件的可访问标签或文本内容，如 "Resume"、"Pause"。
  • value（取值）：输入框文本、滑块当前百分比等动态属性。
  • state（状态）：focused、disabled、selected 等状态位。
  • relationship（关系）：父子视图节点、从属约束。
  • actions（支持动作）：控件所声明支持的语义动作集，如 {press}、{setValue}。

借助开源项目 Dioxus 的 accessibility-cli 命令行工具，Devin 获得了对无障碍树查询、输入模拟与画面截取等原生基础能力的支持，构建出高效的结构化语义交互闭环：

智能体操作 iOS 模拟器的语义闭环

1. 智能体发起结构化控件查询 (JSON 语义匹配)
{
  "action": "query",
  "target": "ios",
  "role": "button",
  "name": "Resume"
}

2. 系统返回语义树匹配结果与临时句柄 (@handle)
@i17 button "Resume" {press}
（@i17 为精准引用句柄，button 为角色，Resume 为名称，press 为支持的操作）

3. 智能体直接调用句柄执行语义动作 (无需猜测像素坐标)
{
  "action": "act",
  "target": "ios",
  "reference": "@i17",
  "operation": "press"
}

4. 智能体重新读取无障碍树并断言状态变化 (例如按钮变更为 "Pause")

通过该闭环，Devin 无需在数百万像素中猜测坐标，而是直接定位稳定的系统句柄发起原生操作，执行耗时从数秒降低到数百毫秒，Token 消耗压减超过一个数量级。

多模态截图的互补定位：无障碍树并非万能。对于利用 Metal、OpenGL 或 Canvas 自定义绘制的游戏画面、自定义手绘曲线，控件并不存在于系统的原生无障碍树中。此时系统自动保留屏幕截图能力作为补充通道，形成“语义树操作为主、视觉截图核对自绘画面为辅”的完备双轨制。

06适用边界与工程启示

无障碍树的自绘画面盲区与视觉互补

Devin 的原生 macOS 支持打通了云端开发与验证苹果原生应用的技术路径，但在评估其工业落地适用范围时，必须清醒认识到其现阶段的技术边界：

  • 无障碍树无法覆盖所有视觉状态：无障碍树能够精准捕捉按钮状态变化（例如“暂停菜单从视图树中卸载”），但这并不能在数学上证明游戏角色的像素级物理坐标已经百分之百还原到原始位置。对于游戏物理引擎或图形渲染管线，系统必须依托屏幕截图核对视觉渲染结果。
  • 自绘 UI 框架的语义穿透损耗：如果应用采用自绘跨平台引擎（如部分自绘 Flutter 或 Unity 界面）且开发者未显式补全可访问性标签（Semantics），无障碍树将退化为一个单一的大黑盒，迫使智能体回退至纯多模态截图方案，交互效率将出现阶梯式下降。

工程基准的缺失与全链路启示

Cognition 的这篇官方技术说明详尽阐述了工作区的底层系统架构与产品实现路径，但从学术和严格工业评测的角度来看，仍存在客观局限：

缺乏量化基准数据：技术文档中交代了体系结构与交互方案，但未披露具体的运行性能、裸金属资源调度吞吐、基础设施金钱成本或端到端自动化成功率的量化数据。因此，尚无法直接将其与纯本地开发环境或常规 Linux 模拟工作流进行 ROI 的硬指标横向对比。

从虚拟磁盘 NBD 协议接驳、网络 L2 用户态网关规避防火墙竞态、镜像构建期离线注入消灭权限弹窗，到实时低延迟推流控帧、语义无障碍树快速驱动与多模态兜底核验，Cognition 展现的不仅是“让 LLM 多调几个 API”，而是扎扎实实的现代操作系统级虚拟化工程。

正是这些底层工程基础设施的打通，才让 Devin 跨越了“只会写代码的玩具”与“能够真机独立验证的工程师”之间的鸿沟，将单纯的语法生成延伸为面向真实应用世界的完整“开发—运行—验证闭环”。这正是本次原生 macOS 支持带给整个智能体行业的最大启示。
