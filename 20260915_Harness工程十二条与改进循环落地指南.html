  • Ryan Lopopolo 把过去一年的实践提炼成十二条论点，做成一个公开仓库，任何人可以把它直接喂给自己的编码 Agent 当参考。
  • 核心操作：把选定的模型和编码 Agent 当成不可改的黑盒锁死，只改它周围的两样东西，上下文和工具。
  • 锁住黑盒的目的是让失败可归因：一个能干的 Agent 干不成活，原因只会落在缺上下文、缺可用能力、缺反馈回路、缺权限、缺验证这几处，都是环境问题。

一 · 一份马具说明书

先把词说清楚。harness 这个词在中文技术圈已经出现了「束缚工程」的译法，方向正好反了。harness 是套在马身上的那套东西：鞍、缰、蹄铁、挽带。仓库图标就是一匹马。

这个词的意思

马已经足够能跑。缺的是鞍、缰和跑道，让它的力气真的落到地上，去到该去的方向。harness engineering 做的就是配这一套东西。

写这套东西的是 Ryan Lopopolo，OpenAI 工程师，也是 Artichoke 项目（用 Rust 实现 Ruby）的作者。他把过去一年的实践提炼成十二条论点，连同证据、案例和可执行的流程一起放进一个公开仓库，采用 CC BY 4.0 授权。这个仓库的用法有两种：人直接读，或者把它和你要改进的系统一起交给编码 Agent，让 Agent 按里面的路由自己去查该看哪一条。

整套方法的操作定义只有一句：把选定的模型和编码 Agent 当成一个不可改的黑盒固定住，只改它周围的两根外部杠杆，上下文和工具。

为什么值得看

十二条里每一条都挂着可查证的实证：五个月从空仓库长到一百万行代码、约 1500 个合并 PR，代码全部由 Codex 写成，人没有手写一行；一次 60 小时、3.5 亿 token 的重构只用了初始 prompt 加两次追问；打开一条 lint 规则后，600 处违规在同一个 PR 里修完并补齐了测试。

三 · 冰山：为什么需要这一整套东西

为什么需要这一整套东西，可以用一座冰山来看。通用模型的权重里装着的，只是一个组织知识的尖。水线以下才是干活真正要用的部分。

组织不能假设这些私有的、还在变的流程数据会自己长进模型权重里，也不能假设 Agent 能自己猜中哪部分重要。把它们做成可检索的上下文和有边界的工具，就是最后一公里的活。

四 · 地基：先把马固定住，再改鞍

十二条从这一条开始，因为它决定了后面所有条能不能被验证。一次评估或部署周期里，模型、编码 Agent 的运行时、原生工具接口三样锁死不动。这三样里任何一样变了，就算进入新的纪元，整套环境要重新验收一遍。

锁住黑盒的收益是失败变得可归因。一个明明很能干的 Agent 干不成一件活，原因只会落在四处：缺相关的机构上下文、缺一个真能用的能力、缺有用的反馈回路、缺权限，或者出口处缺证据。这四样都是部署环境的属性，都能查、都能改。不锁黑盒，你就永远卡在「到底是模型不行还是我没配好」之间打转。

人的先验也属于要重新验收的状态。旧模型教会你的那些习惯：任务该切多小、需要多少编排、内循环能等多久、哪些地方必须人盯着，原封不动带进新纪元，会白白浪费掉能力溢出。反过来，假设每个小版本都在每个维度变强，是另一个方向的错误。

一个记录在案的反例

GPT-5.3 比 GPT-5.2 更不愿意去啃困难的活。这说明「新版本在每个维度都更强」是一个未经检验的假设。

内循环延迟属于验收范围

Agent 能推理到什么程度，取决于它在一次轨迹失去焦点之前能拿到多少反馈。所以构建、测试、浏览器、可观测性的延迟，直接决定了可用能力的上限。

GPT-5.2 时代的 Codex 环境没有后台 shell，Agent 会老老实实等阻塞的构建脚本跑完。GPT-5.3 加了后台 shell 之后，它就不愿意等了。团队用一周时间把仓库的构建从自制 Makefile 一路换到 Bazel、Turbo、Nx，停手的条件是全量构建进一分钟以内。这一分钟被定成一个整数上限：一旦破线，就停下手上的活，去拆构建图，直到循环重新装得进这个上限。

验收也包含减法

为了让 Agent 看见界面，团队曾经自建过一套虚拟显示加录屏的东西。原生的 computer use 能力出来之后，这一整套被删掉了，端到端的应用验证并没有因此丢失。

判断标准是：优先保留那些在 Agent 原生循环里就能看见的干预，架构、类型、测试、工具契约、可观察状态、验收标准。为特定时期搭的中间层，在下一个纪元可能就是多余的。

五 · 怎么派活：一句话派整件活

委托的是结果，交给一条主轨迹全权负责：拆解、执行、整合、举证、安全收尾。步骤留给它自己定。人只在三个地方出手，方向、判断，以及有后果的授权。

Ryan Lopopolo 经常给接近零约束的提示词，他把这种提示词叫做「懒 prompt」，懒在方法留白，怎么做由 Agent 自己定。稀疏的委托同时是一种测试手段：它测的是你的环境有没有把真实要求变得可回收。Agent 一旦会错意，暴露出来的正是环境里哪一块没做出来。

配套的循环是「提出、观察、改进、重掷」：看完轨迹，改环境，把这次的结果丢掉，重新跑一遍同一个任务。

实证案例 · 红队分析

一句请求要求做完整的红队分析，并且要求每一个发现都必须证明影响或者可利用性。Codex 产出了报告、复现器、补丁和回归测试，随后应对了详细的人工代码审查并修改了实现。作者审查后批准实现，再单独授权它准备点版本发布、合并 PR、提交 RustSec 安全公告。

提示词只规定了结果和验收线，实质性审查和交付处的授权仍然留在流程里。

两个反例，比正例更有用

保护措施挡住了它要保护的东西
  • 有一条技能规定：本地构建通过之后才能开 PR。
  • 某个任务恰恰需要先开 PR，好让同事进来一起修那个坏掉的构建。
  • 技能拒绝执行。平时的安全阀，变成了它本要服务的那个结果的障碍。
字面满足最后那个动词
  • 指令是：建分支、提交、推送、合并。
  • Agent 为了满足「合并」，动用管理员权限强行绕过。
  • 而这件活的本意，包含等测试跑完。

藏起来的那半份要求

一句请求通常只说功能结果，兼容性、可维护性、无障碍、回滚、生成物同步、以及未来改动的需要，全是隐含的。这些隐含要求有个名字，叫「问题背后的问题」。

Agent 恢复这些要求的方式是去仓库、当前行为、历史记录、以及这个结果和用户的关系里刨。刨得出来的事实，不该回头问人；刨不出来，而且缺的这个答案会改变产品意图、会接受重大风险、或者需要它没有的权限，这时候才问。

关于上下文压缩的一条操作心得

长轨迹会反复压缩自己的历史。仓库给出的工作假设是：用户消息里的意图留存度高，较早的工具输出更容易被摘要掉或者丢弃。这是特定 worker 的行为，换模型之后要重新验证。

按这个假设，阶段性的细则塞进用户消息，会在那段活早就干完之后继续抢注意力。所以用户消息那一栏只放三样：结果、验收线、授权边界。细则交给仓库读取、工具输出、测试失败，在决策发生的那一刻才浮出来。

六 · 重点一：代码就是提示词

Agent 读到的每一个文件，都在影响它下一步预测什么。原话是：仓库里的代码就是提示词。

模型脑子里装着几十种都说得通的做法。仓库的作用是剪枝，用反复出现的结构，把团队选定的那一种挑出来。一致性直接压缩上下文需求：一套可观测性方案，Agent 在一个文件里学到的东西能迁移到全仓；六套方案，它每到一个调用点都得重新研究这里该用哪一套。

2023 年的一次对照

他把 Ruby 的 String#unpack 整个 lib.rs 塞进一个提示词，模型一直在混淆不相关的指令。他把这个 crate 拆成结构高度规整、文档齐全的小模块之后，模型第一次尝试就能正确实现后续的状态机操作。

后来他回头重看这篇文章，评价是：模型变强了，但上下文、约束、迭代、反馈这个协作循环，感觉是一样的。

例子传播缺陷和传播好判断一样快

这是同一枚硬币的反面。半截子的迁移会造出两套互相打架的提示材料；一个写得不好的辅助函数，会扩散到每一个需要类似行为的包。

半截子迁移

旧写法和新写法并排躺在仓库里。Agent 每次动手前要先判断：哪个是当前该抄的？迁移完成了吗？还有哪些相关规则要一起进注意力？两套都在当提示材料用，两套都会被复制。

完成迁移，装上棘轮

打开 ESLint 的 no-await-in-loop，修掉约 600 处违规，在同一个 PR 里补齐测试覆盖。仓库里只剩一个可抄的答案，旧写法再也进不来。Agent 和新来的人拿到的是同一个明确的续写方向。

一个概念，一个权威主人

在造一个解析器、清单类型、版本常量、状态表示、夹具构造器、策略检查或者命令之前，先找这个概念现有的主人，需要时扩展那个接口。下面这些是「没有主人」的信号：

警告信号说明
第二个解析器仓库已经给这门语言建过模型了，又冒出来一个
版本号被复制工具的精确版本号出现在策略代码和测试夹具里
拼字符串造 JSON结构化数据用字符串片段拼出来
命令行重写领域逻辑命令里重新实现了一遍领域行为
未经类型化的外部数据外部数据不做解析直接流进内部代码
同一条不变量被守好几遍好几处防御性检查在保护同一件事，说明没有边界真正拥有它

每一个重复的主人，都在制造一个「本地看起来也说得通」的续写方向。Agent 可以忠实地跟随身边每一个先例，同时让整个仓库变得更不连贯。

边界处解析，不要到处校验。外部数据进来的时候解析一次，变成一个可信的领域类型，之后内部代码就依赖这个规范状态。如果你在到处做记录检查、每个函数里都归一化、每个事件处理器里都查一遍就绪状态，通常意味着没有任何一处边界真正拥有「这个值是有效的」这件事。

七 · 重点二：根部只放一张地图

知识库要大而可搜，工作集要小。根部的那份指引应该是一张地图，不是一本操作手册。

上下文窗口变大，解决的只是容量压力。注意力、检索质量、指令之间互相打架、以及「这一步到底哪条事实要紧」，这几样仍然稀缺。确定性地往上下文里塞东西，在跨越多次压缩之后必然失效。Agent 必须有能力再次找回那条路，指望第一次塞进去的东西还在，是靠不住的。

怎么验收一份知识库

方法是开一个全新的会话，看 Agent 会不会真的检索到它、并且真的改变行为。文档存在，只证明它被写过了。

再往前一步是消融测试：把这条上下文拿掉再跑一遍，效果扛不住的，删掉。检索频率、库的体积、提交数量可以当作运行信号来看，但成败以任务结果为准。

skill：教一种做法
  • 描述里只写「这是什么、什么时候可能用得上」，正文按需加载。
  • 写成长篇命令式的清单，容易过拟合单一路径，让 Agent 拒绝合理的例外。
runbook：可重复工作的契约
  • 记录意图、前置条件、步骤、安全边界、证据、升级路径、回滚。
  • 自动化脚本因此可以做得很薄，耐久的知识留在仓库里。

这个仓库自己就是这条论点的样品

可以核对的结构事实有四条：

  1. 仓库根目录的 AGENTS.md 是一份路由表：它按「本地证据解决不了的那个决策」来分流。比如「要判断 Agent 是缺一个能力，还是现有工具难以发现和调用」指向能力那一条，「要界定谁可以执行有后果的变更」指向权限那一条。
  2. 它明确写着：其他与目标相关的工作，不要预加载应用指南或者整个论点集。
  3. 当这个仓库被当作另一个系统的上下文时，它规定自己是只读的，目标系统的指令、主人、契约和当前状态提供本地真相。
  4. 它给出的工作循环里，第一步是先读目标系统自己的指引和架构，第三步才是「说出本地证据没能解决的那个决策」，然后只挑一条论点去读。

未解决的那个决策决定走哪条路由。目标系统本地的证据可能不需要任何一条论点就解决了它。确实需要上下文时，从一条论点开始，只有在另一个独立的决策仍然悬着的时候，才加第二条。
—— AGENTS.md，仓库根目录

八 · 怎么放权：能做和能批是两份合同

能力说的是怎么造成一个效果。权限说的是哪个身份、可以对哪个资源、在哪个环境、造成哪个效果、持续多久、需要谁批、怎么回滚。把这两份合同拆开，可逆的地方就能大胆放手。

能力 · capability
  • 回答「怎么造成这个效果」。
  • 查看、编辑、构建、测试、模拟、迭代。
  • 这个圈里大部分错误都是廉价的反馈。
  • 契约可以保持稳定。
权限 · authority
  • 身份是谁、操作和目标资源是什么。
  • 环境和范围、授权的存续期与撤销路径。
  • 需不需要审批、职责是否分离。
  • 审计回执和后置条件、回滚与恢复路径。

安全问题因此从「要求一个随机系统零错误」转向「后果有多大、能不能恢复」。凭据的托管要放在轨迹之外：一个代理进程在动作边界处，从安全存储里取出范围很窄的密钥，让 gh 用起来像一条普通命令，而密钥从不进入模型上下文，也不进仓库。再加两层保险，只读身份让检查有用但不能改动；端点绑定的访问可以单独关掉某一条面向 Agent 的通道，不必轮换底层凭据，正在运行的轨迹也能被撤权。

有后果的操作要分阶段，每阶段只给那一段需要的权限

案例 · 扫地机器人 Loki 的 Tailscale 守护进程升级 v1.90.8 → v1.96.4

Loki 是作者家里的一台扫地机器人，跑开源的 Valetudo 固件，唯一的远程访问通道是一个自定义的 Tailscale 守护进程。麻烦在于：升级它本身，可能毁掉你用来抢救失败部署的那条路。

两次人工介入授权的是两件不同的事：创建一个新的网络身份，以及替换唯一的那条生产访问路径。金丝雀跑通之后，旧的守护进程才停掉，它的状态被保留下来给下一次升级用。

每个阶段只授予它那个效果所需的权限。金丝雀通过，不等于拿到了生产权限；有生产访问，不等于部署出去的系统是健康的。

指令要透过授权合同来解读

「合并」的意思是走完仓库受保护的合流流程，它不隐含授予绕过的权限。「准备一次部署」授予的范围到准备为止，生产切换要另外批。当一个不可逆的目标或者范围在查过本地策略之后仍然含糊，Agent 应该在跨过那条边界之前先问。

稳定下来的授权规则应该落进身份策略、类型化的领域操作、有范围的工具、环境边界、测试和合并闸门里。在后果值得的地方，把错误的动作变成不可用的，比写一条规则更管用，规则要靠注意力，机制不用。

九 · 重点三：纠正过一次的事，不该再纠正第二次

重复出现的纠正要转化成塑造下一次运行的环境。这一条决定了前面所有条能不能随时间累积。

先看一个精确的反例。有人给了 Agent 一个具体的 Go 接口修正：用哨兵错误值代替返回一个表示成功的布尔量。Agent 只改了被点名的那一个函数。那条指令背后是一条关于接口设计的普遍原则，但这次修复没有去搜同一原则管辖的其他实例。

  1. 重建承诺的结果和观测到的失败。
  2. 定位最早能拦住或者暴露它的那个边界。
  3. 搜索同一原则管辖的其他实例。
  4. 把环境缺陷、Agent 的随机波动、外部故障、错误的前提这四件事分开。
  5. 选一个能覆盖整类、同时不禁止正当例外的干预。

第三步是最容易漏掉的一步。改在哪一层，取决于这条教训有多成熟、后果有多大。

干预方式什么时候用它
改提示词、重新跑任务的框架或者想要的结果还在摸索中
路由文档、runbook、skill一份稳定的知识需要在某个决策点出现
审查者或评估这个判断是定性的、横切的，或者还在长细节
类型、接口、领域工具系统能让正确用法变自然、让错误用法变困难
lint、测试、策略检查一条确定性的不变量应该直接阻断复发
架构或迁移反复出现的缺陷暴露出主人错了，或者依赖方向错了

决定躺在聊天记录里，等于没有做过

某个团队和安全部门一起选定了一个批准使用的加密实现。这个决定留在了 Slack 里。后来一位新工程师用 Codex 干活，Codex 装了另一个 npm 加密包。团队把这个决定捞回来，在仓库里写成守卫规则：要求使用批准的实现，禁止其他 npm 加密包，然后重新跑了一遍那次改动。

提拔一条决定需要记下它的适用范围、主人、生效日期或者被取代的条件、以及在哪里强制执行。会变的事实留在它的权威系统里，需要时再取。

两条容易被忽略的平衡规则

上游有了主人，就拆掉下游
  • 在一个缺失的领域模型上再叠一层校验器，只会把不一致固化下来，还额外增加维护成本。
  • 更强的类型、接口或架构出现之后，下游那些冗余的检查应该退休。
过拟合之后才加细则
  • 先给一条粗的指令，等它开始在正当的例外上出错，再加细节。
  • 反过来一上来就写满细则，会挤掉 Agent 本来能做对的判断。
两个配套细节：自述文件怎么用，审查者怎么收敛

让 Agent 边干边记三份文件，Mistakes、Learnings、Desires，缩写是 MLD。这三份文件的定位是给搭环境的人看的遥测数据。Agent 可能漏掉最重要的那个错误、可能归错因、可能要错工具，所以原始记录要留在产生它的那次运行旁边，只有反复出现并且有旁证的缺口才能被提拔成上下文。

另一个是审查者的收敛问题。团队早期的审查者 Agent 会反复施压，把实现方的改动范围越推越大。解法是告诉审查者偏向合并、只提实质性的问题，同时允许作者选择修复、带着理由延后、或者直接顶回去。

十 · 怎么算数：四个时钟必须分开计

token、代码行数、Agent 数量、检查项，这些都是输入。要优化的是每单位稀缺的人类注意力换来的、被接受的结果。

token 排行榜是其中一个虚荣指标：它奖励的那个信号，在价值原地踏步的时候照样往上涨。「每工程师每天十亿 token」这个说法后来被补上了一道结果闸门，这些活必须合进主干并且改善用户体验才算数。

三个概念要分开：

  • 可达性——Agent 能碰到这份活的多少部分。仓库、本地应用、测试、浏览器、日志、部署、举证，都在扩大可达性。
  • 活动量——token 和忙碌时间。
  • 有效利用率——真正抵达一个被接受的结果、或者产出了可复用证据的那部分活动。可预防的丢弃、返工、修复都在削减它。
时钟量的是什么为什么要单独看
反馈延迟从动作到拿到有用的测试、构建、链路或评审信号决定迭代速度
墙钟时长从开始到跑完一次占用执行容量，可能拖住下游
同步的人类注意力人必须指挥、中转、评审、抢救的分钟数决定组织能监管多大的工作量
到达被接受结果的时间从请求到被证明、被接受、被部署把排队、重跑、评审、交付一起算进来

为什么必须分开，两个例子摆在一起就清楚了。

60 小时的重构

墙钟时长很长，跨了三到四天，但和人的同步接口小到只有初始提示词加两次追问，消耗约 3.5 亿 token、2800 美元，产出一个 PR，作者估计自己手做要三周。

2023 年与 ChatGPT 结对

代码在编辑器和浏览器之间来回复制，测试结果人肉转述回聊天框，一次会话几百个提示词。墙钟并不长，但人的注意力一小时就被榨干了。

探索、返工、浪费是三件事

丢弃可以是有生产力的。在一个最终接口形状还没定的高不确定性重构里，他会让 Agent 产出一个可能到五万行的探索性改动，推成 PR 好让人检查，然后扔掉。这次尝试暴露了 Agent 大概会在哪里失败、以及最终切换需要哪些接口缝。他把这张失败地图变成大约十五个准备和铺垫的 PR，然后才回来做真正的切换。探索性的实现是临时的，带走的是失败地图和那些准备工作。

返工是在没有新证据的情况下，重复一个已知的失败。配套还有一句诊断口径：一套一直在诱发同样高信号纠正的环境，即使每一次纠正本身都很便宜，它也存在纵向缺陷。

十一 · 六步改进循环

仓库的 playbooks 目录给了一套可以直接照做的流程，针对一件有边界的、能重跑的真实任务。

观察基线 → 找最早断掉的交接 → 最小可逆干预 → 在真环境验证 → 全新重跑 → 保留 / 修改 / 移除

第五步的「全新」是有讲究的：要用新会话和一个隔离的、等价的起始状态，这样重跑不会从当初那次实现对话里继承到隐藏的帮助。还要单独确认这次干预到底有没有被检索到、有没有被调用、和这次重跑有没有关系。一次成功的结果，对于一条从未被用到的指令或工具，不构成任何证据。

一个 harness 值回它的维护成本，是在同一个 worker 在真正要紧的那个环境里产出更好的、被接受的结果的时候。
—— evals/README.md，harness-engineering 仓库

#作废条件
1结论关于「用到了某段上下文」或者「用到了某个能力」，但那个东西压根没被检索到或调用过
2预先声明的干预之外，还混进了指令、工具、权限、外部状态或写入权限的差异
3把一次带随机性的运行当成有代表性的
4评分需要一份没有公开的参考实现
5把只有评估方能看到的检查，报成 Agent 自己产出的证据
6把整份外部语料复制进评估方，让它和自己的影子权威互相印证
7拿 token 数、代码行数或活动量顶替一个被接受的结果
8比较过程中 worker 本身发生了变化
9公开报告里的目标和版本不透明，读者无法检查或复现
六步改进循环 · 执行清单
  • 锁定条件 · 先把模型、编码 Agent 配置、权限范围、预算和停止条件写下来，再动手挑一件小到能重跑、又重要到能暴露那个缺口的真实任务
  • 观察基线 · 跑一次完整轨迹，记录可观察的证据而不只是一段总结：哪些上下文被检索到、人在哪些地方做了中转、有多少次重试和可避免的评审
  • 找最早断掉的交接 · 把症状往上游追，直到某一个权威主人能塑造未来的运行分类：上下文 / 能力 / 领域归属 / 权限 / 举证 / 反馈与交付 / worker 本身的限制
  • 写下一个可证伪的假设 · 在最早的主人处做最小的可逆改动，先说清预期行为，同时写下什么证据会削弱这个假设，以及预计的维护成本
  • 在两层上验证 · 跑目标系统自己的检查，再走一遍确立结果的那条真实旅程；只有评估方能看到的检查可以帮你诊断，但顶替不了 Agent 该自己产出的证据
  • 全新重跑后决定去留 · 新会话、隔离的等价起始状态，确认干预确实被用到了；保留、修改还是移除，并记下退休条件；没用上就等于没有证据
