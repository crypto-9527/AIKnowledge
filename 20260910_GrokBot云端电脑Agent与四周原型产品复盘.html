一个月做出 GrokBot：从聊天框到「拥有自己电脑的 AI 同事」

Roman Ugarte 讲述 GrokBot 的诞生：为什么离开 Cursor 另起炉灶、为何给 Agent 一台云端电脑， 以及一支数人小组怎样用四周做出内部可用原型，再靠人工引导、删功能和可靠性修补走向公开发布。 本文在忠实还原访谈内容的基础上，把其中的定性判断转写为四组可计算的交互沙盘， 并对所有无法独立核验的数字做出显式标注。

受访者：Roman Ugarte（GrokBot 产品负责人，Cursor 第 15 号员工） 节目：Lenny’s Podcast #713 · 2026-09-08 消化日期：2026-09-10 四组可计算沙盘 · 零外部依赖

核心要点（TL;DR）

  • 90% 与 100% 之间是质变，不是量变。只要你还不敢离开，任务就没有真正交出去——AI 只是换了一种方式把工作还给你。
  • 两个底层架构决策：一切长在云端（状态持久、跨端连续）；每个 Bot 拥有自己的云端电脑（Computer Use），而不是共享屏幕。
  • 不把知识工作塞进 Cursor，是为了避免「把公司内部组织架构当成产品形态交付给用户」（Shipping your org chart）。
  • 三阶段时间线：约 4 周做出内部可用原型 → 约 3 周内测走向公开上线 → 录制时距公开发布又过约 3 周。
  • 内测三周主要在「删」：拿掉思维链与工具调用日志，把「GrokBot now has …」改写成「GrokBot can now …」。
  • 护城河是被发现的，不是被规划的：预判未来 3–6 个月模型能做什么 → 用脚手架提前交付 → 模型原生补齐后果断删掉脚手架。

一 · 以同事为尺：把 Agent 当作拥有电脑的同事

Roman 认为，多数人目前仍把 Agent 理解为「聊天机器人 + 若干外部连接（API / MCP）」：你向它发问， 它调用搜索或特定的企业软件接口，最后给出一段回答。GrokBot 团队在一开始就确立了一个思考锚点—— 以同事为尺（Colleague-pilled）：如果把 AI 当作真实世界里招募的一位新同事，我们究竟会如何与它协作？

这个锚点的价值在于它把产品问题从「我们该接哪些 API」改写成了「一个新人入职需要什么」。 顺着后者推导，会得到两个在前一种框架下几乎不会出现的架构决策。

1.1 决策一：彻底全云端化，状态持久保留

在早期探索中，OpenClaw 给团队带来了重要启发。Roman 提到它做对了两件关键的事： 一是给强模型提供了更真实的系统工具能力，二是率先把 AI 的心智模型从「聊天对话」推向了「协同工作的同事」。 GrokBot 从中汲取灵感，并试图把这些原语产品化，以降低设置门槛。

Roman 所描述的使用摩擦集中在三处：

  • Agent 究竟运行在本地还是云端——这个选择本身就不该抛给用户；
  • 电脑是否需要保持唤醒——手机下发的任务不该依赖家中那台机器的电源状态；
  • 从手机发出的任务是否仍依赖家中的电脑——跨端连续性被物理设备绑架。

GrokBot 的回应是让所有 Agent 统一长在云端。每一个 Bot 都是一个长期存续的实体， 拥有连续的交互记忆，不再是「一开新会话就失忆」的临时会话。用户在手机上发一条消息、 在电脑上安排一项长期任务，Bot 都在同一套状态下在后台静默运转。

为什么这不是一句口号

「云端运行」在工程上等价于三件事：状态存储与进程解耦、任务可在无人值守下继续推进、 以及跨端会话共享同一份长期记忆。这三件事任意一件缺失，用户就会退化回「我得盯着它」的状态—— 而这恰恰是 GrokBot 想消灭的东西。

1.2 决策二：让每个 Bot 能使用自己的云端电脑

这是整个产品最核心、也最具争议的技术决策。很多技术团队倾向于通过 API 或模型上下文协议（MCP）去连接外部工具， 但真实工作场景中存在两个现实障碍。

障碍一：现实世界中大量关键业务工具没有好用的 API。 Roman 以销售团队使用的工具和 Salesforce 仪表盘为例；即使存在部分接口，也未必足以覆盖真实工作流程。 这是一个覆盖面问题，而不是接口质量问题——接口再好，只要不存在，路径就是断的。

障碍二：共享屏幕的荒谬性。Roman 打了一个比方：

如果公司新入职一位人类同事，你绝不可能对他说：「你没有自己的电脑，你就坐我旁边，我们俩共用这台笔记本，共用一套账号密码，屏幕点按互相打架。」

团队没有在访谈中公开具体的运行实例拓扑，但 Roman 确认这些长期存续的 Bot 能使用自己的云端电脑。 这意味着它能尝试像人类一样通过像素识别、移动光标与输入字符，与各种网页和桌面应用交互。 当遇到没有 API 的老旧系统或复杂网页时，Bot 因而多了一条通过图形界面推进流程的路径。

访谈未披露的部分，本文不做增益。每个 Bot 具体如何做资源隔离、单实例成本是多少、 闲置时如何回收——访谈均未公开。因此能够确认的只是「Bot 可使用自己的电脑」这一产品抽象， 而不是一套可以据此估算的基础设施拓扑。

更重要的是，GrokBot 团队认为这种云端电脑的底层操作在未来应当对用户彻底无感。 用户不需要像操作远程桌面一样去接管屏幕，AI 只需要汇报工作进度， 底层的「电脑操作」只是它干活的实现机制——这一判断直接决定了后文第三节的「删产品」动作。

1.3 沙盘 · 委托减负：为什么 90% 完成度不等于 90% 减负

Roman 的核心断言是：「完成 90%」与「完成整项工作」之间存在质变。 前者仍需人全程监督，后者才会带来把责任交给一位同事的感觉。这个断言很好，但它是定性的。 下面这组沙盘把它转写成一个可计算的约束。

沙盘 1 · 委托减负计算器

Delegation Lab

模型：端到端成功率 P=sk（单步成功率 s 的 k 次方）； 人类总投入占全量工作的比例见下方公式。其中核验项 θ(1−P)η 是模型的关键——要判断那 10% 对不对，你必须先理解全部 100%，所以核验成本是完成度的凹函数而非线性函数。 所有参数均为可拖动假设值，非访谈数据。

EC=d+θ(1−P)η+(1−P)β R=1−EC,P=sk,η=0.5
E = 人类总投入；C = 人类亲自做完这项工作的成本；d = 委托成本（说清需求 + 最终验收）占比； θ = 核验门槛系数（通读并判断产出是否可信的固定开销）；β = 返工系数（修复未达标部分的开销）； η = 核验凹性指数（0 < η ≤ 1，越小表示核验的固定门槛越硬）。R 为有效减负率。 令 x=1−P，盈亏平衡点由 βx2+θx+d−1=0 反解得 P*=1−x2。

人类投入 E / C0.7790
有效减负率 R22.10%
盈亏平衡临界 P*0.3229
达标所需单步 s0.99475
判定：尚未真正交出去。端到端成功率 54.38%，有效减负 22.10%——你省下的远少于一半， 而核验与返工吞掉了绝大部分收益。这正是「90% 完成度」的真实处境：任务名义上快做完了，责任却还压在你身上。

曲线在纵轴下界（−30%）处会被坐标区裁剪；精确值请以数值槽位为准。虚线为盈亏平衡临界点 P*，圆点为当前参数组合所处位置。

沙盘 1 读出的三条结论

  1. 减负率随完成度呈凹形追赶，而不是线性跟随。在默认参数下（θ=0.60、β=0.60、d=0.10、η=0.5）， P=0.95 时有效减负 73.58%，P=0.90 时 65.03%，P=0.70 时 39.14%， P=0.50 时仅 17.57%。也就是说，「做对了 90%」换来的只是不到三分之二的减负。
  2. 存在硬性的盈亏平衡点。默认参数下 P*=0.3229： 端到端成功率低于 32.29%，委托在数学上反而比自己做更贵（P=0.30 时减负率为 −2.20%）。 「有点用但不太可靠」的 Agent 是负资产，不是打折的正资产。
  3. 长流程是单步可靠性的放大器。单步 s=0.97 看似优秀，但 20 步任务的端到端成功率只有 54.38%； 要让 20 步任务达到 P=0.90，单步成功率必须提到 0.99475；要达到 P=0.95 则需 0.99744。 这解释了为什么 GrokBot 内测三周把力气花在「点得准不准、能不能登录」这类基础能力上，而不是堆功能。

稳健性检验（结论定稿前必做）。上述第 1 条对参数敏感吗？把 η 从 0.5 扫到 0.3 与 1.0， P=0.90 对应的减负率区间为 53.93% ~ 78.00%；把 θ 从 0.30 扫到 0.90，区间为 55.54% ~ 74.51%；把 β 从 0.30 扫到 1.20，区间为 59.03% ~ 68.03%。 结论方向稳健：在全域扫描下，90% 完成度的有效减负率始终显著低于 90%， 但幅度对核验凹性 η 最敏感（跨约 24 个百分点），不可当作精确值引用。 详见附录。

二 · 为什么离开 Cursor 另起炉灶

在孵化 GrokBot 之前，团队背后的核心产品是已经在程序员中建立起口碑的 AI 代码编辑器 Cursor。 Roman 加入时团队约 15 人，后来扩至 1000 多人。主持人在访谈中把 GrokBot 的选择与另一种产品路径对照： 把多种 Agent 形态放进同一个界面，每扩展一种任务形态就增加一个标签页，最终容易显得拥挤。

Cursor 团队内部曾有过激烈探讨：程序员也经常在 Cursor 里写非代码的内容，直接在现成产品上迭代岂不是阻力最小？ 但他们最终选择了完全从零开始做独立产品。

2.1 避免「把公司的内部组织架构当成产品形态交付给用户」

这个理由被 Roman 概括为 Shipping your org chart——当一家公司有多个团队、 多条产品线时，最容易发生的错误是让产品界面去映射内部的汇报关系，而不是映射用户的心智模型。 具体到 Cursor 与 GrokBot，这个判断有两条支撑：

支撑一：认知门槛与心智包袱

代码工具的界面密布着终端、文件树、调试面板，对非技术人员具有天然的劝退感。 如果只是在一个代码工具上硬塞一个「非代码工作区」，不仅界面会变得杂乱臃肿， 而且用户能清晰地感觉到这是几个不同产品愿景在强行共用一块屏幕。

支撑二：全生命周期的产品控制力

要打造适合通用办公的「同事感」，必须对界面上的每一个像素、每一处交互流向拥有完全从零设计的掌控力。 这不是审美偏好问题——后文第三节的「删掉自动化配置页」这类动作，只有在你同时拥有界面与行为的定义权时才做得到。

2.2 三阶段时间线：一个月做到的是什么，没做到的是什么

访谈中的数字均为约数，但结构清晰。需要强调的是：「一个月做出 GrokBot」指的是内部能跑通关键链路的最小可用版本， 绝非对外发布的成熟成品。

  • 第一阶段（约 4 周）：写下第一行代码到拿出首个内部可用的原型（functional, useful prototype）。
  • 第二阶段（约 3 周）：从内部测试（Internal Beta）走向公开上线（Public Launch），集中攻克关键系统问题。
  • 第三阶段（约 3 周）：录制访谈时，距离公开发布又过去了约 3 周，产品仍在极早期演进中。

团队先在全员会上推广 GrokBot，把它当作现实压力测试；第一周，来自意料之外部门的一些同事 把原本在 ChatGPT 或其他聊天界面上做的日常 Agent 任务迁到 GrokBot； 看到这种跨部门的真实工作迁移后，团队立即转向公开发布准备。 这里的关键信号不是「用得多」，而是「迁移」——用户把已经在别处跑通的工作搬了过来， 说明新产品在那件事上确实更好，而不只是新鲜。

2.3 小团队为什么能在四周内做出原型

在 Roman 看来，能在一个月内拿出原型，不仅是研发隔离的结果，更依赖于特定的组织条件。 团队组建了一个极小的封闭小组（仅有数人），搬到办公室的独立物理区域， 使用独立的私密 Slack 沟通频道，在与外界相对隔离的状态下快速做出海量微观决策（micro decisions）。

条件具体做法作用机制
物理与信息隔离数人小组、独立办公区域、独立私密频道压缩协调面，把决策回路缩短到「看到即改」
高度信任与共识对前进方向有清晰共识，彼此信任对方能独立交付省掉对齐成本，避免共识驱动的漫长规划周期
守护初创感即使公司整体规模扩大，仍刻意保留「略带混乱但能极速产生实际影响」的氛围防止流程化吞噬速度
删产品（deleting the product）敢于下线甚至砍掉多余功能让界面与代码量始终小于问题规模
直接把事情办成（just do the thing）看到该做或该修的事时，不层层请示，主动认领并拉齐资源消灭等待队列，这是速度的直接来源

Roman 认为，如果当时采用大团队配合 6 到 12 个月的宏大愿景推进，很可能根本走不到最终结果。 需要说明的是，他将这些解释为小团队在早期保持超常敏捷的组织土壤，而非普适的通用管理法则。

一个可算的旁证。沟通通道数随人数按 N(N−1)/2 增长： N=5 时仅 10 条，N=15 时 105 条，N=1000 时 499500 条。 这条算术本身不能解释 GrokBot 为什么成功，但它说明了「隔离」这个动作在数学上削减的是什么。 本文不引入 USL 之类的并发模型去拟合团队产出——访谈没有提供任何可拟合的数据，那样做只会制造伪精确。

三 · 从内部原型到公开上线：接下来三周主要在「删」

当产品在公司内部推开、并逐步启动外部定向测试时，团队面临的最大挑战不是「功能不够用」，而是「功能做多了」。 在临近正式发布前的约三周里，产品经历了密集的下线功能（Unshipping）过程。

3.1 拿掉工程师思维的「透明度工具」

内测初期，为了方便排查问题，界面暴露了模型内部思考、记忆与工具调用等调试信息。 这些细节在开发者看来很有掌控感，但在通用办公中却造成了严重的认知过载。

你不会要求真实同事每隔三秒向你汇报「我刚才点了哪个按钮、在脑子里想了哪句话」。

团队收到过一些反馈，部分用户希望看到 Bot 的待办清单和大致优先级； 但没人要求长串文本流和 chain-of-thought。 最终团队将界面大幅精简：Bot 收到任务后，用户主要看到的是类似 Slack 风格的「正在输入」与绿色在线状态灯； Bot 按需发送阶段性进度，完成后呈现结果。

这个动作与第一部分是同一个判断

「云端电脑操作应当对用户彻底无感」这句话，在工程上的落地形态就是删掉所有暴露实现机制的界面。 展示工具调用日志，等于强迫用户去理解一台他本不该关心的电脑。 反过来说，只要你还觉得这些日志有用，通常意味着端到端成功率还不够高，你得靠读日志来判断它有没有做对—— 而这正是沙盘 1 中核验成本 θ 居高不下的症状。

3.2 沙盘 · 从「增加了什么按钮」到「Bot 能完成什么」

传统 SaaS 软件非常执着于在界面上展示「功能点」（侧边栏设置项、流程图构建器、多选下拉菜单）。 但在 Agent 时代，每增加一个复杂的界面控件，往往意味着把本该由 AI 处理的负担甩给了人类。

典型的例子是自动化流程（Automation）的配置：很多工具的做法是在界面左侧提供复杂的流程画布—— 点击新建、选择触发条件、选择响应动作、配置定时器，交互极其繁琐，导致普通用户极少去配置自动化。 GrokBot 选择彻底干掉自动化配置页面，直接支持自然语言定义：「每天早上 8 点提醒我。」 所有的调度逻辑全由 Bot 在后台自行管理。据 Roman 称，平台上 99% 的自动化是通过这类自然语言对话建立起来的 （受访者口述，非独立第三方审计）。

这种对多余控件的克制，逐步沉淀为团队内部可复用的两道判断题，下面这组沙盘把它做成了可操作的工具。

3.3 沙盘 · 内测三周的真实攻坚：可靠性，而不是功能

在公开发布前的约三周内测中，团队所做的工作远不仅是做视觉减法。Roman 透露，当时的 Bot 依然存在大量基础失败， 例如经常点不中目标按钮、或者卡在系统登录环节无法进入。 团队紧盯真实用户的具体任务，收集任务与失败类型，量化并按周改善。 在那三周时间里，工程团队集中处理了大约 5 个最关键的后端问题。 即便如此，系统也并非已经能稳定接管任何复杂流程。

沙盘 3 · 电脑操作可靠性攻坚

Reliability Lab

模型：初始单步失败率 f0 由 m = 5 类已知缺陷 （此处取访谈中「约 5 个最关键后端问题」作为结构假设，非精度数据） 与一类残余未知缺陷构成，残余权重 wres。修复 n 类已知缺陷后：

f(n)=f0[(1−wres)(1−nm)+wres],s=1−f(n),P=sk
残余项是关键：它意味着修完 5 个已知问题不等于成功率为 1。 本文初稿曾使用等权模型（修满即 s=1），会显著高估收益；加入残余项后结论被自己的模型修正，见下方读出的第 2 条。
修复后单步成功率 s90.00%
端到端成功率 P = s^k12.16%
相对 n=0 的提升倍数1.00×
残余失败率 f(n)10.00%
判定：不可委托。端到端成功率 12.16%——在 20 步的任务上，这个 Bot 几乎每次都需要人工接管。 此时任何界面优化都是次要的，首要工作是把 s 拉上去。

沙盘 3 读出的三条结论

  1. 在长流程上，基础可靠性压倒一切。默认参数（f₀=0.10、w_res=0.25、k=20）下， 一个问题都没修时 P 仅 12.16%；全部修完后升至 60.27%，提升 4.96 倍。 同一组参数下，任何界面层面的优化都不可能产生这个量级的差距。
  2. 收益是加速的，但天花板由残余缺陷决定。P 的增量序列为 12.16% → 16.92% → 23.42% → 32.26% → 44.20% → 60.27%，每修一个问题的边际收益递增。 但即便修满 5 个，残余失败率仍停在 2.50%，20 步成功率只有 60.27%—— 距离沙盘 1 给出的 90% 门槛（需单步 s ≥ 0.99475）仍有数量级差距。 这也修正了本文初稿的等权假设：把 5 个问题全修完并不能让成功率归 1。
  3. 步数是比失败率更强的杠杆。把 k 从 20 降到 10，P 从 12.16% 升到 34.87%。 这提示另一条工程路径：与其无限提高单步可靠性，不如缩短任务链路—— 例如把长流程拆成可独立验收的段，或对高风险步骤改用 API 直连而非像素操作。

与沙盘 1 的联动。把沙盘 3 的 P 代入沙盘 1：即使修满 5 个问题（P=60.27%）， 有效减负率也只有约 28%——离「闭眼传球」还很远。 这正好对应 Roman 在访谈尾声的定性判断：这一波 Agent 仍处于极其早期的阶段（very early innings）。

四 · 把产品扔进真实工作：团队究竟验证出了什么

4.1 一对一人工引导：用最笨的方法拿最高密度的反馈

在产品走向公开发布前的大约两周时间里，团队做了一件极其重度的事：由核心团队亲自下场， 一对一手动为数百名早期用户（主持人估算约 200 到 300 人）完成使用引导（Onboarding）。 这不只是数字展示，更形成了一个紧密的高频反馈闭环：在早期的 20 分钟辅导通话中， 经常出现云端电脑起不来、或者用户面对界面完全不知如何开始的窘境。

团队确立的原则是「今天发现的问题，必须在明天引导下一位用户前修掉」。 同时，团队刻意邀请了独立咖啡店老板等完全处于硅谷技术圈之外的非技术用户， 核心目的正是借此检验它是否真正算得上一款通用的知识工作产品，而非仅限极客使用的玩具。

这个动作的方法论含义

人工引导 200–300 人是不可扩展的，但它在早期提供的是别的方法拿不到的东西： 观察用户自己发现了什么用法，而不是教他们该用什么用法。 Roman 明确的一条经验是——不要用预设范式去引导早期用户，要看他们自发走到哪里。 下一节的五种形态，全部是观察出来的，不是设计出来的。

4.2 沙盘 · 五种自然涌现的工作流形态

五种形态的要点速览

1. 幕僚长（Chief of Staff）协同模式

内部推出后的最初一两周，常见模式是每人建立 5 到 10 个 Bot，每个负责不同的工作领域。 到第二周末，团队观察到一些用户会挑一个表现突出的 Bot 作为「幕僚长」，主要与它对话， 再由它把任务分派给其他 Bot。这是部分用户自发形成的用法，并非多数人的普遍状态， 也不是不可逆的固定层级；团队只考虑对这种模式作轻度引导。

2. 人才招聘的主动挖掘

在人才招聘场景中，该公司的招聘团队认为，顶尖人才往往不是那些正在积极投简历的人，而是需要主动发掘的目标。 团队内部配置的招聘 Bot 展现了一种探索流程：

  • 访问前沿学术会议的网站，下载那些尚未被 Google Scholar 收录的最新 PDF 论文；
  • 提取论文中的作者名单，将新名字添加到表格（Spreadsheet）中；
  • 随后检查公司内部是否有人与其具备直接联系；
  • 如果有，就直接向相关同事发送一条 Slack 消息请求引荐。

这一链条展示了云端电脑配合长流程 Agent 在串联非标网页、文档提取与内部协作上的探索潜力。

3. 销售与非标企业后台的探索

销售人员经常需要与缺少好用 API 的工具和企业看板打交道。在内测中，Bot 曾因鼠标无法精确点击 Salesforce 仪表盘的目标位置， 或无法登录系统而失败。团队通过改善浏览器可见性、屏幕像素与鼠标控制等基础能力， 尝试让 Bot 逐步具备操作这类界面的能力。但 Roman 同时指出， 这种交互在当时仍会失败，仍需持续优化，并非已经稳定接管任何系统。

4. 个人探索案例：递归测试（Bot in Bot）

在内部测试中，这也催生了一些极客式的个人用法。例如 Roman 个人曾在自己的云端电脑环境中， 反向下载并安装了桌面版 GrokBot 自身。他设置了一个 QA tester bot， 专门用来测试 10 个需要持续确认其越来越好的关键工作流，并将测试结果写入 Notion 与历史客户端版本进行对比。 需要指出的是，这属于 Roman 个人的使用尝试，并非团队已经全面制度化运行的固定 QA 流程。

5. 从「被动等待」到设定边界的主动提醒

初阶用户通常把 Agent 当作被动的信息整理工具，让它定期通报总结。 而更进一步的探索方向是：在让 Bot 接入邮件、即时通讯等信息流后，给它设定明确的触发边界—— 在大多数时候保持静默，只在用户预先定义的极少数紧急情形下触发主动呼叫（Page）或提醒人类。 这种用法成立的前提，是用户足够信任 Bot 不会频繁误报。

高阶协作：统一输出与每日摘要

除了单点任务，Roman 还提到了高阶用户的第二层协作方法：设计多个 Bot 之间的协同， 让负责不同垂直领域的 Bot 把各自的产出集中写入一个统一、对人可读的数据库或存储区（如 Notion 或统一表格）， 人类用户无需逐个检查每个 Bot 的会话，而是通过一份整合后的每日摘要（Daily Digest）集中阅读与决策。

4.3 演进路径：从个人信息闭环到企业渗透的未决挑战

在信息闭环的探索中，Roman 区分了不同主体的模式：V1 是很多用户会采用的常见模式， Bot 覆盖 Slack 和邮件，按优先级即时提醒或放入每日汇总；Roman 说自己的个人配置大约处于 V3 或 V4， Bot 摄取 X 上的 GrokBot 提及，结合内部上下文，协同 QA tester 尝试复现 bug， 再通过他自己的消息渠道快速响应反馈。这一探索的新增价值集中在 「外部信号 → 内部上下文 → QA 复现 → 响应反馈」的链路。

从个人探索走向企业落地，Roman 回顾了 AI 编程工具的扩散路径：早期 AI 编程工具用户先在晚上和周末的个人项目中体验价值， 回到工作场所后要求使用；Roman 预计知识工作 Agent 也会先在个人场景产生 aha moment，再进入团队并贡献有经济价值的工作。

但 Roman 同时列出了悬而未决的问题（unanswered questions）： Bot 如何进入复杂公司系统、理解公司上下文和历史；如何在更大团队中工作； 以及组织级记忆究竟应该是什么样。这些问题至今没有答案—— 本文不替他给出答案。

五 · 护城河怎么来：先把未来三到六个月的能力做出来

在当前的 AI 创业环境中，创始人和投资人最焦虑的问题往往是： 「如果底层大模型厂商在下一代底座模型里直接集成了这类能力，上层产品的护城河究竟在哪里？」

针对这种战略焦虑，Roman 强调：不要从 12 到 24 个月后的战略图倒推产品，而要先专注于今天真正有用的东西。 Lenny 随后把这套看法概括为：先做出一款让人着迷（Obsessed）的产品，护城河往往是在这个过程中被发现的，而不是预先规划出来的。

时间机器的三步节奏

  1. 预判趋势：大致判断未来 3 到 6 个月里，模型能力的提升会让哪些今天做不到的事变为可能。
  2. 提前拉取未来：不要只等底座模型成熟，而是在现有模型之上搭建工程脚手架（Scaffolding），尽量把那种未来体验提前交到用户手里。
  3. 果断删除脚手架：当底层模型原生补齐能力后，删掉已经不再必要的脚手架，把它变成产品的默认能力；然后继续瞄准下一个仍然困难的边界。

为什么这要求「敢于删代码」的文化

这三步里最反直觉的是第三步。脚手架是团队自己一行行写出来的、正在为用户提供价值的工程资产， 把它删掉在组织上极难通过。Roman 认为，团队大约每六个月、近期甚至更短， 就需要显著重塑产品优先级与核心形态——当模型能力和用户行为都在快速变化时，今天成立的产品边界未必能长期保留。

Roman 认为，这种不断「自我颠覆、敢于删代码」的快速循环，其核心逻辑在于不被动等待底座升级， 而是通过工程手段把未来的能力提前交付给用户；在此过程中，团队有可能在真实用户的日常使用习惯、 数据反馈与分发渠道上建立起先发优势，而不是依赖静态的战略图纸去空谈无法撼动的护城河。

本文不给这个战略配数学模型。「脚手架投入—底座追平—删除」的收益曲线需要 模型能力增长率、脚手架维护成本与用户迁移黏性三类参数，访谈一项都没有提供。 凭空设定这些参数再画出一条漂亮的曲线，属于沙盘造假。这里只保留可核查的部分： 三步节奏本身是受访者的明确陈述；「每六个月重塑一次」是他的明确判断； 两者都不需要数字包装也已经足够锋利。

六 · 普通人怎么开始：先交出一件边界清楚的工作

对于初次尝试脱离单次对话模式、尝试构建长效 Agent 助手的读者，访谈中给出了具体的落地切入点。

6.1 像对待新员工一样提供真实上下文，但坚守安全边界

不要指望一个漂浮在真空中的模型凭空替你分忧。第一步往往是让 Bot 接入日常工作涉及的关键渠道 （如工作邮箱、团队协作即时通讯工具、知识库）。Roman 认为，许多人会要求个人工作与公司工作彼此分离， 并承认组织级记忆、多个 Bot 如何在真实复杂团队中协作仍有大量悬而未决的问题； Lenny 随后进一步提出了个人与工作数据混用（cross-contamination）及 工作数据外泄（exfiltration）的风险。

本文基于上述风险补充的操作底线（非访谈原文，为本文建议）： 实际开放权限时从最小权限与个人/工作数据分离起步； 优先采用可随时撤销的授权（OAuth 令牌优于长期密码）； 对涉及对外发送或高风险操作的动作设置人工确认—— 这与沙盘 1 的结论一致：只要端到端成功率还没跨过临界点，人类确认就不是可选项，而是安全机制的一部分。

6.2 用「反向发问」破局冷启动

面对全新的 Agent 界面，很多人的困惑是「我不知道该让它干什么」。 Roman 提到他在实际使用中的做法是让 Bot 翻阅自己的邮件与 Slack，并给出提示： 建议 5 件可以帮我分担的事情，以及为了做到这些分别需要什么条件 （Suggest like five things that you can take off of my plate and what it would take for you to do that）。

在实际尝试中，可按这个思路将其改写为更易落地的提示词：

请通读我近期的邮件与日常沟通记录，结合我的业务角色，主动列出 5 项你可以直接帮我分担的具体工作块；并告诉我，如果要搞定这几项工作，你分别还需要获得哪些系统权限。

Roman 在自己的那次尝试中，5 项里有 2 项对他确实有用，于是他为这两项各建了一个 Bot。 对读者来说，更稳妥的起点是先选择 1 到 2 项边界清楚、结果可校验的任务， 而不是立刻把全部工作一次性交出去。

6.3 三条可操作的起步判据

  • 边界清楚：能说清输入是什么、交付物长什么样、什么算做完了。
  • 结果可校验：你能用不到几分钟判断它这次做对了没有——否则核验成本 θ 会把减负率吃光。
  • 失败可逆：做错了不会造成外部影响，这样你才敢在端到端成功率还不高的时候放手试。

七 · 结论与未决问题

从聊天框里的文字生成，到云端电脑上长效驻留的数字协作网，AI Agent 正在经历一场由「炫技演示」向「实际可用」的重心迁移。 然而必须清醒地看到，正如 Roman 在访谈尾声所强调的，这一波 Agent 的探索仍处于极其早期的阶段（very early innings）。

本文确认成立的四条结论

  1. 委托是二元体验，不是百分比体验。沙盘 1 显示，在合理的核验成本假设下， 90% 完成度只换来 65.03% 的有效减负；70% 只换来 39.14%；低于 32.29% 则转为净负担。 Roman 的「90% 与 100% 之间是质变」在数学上成立。
  2. 两个架构决策是可复用的，而具体拓扑不可复用。「全云端 + 每台 Bot 一台电脑」是可迁移的产品抽象； 但资源隔离方式、成本与闲置策略访谈均未披露，不可据此推算。
  3. 四周原型的真实前提是组织隔离，不是技术奇迹。数人小组 + 独立物理区域 + 私密频道 + 「删产品 / just do the thing」两条原则，才是这套速度的产生条件；Roman 本人也明确说这不是普适管理法则。
  4. 内测三周的价值集中在可靠性而非功能。沙盘 3 显示，在 20 步任务上修完 5 个关键问题能把 端到端成功率从 12.16% 拉到 60.27%（4.96 倍），这个量级是任何界面优化都达不到的。

仍未解决的问题

  • Bot 如何进入复杂公司系统、理解公司上下文与历史；
  • 多个 Bot 如何在更大的真实团队中协作；
  • 组织级记忆应有的形态；
  • 个人数据与工作数据的混用（cross-contamination）与外泄（exfiltration）边界如何工程化；
  • Computer Use 的长期可靠性上限——它能逼近沙盘 1 要求的单步 0.99475 吗？访谈没有回答。

它远没有达到能让人类完全闭眼放权、彻底托付后背的成熟程度；更现实的路径， 是在明确边界、保持校验的前提下，将那些重复性高、流程明确的劳动逐步交付， 在人机协作的持续磨合中探索新的工作形态。

附录 B · 术语表

以同事为尺（Colleague-pilled）
GrokBot 团队的产品思考锚点：把 AI 当作真实世界里新招募的一位同事，据此推导协作方式，而不是从「聊天机器人 + 工具」出发。
Computer Use（云端电脑操作）
让 Bot 通过像素识别、移动光标与输入字符来操作网页与桌面应用，用于覆盖没有好用 API 的系统。Roman 认为其底层机制应对用户彻底无感。
Shipping your org chart
把公司内部组织架构映射成产品形态——每多一个团队就多一个标签页。GrokBot 选择从零开始以避免这一点。
Unshipping（下线功能）
公开发布前约三周的主要工作：主动删除已建成的功能与界面，尤其是暴露实现机制的「透明度工具」。
has → can
团队内部的界面克制判据：把「GrokBot 现在有了 X（某个按钮/面板）」改写为「GrokBot 现在能做 Y（某件完整工作）」，改写不了的大概率不该做。
脚手架（Scaffolding）
为提前交付未来体验而在现有模型之上搭建的工程层。当底座模型原生补齐能力后应果断删除。
端到端成功率 P
本文引入的分析量：单步成功率 s 的 k 次方。用于把「90% 完成度」转写为可计算的委托判据。
核验凹性 η
核验投入随 (1−P) 变化的指数。η 越小，表示「要判断产出对不对必须先理解全部」这一固定门槛越硬。
