01一分钟速览

Google Research 和弗吉尼亚理工大学（Virginia Tech）提出了一个名为 WikiSkill 的框架，核心目的是让 AI Agent 能够将执行任务中的经验和教训，沉淀为像维基百科（Wiki）一样的持久知识库，进而持续进化出更强大的可执行技能。

也就是研究如何让 AI Agent 从一次次任务中学习，并把零散经验逐步变成以后可以直接使用的能力。

核心要义三项原则
  • 经验沉淀为持久 Wiki：WikiSkill 把 Agent 经验沉淀为持久 Wiki，让技能能够摆脱单轮优化或临时上下文的束缚，实现持续自主进化。
  • Raw、Wiki、Skills 三层解耦：三层架构清晰划分“事实、认识、执行”。Skill 验证失败可以安全回滚，但总结出的宝贵经验不会跟着消失。
  • 主实验全线大幅领先基线：WikiSkill 在测试的全部五个模型上平均分均领先现有最强基线，且参数量仅 9B 的小模型装配 WikiSkill 后的综合表现，全面超越了不带技能的 27B 大模型。

02为什么需要 WikiSkill？（背景与痛点）

今天的 AI Agent 已经能根据执行记录自动生成 Skill。比如它做表格时反复写错公式，系统可以总结出一条“写入后必须重新读取并校验”的操作规则，放进下一轮 Prompt，让它以后少犯同类错误。

问题在于，以往的技能进化方法（如 EvoSkill、Trace2Skill、SkillOpt 等）主要在优化“当前这份 Skill”，并没有单独维护一套持续增长的独立知识体系：

  • EvoSkill：会保存历次提议及其评测结果，但知识仍附着在提议序列中；
  • Trace2Skill：会直接从轨迹中提炼经验，但在进入下一轮时被重写压缩；
  • SkillOpt：会利用被拒绝的修改继续优化，但未将失败模式结构化归档。

这些信息大多停留在优化历史记录里，或者被直接压缩进新版 Skill。这带来了三个不可调和的核心瓶颈：

传统技能进化的三大死穴
  1. 经验很难跨轮次复用：第六轮遇到的错误，系统未必知道第二轮已经深入分析过相似根因，容易反复“重新造轮子”或陷入重复分析。
  2. 失败修改的价值容易丢失：某次 Skill 更新虽然让综合评测分数下降，但它暴露出的错误模式与边界条件仍然极有价值。以往系统只单纯回滚 Skill，导致下次可能再次提出近似方案，重复支付高昂的验证成本。
  3. Skill 承担了过多职责：Skill 既要作为历史经验的存储介质，又要充当执行推理时的简洁指令集。经验越积越多，Skill 必然迅速膨胀，导致上下文注意力稀释；而如果压缩得太狠，又会丢掉规则形成的因果链条与适用边界。

WikiSkill 引入的 Wiki 层，正是为了彻底缝合这层知识断档。它将“发生过什么（证据）”、“从中学到了什么（认识）”、“执行时具体遵守什么（动作）”完全拆开保存，让失败经验也能成为下一轮提议的结构化输入。

03WikiSkill 的“三层知识架构”

WikiSkill 的设计重点不只是一套新 Prompt，而是一个清晰划分职责的工作空间（Workspace），分为三层：

知识层次 存储核心载体 读写权限控制 核心职能与解决问题
原始层 (Raw Layer) trajectories/, 交互日志 只追加写入，不可改写 保存客观证据：记录完整推理轨迹、工具调用、输入输出与真实反馈。防止事后总结被篡改或覆盖。
维基层 (Wiki Layer) patterns/, logs.md, skill-impact.md Maintainer 持续归纳扩充；不回滚 保存高维认识：跨轨迹提炼错误根因、成功做法、失败模式库。即便技能回滚，经验依然永久沉淀。
技能层 (Skills Layer) SKILL.md, PURPOSE.md 执行 Agent 唯一读取对象；受严格门控，可随时回滚 保存纯净动作规则：保持指令高度精炼，避免上下文污染。配对的 PURPOSE.md 显式溯源至 Wiki 页面。

三层分别精准解决“可追溯、可积累、可执行”：

  • Raw Layer 防止事实被覆盖：文件只写不改，保证后续分析看到的是当时真实发生的过程，而不是被事后总结改写过的版本。
  • Wiki Layer 防止经验随版本消失：Wiki Maintainer 会把多条轨迹中的共同模式整理成独立页面，例如某类失败为什么发生、哪些做法有效、有什么可执行的修复办法。logs.md 记录每轮发现，skill-impact.md 记录每次 Skill 修改、验证分数以及接受或拒绝结果。
  • Skills Layer 保持执行指令足够集中：执行 Agent 真正读取的是这里的 SKILL.md。配套的 PURPOSE.md 会指出这条 Skill 源自哪些 Wiki 模式，使一条简短规则仍然能追溯到背后的证据和原因。
核心公理：Skill 可以回滚，Wiki 不回滚！
系统因此可以从容撤销一次无效或负向的改动，同时完整保留“为什么这次改动无效”的经验与认知。

04系统是如何循环演进的？（四步工作流）

WikiSkill 的自我进化不是盲目的随机修改，而是一个包含严密分工与准入门控的四步闭环循环：

四步演进闭环详解
  1. 步骤一：推理执行（Inference Agent）
    Agent 仅带着当前版本的 SKILL.md 去执行训练集任务，所有完整的思考链、工具调用与环境反馈原汁原味写入 Raw Layer。
    设计铁律：刻意禁止 Inference Agent 在此步骤读取 Wiki！因为 Wiki 是给“改进技能的人”使用的分析材料，直接交给执行者可能让它绕过 Skill 现有的缺陷去投机完成任务，从而产生失真的训练轨迹，掩盖真实弱点。
  2. 步骤二：维基维护（Wiki Maintainer）
    维护器从本轮的执行轨迹中精准抽取最多 8 条样本（最多 5 条失败样本 + 最多 3 条成功样本）。失败轨迹用于深入剖析根因，成功轨迹则用于总结有效策略，并防止在后续优化中把已经正确的行为“改坏”。新的发现会结构化写入 patterns/ 页面，并追加记录到 logs.md 演进日志中。
  3. 步骤三：技能提议（Skill Proposer）
    Proposer 采用 ReAct 范式，先浏览 Wiki 索引、历史修改结果（skill-impact.md）以及本轮任务的成败摘要，再按需主动调阅模式详情或原始轨迹。
    工程铁律：每轮迭代严格限制只创建或修改 1 个 Skill！避免一次性混入多条规则导致变量纠缠；一旦验证失败，无法辨识究竟是哪条规则引发了负面回归。
  4. 步骤四：门控与回滚（Gating & Rollback）
    候选 Skill 必须在独立的验证集上执行，且验证成绩必须严格超过历史最高分才能被接受合并；如果成绩持平或下降，该候选 Skill 立即被原子级回滚。
    关键特征：无论接受还是回滚，代码差异、验证分数与最终结论全量写入 skill-impact.md。下轮提议者可明确查阅“某方案曾在第几轮测试过且因何失败”，避免陷入死循环尝试。
演进实证案例：死循环物品拿放的破局之路
在具身具象环境（ALFWorld）中，Agent 曾反复把物品拿起、检查、又放回原处，陷入无限探索死循环。系统首先提出一条粗糙规则试图修复，但验证未获提升，Skill 被果断回滚；然而 Wiki 完整保留了“拿放循环行为”与“粗糙修复无效”的认知。
下一轮 Proposer 汲取该认知，提出了更精确的“不要把已检查物品放回原位”，验证通过并合并；后续面对新的循环变体，更进一步精炼收敛为“对同一物品的每种操作只允许执行一次”。

05核心实验结论与高价值发现

研究覆盖五类差异极大的典型复杂任务：数学推理 LiveMath、网页搜索 SealQA、复杂表格操作 SpreadSheet、长文档问答 OfficeQA 以及连续具身环境 ALFWorld。测试模型涵盖 Qwen 系列（4B、9B、27B）、Gemma-31B 以及商业顶尖模型 Gemini-3.5-Flash。所有实验均来自 3 次完整进化流程的平均值，并通过严格的配对 Bootstrap 统计检验。

发现一：WikiSkill 优势全面且显著领先所有基线

在测试的全部五个模型上，WikiSkill 的平均得分均大幅刷新同类技能进化的最高水平。相比各自对应的最强竞争方法，WikiSkill 仍能实现 3.3 ~ 12.0 个百分点的净提升：

测试基准模型 No Skill (无技能) 最强基准 (Best Baseline) WikiSkill (本文) 净绝对提升 超最强基准超额
Qwen-3.5-4B 26.2 35.2 38.5 +12.3 +3.3
Qwen-3.5-9B 29.9 42.3 47.4 +17.5 +5.1
Qwen-3.6-27B 39.4 53.3 63.3 +23.9 +10.0
Gemma-31B 41.3 49.1 54.9 +13.6 +5.8
Gemini-3.5-Flash 49.5 56.1 68.1 +18.6 +12.0

典型单项突破尤为亮眼：

  • Gemini-3.5-Flash 在 LiveMath 任务上从无技能的 33.0 暴涨至 72.6（净增 +39.6%）；在 SpreadSheet 上从 50.5 提升到 76.6。
  • Qwen-3.6-27B 在具身决策环境 ALFWorld 上从 52.8 提升至 77.6。

发现二：模型规模扩大与 Skill 进化呈现“相互放大效应”

在 Qwen 体系内，模型规模与技能增益呈现极强的正相关：4B、9B、27B 从 WikiSkill 获得的绝对提升分别为 12.3、17.5 和 23.9 个百分点。这证明：

  • 更强大的模型不仅能总结出更高抽象度的程序化规则，也更具备严格遵循复杂长链 Skill 的抗干扰能力。
  • 同时，Skill 能够显著弥补模型参数规模的劣势：装配 WikiSkill 的 Qwen-9B（47.4 分）甚至显著超越了完全不带技能的 Qwen-27B（39.4 分），实现了以小博大的工程代差反超！

06跨模型迁移与知识隔离消融机制

发现三：技能可以跨模型迁移，但不对称性暗藏陷阱

技能库是否能从一个模型训练，直接导出给另一个模型执行？实验证明迁移是可行的，但绝不是单向对称的：

正向惊喜案例：强总结赋能小执行，大模型补足小规则
  • 强带弱：Qwen-27B 自我进化出的 SpreadSheet 表格技能，移植给 Qwen-9B 执行时，成绩从原始 24.3 飙升至 50.5，远高于 Qwen-9B 自己闭环摸索出的 33.6。在 ALFWorld 上更是直接将 9B 从 34.7 拉升到 70.2。
  • 弱规整强执行：Qwen-4B 总结出的 OfficeQA 多步检索规则，对自己毫无帮助（从 30.2 降至 28.5），但交付给指令遵循力强的 Qwen-27B 时，却成功把 27B 从 42.1 提高到 52.9。这深刻证明：“从经验中发掘归纳规则”与“严谨执行多步规则”是完全解耦的两种智能维度！
负向灾难案例：弱模型的防御性补丁成为强模型的“束缚毒药”

Qwen-4B 总结出的表格技能，让强大的 Gemini-3.5-Flash 在 SpreadSheet 上的成绩直接从 50.5 断崖式崩跌至 18.1！

底层深度归因：论文调阅轨迹发现，小模型由于算力与代码能力较弱，在踩坑后为了防崩，硬编码了诸如“只允许使用单行 Python、每次写入前后必须强制做字符串转换”等底层防御性补丁。这些补丁在保护小模型不犯低级错误的同时，却彻底禁锢了强模型直接编写完整复杂数据处理脚本的能力，还会造成海量繁琐的碎片化工具调用，导致交互步数迅速耗尽，提前触碰单任务预算上限！

工程结论：只有具备普适逻辑的通用流程规则才能跨模型迁移；针对特定模型缺陷打的防御性权宜补丁，直接迁移给更强模型反倒会造成劣化。

发现四：消融实验证实——Wiki 必须服务于提议，严禁参与推理

论文对 Gemini-3.5-Flash 进行了精细的消融实验，对比不同知识访问配置下的表现：

实验消融组配置 Inference Agent (执行) 权限 Skill Proposer (提议) 权限 四项综合平均分 LiveMath 专项分 机制机理解释
完全移除 Wiki 禁读 (No) 禁读 (No) 48.7 52.1 无持久经验积累，每轮仅凭当前轨迹局部盲探。

为什么把 Wiki 也喂给执行 Agent 成绩反而下降了近 3 个百分点？

论文给出了深刻洞见：执行 Agent 一旦能直接读取 Wiki，就会借助维基库中记录的历史解法直接抄近道做对训练题。此时暴露出来的执行轨迹不再是当前 Skill 的真实短板，Skill Proposer 失去了高质量的负向反馈信号，无法精准定位 Skill 到底缺了什么，最终导致技能进化陷入停滞与失真！

07理论建模与数学推导

为了深刻理解 WikiSkill 的三层解耦与单变量门控机制，我们引入信息论容量衰减与马尔可夫门控演进模型进行数学形式化推导：

模型 1：Skill 上下文容量与注意力信噪比衰减模型
SNReff(L) =
I(Skill) · exp(-α · L) I(Noise) + β · Lcontext

在以往方法中，如果将全部认知经验直接压缩追加进 SKILL.md，会导致上下文长度 L 随轮次线性发散。LLM 内部的注意力权重会在冗长规则中迅速稀释。通过将认知剥离到 Wiki Layer，使进入执行 Agent 上下文的规则长度恒定保持在低阈值 Lskill≪Lmax，确保有效信噪比 SNReff 维持在最高区间。

模型 2：严格单调门控下的单变量提议优势定理
Paccept(k) = pk,    E[T] =
M pk
,    损耗比 =
1 - pk pk

设单条规则经过提炼后带来正向收益的概率为 p（通常 0.6≤p≤0.7）。如果在单轮迭代中贪婪地同时提议修改 k 条规则，在严格门控标准（要求验证集绝对占优、杜绝负向回归）下，复合修改成功的概率迅速衰减为 pk：

  • 当 p=0.65 时，单变量修改（k=1）的接受率为 65.0%，达到 5 次有效进化仅需 7.7 轮；
  • 若一次改 3 条（k=3），接受率断崖下跌至 27.5%，期望需要 18.2 轮，被回滚丢弃的无效尝试激增 2.64 倍！

这从统计学上严格论证了 WikiSkill 坚持每轮只修改一个 Skill 规则 的必然性与优越性。

沙盘 1：WikiSkill 三层工作空间演进与回滚状态机

Workspace State Machine

1. RAW LAYER (证据层) 只写不改

09局限性与未来演进方向

WikiSkill 首次系统性证明了“持久维基知识库”能够强有力地驱动 AI Agent 自我进化 Skill，但从学术前沿迈向生产环境自主成长，论文也坦诚指出了目前存在的四大明确边界：

当前架构的四大技术瓶颈
  1. 未解决大规模 Skill 的动态检索与路由机制
    在实验中，论文为了排除“Skill 触发召回失败”这一干扰变量，将所有当前活跃的 Skill 直接全量静态注入到系统 Prompt 中。但在真实工业级海量技能库（例如上千个垂类技能）场景下，必须建立专门的层次化检索与路由器（Hierarchical Router），否则上下文预算将被耗尽。
  2. 门控评判标准过于严苛，易陷入局部极值
    当前的门控策略要求候选 Skill 必须在验证集上“立刻严格超越历史最高分”才能被合并保留。然而在复杂技能重构中，某些底层架构层面的重构可能在短期内出现持平甚至轻微波动，但它是后续质的突破的前提。过于机械的单调占优策略容易扼杀有潜力的前置重构。
  3. Wiki 知识库无限线性膨胀，缺乏自治治理机制
    当前系统在多轮迭代中不断追加新的 patterns/ 页面与日志，尚未建立自动合并同质模式、解决冲突知识条目或主动清理过期陈旧策略的治理流水线。长久运行后，Wiki 本身也将遭遇“维护复杂度危机”。
  4. 本质仍属于“离线、批次化演进”，缺乏在线实时自适应能力
    实验是在“先跑一整批训练任务 → 统一维护 Wiki → 单步提议修改 → 批量跑独立验证集”的离线迭代节奏下展开的。系统尚无法支持在一个长达数小时、涉及数百个连续复杂环境交互的任务中，一边执行一边动态自我改写技能。

10工业工程落地实操与启示

对于工业界 AI Agent 系统研发架构师而言，WikiSkill 提供了极具实操价值的系统设计范式：

传统工程做法 WikiSkill 架构升级方案 工程收益与落地效果
把所有踩坑教训写在同一个系统 Prompt 里 拆分为 Raw（日志层）、Wiki（模式库）、Skills（动作指令） 执行 Prompt 极致瘦身，降低单次推理延迟与 Token 成本，彻底消除注意力稀释。
更新 Prompt 后如果线上报错，只能全量回滚，经验直接丢失 Skill 回滚，Wiki 不回滚，在 skill-impact.md 归档死因 失败成为系统持久资产，下次优化自动规避重复试错。
一次性修改多个规则并上线 严格遵循单变量提议原则，配对验证集独立回归 因果关系清晰可溯，防止多个补丁互相死锁导致回滚率激增。
直接将小模型验证过的 Prompt 迁移给大模型 区分“通用逻辑流程”与“模型底层权宜补丁” 防止小模型的防御性低级约束抑制强模型的全量代码与推理潜能。
终局认知总结

WikiSkill 为智能体自我进化提供了一条兼具数学严谨性与工程可落地性的新范式：

“智能的成长不在于写出多么庞大的指令集，而在于建立一个永不遗忘失败教训的维基，并以极度克制的单变量节奏，将成熟认知编译为纯净的可执行指令。”
