01

范式革命：从“任务答案”转向“执行基础设施”

在过去数年的大语言模型与自主智能体（Autonomous Agents）评测体系中，无论是衡量代码修补能力的 SWE-bench、通用计算机助手的 GAIA，还是衡量端到端操作系统操作的 OSWorld 与 Terminal-Bench，业界几乎无一例外地遵循着一条隐式假设：将 Agent 的外部执行环境（Harness）视作不可变常数，只记录与评测模型生成的“最终任务答案”。

⚠️ 权重冻结下的“Harness 决定论”现象

论文开头引用了一组极具震慑力的公开实测数据：同一个冻结权重的 GPT-5 模型，在 Terminus 2 执行框架下仅能通过 Terminal-Bench 2.1 中的 35.2% 的任务；然而一旦切换到 Codex CLI 这一更为成熟的工程 Harness 内部，相同任务的通过率骤升至 49.6%。在模型权重没有发生一个字节变化的前提下，仅靠外部基础设施的重构就拉开了整整 14.4 个百分点的绝对差距。同周在 ARC Prize 上 Astra 框架亦展现出高达 37 个百分点的 Harness Gap。

这层包裹在模型核心外部的系统软件被定义为 Agent Harness：它承载着任务执行主循环、原子工具调度与修补策略、长短程上下文窗口生命周期、工作区状态持久化与容灾断点恢复，以及严苛的交付结果环境级校验。它本质上是 Agent 的“执行基础设施与专用微型操作系统”。

现有评测的致命盲区在于：既然工程 Harness 对下游成功率的影响甚至超越了模型底座的微调迭代，那么“前沿大语言模型能否自主从零构建并持续演化这套基础设施？” ByteDance Seed 等团队推出的 HarnessDev 正是填补这一历史空白的奠基之作。

02

HarnessDev 评测基准机制设计

HarnessDev 彻底颠覆了以“任务解答分”为单一终点的评分逻辑，将评测工件（Evaluation Artifact）定义为“一组完全自包含、可独立部署并跨任务执行的软件基础设施代码库”。整个基准包含两大核心评测阶段。

评估阶段 初始输入条件 演化交互与反馈 验证与测试集 核心检验维度
Creation（从零构建） 弱种子（Weak Seed）+ 任务规范 + 1~3 个示例任务 Claude Code / Codex 交互式开发环境，支持自主编码与测试 4 大领域 5 套基准（2,207 实例），独立创建 3 次汇报 avg@3 从无到有的架构设计力、控制流闭环完整度、语法与运行稳健性
Evolution（持续演化） 自身 Creation 阶段最终输出的成品 Harness 189 个下游反馈任务执行结果，允许最多 10 轮演化迭代 630 个完全未公开的 Held-out SWE-Pro 实例，全程对模型盲测 假设驱动调试力、反馈过拟合抑制、跨任务长期泛化能力

2.1 弱种子（Weak Seed）哲学：杜绝任何既有架构“送分”

基准设计者刻意规避了两个极端：若提供一个完全空白的空仓库，模型的工程开销将被大量琐碎的参数解析与 CLI 模板所浪费；若提供 LangChain、AutoGen 等现成框架骨架，则无异于将规划、重试与验证逻辑直接送分。

弱种子是一个仅能解析任务配置、暴露被动原子工具（读文件、写文件、执行 bash 命令）并输出基础审计日志的空壳程序。它完全不包含任何六大核心控制模块：执行循环、工具调用策略、上下文修剪、状态与检查点、生命周期恢复、结果验证门禁。在弱种子状态下，其在全部 5 套基准上的原始得分为 0.00 分。因此，最终获得的每一分都绝对来源于模型自主编写的控制逻辑。

2.2 评估视角的解耦：Self-Eval vs. Unified-Eval

为探究自研基础设施的普适性与迁移性，HarnessDev 引入了严密的双重视角分离评估机制：

  • 自执行评测（Self-Eval）：由构建 Harness 的原模型自身来执行下游测试任务。衡量的是“特定模型与其自造 Harness 的共生协同（Co-adaptation）上限”。
  • 统一执行器评测（Unified-Eval）：固定将所有被测 Harness 交付给统一的 Gemini 3.1 Pro 作为基准执行器。通过将底层执行算力完全钉死，纯粹剥离并量化 Harness 本身作为“可迁移通用工程资产”的代码质量。
🛡️ 防作弊物理隔离：剥夺 Harness 自身的“自评裁判权”

在 Agent 评测中，模型极易产生“虚假繁荣”——Harness 汇报自身成功完成了任务，但实际环境状态毫无改变。HarnessDev 设立了铁律级别的物理判分隔离：SWE-Pro 只认 Git 仓库最终落盘的真实代码 Diff 并运行单元测试；Terminal-Bench 只认宿主容器文件系统与环境变量终态。Harness 自报的任何 success 状态在评分引擎中计分为 0。

3.1 极端的领域能力分化

实验揭示了模型构建基础设施时的巨大领域偏向性：

  • 长文写作域全面比肩/超越人类：Opus 4.8 自建 Harness 录得 84.6 分，超越人类工程 Harness 的 83.7 分。写作任务的核心控制流主要是分章规划、递归润色与自我批判，此类线性与分支逻辑模型极易内化。
  • ML 实验域双双打破人类基准：MLE-bench 模拟 Kaggle 比赛评判奖牌率，人类参考基线仅 24.0%，而 Opus 4.8（32.9%）与 Gemini 3.1 Pro（32.4%）的自建 Harness 实现了对人类工程师框架的碾压。其构建的自适应调参循环和多脚本尝试机制展现出极高鲁棒性。
  • 代码工程与终端运维明显落后：SWE-Pro 最高仅 69.3（落后人类 10.7 分），Terminal-Bench 最高 68.8（落后人类 20.0 分）。数据分析任务中 77.8% 的失败被归因为 Harness 本身的控制逻辑缺陷（例如过严的超时规则提前放弃），而非模型不会写代码。
  • 长程搜索研究形成断崖级鸿沟：搜索基准上人类参考高达 92.2 分，而模型构建的最佳 Harness 仅 52.6 分（落后近 40 分！）。模型完全无法自主设计出多源交叉验证、逆向反查与防止信息污染的高阶上下文管线。

3.2 机器设计的“共适应陷阱（Co-adaptation Trap）”

当把这些 Harness 交由固定的 Gemini 3.1 Pro 执行时，基础设施的通用性遭遇了残酷检验：

💥 典型事故：Opus Harness 遭遇步数硬编码截断

Opus 4.8 自身运行该代码 Harness 时得分高达 69.3，但换由 Gemini 执行后，SWE-Pro 得分暴跌至 33.0（跌幅高达 52.4%）！深入源码分析发现，Opus 针对自身单步推理较快但步数偏保守的习性，在 Harness 内部硬编码了 max_steps = 120。而 Gemini 模型的求解模式倾向于小步探索（通常需 150~180 步），导致在统一执行时几乎所有长程任务都在即将产出补丁前被 Harness 的刚性截断强行杀死。

搜索领域的共适应更加隐蔽：Opus 自建的搜索 Harness 在原模型运行时重复查询率仅为 10.1%；但换由 Gemini 驱动后，重复查询率激增至 88.2%。这表明其查询去重、相似度检测规则与原模型的 Prompt 特征高度过度绑定。

反向正例同样存在：Qwen 与 DeepSeek 构建的部分 Harness 在交由更强执行器 Gemini 运行后，BrowseComp 分数反弹上涨 +17.6 分，MLE-bench 上涨 +12.9 分。这证明这两个模型具备良好的架构抽象设计能力，此前的低分受制于模型底座执行力的薄弱，而非 Harness 缺陷。

3.3 代码虚胖与“全量死代码”灾难

通过对 18 个代码域 Harness 的静态与动态跟踪，论文揭示了令工程界深思的质量特征：

  • 代码量完全不预测性能：Gemini 仅增加了 1,006 行代码，代码量全场最少，却摘得 Terminal-Bench 冠军（68.8 分）；Qwen 堆叠了 3,562 行繁琐代码，得分却仅有 41.3 分。
  • 状态记忆几乎 100% 沦为死代码：18 个 Harness 中有 11 个显式定义了 State 类，但仅有 1 个提供了状态保存接口，仅 1 个实现了周期性持久化。在全局 26,679 条真实运行轨迹中，Checkpoint 恢复机制实际触发次数为 0 次！一旦中途因超时或异常断开，没有任何一个 Harness 具备断点恢复能力。
  • 验证流停留于浅层语法检查：写作域 587 项声明特性中有 124 项从未在执行中走入；数据分析中有 441 个退化提交被 Harness 判定为“Success”，缺乏对输出内容进行物理真值断言的能力。
  • 开发范式的胜负手：模型在开发环境中的行为分析表明，“盲目堆砌自测试”与最终成绩的相关性仅为 0.13~0.26；而“读取失败日志 → 定向缺陷修复 → 闭环再验证”的迭代次数与最终分数呈现极显著正相关（r = 0.57, p < 0.01）。
04

Evolution 阶段实证深剖：噪声演化与假象

在演化阶段，模型以自身 Creation 的成品为起点，利用 189 个反馈任务（100 个 SWE-Pro + 89 个 Terminal-Bench）的结果反馈，自主迭代 10 轮升级 Harness。演化产生的全部版本被冻结，随后在 630 个完全隔离的 Held-out SWE-Pro 实例上接受盲测。9 条演化谱系共产生了 73 个正式版本、64 次相邻版本切换。

4.1 反馈集狂欢与 Held-out 寒冬

在模型“可见”的 189 个反馈任务集上，演化呈现出令人欣喜的繁荣：5 条自执行谱系全部录得显著提升，涨幅在 +3.0 到 +13.9 分 之间。然而，当这些被模型寄予厚望的 Harness 部署到未曾见过的 630 个 Held-out 任务上时，真实涨幅全部发生严重衰退与缩水：

更震撼的结论出现在统一执行器视角下：除 Opus 的演化版本仍保留微弱正向增益（+2.15）外，其余所有谱系的演化版本在 Gemini 驱动下全部发生严重倒退，GPT-5.5 的演化 Harness 甚至倒退了整整 -10.32 分！模型为了让特定反馈集分数上涨而实施的代码微调，对通用执行能力而言几乎全部沦为“负资产”。

4.2 噪声带内的虚假演化：64 次切换中仅 2 次有效

通过对同一 Commit 镜像进行重复运行标定，论文测得评测环境的固有波动标准差为 σnoise≈±4.75 分。在 64 次模型自主执行的版本更迭决策中：

  • 8 次切换导致两个基准同时发生性能回退；
  • 16 次切换导致其中一个基准单向回退；
  • 27 次切换所谓的“增益”，幅度完全落在 ±4.75 分的随机波动噪声带内；
  • 1 次切换修改的代码根本未接入任何运行路径（无效改动）；
  • 在整场耗资巨大的演化实验中，真正具有统计学意义、超出噪声置信上限的确定正收益仅发生过 2 次！

4.3 选择困境与诊断瘫痪

模型不仅在演化中追逐噪声，而且在发版选型上展现出系统性选择盲目（Selection Dilemma）：

  • 反馈集分数上涨与 Held-out 泛化集分数上涨的方向一致性仅有 53.1%（几同抛硬币）；
  • 9 条谱系各自选出的所谓“最终最优提交版”中，仅有 2 个（22.2%）在未见的泛化测试上真正对应最优解。反馈分数只能作为试探性启发信号，绝对不能直接用作发版判定门禁。
  • 诊断机制形同虚设：基准环境专门提供的单步失败轨迹分析接口（Trace Inspector），在全演化周期内被模型调用的次数总计仅有 2 次！模型宁可基于 5 个样例的小样本抽查做出误判（抽查 5/5 全过，全量跑分仅 58.4），也不愿深挖系统性日志。
💡 唯一有效破局正例：Opus 的“真实完成检查门”

在全场极少数成功的演化案例中，Claude Opus 展现出了卓越的系统洞察力：它通过分析执行日志，震惊地发现 100 次运行中 Harness 自报成功达 99 次，但实际物理真值仅通过了 48 次（假阳性率高达 51.5%）。Opus 敏锐定位到了“任务遇到困难时控制循环过早退出”的结构性漏洞，于是重构并加入了一道严格的 Completion Verification Gate（真实完成检查门）。这一改动直接推动了反馈集与 Held-out 泛化集的同步大幅上涨，成为全场最具工程启发性的高光时刻。

05

严密理论压力测试与可计算数理模型

为了让 HarnessDev 的定性经验转化为指导工程落地的可计算模型，我们将论文中的四大实证现象形式化为严格的数学表达式。

模型一：Harness 共适应张量与跨模型迁移衰减模型
S(Me,HMc) = αΨ(Me) + βΦ(HMc) + γΩ(Me,Mc) − δ⋅Penrigid(HMc,Me)
定义：Mc 为创建者模型，Me 为执行者模型。Ψ 为执行器基础能力，Φ 为基础设施架构质量，Ω(Me,Mc)=exp(−∥we−wc∥22τ2) 为推理步调相似度，Penrigid=max(0,Kneed(Me)−Kcap(HMc)Kcap) 为硬编码步数截断惩罚。迁移弹性系数定义为：ηtrans=S(Munified,HMc)S(Mc,HMc)。
模型二：演化噪声置信边界与真伪版本检验准则
Z=ΔS2⋅σnoise ⟹ΔScrit(1−α) = z1−α/2⋅2⋅σnoise
单次评测标准差 σnoise=4.75，差值标准差 σΔ=2×4.75≈6.7175 分。在 95% 置信度下（z0.975=1.96），真收益门槛必须达到 13.17 分 才能彻底排除测量噪声！在未达阈值前，单次假阳性率 P(False)=1−Φ(Z)，10 轮演化累计误判率高达 Pcum=1−(1−P)10。
模型三：基础设施 Token 边际效用与无断点雪崩损耗模型
E[Costtotal] = (1+ρdead) ⋅ ∑k=1L [cstep(k) + pfail⋅(1−λckpt)⋅k⋅cstep(k)]
ρdead 为死代码与冗余控制分支开销占比，λckpt∈[0,1] 为检查点激活度。当 λckpt=0（如实测中的 26,679 条轨迹）时，任何单步故障都将触发从第 0 步开始的完全回滚重试，使得 Token 消耗呈现二次方级膨胀，最高导致同等准确率下 19 倍的算力黑洞。

自主演化工程启示与落地治理规范

HarnessDev 基准不仅是学术界的评测革新，更是工业界构建下一代具备自主进化能力的 Agentic 系统（如 JIT-Agent 与 Fleet 编排平台）的核心行动纲领。基于前述实证与推导，我们提炼出四大工程铁律：

📌 铁律一：基础设施与执行模型深度解耦，严禁硬编码控制常量

Opus 120 步上限导致 Gemini 性能腰斩的教训表明，Harness 绝不可写死任何特定模型的步数上限、提示词正则或输出格式假定。必须将控制参数（如探索深度、反思阈值、最大步数）外部化为由环境动态探测（Environment Probing）驱动的配置接口，实现“模型可热插拔、Harness 跨底座可迁移”。

📌 铁律二：建立噪声门禁机制，彻底废黜“小样本自选发版”

在单次评测波动达 ±4.75 分的现实下，任何低于 11~13 分 的单次反馈涨幅均不可作为发版依据；抽查 5 个用例全过不仅毫无统计效力，更是导致全局崩塌的虚假安全感来源。自主演化系统必须采用统计假设检验（Z-Gating / t-test），至少进行 3 次以上独立重跑并确认 p < 0.05，方可批准代码合并（Auto-Merge）。

📌 铁律三：以物理环境真实 Diff 替代语义自评，加装 Completion Gate

坚决剥夺 Agent 自身对任务是否成功的自评裁判权（自报 99 次仅真过 48 次）。在 Harness 终止前，必须强制调用外部环境验证器：编译是否通过、单元测试是否全绿、Git Diff 是否满足非空且语法正确。未通过外部断言的提前退出一律视为崩溃并执行重试。

📌 铁律四：斩断死代码，构建真实的 Checkpointing 容灾闭环

26,679 条轨迹零存档是当代 Agent 系统的巨大耻辱。在长程工程任务中，必须强制落地“每 N 步/每次有效工具调用落盘快照”的 WAL（Write-Ahead Logging）持久化机制。将崩溃重试从“全局归零”降级为“断点重放”，直接消灭 7~19 倍的 Token 浪费黑洞。

将 HarnessDev 与同门研究 Aspire（解决模型自主提出可学目标与任务生成）和 S³Gym（解决自主演化沙箱环境探索）相结合，便构成了完整的 递归自我改进（Recursive Self-Improvement, RSI）闭环图谱：模型不仅能自主设定学习目标、在沙箱中探索，更掌握了自主重塑与打磨自身执行骨架（Harness）的工程能力，推动自主智能体向着具备工业韧性的自主演化系统稳步迈进。
