0. 范式总览：软件生产控制层的历史性上移

表面上看，Claude Code 团队工程师 Thariq Shihipar 与 Ryan Peterman 约 70 分钟的深入技术访谈在复盘团队如何使用 AI、如何构建代码助手；但本质上，这场对话揭示了软件工程数十年来最深刻的一次结构性迁移：

“软件工程正在从‘人写代码 + AI 辅助’，迁移到‘人定义目标与判断标准 + Harness 驱动 Agent 持续执行’。”

真正发生变化的从来不是“敲代码的速度变快了”，而是软件生产系统的控制层（Control Plane）正在全面上移。

在传统工程中，人类工程师同时扮演“目标定义者”、“算法设计者”、“语法转译者（敲代码）”与“单体测试执行者”。随着 Agent 运行时间从几分钟延展至数小时乃至数天，敲击键盘转译语法这一低层执行动作已不再是系统瓶颈。工程师的阵地正在被迫、也是必然地退守并升维至：定义什么是好的结果（Domain Taste）、定义不可逾越的硬约束（Specs & Constraints）、构建自动化裁判体系（Verification & Evals），以及装配驱动 Agent 自主运转的工程底座（Harness）。

1. 我认为这篇文章最重要的结论：软件工程能力四元公式

访谈与深度评注给出的最关键论断，可以用一个高度凝练的形式化乘法模型表达：

CapabilitySE ≈ CapabilityModel × CapabilityHarness × CapabilityVerification × Domain Taste
公式 1.1：Agent 时代软件工程综合生产力模型（非相加，而是四元严格串联乘积）

这个公式彻底击碎了过去两年的流行误区——“软件工程能力 ≈ Prompt 写得好不好”。更揭示出一个颠覆直觉的技术剪刀差现象： 

模型基座能力提升 (Model Capacity ↑)
       ↓
Prompt / System Prompt 可以大幅减薄 (Prompt Thickness ↓)
       ↓
但 Harness 运行时系统反而越来越强、越来越复杂 (Harness Engineering Complexity ↑)
       ↓
因为模型能够承担越来越长程 (Long-Horizon)、越来越高自主度的复杂工程任务

正如 Thariq 明确强调的那样：随着模型能力增强，Harness 并没有变得无足轻重；恰恰相反，为了让模型能够安全可控地连续运行数小时、操作数十种异构工具、执行成百上千个 step、实时呈现中间结果并接受动态验证，Harness 变得极其关键。Auto mode、操作系统沙箱（Sandbox）、自愈重试流水线、动态 Workflows 与 Artifacts 管理，全部沉淀在这一层。

💎 访谈金句原声提炼

“强模型减少的是‘微观指令’（Micro-instructions），增加的是‘宏观自治’（Macro-autonomy）。”

2. 「删掉 80% System Prompt」真正意味着什么：从加法规训到减法释放

在社交网络与媒体二次传播中，最具眼球效应的一句话是：“Claude Code 删除了约 80% 的 System Prompt”。这一事实已被 Anthropic 官方发布的技术博客严格确认：针对新一代前沿模型（Opus 5、Fable 5），Claude Code 移除了大量陈旧的死板指令，System Prompt 缩减超过 80%，在标准 Coding Benchmark 上能力不但没有下降，代码泛化与创造性反而显著提升。

但这绝不意味着“提示词工程（Prompt Engineering）彻底消亡”，而是其内核发生了范式转移：

❌ 旧 Prompt Engineering（Additive / 规训式）
  • 堆砌大量微观行为准则（Micro-rules）
  • 充斥成百上千条 NEVER / ALWAYS 禁令
  • 硬编码 5 个正确输入输出例子、3 个反例
  • 详尽罗列每一处可能出现的语法错误并要求“必须执行 B”
  • 本质：把模型当作脆弱的规则执行器进行加法约束
✅ 新 Context Engineering（Subtractive / 上下文工程）
  • 清晰告知业务上下文与系统架构背景
  • 阐明“为什么这样做”与核心价值诉求
  • 明确可用的工具接口定义与数据契约（Schemas）
  • 定义何为“好的产出物”（Acceptance Criteria & Evals）
  • 本质：保留广阔探索解空间，只提供判断标准与事实基座

“例子锚定陷阱”（Example Anchor Effect）的逆向认知

Anthropic 在研发实践中发现了一个反常识现象：对于前沿高推理模型而言，Few-shot Examples 往往会起到负向扼杀作用。

弱模型需要 Example 依葫芦画瓢以对齐格式；但对于推理能力成熟的高智力模型，当工程师在 Prompt 中写下“这是一个好的重构示例”时，模型会将其误读为隐性强约束：“你的代码实现必须长得和这个例子大差不差”。这导致模型在全局搜索空间中被强行拉入局部的狭窄次优解，丧失了针对具体工程场景设计更优雅架构的可能。

提示词工程正在经历深刻形态演进：从 Instruction-heavy（指令繁复型）转向 Judgement-heavy（判断驱动型）。

3. 极为关键的限定条件：Subtractive Engineering 的准入边界

不能望文生义地得出“把所有项目的 Prompt、CLAUDE.md、Skills 盲目砍掉 80%”这一荒谬结论。Anthropic 官方明确指出：他们是针对不同基座代际的模型，加载完全分级的 System Prompt。

模型代际分级 代表基座模型 System Prompt 策略 主要约束构成 失败模式防御手段
Legacy / Compact Haiku 3, GPT-4o-mini, 早期开源 7B/8B Additive（加法式重型） 严格的格式要求、大量 Few-shot、防御性规则、步骤手把手拆解 依靠 Prompt 内的死板禁令防格式错乱与幻觉
Standard Frontier Sonnet 3.5 / 3.7, GPT-4o Balanced（平衡型） 架构上下文、工具使用指导、核心安全边界、少量领域反模式 Prompt 引导 + 编译器/Linter 浅层验证
Next-Gen Reasoning Opus 5, Fable 5, 深度思考型 Agent Subtractive（减法极致精简） 业务愿景、外部客观验收标准、工具契约、只留“无法推导的私域知识” 完全交由 Harness、沙箱、客观测试闭环进行束搜索校验

因此，高水平架构师在进行 Prompt 与 Skill 审查时的最高准则应当是：

📐 减法工程审查铁律 (Subtractive Engineering Rule)

规则不是越少越好，也不是越多越好，而是——“只编码模型无法可靠自行推断的信息”。

当审查团队的 CLAUDE.md 或工作流规则时，最核心的追问不再是“我们还能补充什么规则？”，而是“这条规则对于今天的基座模型来说，还有哪怕一丝存在的必要吗？”

4. Harness 为什么反而越来越重要：长程任务（Long-Horizon）的系统工程

业界一度存在一种极具迷惑性的技术乐观主义：“随着 LLM 智力攀升，最终一个纯裸模型（Raw Model）配上命令行终端，就能解决一切，外围的框架与 Harness 终将消亡”。

Thariq 与 Claude Code 核心团队在数万小时实战中得到的结论完全击碎了这一假想。当任务耗时从 30 秒的“写个斐波那契函数”演进到长达 8 小时的超大型重构、跨 50 个微服务的全栈功能实现时，系统复杂度的增长是超线性的：

Entropy(T) ∼ O( bT × ContextDrift(T) )
公式 4.1：无强 Harness 约束时长程任务状态熵增模型（随步数指数级发散）

在长程任务中，单纯依赖 Prompt 会瞬间陷入死锁与混乱。Harness 必须承担起完整的分布式系统运行时管理职责（Agent Runtime Engineering）：

Harness 核心子系统 工程职能 传统 Prompt 驱动下的必然崩溃模式 Claude Code 工程实践落地
权限与虚拟沙箱 (Sandbox) 阻断危险系统调用、网络嗅探与不可逆文件覆写 模型执行 rm -rf / 或覆盖核心生产配置 基于 OS 容器的轻量级虚拟工作区与权限策略拦截器
状态快照与回滚 (State Rollback) 当代码重构破坏整体构建时，无损回退工作树 模型在错误路径上越改越错，陷入“修 A 崩 B”无限循环 Git-tree 隐式快照栈，支持对整个 session 任意 step 的原子回滚
上下文主动压缩与遗忘 在 200k+ Token 窗口中动态提炼关键中间工件，丢弃噪声 超出有效注意力跨度，模型发生灾难性遗忘或“迷失在上下文中” 语义缓存、阶段性 Summary 注入与持久记忆层分离
动态工作流编排 (Dynamic Workflows) 将单体宏大目标切解为由数十个专用子 Agent 执行的 DAG 单 Agent 上下文被数千行日志撑爆，失去全局感知 Claude Code 具备“自我装配 Harness”能力，为复杂任务动态派生子 Agent
外部客观验证门禁 (Evals & Gates) 通过类型检查、编译器、单元测试对每次修改进行判分 模型基于自身主观概率自信地宣告“任务已完成” 强制退出准则（Stop Condition），不达标严禁退出

正如 Anthropic 官方在《A Harness for Every Task》中所指出：未来的 Harness 甚至不是静态手写的配置文件，而是由 Agent 根据任务性质，动态自主编写、即时加载运行的动态工作流。

5. Loop Engineering 是第二个核心：从主观宣告到客观收敛

Thariq 对 Loop Engineering（循环工程） 做出了行业迄今最精准的定义：

“Loop Engineering 不再是直接 Prompt Claude，而是去构造一个‘负责持续调度与 Prompt Claude 的系统’。”

这代表着人类在 Agent 体系中抽象阶梯的 5 级跃迁：

【Level 0: 问答】 Human → Claude → Answer
【Level 1: 辅写】 Human → Claude → Code Snippet
【Level 2: 线性】 Human → Goal → Claude → Implement → Test → Fix → Done
【Level 3: 反馈】 Human → Goal + Evals → Harness → [Agent → Act → Verify → Feedback ↺]
【Level 4: 宏观】 Human → Business Objective → Long-running Autonomous Harness 
                                          ├─ Monitor & Research
                                          ├─ Plan & Decompose
                                          ├─ Multi-Agent Implement
                                          ├─ Test & Adversarial Review
                                          └─ Verify against Ground Truth ↺

目前 Claude Code 已经官方规范化了四种 Loop 范式：

  • Turn-based Loop（单轮反馈环）：用户输入一次、Agent 思考并调用工具执行一次、反馈结果。
  • Goal-based Loop（目标驱动环 /goal）：以明确客观验收目标为锚点，只要未达到验收标准就自主循环迭代。
  • Time-based Loop（时间调度环 /loop）：按预定周期或触发器定时巡检、重试或收集遥测数据。
  • Proactive Loop（主动自省环）：Agent 实时监控系统输出，主动发起探索、优化或重构。
⚠️ /goal 命令的核心精髓：阻断主观幻觉完成

很多工程师误以为 /goal 只是写了一个 while (true) 循环让模型“不要偷懒继续干活”。这是极其肤浅的理解。

/goal 的真正数学精髓，是把“模型主观感觉任务已完成”（这是 LLM 最容易发生的高自信欺骗与幻觉点），无情地置换为“外部可计算客观条件通过判定”：

  • ❌ 极差的目标定义（主观）：“把网站的前端性能优化得更好一些” → 模型改了两行动画属性便宣告“优化极佳，已完成”。
  • ✅ 优秀的 Agent Loop 目标（客观约束）：Lighthouse Performance >= 90 && Unit Tests Pass == 100% && Git Diff <= 300 LOC && Console Errors == 0。

6. Verification 是 Agent 自治的真正许可证：成本结构的历史性倒挂

在 X 平台的讨论中，“测试代码量未来需要比以前多 100 倍”常被视作夸张的自媒体营销话术。然而，回归 Thariq 原访谈的语境，这是一条极为严肃严谨的软件工程经济学推论：

“当代码生成的边际成本趋近于零时，验证（Verification）成为整个生产体系中唯一真正昂贵的部分。”

在传统软件工程与 Agent 软件工程之间，工时与算力成本发生彻底的极性倒转：

传统软件工程成本分布：
写代码 (Writing Code)   ████████████████████████ (75% ~ 80%)
验证测试 (Verification) ██████ (20% ~ 25%)

Agent 时代软件工程成本分布：
生成代码 (Generation)   ██ (5%)
验证与评估 (Verification)██████████████████████████████ (95%)

由此推导出一条自治可信度定理：

Autonomy without Verification ≈ Gambling (随机游走与熵增崩溃) Autonomy with Strong Verification ≈ Controlled Search (在确定解空间内的束搜索)
公式 6.1：自治系统稳定性定理

没有严密验证的 Agent，步数越多，失败概率便以几何级数累乘崩溃；而拥有完备 Tests、Fixtures、Mocks、Contract Assertions 与 Evals 的系统，Agent 每一步修改都有 Oracle 进行判定与剪枝。因此，软件工程资产的皇冠，已经正式从“编写好的代码行”，转移到“能够提供绝对判真标准的 Verification 资产”上。

7. “六个月没敲一行代码”的真实口径：工程师抽象层级的结构性跃升

访谈中被广泛引用的“有企业客户六个月没有亲手敲一行代码”，必须在真实工程语境下理解——这是 Thariq 列举的采用高度标准化 Agentic 生产线的大型企业前沿标杆案例，而非行业普遍统计中位数。

更重要的是，这一现象绝不等于“工程师无所事事”或“软件工程消亡”。恰恰相反，它代表着工程师所在的抽象层级彻底脱离了繁琐的语法细节，上升到了更高密度的决策中枢：

软件生命周期阶段 传统 SDLC 模式 Agent-Native SDLC 模式 价值重心转移
问题定义与未知发现 人工零散讨论，漏测边缘情况 人类专家主导 + Agent 深度扫描代码库挖掘未知隐患 提升 3x（决定系统天花板）
目标与 Spec 规约 编写粗糙 PRD，大量细节在代码中补充 人类严密设计：严格的契约约束、时序图与验收断言 提升 5x（成为最核心生产物）
Harness 系统构建 传统的 Jenkins/GitHub Actions 配置 人类 + Agent 协同：编排工具链、Prompt 上下文、沙箱与超时策略 新设立的核心工程岗位
具体代码实现 (Coding) 人类工程师核心体力劳动 Agent 全权接管（极少量特异边界人工介入） 衰减 90%（商品化、机械化）
验证与质量把控 人工点测 + 部分 CI 单元测试 Harness 自动化 Oracle + 综合 Evals 多维矩阵评分 提升 4x（系统可靠性命脉）
产品与架构 Taste 裁决 上线后用户反馈 人类专家绝对把控（从成百上千种候选方案中选型审定） 稀缺性提升 10x

一言以蔽之：Coding 没有消失，Coding 正式变成了 Agent 的“汇编与执行中间语言”。

8. “代码”本身正在从最终产品退化为中间表示（IR）

这是整篇深度评注中最具颠覆性的一项理论推导。在计算机科学中，编译器的流水线通常是：

High-level Source → AST → IR (LLVM / Bytecode) → Optimizer → Machine Binary
传统编译流水线：代码是开发者倾注心血的静态资产

而在成熟的 Agent-Native 软件工程中，架构拓扑被重塑为：

Human Intent & Specs → Verification Oracle → Agent Engine → Code (Transitory IR) → Runtime Execution
Agent 时代系统流：代码是可任意推倒重来的瞬态工件

既然 Agent 可以在短短几分钟内，将一份 5,000 行的 Python 脚本无损重写为 Rust、重写架构、升级版本、甚至彻底删除重现，那么代码文本本身就不再具有不可替代的静态神圣性。它成了一种易耗的“中间表示”（Intermediate Representation）。

💡 软件可维护性（Maintainability）的划时代重定义

过去 40 年：可维护性意味着“人类可读性高、命名规范、目录干净、方便下一个人人肉修改”。

未来 10 年：可维护性意味着“维护一套能够稳定、反复、确定性重新生成正确软件的约束系统（Constraints & Verification Suite）”。只要 Specs 和 Evals 在，底层 IR 代码由谁生成、生成几遍，已经不再关键。

9. Prompt Blame 与 Agent 溯源工程：版本控制的新基石

在传统工程中，团队排查历史债务最核心的工具是 git blame——每一行代码归属于哪位工程师、提交于哪一个 commit、当时的 commit message 是什么。

然而，当工程师通过 Claude Code 一次性提交上千行代码时，简单的 git blame 彻底失效了。审查者面对满屏的代码，无法得知背后的决策路径。Thariq 透露了一个极具前瞻性的内部实践：他在提交大型 PR 时，会主动在 PR 描述中附带自己完整的 Prompt 历史、上下文关键截断、失败尝试的探索分支与最终 Eval 数据。

这标志着版本控制正在从纯文本的 Git History，演进为 Agent Provenance（智能体完整因果溯源图）： 

未来生产级 PR 的元数据全景图：
┌────────────────────────────────────────────────────────┐
│ Pull Request #1024: 重构订单并发结算引擎               │
├────────────────────────────────────────────────────────┤
│ • Git Diff: +1,240 / -820 lines                        │
│ • Prompt Provenance:                                   │
│   ├── User Intent / Goal Spec (Hash: 0x8a9f)           │
│   ├── Base Model: Claude-3.7-Sonnet-Thinking (v2026.03)│
│   ├── Injected Skills: [database-locking, conwip-queue]│

│   ├── Failed Exploration: 3 rollbacks (detected dead-lock)│
│   ├── Verification Pass: 100% (48 unit tests, 4 e2e)   │
│   └── Human Reviewer Touchpoints: 2 guidance nudges    │
└────────────────────────────────────────────────────────┘

没有 Provenance 记录的 AI 生成代码，在企业架构中就是“不可审计的技术黑天鹅”。Agent 溯源工程将成为未来合规、安全与协作的强制基础设施。

10. 为什么 Coding Agent 率先爆发，而写作/通用 Agent 滞后？

这场访谈回答了一个长久困扰学术界与投资界的宏大疑问：为什么在所有 Agent 垂直赛道中，代码编写（Coding）的实用化渗透率与爆发速度遥遥领先于文案写作、商业分析或法律咨询？

主流通俗解释通常是：“因为代码是高度结构化的文本，天然符合语法逻辑”。Thariq 与评注指出了更本质的因果根源——强客观反馈信号的存在与否（Objective Feedback Loop Density）：

💻 代码工程：超稠密客观反馈闭环

模型生成的每一行代码，都能立刻撞上极其坚固的客观判定墙：

  • 语法层：AST 解析器（Pass / SyntaxError）
  • 类型层：TypeScript / Rust 编译器（TypeCheck Pass / Fail）
  • 逻辑层：单元测试框架（Exit Code 0 vs 1）
  • 运行层：沙箱环境（Zero Panic / Memory Leak）
  • 界面层：Headless 浏览器控制台错误与截图 Diff

→ 形成了完美的“生成 - 报错 - 定位 - 修复 - 通过”强化回路！

✍️ 写作/咨询：弱主观离散反馈黑洞

模型写出一篇文章，客观世界无法给出高保真布尔判决：

  • “这篇文章行文是否生动？” → 缺乏数学 Oracle
  • “论证逻辑是否严密深刻？” → 人类读者观点分歧极大
  • “文风是否符合品牌调性？” → 纯主观经验 Taste
  • 无编译器、无自动化测试、无控制台堆栈追踪

→ 无法构建无人值守的高频自愈搜索循环！

📌 关键洞见总结

AI 最先彻底颠覆的，从来不是“人类以为最简单机械的工作”，而是“物理与系统反馈信号最强、最客观的工作”。

11. Taste 为什么在生成充裕时代反而拥有绝对定价权？

当谈及设计、产品架构与数学探索时，Thariq 给出了一条极为深刻的判断：模型能够在一分钟内生成 20 种不同的系统架构方案或界面交互实现，但最核心的致命问题变成了——“你究竟认不认识什么是好东西？”（Do you know what good looks like?）

在经济学中，当某种生产要素供给呈指数级膨胀时，其互补要素的边际收益将呈爆发式上升：

Marginal Value of Taste ∝ ∂Utility ∂(Candidate Pool Size) × Complexity
公式 11.1：候选解充裕时代鉴赏与裁决能力定价权模型

如果你缺乏深厚的领域品味（Taste），面对 Agent 生成的代码，你无法做甄别（Select）、无法敏锐地指出其架构债务并回绝（Reject）、更无法在更高维度指导其深入演化（Push further）。

因此，Agent 时代的降临绝不是“专业经验的贬值”；恰恰相反，低层级的转译经验（如何敲击特定语法）迅速归零，而高层级的系统审美品味、边界洞察力与领域判断力获得了前所未有的价值放大器。

12. 未来软件工程师的能力结构金字塔与角色再定义

基于上述所有论断，我们必须彻底重构软件工程师的人才能力画像。传统以“精通某种语言、熟悉框架 API”为基石的模型已然倒塌，全新的六层金字塔架构正式确立： 

                    ▲
                   /                   /   \  [1] Product Taste & Domain Judgment (品味与领域判断：定义终极标准)
                 /                     /───────\  [2] Problem Framing & Unknowns Discovery (问题构陷与未知发现)
               /                       /───────────\  [3] Specs, Invariant Constraints & Exit Criteria (严密规约)
             /                         /───────────────\  [4] Harness Engineering (运行时、沙箱、上下文与工作流装配)
           /                           /───────────────────\  [5] Verification & Eval Infrastructure (测试网、模拟器)
         /                             /───────────────────────\  [6] Automated Agent Execution (由 AI 完全接管的代码生成)
       └─────────────────────────┘

工程师的法定职业身份正在实现关键蜕变：

  • 从 Coder（代码编写工人） 蜕变为 System Designer（系统架构设计师）；
  • 从 Syntax Debugger（语法排错者） 蜕变为 Agent Supervisor & Critic（Agent 行为督导与裁判）；
  • 从 Task Receiver（需求接收端） 蜕变为 Domain Evaluator（领域评估裁决者）。

13. 这篇文章与「Agent 自主进化」的深度接轨：Harness-Level Self-Improvement

评注指出了一个与前沿演化理论高度契合的盲区：目前业界很多所谓的“Agent 自我改进（Self-Improvement）”，仅仅停留在“Agent 发现自己回答得不好，于是去修改自己的 Prompt”这一玩具级循环上。这种自指修改极易陷入提示词局部极小值崩溃。

而 Claude Code 体系揭示的，才是真正工业级、可计算的自进化系统架构（Harness-Level Self-Improvement）：

System(t+1) = Update( System(t) , FailureClassificationReal Tasks (Context, Skills, Harness, Evals) )
公式 13.1：Harness 级多维度自进化迭代状态转移方程

在真实的工程任务执行失败后，系统通过归因分析，能够精准识别故障点并执行分层进化：

  • 如果是上下文噪音导致的幻觉：进化 Context Trimming 策略与检索路由（Routing）；
  • 如果是特定领域解法缺失：自动封装并固化全新的动态技能包（Skill Accumulation）；
  • 如果是并发写入或状态丢失：升级 Harness 内部的状态快照机制与并发互斥锁（Harness Repair）；
  • 如果是边缘测试遗漏：自动补充高覆盖率的回归测试用例集（Regression Eval Expansion）。

14. 过去三年 Agent 演化五代全景与最终抽象

将 2023 年以来的大模型应用技术演化，可以清晰划分为五代技术浪潮：

代际与时间线 核心技术形态 主要瓶颈 人类开发者的工作重心
第 1 代 (2023) Prompt Engineering 模型无记忆、上下文窗口极小、无工具调用 编写复杂 Few-shot、魔改提示词、防止格式错乱
第 2 代 (2024) Tool-Using Agent 工具调用错误、状态不连贯、缺乏长期规划能力 定义 Function Calling 契约、手写简单 ReAct 循环
第 3 代 (2025) Context Engineering 长上下文注意力衰减、Prompt 规则冲突与膨胀 设计 RAG 架构、构建动态 Skill、实施 Subtractive 瘦身
第 4 代 (2026 当前) Harness + Loop Engineering 长程自治漂移、验证环境昂贵、跨 Agent 并发偏序 构建沙箱、设计 Goal 终止条件、搭建 Evals 矩阵
第 5 代 (Next) Self-Improving Software Factory 未知领域边界探索、高阶系统架构 Taste 的数学形式化 定义战略愿景、裁决业务品味、监督自进化 Harness 运转
🏁 终局结论：软件工程竞争主战场的不可逆迁徙

代码生成已经彻底从核心瓶颈蜕变为大宗商品。在即将到来的 Agent-Native 时代，真正稀缺的核心壁垒是：

  1. 极其清晰地洞察要做什么（Problem Framing）；
  2. 拥有高维的架构品味，知道什么才算真正的高品质成果（Domain Taste）；
  3. 能够将品味与业务标准精确编码为自动化验证系统（Verification & Evals）；
  4. 构建一套足以支撑 Agent 在长程、高并发、复杂约束下持续可靠运行的 Harness 运行时底座。

未来软件工程竞争的主战场，已经不可逆转地从“Who writes better code?（谁写代码更牛）”，迁移至：“Who builds the better system for AI to repeatedly produce, verify and improve software?（谁能为 AI 构建更强大的生产、验证与持续自进化系统）”。
