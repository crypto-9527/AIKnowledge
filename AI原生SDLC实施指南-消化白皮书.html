等待才是瓶颈

Anthropic 于 2026 年 8 月 21 日发布《The AI-Native SDLC playbook》，核心命题只有一句： 代码不再是瓶颈，围绕代码的等待才是。这份消化不重述指南的六个阶段， 而是把它翻译成可计算的约束——用 Amdahl 定律量化"加速 Build 的收益上限"， 用排队论反解"为什么合理并发是 2–3 个 session"，用假绿逃逸模型证明"Hook 的价值不依赖检出率"， 并逆推出原文那个 20–50 条 eval 建议背后的统计含义。

所有沙盘输出的每一个数字，都由本文给出的公式实时运算得出；凡属演示基线而非实测值的参数， 均在界面上显式标注。

证据边界

这是一份厂商实施框架，不是独立效果研究。它提供控制目标与落地手段，但不提供效果证据。 下文所有模型都是把指南的定性命题翻译成可计算的约束条件，用于帮助团队判断"这套蓝图在我的参数下会收敛还是发散"， 而不是证明这套蓝图有效。模型输出的正确性依赖于输入参数的真实性，参数必须由团队自己的试点数据标定。

01 · Amdahl：只加速 Build，收益上限被人类节奏锁死

指南的全局判断是：Build 阶段被压缩到数小时，而 plan、review/test、deploy 仍按人工节奏运行， 流程因此变成"中间快、两头慢"的沙漏形。这句话可以精确地写成 Amdahl 定律的形式。

设改造前交付周期 T 中，Build 占比为 f， 其余以人类节奏运行的部分占比为 1 − f。 Agent 使 Build 加速 k 倍，人类侧流程改善 h 倍 （默认 h = 1，即完全不改造）。则端到端加速比为：

S(k, h) = 1 fk  +  1 − fh

当 h = 1 且 Build 加速到极致（k → ∞）时， 端到端加速比收敛到一个与 k 无关的天花板：

S∞ = 1 1 − f   ·   η(k) = S(k, 1) S∞ = 1 1 + fk(1 − f)
η 为收益捕获率；1 − η 即被人类闸门吞噬、无法释放的加速收益比例。
SANDBOX 01Amdahl 瓶颈迁移与收益吞噬

拖动滑块观察：当 h = 1（完全不改造人类侧流程）时，无论 Build 加速多少倍，端到端收益都被 1/(1 − f) 锁死。请把 k 从 8 拉到 20，看端到端加速比几乎不动， 再把 h 从 1.00 拉到 1.30，对比两者的边际杠杆。

模型结论

在 f = 0.30、h = 1 的默认基线下， 即使 Build 加速 8 倍，端到端仅加速约 1.29 倍；把 Build 加速到 24 倍， 端到端也只能到 1.40 倍左右——因为天花板 S∞ ≈ 1.43 已经被锁死。 相反，只要把人类侧流程改善 30%（h = 1.30），端到端立刻超过 1.3 倍， 且其收益与 Build 的加速是可乘的。

这就是指南那句"瓶颈迁移"的定量含义：继续卷代码生成速度的边际收益趋近于零， 杠杆在人类侧的流程改造上。而工件链、AI review、Hook 审批闸门、确定性控制带， 本质都是在提高 h，而不是提高 k。

02 · 工件链与 Gate 拓扑：六阶段 × 四个必答题

Anthropic 没有删除六个阶段，而是把"人工传话"改造成可读取、可提交、可触发的工件。 贯穿六个阶段的一条主线是：每个阶段结束时向版本控制写入一个工件，下一阶段开始时读取它； 提交链本身就是审计轨迹——谁提了需求、Agent 产出了什么、谁批准了它。

关键结构：Markdown 只是手段，批准状态才是本体

Markdown + Git 是实现选择，不是方法本体。本体是每个阶段都有唯一、可追踪的批准状态。 因此 Jira、ServiceNow、Figma 仍可作为权威源——最低要求是用记录 ID 和 commit SHA 与仓库互相指向。 这条约束值得强调：它同时否定了"必须迁到 Markdown"和"可以保留两份不互链的真相"两个极端。

03 · 控制分层：从软提示到硬边界，各层不能互相冒充

Build 阶段最容易被误解成"让 Agent 写代码"。指南真正的重点是把不同类型的知识放进不同的控制层， 且明确警告：这些层不能互相冒充。

L1 · 上下文
CLAUDE.md — 项目上下文

构建命令、架构约定、反复出现的项目错误。建议保持约一页，细节下沉到目录级规则。这是提高遵循概率的软层，不具备强制力。

L2 · 政策
Skills — 咨询式组织政策

安全标准、设计规范、重复流程。版本化、可复用、跨项目。提高 Agent 遵循组织政策的概率，但仍是建议层。

L3 · 拦截
Hooks / 测试 / CI — 确定性拦截

冻结目录不可修改、修 Bug 时测试不可改写、凭据不得出现在 diff 中。必须永远成立的边界只能由这层强制，Branch protection 与权限系统同属此层。

L4 · 环境
Managed settings / sandbox / 网络白名单 / 短期凭证

限制 Agent 能看到和触达的环境。默认无常驻生产权限，凭证短期且范围受限。

L5 · 判断
人类 — 意图、例外、生产授权

不因自动化而消失，而是上移：从机械操作与逐行审查，上移到判断意图、裁决例外、承担风险、授权生产。

最容易被忽略的一句警告

指南原文强调：硬规则不会自动正确，只会稳定执行被写进去的规则。 翻译成工程语言就是——Hook 与 CI 提供的是执行的确定性（determinism）， 而不是判断的正确性（correctness）。规则或测试设计错误时， 系统只会更可靠地执行错误判断。因此事故必须能反向修改测试、eval、Skill 和权限策略， 否则确定性层会固化为错误放大器。

这条区别在 §06 的假绿逃逸模型里会被精确量化：提示层（L1/L2）提高的是检出率， 而 Hook 层（L3）做的是把某个失效通道的概率直接置零。两者的数学性质完全不同。

04 · 闸门排队论：为什么"2–3 个 session"是理性值

指南给出了一条硬建议和一个硬约束："Two or three sessions is a sensible starting point. The practical ceiling is how many streams one person can review properly." "能审多少"这个约束可以写成排队论模型，并反解出并发上限。

设一名工程师同时驱动 N 个并行 session； 每个 session 产出一个待审单元（plan / PR）的平均周期为 C 分钟， 故待审到达率 λ = N / C。 人类评审每个单元耗时 T 分钟，但并发会带来上下文切换惩罚 γ，使有效服务率随 N 衰减：

λ = NC   ·   μeff(N) = 1 T · (1 + γ(N − 1))   ·   ρ = λμeff = N·TC · (1 + γ(N − 1))

注意 ρ 对 N 是二次的—— 这是整个模型最关键的结论：并发数上升会同时推高到达率并压低有效服务率， 两头夹击。排队等待时间为：

WqM/M/1 = ρ μeff − λ      WqM/D/1 = ρ 2(μeff − λ)      Nmax = max{ N : ρ < 1 且 Wq ≤ Wmax }
M/M/1 假设到达与服务时间均为指数分布（高变异，悲观上界）；M/D/1 假设服务时间确定（变异减半，乐观下界）。 真实情况落在两者之间。Nmax 由数值扫描求得，无闭式解（因 γ 项使方程为二次）。

模型给出的三条可执行结论

其一，并发上限是推导出来的，不是拍出来的。 ρ 对 N 是二次的，所以存在明确的崩塌点； 越过它，增加 session 只会增加在制品，不增加吞吐。

其二，降低评审耗时的变异性，与降低评审耗时本身同等重要。 M/D/1 相比 M/M/1 把等待时间直接减半——这解释了为什么指南反复强调 REVIEW.md 要明确定义"什么算 Important、什么只是 Nit、哪些生成文件应跳过"： 标准化评审标准压缩的正是服务时间的方差。

其三，调度器的首要职责是准入控制，不是事后重排。 一旦 ρ ≥ 1，任何优先级排序都救不回吞吐——队列只会无限增长。 这正是 CONWIP（恒定在制品）的意义：先限流，再谈排序。

05 · USL：团队级并行度的拐点与倒挂

§04 处理的是单人的评审瓶颈。当并行度上升到团队级（多个 worktree、多个 Subagent 同时改动同一代码库）， 需要更一般的模型：通用可扩展性定律（Universal Scalability Law）。

C(N) = N 1 + σ(N − 1) + κN(N − 1)      N* = 1 − σ κ
σ = 争用损耗（共享文件、单一事实源、CI 排队）； κ = 一致性损耗（跨 session 语义写偏序、worktree 合并冲突、同一事实源双写）。 当 κ > 0 时，C(N) 在 N* 之后单调下降——加人减产。

把 USL 映射到指南的 Build 阶段：σ 对应"共享文件较多的工作仍应串行"， κ 对应"不能同时维护两份没有链接的真相"。这两句话在指南里是经验之谈， 在 USL 里就是两个明确的损耗参数。

与指南的对应关系

06 · 假绿逃逸：Hook 的价值不依赖检出率

Test 章节最锋利的一句是："Agent 自测通过"还不够。因为验证证据若能被产生代码的同一执行过程随意改写， Agent 就能通过放宽断言、删除边界条件或重写测试来制造绿色结果。这句话可以写成概率模型。

Pesc = d · (1 − c1) · m · (1 − c2)
d = 改动引入缺陷的先验概率； c1 = 会话内反馈回路（自检）的检出率； m = 自检未检出时，Agent 通过修改测试/断言制造假绿的概率； c2 = 独立 verifier（新上下文、独立工具权限）的假绿检出率。

这个式子的结构暴露了软层与硬层的本质差异：

  • 提示层（CLAUDE.md / Skills）作用于 c1——把检出率从 0.60 提到 0.80 是概率性改善，逃逸率按比例下降，但永不为零。
  • Hook 层（禁止在修复任务中编辑测试文件）作用于 m——把 m 直接置零，使 Pesc 恒等于 0，与 c1 高低完全无关。
  • 独立 verifier 作用于 c2——它是第二道概率性闸门，但无法替代结构性归零。
SANDBOX 04假绿逃逸率与 Hook 的结构性归零效应

先把 c₁（自检检出率）从 0.70 拉到 0.95，观察逃逸率只是按比例下降； 再勾选"启用 Hook 禁止改写测试"，看逃逸率直接归零。 这演示了一个工程原则：检出率是乘法改善，禁止是结构性消除。

对"先写失败测试"这条实践的形式化解释

指南要求：修 Bug 时先写出并提交一个确定会失败的测试，再用 Hook 阻止 Agent 在修复过程中修改它。 这个组合在模型里同时做了两件事——失败测试把 c1 抬到接近 1 （缺陷已被显式复现），Hook 把 m 置零。 二者不是冗余的：失败测试解决"能不能发现"，Hook 解决"发现了能不能赖掉"。 只做前者，Agent 仍有 m 的概率把红灯改成绿灯。

07 · 逆推 20–50：eval 集规模背后的统计含义

指南给出了一条硬数字："collects 20 to 50 real tasks from recent work"， 并要求在模型、提示词、CLAUDE.md、Skill 或 Hook 变化时运行同一批 eval， 且每次生产事故都应变成永久 eval。但原文没有解释为什么是 20 到 50。 这个区间可以用最朴素的覆盖概率反解出来。

设一次配置变更引入某类回归；单个真实任务能够命中该类回归的概率为 p。 则 n 个任务全部未命中（即漏检）的概率为 (1 − p)n。给定可容忍漏检率 α，所需任务数为：

(1 − p)n ≤ α   ⟹   n ≥ ln α ln(1 − p)
假设各任务对回归的命中事件相互独立——这是强假设，真实 eval 集任务间存在相关性，会高估覆盖度。
SANDBOX 05Eval 集规模反解与 20–50 区间定位

拖动单任务命中率 p 与漏检容忍度 α，看所需任务数 n 如何变化。 在 α = 5% 下，当单任务命中率落在约 6%–13% 区间时，反解出的 n 恰好落在原文的 20–50 之间—— 这为指南的经验建议提供了一个自洽的统计学解释。

独立性假设的边界

这个推导依赖"各任务命中事件相互独立"，而真实 eval 集中的任务往往高度相关 （同语言、同框架、同代码库区域）。相关性会使实际覆盖度低于公式给出的值， 也就是说 n 是一个下界而非上界。 这反过来说明指南另一条建议的必要性：每次生产事故都必须变成永久 eval—— 因为事故样本携带的正是"公式漏掉的那部分相关性信息"，它们补充的是任务集的多样性而非数量。

直接从线上异常自动修复开始，等于跳过意图、测试、审批、权限和回滚的全部前提。 Maintain 是六阶段中唯一从"由人启动 Agent"走向"事件自动唤醒 Agent"的部分， 因此指南把它的前置条件放得最重：可观测性、稳定基线、低噪声触发、独立权限边界、已演练的回滚，缺一项都不应上自动处置。

09 · 扩权门控决策器：什么时候有权增加自主度

指南给出的验收判据是一句话："周期缩短且质量和审查负担没有恶化，再逐步增加任务范围、平行会话和权限。" 这句话可以形式化为一个四维权衡的门控函数。注意它与常见的"加权连乘打分"有本质区别： 这里是硬闸门合取（任一不满足即不得扩权），而非优先级排序—— 安全和质量维度不适用加权平均，一票归零是正确行为。

GO ⇔ RT ≤ θT  ∧  RCI ≥ θCI  ∧  Resc ≤ θesc  ∧  Rrw ≤ θrw
R 为改造后/改造前的比值。前两项越小越好（周期、返工），第三项越大越好（首次 CI 通过率）。 准备度分数采用几何平均：保留"单项不达标则总分归零"的硬闸门性质，同时避免算术平均用高分项掩盖致命短板的掩盖效应。

10 · 独立第三方对照：局部提速与端到端提速确实是两件事

指南本身没有效果数据。要判断"加速 Build 是否真的缩短交付周期"，需要引用独立于厂商的研究。 Google DORA 2024 年度研究（约 3,000 名技术从业者样本）是目前最合适的对照组， 它的结论与 §01 的 Amdahl 模型高度一致，且方向相反于直觉。

DORA 数据呈现了一个教科书式的局部—全局背离：五项局部指标全部改善（1.3%–7.5%）， 两项端到端指标全部恶化（−1.5% 与 −7.2%）。用 §01 的语言解释， 就是 k 确实变大了，但 h 几乎没动， 同时加速引入了新的损耗（返工、稳定性下降），使有效 f 反而缩小。

指南的价值正在于此：它不是另一份"用 AI 写代码"的指南， 而是一整套旨在提高 h 的改造方案—— 工件链压缩交接等待，AI review 与 REVIEW.md 压缩评审方差， Hook 与 branch protection 把审批从会议下沉到确定性执行， 确定性控制带把运维响应从人工值班变成自动唤醒。 这四项都不增加代码产出速度，它们减少的是等待。

另一组值得警惕的第三方观察

GitClear 于 2026 年 6 月发布的一项纵向分析（覆盖 2023–2026 年约 6.23 亿次代码变更）报告： 重构活动下降约 70%，代码块重复上升约 81%，错误掩盖结构上升约 47%。 本文转引自第三方技术媒体对该报告的转述，未直接核验一手报告，请按二手证据对待。 若该组数字成立，它指向的正是 §03 那条警告的现实版本： 确定性层会稳定执行被写进去的规则，而"不重构、多复制、掩盖错误"正是缺乏维护约束时的典型漂移方向。 这也解释了指南为什么把 Recurring codebase scans 列为 Maintain 阶段的独立 play。

11 · 三条边界与最小试点清单

边界一 · 蓝图不是效果证据

指南建议观察周期、首次 CI、PR 审查、DORA 与事故复发率，但没有客户样本、前后对照或已实现的效率数字 （已逐段核验确认）。团队必须用自己的试点数据验证，且要用 §09 的门控函数做判断，而不是凭体感。

边界二 · 可追踪不等于已经合规

Git 和 PR 能留下记录，但可靠审计还需要身份、不可绕过的权限、事实源映射、日志保留、职责分离和组织认可。 工件链解决的是"能不能追溯"，不等于"审计是否认可"。受监管行业需要把这六项与工件链一起补齐。

边界三 · 确定性不等于正确

Hook 会稳定执行写入的规则，CI 会稳定运行已有测试；规则或测试设计错误时，系统只会更可靠地执行错误判断。 用 §03 的语言说：L3/L4 层提供的是 P(执行 | 规则) 的确定性， 而不是 P(规则正确)。因此事故必须能反向修改测试、eval、Skill 和权限策略。

最小安全试点的四个组成部分

  1. 选一种低风险、高频、容易验证的改动——文案修正、内部小工具、已有成熟测试的局部 Bug。不要选核心链路，不要选缺少测试覆盖的区域。
  2. 固定 intent → spec → plan → PR 的工件链，四件全部进版本控制，彼此用 commit SHA 互链。
  3. 提供一键验证命令并写入 CLAUDE.md 的"完成"定义；同时设置不可绕过的硬边界（至少一条 Hook：修复任务中测试文件不可编辑）。
  4. 用 §09 的四项指标决定是否扩权：周期比、首次 CI 通过率比、逃逸缺陷率比、审查返工轮次比。四项全绿才增加任务范围、平行会话和权限。
压回三个问题

整份指南最终可以压回三个问题，团队应在每一个阶段都回答它们： 这一阶段留下什么证据？什么边界不可绕过？谁为最后的判断负责？ 先让一种改动完整、可验、可追踪地走到 PR，再谈让整个循环自己运行。
