一、手册概览与四段主线

Anthropic 于 2026 年 5 月 6 日发布了一份 36 页的创始人手册《The Founder's Playbook》（PDF v3 版），把 AI 原生创业的路径重新拆解为 Idea、MVP、Launch、Scale 四个阶段。手册的核心论点很直接：创始人要做的事没变，还是那三件——找到一个真问题、做出解决它的东西、把它做成一家公司。AI 改的是到达终点的路。

它压缩了这条路径，让每个阶段不再自动要求更大的团队和新一轮融资，瓶颈从「你能造什么」挪到了「你选择造什么」。

1.1 一分钟速览

  • 手册把 AI 原生创业路径重新拆成 Idea、MVP、Launch、Scale 四个阶段，每个阶段都给出明确的退出标准。
  • 核心工具栈是 Claude（研究策略）、Claude Code（写代码）、Claude Cowork（运营自动化）三件套，手册给了一张具体的任务对工具对应表。
  • 每个阶段都列出 AI 时代特有的失败模式：把原型当验证、无摩擦范围蔓延、AI 加持的确认偏误、agentic 技术债，并配上对应的 Claude 练习。
  • MVP 阶段的退出标准用 Sean Ellis 测试量化：超过 40% 的活跃用户回答「如果不能用这产品会非常失望」，视为产品市场契合度的信号。
  • 书末附十余家真实创业公司案例，包括每年处理 2.2 万例手术病例、数据摘录效率提升 66% 的 Carta Healthcare，以及帮 150 万用户把想法做成软件的 Anything。

手册全篇反复回到同一个工具三件套：研究策略交给 Claude，写代码交给 Claude Code（AI 自主写代码、测试、调试的编码环境），运营自动化交给 Claude Cowork。下面按四个阶段依次拆，先看 AI 到底压缩了这条路的哪一段。

二、旧路径七步循环，新路径只留四段主线

AI 并没有让创业跳过任何一个阶段，它拆掉的是阶段之间那条默认绑定：过去每进入一个新阶段，都自动意味着招更多人、换一套技能、再融一轮钱。现在这层绑定被解开了。

传统路径 · 每一步都在触发扩张

  • 验证问题 → 招研究 / 分析岗
  • 做原型 → 招工程团队
  • 上线 → 招运营与支持
  • 规模化 → 再融一轮、换管理层
  • 瓶颈始终在「你能造什么」

AI 原生路径 · 阶段间不再自动扩团队

  • 验证问题 → 创始人 + Claude
  • 做原型 → 创始人 + Claude Code
  • 上线运营 → 创始人 + Claude Cowork
  • 规模化 → 系统化的组织与流程
  • 瓶颈转移到「你选择造什么」

2.1 AI 替代的三种能力

手册把 AI 在每个环节替代的能力说得很具体：

环节AI 的角色具体工作
研究随叫随到的各领域专家竞品分析、市场规模测算、财务建模、起草投资备忘录
编码永远在线、永不被阻塞的工程师把过去一整个团队的活，压缩成创始人自己能交付的工作
运营按需的自动化运营团队CRM 在成交推进时自动更新、周报自己编好、产品文档随产品变更同步
角色的整体上移

结果是创始人的角色重心整体上移：从写代码、管人、处理日常杂务的「执行者」，转向生成想法、指挥这些 AI 工具去落地的「编排者」。手册特别点出，这里最有分量的变化，是让那些有行业经验、却没有工程背景的人也能开公司——创业者的来源池就此扩大到工程师之外。

三、同一个 Claude，套着三个不同的工作空间

手册强调：Chat、Claude Cowork、Claude Code 三者背后是同一个 Claude，区别只是外面套的工作空间不同。选错界面，会让本该顺手的事变别扭。下面这张表是可以直接套用的选择框架。

如果任务是该用什么为什么
一个问题、一次改写、快速头脑风暴Chat快、对话式、不用配置
研究、分析，或基于你的文件和系统整理出一份成品文档Claude Cowork能读文件夹、接各种连接器、跑技能、可定时执行
写代码、测试、上线软件Claude Code能读代码库、有 diff、有 git、有开发环境

手册给的直觉是：Chat 处理运营公司时源源不断的小事，比如从一份密密麻麻的投资备忘录里拎出一句话结论、开董事会前核一下某个说法；Claude Cowork 处理真正耗时间的知识工作，比如把一文件夹的客户通话记录整理成主题发现文档、周一早上定时从连接的工具拉指标编成 KPI 简报；Claude Code 是团队里工程师的编码环境，从原型走到生产、迁移 MVP 时期的旧代码，都不必再等更多人手。

📋 Chat / Claude Cowork / Claude Code 怎么选
任务是快速问答、改写、头脑风暴 → 用 Chat（快、对话式、不需要配置）。任务是研究、分析，或者要基于你的文件和系统整理出一份成品文档 → 用 Claude Cowork（能读文件夹、接入各种连接器、跑技能、可以定时执行）。任务是写代码、测试或者上线软件 → 用 Claude Code（能直接读代码库、有 diff、有 git、有开发环境）。三者背后是同一个 Claude，区别只是外面套的工作空间不同。

四、Idea：先别急着写代码，把「这是不是真问题」验证透

每个创始人都从同一个地方出发：一个自己停不下来去想的问题。Idea 阶段的心法只有一句——证据没到之前，不许动手建。这一阶段的活是研究、客户访谈、竞品分析，以及诚实评估那些反对你的证据，全部要发生在让 Claude Code 写第一行生产代码之前。

手册把 Idea 阶段列成一串按顺序回答的问题：这个问题真实、具体、频繁到值得围着它建公司吗？谁在遇到它，这构成一个市场吗？有没有别人在解，解得怎么样？一个方案要真正解决它得做到什么，我的想法做到了吗？这些加起来回答一个终极问题：这值得建吗？

4.1 关键是先具体，再动身

✕ 一句观察（没法验证）

「大家报销都很头疼。」——这只是一句观察，没法验证。

✓ 一句可验证的假设

「中型公司的财务经理每周花 4 小时以上核对报销，因为现有工具不接他们的记账软件。」——换成一句可验证的假设，事情才立得住。

4.2 退出标准：三个问题全答「是」才走

Idea 阶段的退出条件是找到问题与方案的契合，也就是先有实打实的定性证据（主要来自真人对话），证明你在为真实的人解决真实的问题，然后才去建那个解决方案。三个问题全为「是」，才算能走：

判断问题具体要求
问题真实且具体吗能说出谁遇到、多频繁、多严重、他们现在怎么应付
方案对准的是真问题吗是验证过程揭示的那个问题，不一定是你最初假设的那个
信号够支撑开工吗这阶段永远不会有确定性，等确定本身就是一种失败；但要够到能理性决定做 MVP，而不是凭一股信念

4.3 这一阶段的三个陷阱

陷阱一 · 把构建当验证

技术门槛一被搬走，一个上头的创始人最容易跳过整段旅程里最重要的活：验证这想法真是人们需要、会用的东西。就算在 agentic 编码出现之前，也有 42% 的创业公司因为做了没人要的东西而失败。现在从「我有个想法」到「我有个产品」的距离被压得极短，这个失败率只会往上走。

原型的正确用法

一个能跑的原型太容易被误当成「我在解决真问题」的实证，但它不是。原型真正的用处，是当你和潜在用户对话时的一个压力测试道具——那些对话本身才是证据。

42%
AI 编程工具普及前，因「做了没人要的东西」而失败的创业公司占比。手册预计这个数字随原型变得极易生成还会上升。

陷阱二 · 过早规模化

建东西一旦变得毫不费力，你会在还没验证问题与方案契合之前，就把执行推到远超需求的地方，而且往往是无意识地跑偏。agentic 编码工具会用同样的热情，围着一个根本错了的前提生成、测试、调试、重构一整套代码。

对策：让理解跑在构建前面，尤其是在建东西又快又不费力的时候。

陷阱三 · AI 加持的确认偏误

让 AI 证明你的想法，它就找得到支持证据；让它测算你的市场，它就给出让 TAM 看起来能拿到融资的那个数。AI 跟着你的指令走，一个不问难题的创始人，现在能比以往更快地为一个坏想法搭起一份看起来很扎实的论证，还自以为在做尽职调查。

对策：把同一个工具掉转枪口，让 AI 去攻击你的想法、专门找能推翻假设的反面证据。研究和结构化的对抗性思考如果指向「想法需要修正」，那就是转向的信号。

4.4 怎么用 Claude 走完 Idea 阶段（四组提示词）

先把假设打磨到真能验证。Claude 在这里最有用的地方是逼你说具体：到底谁有这问题、多频繁、多严重、现在怎么办。答不上这几个的问题陈述，还没到能验证的程度。

📋 把模糊问题压成可验证假设
把你的问题陈述讲给 Claude，让它帮你打磨成一句可验证的假设。反面例子：「合同审查太慢了」，这话没法验证。正面例子：「中型公司的内部法务团队每次合同审查要花 3 天以上，因为红线修改是靠邮件往来管理，而不是一个版本控制的单一文档」，这话可以验证。打磨完假设后，下一步是让 Claude 反过来攻击你的想法，专门找能推翻这个假设的反面证据。

接着是竞品。手册点了一个创业者特有的毛病叫 competitor neglect（竞争对手忽视），意思是太专注自己的愿景和执行，系统性地低估同赛道里别人在做什么。解药是让 Claude 反着来，论证一个竞争对手为什么会赢、而你会输。

📋 竞争格局分层扫描
让 Claude 按层级画出你的竞争格局：直接竞争者、间接竞争者、潜在收购方、可能跨界进场的邻近玩家。然后让它论证每一层为什么对你构成真实威胁，而不是给你一个最容易被反驳的弱化版本。
难词翻译 · TAM / SAM / SOM

手册让你用公开数据搭 TAM / SAM / SOM 模型再压力测试。这是分析一个市场能有多大的三层框架。

TAM
最外圈，这个问题理论上能覆盖的全部市场（所有可能的买家）。
SAM
中间圈，你的产品实际够得着的那部分人。
SOM
最里圈，你现实中能签下来、拿到手的那批客户。

然后是设计客户访谈。手册说，一个菜鸟创始人最常犯的错，是问一个宽泛、面向未来的问题（「你会用这样的产品吗」），而不去问具体的过去（「说说你上次遇到这问题是怎么处理的」）。让 Claude 审你手写的问题，把引导性的、假设性的、太宽泛的都揪出来。

📋 用户访谈提问自查
先自己手写访谈问题，再让 Claude 审核。明确要求它标出哪些问题是引导性的、面向未来假设的（比如「你会用这样的产品吗」）、太宽泛的，或者容易让对方给出讨好式回答而非真实回答的。然后让它针对访谈中最容易被对方回避的两三个关键节点，设计追问话术。

验证做到位、方案概念也经过压力测试之后，才轮到 Claude Code 登场。这一步不是建真产品，而是造一个能让真人上手摸到的功能样本，用在客户和投资人对话里。

📋 轻量原型验证清单
明确你的方案依赖的那一个核心交互是什么，只让 Claude Code 把这一个核心交互做出来。做好后拿给验证过的目标用户画像里的 5 个人试用，观察他们的真实反应，决定继续做还是回去重新验证。

五、MVP：做出来只是开始，证明有人离不开它才算数

很多创始人把 MVP 当成纯粹的施工阶段，但它本质上还是在收集证据。不同的是，现在收集的证据是关于解决方案的：一群真实、能被识别出来的人，是不是觉得它有价值到愿意用、愿意回来、愿意付钱、愿意推荐给别人。

手册给 MVP 阶段压了三个目标：

  1. 把验证过的问题变成真实用户会用的产品，是最小、最聚焦的那一版，不是塞满路线图功能的完整版。
  2. 快，但别欠下会复利的技术债。
  3. 从第一天就投资持久上下文，这是让 AI 保持放大器、而不是变成熵源的关键。

5.1 退出标准：Sean Ellis 测试 + 用力测试

宣布拿到产品市场契合度、可以从 MVP 进 Launch，最终是一次结合创始人直觉和已收集证据的判断。手册给了两把好用的尺。

尺一 · Sean Ellis 测试

问活跃用户一个问题：如果明天不能再用这个产品，你会怎么样？回答「非常失望」的比例超过 40%，就是一个有意义的产品市场契合度信号。

尺二 · 用力测试

找到 PMF 之前，留存靠创始人不断使力：频繁触达、给激励、人肉跟进；找到之后，产品开始自己做这件事。当感觉从「你推着用户走」变成「产品拉着用户来」，这个用力方式的转变，是发生了真实变化最清楚的信号之一。

40%
回答「非常失望」的活跃用户占比越过 40% 这条线，视为产品市场契合度的信号。手册强调这不是单点数据能确认的，需要在多轮迭代里都稳住这个模式，才敢下定论。

它的退出条件是拿到产品市场契合度的真实证据，也就是留存、付费、推荐三者里，至少有一样被实证出来。

5.2 四个陷阱，两个最有 AI 时代特色

陷阱一 · agentic 技术债

普通技术债是慢慢累积的，能在后面某个专门的冲刺里清掉。AI 技术债不一样，它会复利。如果没有把架构约束写在 AI 能读到的地方，每一次会话都会从零重新推导那些底层决策，而这些决策会漂移。最后你得到一个没有连贯心智模型的代码库——不是哪一块单独很烂，而是这些块从一开始就不是为了拼在一起而设计的，这个问题往往很晚才浮现。

手册开的药，是在打开 Claude Code 写第一行代码之前，先用 Claude 定义并写下架构决策，存成 CLAUDE.md 文件。它是 Claude Code 的项目级指令，会被 Agent SDK 在目录里运行时自动读取，功能上就是这个项目的持久「记忆」。

📋 开工前先让 Claude 写 CLAUDE.md 架构文档
在打开 Claude Code 之前，先跟 Claude 说清楚你要做什么：这个产品解决的核心问题、服务的用户、未来六个月现实预期的规模。让它帮你定义 MVP 阶段该遵守的架构原则、该规避的依赖项，以及你在这个阶段有意识接受的取舍。把这次对话的产出存成 CLAUDE.md 文件，作为后续每次 Claude Code 会话都要读取的架构上下文文档。

陷阱二 · 无摩擦范围蔓延

范围蔓延一直是创业风险，过去挡它的力量是工程时间的真实成本。现在加一个功能只要一个下午，那道天然的闸门没了。麻烦在于每一个添加单看都站得住：这个边界情况当然该处理、用户当然会想要那个流程。它们在当下都不像范围蔓延，可产品一旦漫出原定边界，你就有丢掉方向和势头的风险。

对策：在动手前写一份书面的范围文档，说清产品做什么、刻意不做什么、以及什么样的真实用户证据才够格新增一个功能。这样决策点就从「我们该建这个吗」变成「有没有一批关键数量的用户告诉我们，缺了它他们就用不出价值」。

陷阱三 · 把早期热度误当成产品市场契合

AI 工具能造出漂亮的早期数字，但这不保证市场需要你的产品。上线时的热度来自转瞬即逝的力量：创始人的朋友、投资人旗下其他被投公司里的潜在买家、一条冲上热榜的头条。这些都无法可靠预测第六周、第十二周初始助推退潮后会发生什么。

对策：在第一个用户到来之前就建好度量框架——先设好留存基准、激活标准、第 7 天和第 30 天目标，并定义清楚对你这个产品来说「假阳性」长什么样。

陷阱四 · 新手最容易漏掉的安全风险

agentic 编码工具生成的是能跑的代码，不是天然安全的代码。功能好坏很直接，要么能跑，要么跑不起来；安全漏洞在被利用之前是隐形的，没有天然的反馈回路来提醒一个新手创始人哪里出了问题。上线一个真用户能碰的 MVP，意味着真数据、真暴露、真后果。

对策：在任何用户碰到应用之前做一次安全审查，这是把一个 MVP 放进真实世界的最低责任门槛。

📋 上线前安全审查任务书
正式让任何真实用户接触产品之前，用一份明确的审查任务把核心应用代码交给 Claude 过一遍：检查身份验证和会话管理、API 响应中的数据暴露、输入校验和注入风险、以及有已知漏洞的依赖包。每一个发现都认真对待，凡是涉及身份验证、密钥或数据处理的问题，都要走人工复核。
手册注明的能力边界

Claude Code 的 AI 扫描是辅助，不能替代安全工具，更高风险处也不能替代人工复核。另有一个 Claude Code Security 能进一步扫漏洞并给出待人工审阅的补丁，出版时它还是限量测试版，用之前要确认可用性。

5.3 如果三轮迭代还没起色

如果做了三轮以上迭代，产品市场契合度的关键指标始终没明显起色，手册说这不是失败，而是系统在正常工作——MVP 阶段本就是设计来在你过度投入错误答案之前把这个信息暴露出来。这时先别急着定下一步，让 Claude 跑一遍诊断。

📋 没到 PMF 时的三问诊断
如果你已经完成三轮以上迭代，产品市场契合度的关键指标却始终没有明显起色，先别急着决定下一步，让 Claude 跑一遍诊断。把留存数据、用户反馈和最初的问题假设都喂给它，问它三个问题：这批数据里有没有一个细分群体的反应和其他人明显不一样？设计时预想的价值和用户实际体验到的价值之间的落差，是定位问题还是产品问题？现有产品要达到真正的产品市场契合度，需要满足什么条件，照你现在看到的情况，这个条件现实吗？

六、Launch：从「我一个人扛」到「系统自己转」

如果说 MVP 阶段是在证明产品值得存在，Launch 阶段就是在证明这门生意值得长大。除了把产品做到能上生产，还得同时给它下面的基础设施加固，并且真正围着产品搭起一家公司。

手册特别提醒一个转折：Idea 和 MVP 阶段公司天然以创始人为中心，因为你需要完整的情境感知和紧密的反馈回路。到了 Launch，还想亲手攥着每一根线的创始人，就成了瓶颈。目标不是把自己从公司里抽走，而是搭起运营系统，把注意力腾出来给只有创始人能做的决策。

6.1 退出标准：三条同时成立

退出条件具体要求
增长可复制且渠道驱动不只是留住用户，还能通过具体渠道可预测地获取用户，CAC、LTV、回本周期你都清楚、都能站得住
产品扛得住生产负载基础设施加固到位，安全合规就绪，在真实生产条件（不只是你测过的那些条件）下可靠性稳得住
运营不再靠创始人兜底流程和自动化就位，你不再是那个亲手处理支持、分诊、冲刺规划、出报表的人
难词翻译 · CAC / LTV / 回本周期
CAC
获取一个付费用户平均要花的钱。
LTV
这个用户整个生命周期能给你带来的总收入。
回本周期
花在他身上的钱要多久才能通过他的付费赚回来。这三个数能不能说清、经不经得起追问，是「增长可复制」的硬门槛。

6.2 怎么看出自己已经成了瓶颈

从「亲手做活」到「设计那套替你做活的系统」，是整个创业周期里最难的转变之一。难在它很少有一个清晰的时刻，风险就是你完全错过它——组织在你身边停滞，你却还留在建造者模式里。手册给了三个可以对照的信号：

⏳
本该一小时定的决策，现在要拖一周才轮到你处理
📥
支持请求堆着，因为只有你知道答案
🧠
有些运营任务，只有你亲自记得才会发生

补救的办法，是对你亲手在处理的一切做一次彻底盘点，从最小的任务到最高风险的决策，分出哪些能系统化、哪些能交给别人（未必是你）、哪些确实还值得创始人的时间和注意力。

练习 · 亲手事务三分法（手册正文描述，非原文提示词）
  • 能系统化：交给 Claude Cowork 的定时工作流、模板与自动化，例如 KPI 简报、CRM 更新、文档同步。
  • 能交给别人：不必然是你，可移交给人或 AI 系统，但需先把机构知识写成文档。
  • 留给自己：只有创始人带着完整背景才能拍的决策，如定价转向、关键 hires、融资节奏。

另外两块补课手册也点了名：MVP 时期为速度欠下的技术债，现在开始计息，越拖越贵，要做系统性的架构审计、针对性重构、并实打实扩测试覆盖；安全与合规也不再能延期，一旦处理真实用户数据、处理支付、或卖进受监管行业，那些原型阶段不适用的合规要求全都适用了，浮出来的每一项都当成必须修的，不是建议。

📋 技术债审计 + 排期
让 Claude Code 对 MVP 代码库做一次完整架构审计，产出一份按优先级排序的清单：结构脆弱点、测试覆盖率缺口、值得重构的候选项。把这份清单交给 Claude，让它把补债工作排进接下来的几个 sprint：哪些必须在下一次发布前修完，哪些可以和新功能开发并行处理，哪些是当前阶段可以接受的债务。
点开看：Launch 阶段还要防的一个陷阱，过早扩张

新市场和新融资机会看着都像增长机会，但它们也可能是产品市场契合度死掉的地方。你建起来的初始牵引是真的，但它也是特定于早期受众的。太早扩进一个和原市场差别很大的市场，会引入新的用户行为、合规要求、支付基建和基线预期，这些都是你产品当初没照着设计的。变量一多，你就失去了清晰解读自己数据的能力，还可能一边追逐新的、未经验证的受众，一边冷落了原来的用户基本盘。

七、Scale：护城河从数据飞轮和工作流锁定里长出来

进入 Scale 阶段，创始人的角色从建造者再度转向对外的公司高管，日常工作越来越多地关于公司本身。规模上看，是从数千用户走向数百万、从一个市场走向多个。目标从「贴着用户凭直觉调方向」，换成建立由成熟组织运营支撑的系统化增长。

手册说，对一个 AI 原生创业公司，这阶段该建的是靠积累的深度撑起的护城河，来自你嵌进产品的专业知识、产品和用户依赖的其他工具平台的整合深度、以及专有的系统数据和工作流。它的退出条件不再是单一里程碑，而是一个门槛事件：公司在创始人越来越少直接管日常运营的情况下，依然可持续。

可持续盈利 / IPO 就绪 / 被收购，这三种形态三选一，共同前提是：增长系统化且可审计、产品护城河经得起推敲、组织运营成熟可持续。到这一步，手册说恭喜，你的创业从一个赌注变成了一门生意。

7.1 护城河一：用户数据复利飞轮

用户和产品交互时会产生行为信号（他们接受哪些输出、拒绝哪些），这些信号喂进产品路线图。时间一长，你会摸清自己这批用户特有的模式、偏好和边界情况。这就是复利的意思：每一次改进让产品更有用，带来更多使用，产生更多反馈，又推动更多改进。

飞轮循环：更多使用 → 更多行为数据 → 更好的产品 ↻

手册强调，这份数据是时间锁定、情境特定、抄袭者无法复现的：你买不到成千上万名用户在你产品里打磨工作流留下的行为指纹。

📋 数据飞轮护城河叙事
把产品交互数据的情况喂给 Claude：你收集了什么数据、收集了多久、对用户如何随时间使用产品有什么了解。让它从中找出信号最强的三个行为模式，并为每一个设计一套能转化为系统性产品改进的反馈循环。然后让它帮你起草一页纸的护城河叙事：你的数据飞轮是怎么转起来的、转了多久，以及一个资源充足的竞争对手今天开始追赶，为什么两年内也追不上。

7.2 护城河二：工作流深度锁定

数据网络效应让产品更难复制，工作流锁定让产品更难离开。用户在日常运营里跑你产品越久，它嵌得越深：他们在上面搭了自动化、培训了人、接了数据源和其他工具。他们开发的提示、打磨的流程、标准化的输出，全都围着你产品的做法成形。到这一步，更换供应商就从一个产品决策，变成一整个运营项目。手册让你先用 Claude 按整合深度给客户分层，看产品在哪里粘住了、哪里还需要往深里走。

Scale 阶段最难的一关：真正放手

对一个从第一天就亲力亲为的创始人，把运营层交出去，既是结构问题也是心理问题。交太多太快，尤其是交给 AI 自动化系统，关键决策就会在缺少只有创始人能提供的关键背景下做出；抓太久，你又成了瓶颈。核心难点是找出只活在创始人脑子里、或散落在没写下来的工作流里的机构知识，把它编码成有文档、可审计、可移交的系统。手册的做法是用 Claude 画一张瓶颈地图，再推演你消失一周会怎样。

📋 「消失一周」瓶颈地图
让 Claude 帮你画出当前运营层的瓶颈地图：每一个要经过你手的工作流、决策和审批。然后让它推演如果你一周内完全不在，每一项会发生什么。会卡住的那些工作流，就是你现在还插手太深、拖慢进度的地方。

九、交互沙盘：把两条硬门槛变成可计算的判定

手册给的两条硬门槛——Sean Ellis 40% 与 CAC / LTV / 回本周期说得清——都可以落成实算。下面三个沙盘全部由公式实时求解，不含任何预设结论或编造数值；滑块默认值仅为演示起点，可自行调整。

9.1 Sean Ellis 测试判定器（含样本量校正）

手册只给了 40% 这条线，但没说样本量要多少。直接用点估计判断会掉进一个坑里：40 人里 18 人说「非常失望」，点估计 45% 已经过线，可它的 95% 置信下界只有 30.71%——离 40% 还差得很远。这里用 Wilson 评分区间补上这一层。

p̂ = d / n ；Wilson 95% 下界 = [ p̂ + z²/(2n) − z·√( p̂(1−p̂)/n + z²/(4n²) ) ] / ( 1 + z²/n )，z = 1.959964

在观测比例固定的情况下，置信下界随样本量上升的曲线；橙点为下界首次触及 40% 所需的最小样本量

点估计 p̂
45.00%
95% 置信下界
30.71%
下界过 40% 所需最小 n
350
证据不足：点估计 45.00% 已过线，但 95% 置信下界仅 30.71%，样本量不足以支撑「已过 40%」的结论。

口径说明：40% 阈值来自手册所引的 Sean Ellis 测试通行判据；Wilson 区间为本页附加的样本量校正，用于防止小样本下的假阳性。手册本身强调「要在多轮迭代里都稳住这个模式，才敢下定论」，与此处统计口径一致。滑块默认 n = 40 / d = 18 为演示起点假设值。

9.3 CAC / LTV / 回本周期测算器

Launch 阶段的硬门槛是「CAC、LTV、回本周期你都清楚、都能站得住」。这里给出最小可算模型：以月毛利和月流失率反解 LTV，再对 CAC 求比值与回本周期。

月毛利 m = ARPU × 毛利率 ；LTV = m / 月流失率 ；LTV/CAC = LTV ÷ CAC ；回本周期（月）= CAC ÷ m

96.00

2400.00
LTV / CAC
3.00

8.33
两项通行门槛均达标：LTV/CAC = 3.00 ≥ 3，回本周期 8.33 个月 ≤ 12 个月。

口径说明：手册只要求这三个数「说得清、站得住」，未给出具体阈值。此处 3 倍与 12 个月是业界通行的参考线，仅作对照，不构成手册结论。模型为恒定流失率的稳态近似，未包含扩展销售（NRR > 100%）与收入递延，实际测算应按自身账期口径修正。
