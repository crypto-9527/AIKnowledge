从换工具到改写工作方式：面向多 Agent 研发实践的 10 条原则

AI 编程没有让交付显著变快，往往不是模型不够强，而是人仍卡在每一步。Kiro 的 10 条原则把问题落到 意图、验证、代码库、权限与注意力管理五个可操作的工程面上——而不是换一个更聪明的补全工具。 本文对照 kiro.dev 一手源逐条核验原文口径，并把其中三条定性主张改写为可计算的模型。

一手源：kiro.dev/topics/frontier-engineering 主笔：Clare Liguori（AWS 资深首席工程师） 消化日期：2026-09-10 4 组可计算沙盘 零外部依赖单文件

核心结论（先读这一段）

  • 工具从来不是变量。Kiro 官方在 Amazon Stores 的 50 个常规团队试点中，90% 的团队用着同一批工具，中位数增益却分裂成「不足 3 倍」与「4.5 倍」两半——差异来自工作流，不是模型。
  • 人的职责从执行移到定义与验收。前沿团队手写代码占比降到 1–2%，但每人每周提交数显著上升；成本重心转移到「定义什么叫 Done」与「验证输出是否符合意图」。
  • 打破人肉轮询是吞吐跃迁的前提。每轮都等人介入，人就是流水线上的串行瓶颈；把验证闭环打包交给 Agent，Agent 才能连续运行数小时。
  • 并发不是越多越好，存在倒挂点。用通用可扩展性定律建模，当跨 Agent 语义冲突成本 κ > 0 时，超过峰值 N* 后总产出单调下降（实测默认参数下 N=30 反比 N=14.45 低 16.34%）。
  • 本文推翻了一个流传的直觉：自愈闭环并非永远优于人肉轮询——收敛轮次 n 低于临界值 n* = 3.00 时，闭环反而更慢。详见「稳健性复检」。

三、人肉路由器的吞吐天花板

不少开发者日常使用 AI 编程助手时，会陷入这样一种状态：

在 IDE 里敲下一行提示词，屏住呼吸等待几十秒，看到代码刷出来，顺手点击接受；本地一运行，控制台红了一片；于是把报错日志复制回对话框，再等几十秒……循环往复。

你确实换了更新的工具，打字与生成速度也变快了，但如果退后一步看整体交付周期：从需求提出、系统设计、代码编写、反复调试到上线发布，整体交付往往并没有带来预期的显著提速。开发者依然容易陷入疲态，核心原因在于许多人仍把自己放在 AI 与终端之间，充当实时的人肉路由器、异常传递员和点击确认器。

2025 年 9 月，Kiro 团队发布了由 Clare Liguori 主笔的工程专题《Frontier Engineering》（前沿工程学），系统梳理了 10 条面向多代理（Agent）研发实践的探索性原则。

作者的核心主张

当前的软件研发实践正在出现分化。一部分团队只是在既有流程中换了编码工具，而前沿探索者则在尝试重构工作方式——从亲自手写每一行代码，转向搭建让 Agent 自主闭环推进的工程基础设施，以追求显著乃至阶跃式的交付提速。

如果你已经熟悉 AI 辅助编程，却发现端到端交付依旧频繁受阻于人肉卡点，本文将结合 Kiro 的 10 条原则，解析这套工作流背后的运行机制、依赖条件与工程边界。

3.1 两种工作模式的定性对比

低效的人肉轮询

  • 人发 Prompt → 等待约 60 秒 → Agent 生成代码
  • 人手动测试和看日志 → 人复制报错回去 → 再次等待
  • 人的注意力与切换成本决定了吞吐上限
  • 单任务独占注意力，无法真正并行

长程自愈闭环

  • 人先定义目标、验证脚本与验收指标
  • Agent 连续运行数小时：编写实现与测试 → 执行本地验证
  • 未通过时捕获错误并修复，返回上一步
  • 全部通过后提交 Diff，等待人异步审查

当单个 Agent 能在数小时内自主闭环时，开发组织模式也随之升级：开发者可以并发调度多个面向独立任务的 Agent，或者将长任务置于后台运行，后续再统一进行异步审查（Async Review）。

3.2 沙盘 A：把「注意力」变成可计算的吞吐

上面这段对比是定性的。要判断它值不值得投入，需要把它写成一个可计算的式子。核心洞察是：在轮询模式下，人的注意力被任务的墙钟时间串行占用——Agent 生成的那段时间人也不能离开，因为每轮都要即时响应。

沙盘 A · 注意力吞吐模型（轮询 vs 自愈闭环）

模型定义：一个任务需 n 轮迭代收敛；每轮 Agent 生成耗时 ta；轮询模式下每轮需人工介入 th（等待 + 手动验证 + 反馈）； 闭环模式下人只在末尾异步审查一次，耗时 tr；专注时段长度 W；并行 Agent 数 K。 所有默认值均为基线假设，非官方实测数据，请在自身环境中替换后重算。

两个式子的结构差异正是原则二的数学表达：轮询模式下，ta 与 th 是串联相加的——Agent 思考的每一分钟，人的注意力同样被锁定；闭环模式下二者被解耦，人的投入只剩末尾一次 tr，Agent 的 n·ta 变成与人无关的墙钟背景。闭环吞吐取「人侧」与「墙钟侧」两个上界的较小值，即木桶效应。

3.3 稳健性复检：闭环并非永远更优

直觉上很容易写下「自愈闭环优于人肉轮询」这样的结论。但把上式化简后会发现，这个结论只在收敛轮次足够大时成立。

当人侧绑定时（即 W/tr ≤ K·W/(n·ta)），增益可化简为：

G = n·(ta+th) tr ⟹ n* = tr ta+th

当墙钟侧绑定时，n 被约掉，增益收敛到一个与迭代轮次无关的上确界：

Gsup = K·(ta+th) ta
该检验推翻了「闭环永远更优」的直觉假设

在默认基线（ta=4、th=2、tr=18、K=4、W=240）下，临界轮次 n* = 3.00。 当 n = 1（任务一次就过、无需迭代）时，G = 0.33×——闭环反而比轮询慢三倍：为一次不需要的「异步审查仪式」付出了 18 分钟，而轮询只需 6 分钟墙钟。 n = 3 时 G = 1.00×，两者打平；n = 12 时 G = 4.00×；n ≥ 18 后触达上确界 6.00× 不再增长。

这条复检的工程含义很实际：闭环的价值来自「迭代轮次足够多」这一前提。对于一次就能写对的小任务，强行套用「长程自愈 + 异步审查」的重流程是净损失。因此任务分诊是必要的——按预期迭代轮次把任务分流到「直接改」与「打包给 Agent 自愈」两条通道，而不是把所有任务都塞进同一条流水线。

但 Kiro 在专题中特别强调了注意力管理（Attention Management）：这绝不意味着盲目追求并发 Agent 的数量。核心在于只让那些拥有清晰目标与可靠验证闭环的任务持续运行，并在整个过程中严格维持质量标准；同时开发者需要建立清晰的注意力预算与生活边界，克制在晚餐时或深夜反复查岗看进度的冲动。官方原文把这项能力描述为长期要持续发展的技能：

Over the long term, the skill you keep developing is managing your own attention. As agents take on more of the execution, that means carrying the cognitive load of context switching between several agents at once, deliberately holding a quality bar while everything moves faster, and mustering the self-restraint to stop checking on agents at dinner and late at night.

四、原则一：你是架构师，不是打字员

01

You are the architect, not the typist

你是架构师，不是打字员

在前沿工程实践中，Kiro 观察到走在最前面的开发者手写的生产代码占比已经降至 1–2%（一手源口径为 1–2%，分析稿写作「1% 以下」已在上文校正）。需要强调的是，这是作者在特定团队中观察到的现象，而非要求所有团队生搬硬套的目标 KPI；官方同句还并列了另一半事实——「每人每周提交数显著高于从前」。这并不意味着开发者的职责变轻了，而是工程重心发生了显著转移。

以往大部分时间消耗在敲击键盘、寻找语法细节与排查低级 API 调用上。但在由 Agent 承接具体编码的模式下，软件研发的核心成本转变为两件事：第一，清晰定义什么叫「Done」（需求边界、约束、验收准则）；第二，验证输出物是否真正符合系统意图。

很多开发者使用 Agent 效果不佳，第一步往往踩在「意图模糊」的陷阱上（以下对比为说明意图表达机制而展开的示意，并非 Kiro 原文用例）：

  • 低效意图：「给这个 API 加上用户鉴权。」
    面对这句指令，Agent 往往自行脑补技术选型、随意决定拦截范围与默认错误响应格式。一旦其假设与业务实际冲突，开发者就需要耗费额外精力推倒重来。
  • 合格意图：把范围、角色矩阵、错误契约与验收测试一并写死。
为以下端点增加基于角色的访问控制（RBAC）：
  /admin/*        仅限 Admin 角色
  /api/v1/user/*  允许 User 与 Admin 角色访问

当 Token 过期时，按照规范返回 401 状态码及 TOKEN_EXPIRED 错误体。
提供针对「未授权访问」「令牌过期」「伪造签名」的测试用例，并确保全部通过。

在这里，具体代码执行的边际成本大幅下降，而定义系统方向（Direction）的权重被显著放大。

系统架构、API 契约、外部依赖选择以及核心权衡（Trade-offs）一旦偏离，推倒修正的成本依然不低。因此，开发者应当把精力聚焦在系统的关键骨架上。在设计阶段，也可以让 Agent 成为方案推演的助手：例如让它调研多种可行的技术路线并编写可对比的原型，通过原型运行结果与实际证据来辅助团队做决策。

方向确定后，工作应当转入规格驱动开发（spec-driven development）：先与 Agent 共同写清规格与需求，以减少生成代码之前的歧义；在推进过程中持续判断架构能否承受真实负载、既有权衡是否需要重审，以及产品是否已经达到可以交给用户的状态。

五、原则二：最大化 Agent 时间，最小化你的介入

02

Maximize agent time, minimize your involvement

最大化 Agent 时间，最小化你的介入

要实现开发吞吐量的跃迁，必须打破「人在回路中（Human-in-the-loop）」的紧耦合。

如果你坐在屏幕前，每次发完指令就盯着光标闪烁，等待 60 秒后手动帮它测、手动喂报错，那么你就是整个流水线上最大的并发瓶颈。

前沿开发者的做法是给 Agent 分配具备明确验证标准、生命周期更长的任务。典型任务指令形如（此为闭环模式的示意，用于展现将实现与校验打包交付；其中「覆盖率 90%」为分析稿示例值，官方一手源未见该硬性 KPI）：

实现功能、编写测试、运行测试并确保全部通过，
且新代码测试覆盖率达到 90%。

在这个过程中，Agent 初次写出的代码存在缺陷十分常见。关键在于：不要替它去排查语法错和环境错，让它在受控环境中自行运行、捕获错误输出并自我修正，直到收敛出符合预期的结果。

值得注意的是，Kiro 官方给出的量级比「30 分钟」更激进：前沿团队「让 Agent 连续运行数小时，常常是通宵，第二天早上再审查生成的代码」。一位首席工程师在「仅有几小时连续时间」的情况下交付了完整改动，因为 Agent 在他往返于代码评审、运维支持和会议之间时持续工作。

与沙盘 A 的对应关系

本原则等价于把模型中的 th（每轮人工介入）从每轮必付，压缩为只在末尾付一次 tr。但请记住 §3.3 的复检结论：当任务收敛轮次 n < n* 时，这个交换是负收益。分诊优先于流程统一。

六、原则三：为 Agent 改造代码库

03

Build your codebase for agents

为 Agent 改造代码库

人类团队成员入职，往往只需要通读一次文档、配好一次本地环境，相关的业务背景和工程默契就会长期储存在大脑中。

但 Agent 不一样：每一个全新的会话（Session），都像一位不了解当前业务的新协作者在「第一天入职」。

如果代码库全靠口口相传的默契运行，Agent 就会反复在缺乏上下文的地方受阻。要让 Agent 高效工作，仓库必须建立起面向代理的基础设施：

6.1 仓库级基础支撑与工程卫生

  • 完备的 README 与架构文档：提供清晰的系统全貌、技术栈选型与目录指引，让新会话能迅速建立系统级认知。
  • 描述预期行为的测试套件：编写能清晰反映业务预期行为的测试，为 Agent 提供自验证的直接依据。
  • 清晰的模块边界与强类型：通过严谨的模块解耦与强类型约束，减少隐式依赖；含混的类型往往会显著增加 Agent 推理歧义的概率。官方记录的极端做法是：有团队把无类型的 Python/JavaScript 换成 TypeScript 或 Rust，为的是让编译器给 Agent 可执行的反馈。
  • 快速构建与高信息量报错：确保本地构建与测试反馈足够快，且编译器和测试报错包含具体、可定位的线索。
  • 遗留大型仓库的应对策略：对于历史包袱重的大型代码库，不要指望一蹴而就，而应采取逐模块改造的方式，并在任务中收窄 Agent 的上下文与操作范围（Scope）。

6.2 显性化的工程规则与工具集成

  • 引导文件（Steering Files）：将团队的代码规范、目录约定与常用规则提炼成规则文件，提供持续适用的工程约定与编码标准。
  • 按需技能（Skills / Procedures）：将复杂流程（如数据库迁移、API 发布）封装为模块化步骤，仅在特定任务触发时动态载入，避免无关信息挤占上下文。
  • 环境脚本与 CLI/MCP 工具：提供可脚本化拉起的本地环境，并通过 CLI 或 MCP（Model Context Protocol）工具让 Agent 能自主查询日志、拉取 Schema 或调用辅助服务。

6.3 持久化关键决策与上下文约束

在任务推进过程中，要求 Agent 记录设计决策（例如使用 ADR）并在核心链路补充关键上下文与约束注释。这并非要求把冗长的模型思考过程原样堆进代码库，而是将必要的设计决策、背景假设与限制条件持久化，为后续会话及其他协作者提供连续的工程记忆。

官方给出的一个反直觉做法是：某基础设施团队把全部代码与文档放进单一 monorepo，并且保留 Agent 生成的内联注释，将其当作持久化记忆来对待。跳过这一步的团队，往往困惑于「为什么我的 Agent 总在犯同样的错误」。

七、原则四：给 Agent 一条快速反馈闭环

04

Give agents a fast feedback loop

给 Agent 一条快速反馈闭环

Agent 能够自主定位并修复问题的基础，在于拥有一套敏捷、本地化、自动化的反馈工具链。

如果 Agent 每次调整界面，都必须依赖人类打开浏览器人工核对；或者修改接口必须部署到远端测试服才能验证，自愈反馈就会被打断，人类也会重新被卷入繁琐的实时确认中。

在前沿实践中，快速反馈通常依赖以下本地能力：

  1. 静态代码检查器（Linter）与单元测试（Unit Tests）：快速发现语法、代码风格与基础逻辑偏差。
  2. 可渲染并视觉验证界面的浏览器（Browser）：供 Agent 自主加载前端页面，进行 DOM 结构与界面呈现的视觉比对校验。
  3. 本地轻量级依赖与模拟（Local Mocks）：通过本地 Mock 或容器化手段，支持脱离外部公共环境在本机拉起全栈端到端测试（E2E）。

7.1 属性测试：为什么它比「Agent 自己写的单测」更值钱

而在各类测试手段中，基于属性的测试（Property-based Testing）是一种尤其有价值的补充，尽管它并非必须引入的门槛，也不能直接替代基础的单元测试。

传统的示例型单元测试通常针对特定输入断言固定输出。当 Agent 自行编写测试覆盖自身代码时，容易陷入与实现逻辑相同的思维惯性。而基于属性的测试则要求声明系统在广泛输入下必须满足的不变量（Invariants）（以下示例为说明机制而展开的示意，非 Kiro 原文用例）：

  • 序列化不变量：「对任意满足约束的对象，serialize 后再 deserialize，与原对象在规定语义上等价。」
  • 资金划转不变量：「在不考虑手续费、汇率换算与舍入误差的前提下，两账户余额变化量之和恒等于 0。」

借助属性测试在随机生成的广泛输入样本中检验边界，Agent 能更容易暴露隐藏在常规测试之外的边缘异常，进而针对失败用例做进一步的代码调整。Kiro 官方把这条上升为产品的第三根支柱「Correctness」：从需求中直接抽取可测试属性，生成数百个随机用例来探测人类不会手写覆盖的边界。

八、原则五：执行很便宜，方向才是一切

05

Execution is cheap. Direction is everything.

执行很便宜，方向才是一切

具体代码执行的边际成本大幅下降，而定义系统方向（Direction）的权重被显著放大。系统架构、API 契约、外部依赖选择以及核心权衡（Trade-offs）一旦偏离，推倒修正的成本依然不低。因此，开发者应当把精力聚焦在系统的关键骨架上。

在设计阶段，也可以让 Agent 成为方案推演的助手：例如让它调研多种可行的技术路线并编写可对比的原型，通过原型运行结果与实际证据来辅助团队做决策。

为什么「先写文档再写代码」更快

官方给出的理由是：当初始意图错了，与模型在一篇文档上迭代，要比在散落于整个代码库的实现上迭代快得多。并且 Kiro 可以生成规格草稿，由人来细化——把「从空白到第一版」的成本也压掉一部分，人只承担判断与修订。

方向确定后，工作应当转入规格驱动开发：先与 Agent 共同写清规格与需求，以减少生成代码之前的歧义；在推进过程中持续判断架构能否承受真实负载、既有权衡是否需要重审，以及产品是否已经达到可以交给用户的状态。

九、原则六：把代码当作可丢弃品

06

Treat code as disposable

代码可重写，边界测试是契约

在传统研发流程中，推倒重写往往伴随着高昂的时间成本与心理阻力。

但随着代码生成与重写成本的实质性下降，当既有实现或架构方向被证实并不理想时，果断舍弃错误方向、重新生成实现变得更加可行。这并不意味着所有工程成本归零，而是团队不再需要为了挽救别扭的局部实现而承担长期的技术债。

这里需要区分两层：

  • 可替换层（Disposable Layer）：具体的内部实现逻辑与局部私有函数。方向不佳时，可以让 Agent 重新起草。
  • 契约保护层（Contract Layer）：端到端集成测试、基于属性的测试、负载与性能基线测试。它们描述外部行为与系统边界，是重写过程中应当保留的验收标准。

在这类重写中，应当被重点保留并作为重构基石的，是边界测试（Boundary Tests）：

  • 覆盖外部预期行为的端到端测试（E2E Tests）；
  • 检验核心规则与不变量的属性测试（Property-based Tests）；
  • 验证高并发与极限表现的负载测试（Load Tests）。

这三类外围测试构成了系统对外承诺的重写契约（Contract）。内部私有函数或过度耦合的单元测试可以随着旧代码一同更替；只要高层的边界契约清晰有效，Agent 就能在明确的约束范围内探索不同的实现路线，逐步收敛出符合系统预期的代码。架构设计与 API 取舍仍是昂贵、需要审慎判断的方向性决策，但当事实证明原方向有误时，它们也需要被重新审视。

十、原则七：AI 产出也要守住人类标准

07

Hold AI output to human standards

人类标准的坚守与审查层级分工

不论代码是由人类手敲还是由 Agent 生成，最终合入主干并投入运行，工程责任始终由人类工程师承担。

随着生成代码量的增加，团队不能因追求吞吐而稀释质量标准。但在高频输出面前，完全依靠人类逐行做最初步的机械审查往往难以维系。Kiro 提出的审查演进路径包含明确的前提与分工：

  1. 初期人工逐行校准：在团队引入 Agent 的初期阶段，工程师需要坚持逐行阅读审查生成代码，以准确摸清所使用模型的长处、编码偏好与常见失败模式，建立基础的校准判断。
  2. AI Reviewer 承担前序检查：随着对模型特性的掌握，可以在本地提 PR 前和 CI 流程中引入专门的 AI Reviewer，负责自动化检查代码正确性、安全性、可维护性、测试质量与典型 Bug 模式，逐步承担起前几轮反馈的工作。
  3. 人类聚焦核心架构与系统影响：人类工程师将注意力聚焦在更关键的高阶判断上——整体架构与模块职责划分是否合理？变动对上下游依赖会产生怎样的连锁影响？安全边界与业务权限是否严密？改动是否真正契合系统长期意图？
  4. 部署后验证与回归监控：Agent 的闭环并不仅停留在提交 PR。还可将其延伸到部署阶段——让 Agent 参与部署监测、验证生产环境运行行为，并在出现指标回归或异常时协助启动排查与修复流程。

官方记录的一个副作用值得注意：当自动化护栏、组件测试、性能检查与格式化器把低级问题提前拦掉之后，代码评审的焦点自然从「代码风格与命名规范」上移到「接口定义与架构决策」——这正是人类审查者应该待的位置。

十一、原则八：信任边界，而不是信任 Agent

08

Trust the boundaries, not the agent

防护栏工程：最小权限边界与分层防护

给予 Agent 充分的自主运行空间，并不意味着可以不做安全控制。

许多团队在引入 Agent 时容易出现两种偏差：一种是过度设防，几乎对所有只读或本地命令都设置弹窗审批，很快导致人类产生严重的「审批疲劳」并失去辨识力；另一种则是防护缺位，随意赋予全盘读写或敏感凭证，带来不可逆的操作风险。

Kiro 在安全原则中给出的核心策略是：按当前任务的最小必要范围限制文件、工具、网络与凭证访问，在此前提下让 Agent 无人盯守运行（run unattended）。

实施时通常遵循「从窄开始、逐步放宽」的路径，并建立分层防护：

防护面需避免防护栏做法
权限与工具边界默认赋予全系统或全工具读写权限从较窄的必要工具集开始，根据任务逐步放宽，仅在确有需要时挂载对应能力
操作审批设卡无论操作轻重频繁弹窗，或完全不设审批允许只读操作和受控的本地测试自主执行，仅对真正具有不可逆影响的高危动作设卡审批，例如破坏性数据变更或外部生产发布
凭证与生产授权将高权限凭证混入全局环境变量生产权限与凭证默认严格不授予；日常使用模拟数据或有限沙箱凭证，只有在经过明确、审慎的授权时才可开放特定权限
安全与代码防护仅靠合并前的人工肉眼扫视结合自动化静态分析（SAST）、自动化推理或形式化分析类工具、敏感信息扫描等能力，构建分层的安全防护网

这种边界设计的目标，是在保障系统与数据安全的前提下，让 Agent 在受控范围内顺畅推进，最大程度降低因频繁打断而带来的流程停滞。

十二、原则九：Agent 不只用来写代码

09

Use agents for everything, not just code

全流程协同：Agent 不只是写代码的工具

在多代理实践中，另一个常见的误区是将 Agent 狭隘地等同于「写代码的打字机」。Kiro 的第 9 条原则明确指出：Agent 的能力应当贯穿软件研发与运维的全生命周期。

除了编写和重构业务代码，Agent 还可以广泛应用于：

  • 方案与设计文档：起草架构方案草案、接口设计说明与技术调研报告。
  • 运营与故障调查：在排障与事件响应中聚合错误日志、定位调用链路异常。
  • 项目与运维协同：生成状态更新、Sprint 总结报告、On-call 轮值交接与日常工程文档维护。

这类任务遵循统一的协作流程：提供上下文（Context）→ 明确预期结果（Outcome）→ 由 Agent 起草初稿 → 由人工审阅并修订后再对外分享。

更进一步，在规划、开发、测试、部署到日常运维的不同环节中，负责各类任务的 Agent 应当尽可能共享工程上下文、Steering 引导规则与底层工具（CLI/MCP），从而在整个研发生命周期内形成连贯的协作合力。官方在产品侧的实现是「One agent. Every surface.」——同一个 Agent、同一份记忆、同一套推理，横跨 IDE、CLI 与 Web。

十三、原则十：持续调优你的 Agent 环境

10

Continuously tune your agent setup

建立持续调优的飞轮系统

前沿工程学绝非一劳永逸的配置，而是一种演进式的工程实践。

在日常开发中，每一次 Agent 遇到阻碍、执行跑偏或者产生不必要的打断时，不应简单归咎于模型能力，也不应盲目把所有问题都一律归为环境缺陷。前沿实践的做法是：对反复出现的错误或打断进行深入的根因分析，判断其症结究竟在于业务约束不清、工具缺失还是权限过于严格，进而将其沉淀为对 Agent Setup 的具体改进：

  • 经常混淆两个相似工具的用法？→ 在 Steering 规则文件中补上明确的使用场景与正反例说明。
  • 复杂的操作流程反复失误？→ 将该流程提炼固化为一个独立的 Skill 脚本。
  • 缺乏必要的环境上下文数据？→ 编写轻量级 CLI 工具或通过 MCP Server 提供信息获取通道。
  • 在安全的本地操作上频繁打断等待人工放行？→ 根据根因审慎调整执行环境的权限配置。

这条飞轮可以压缩为四步：

  1. Agent 执行长程任务；
  2. 记录反复报错、不必要打断与其他阻碍；
  3. 由人做根因分析，区分业务约束、流程、工具与权限问题；
  4. 更新相应的 Steering、Skill、CLI/MCP 或权限边界，再让下一轮任务验证改进是否有效。
最容易漏掉的半步：模型变强后要「删规则」

官方明确要求：新模型发布后，应重新评估那些为了弥补旧模型弱点而设置的 workaround；只有经验证不再必要的规则或提示词才清理。Clare Liguori 举的具体例子是——去年中旬的 Sonnet 3.7 需要大量「不要做 X」的负面规则，而到 Opus 4.5 时这些规则已成为需要剪掉的负担。只增不减的 Steering 文件会从资产退化为负债，持续挤占上下文窗口。

随着这种根因分析与调优的积累，工程环境对 Agent 的支撑会愈发稳健。更重要的是：底层基础模型总是在持续演进。而围绕代码库沉淀下来的清晰契约、自动化测试套件、受控权限边界与 MCP 工具链，能够继续复用并帮助新模型更稳定地发挥作用。

十四、并发的倒挂点：多 Agent 不是越多越好

原则二鼓励并行调度多个 Agent，原则十强调注意力管理——这两条合起来会自然引出一个问题：并行度究竟该取多少？「越多越好」是线性外推的直觉，而并发系统从来不是线性的。

用通用可扩展性定律（Universal Scalability Law, USL）建模。令 N 为并发 Agent 数，σ 为串行/争用系数（共享文件锁、构建缓存、CI 排队、本机资源争抢），κ 为跨 Agent 一致性成本（语义写冲突、合并冲突、返工）：

C(N) = N 1+σ(N−1) +κN(N−1) N* = 1−σ κ

κ 项的存在使 C(N) 在越过 N* 后单调下降——继续加 Agent 会让总产出变负收益。默认基线 σ=0.06、κ=0.0045 下，N* = 14.45，C(N*) = 5.39；而 N=30 时 C 只有 4.51，比峰值低 16.34%。

14.1 沙盘 B：并发曲线与峰值

沙盘 B · USL 并发曲线（σ / κ 可调）

敏感性结论：杠杆在 κ，不在 σ

N* = √((1−σ)/κ) 对 κ 是平方根倒数关系，对 σ 只是被减数关系。把 σ 从 0.02 抬到 0.30（15 倍）只让 N* 从 14.76 降到 12.47（−15.5%）；而 κ 从 0.0045 降到 0.0020（−55%）就让 N* 从 14.45 涨到 21.68（+50%）。

工程含义：与其优化构建缓存、抢 CI 队列（降 σ），不如优先做任务间的写隔离——让并发 Agent 改不同的模块、不同的文件、不同的分支（降 κ）。这与原则三「清晰的模块边界」是同一件事的两个说法。

十五、三因子乘法：增益从哪里来

Amazon Prime Video 的 10 天冲刺给出了一个可拆解的官方口径：增益来自三个因子相乘，而不是单一杠杆。

The gain came from three factors multiplying together. Acceleration of low-judgment work (1.5x) × uninterrupted focus on high-judgment work (1.5x) × instant access to agent-captured domain expertise (1.5x).

Gtotal = glow × gfocus × gexpertise = 1.5×1.5×1.5 = 3.375

17.1 建议的起步顺序

  1. 夯实代码库基础：补齐核心模块的 README 与架构文档，明确模块解耦与强类型定义，确保本地构建与测试反馈快速可靠；
  2. 跑通首个验证闭环：选择边界清晰的独立模块，编写明确预期行为的测试脚本，尝试交付带有自愈验证的长程任务；
  3. 逐步沉淀规则与工具：在初期保持人工逐行审查以校准模型表现，对反复出现的阻碍进行根因分析，沉淀团队的 Steering 文件、操作 Skill 与必要 CLI/MCP 接口；
  4. 拓展全流程协同并管理注意力：将方案起草、排障调查与文档更新逐步纳入协同，同时明确注意力预算，保持对系统质量与个人工作节奏的合理把控。

十八、边界、反例与适用条件

需要客观指出的是：这套面向 Agent 的工程范式目前仍然处于早期探索者（early-adopter）实践阶段。Kiro 官方自己的措辞也相当克制：

  • 「还没有人摸清如何最有效地审查 Agent 产出，也没有人摸清如何为 Agent（而非为人）设计工具与测试基础设施。」
  • 「这种工作方式仍然依赖直觉：知道该委派什么、如何界定范围、何时介入。而直觉来自实践。」
  • 「这不是一个开关，是一项工程投资。你会花上数周去建立直觉、写 Steering 文件、重构代码库、学习为 Agent 拆解任务。如果期待不改工作流就立刻见效，你会失望。头几周更慢，之后几周会显著变快。」

这套方法的失效场景

  • 一次就过的微小改动：沙盘 A 证明 n < 3 时闭环是负收益
  • 无本地反馈回路：反馈延迟 30 分钟以上时，迭代预算跌破收敛所需轮次
  • 跨 Agent 写同一批文件：κ 升高使并发峰值塌陷，加 Agent 反而减产
  • 期待立竿见影：头几周必然变慢，中途放弃则成本沉没
  • 把 1–2% 当 KPI：它是观察值，且伴随着提交数上升，单独追求无意义

成立的前提条件

  • 任务有清晰可判定的验收标准（可自动验证）
  • 存在本地秒级反馈（编译 + 测试 + 格式化）
  • 模块边界清晰，并发 Agent 写隔离
  • 团队愿意先慢后快，接受数周投资期
  • 人类保留架构与方向的判断权与最终责任
被本文数据推翻的三个流行说法

1. 「自愈闭环总是优于人肉轮询」——不成立。n < n* = 3.00 时 G < 1，n = 1 时仅 0.33×。任务分诊先于流程统一。
2. 「Agent 越多越好」——不成立。USL 下 N > N* 后总产出单调下降，默认基线 N = 30 比 N = 14.45 低 16.34%。
3. 「瓶颈在构建缓存与 CI 排队」——优先级错位。敏感性显示 N* 对 κ（写冲突）远比对 σ（争用）敏感：κ 减半让峰值涨 50%，而 σ 抬升 15 倍只让峰值降 15.5%。

从简单的对话补全转向构建由 Agent 驱动的工程基础设施，并非一键切换的过程。Kiro 提醒，前几周的速度会更慢，并需要投入数周完善环境——理清模块边界、补齐测试与规则文件、搭建可靠的自动化验证环境。而这套投入的回报结构是复利式的：官方原文的落点是——「每一次 Agent 能力的跃升，都叠在你已经学到的东西之上」。
