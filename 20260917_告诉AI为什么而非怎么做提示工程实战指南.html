告诉 AI 为什么 而不是怎么做

前沿模型出错，多半是猜错了你的目标和取舍。把目标、约束和可以让步的地方讲清楚，模型才能帮你找到更好的做法；文中附一段真实提示词和深度拆解。

原作者 Sean Goedecke (软件工程师)
核心模型案例 GPT-6-Astra / Gradient 4-bit
项目实战载体 Deckard (Chrome 扩展)
发布与收录基准 2026-09-17 • 架构研讨
核心要旨 • Executive Summary
  • 早期 Agent vs 现阶段前沿模型：早期 Agent 要把做法一步步交代清楚；如今前沿模型出错，多半是对你的目标或优先级做了错误假设，比如 GPT-6-Astra 以为代码只给自己看时，会写出人很难读的压缩代码。
  • 背景与优先级占比过半：Deckard 项目的起始提示词约一半在讲背景和优先级，并邀请模型提出更好的办法；最终方案用上了 native messaging 和 Gradient 模型，Sean 认为只写技术规格会错过这两点。
  • 明确相对优先级与规避 XY 问题：交代技术取向时要排出相对优先级，明说哪些可以牺牲；只给模型具体规格、不给目标，等于向专家提问时犯了 XY 问题。

软件工程师 Sean Goedecke 在博客文章里讲了一个观点：给前沿 AI Agent 提需求时，别只当指挥官抠具体步骤，要把你的最终目标、背景原因和优先级取舍交代清楚。

01 核心转变：AI 不再是“傻小子”，它缺的是全局背景

过去与顶尖模型的本质认知分水岭

人机协作范式正在发生根本性转移。很多工程师依然停留在“微观管理（Micromanagement）”式的提示词习惯中，而忽略了顶尖推理模型的底层决策逻辑：

AI 演进阶段 典型行为特征 失控/出错根因与应对方案
过去的 AI
热情的笨蛋		 必须把要做的事交代得极其具体，例如：「类 B 上有方法 A，请给类 C 到 F 各加一个等价的方法」。一旦指令模糊就会彻底做错。 能力不足导致的理解断层：模型缺乏自主泛化能力，必须依赖人类给出极其微观的执行树，人类充当全量脑力外包指令生成器。
现在的顶尖模型
前沿推理伙伴		 具备强大的系统架构推理、跨语言方案迁移和全局代码生成能力。跑偏通常不是没看懂步骤，而是对你的意图做了错误假设。 全局背景与优先级缺失：模型在空白处自行填补了与人类隐式期望相反的权衡。解决方式是补充“为什么”、“为谁而做”以及“可以让步的项”。

深度剖析：GPT-6-Astra 为什么会写出压缩代码（Minified Code）？

现实中前沿模型最典型的误判案例发生在代码生成领域：比如 GPT-6-Astra 以为代码是写给自己看的，就会写出省掉空格和格式的压缩代码（minified code）。

Armin Ronacher（Flask 作者）的深度推测与实测

Armin Ronacher 推测，这是因为模型调用工具时为了省 token，练出了越短越好的写法，结果漏进了要提交的代码里：

  • 测算数据：这样编写的单元测试比格式化后省约 10% 的 token。
  • 发生场景偏好：越像没人在看的环节（比如子 Agent 的工作、测试代码），越容易冒出这种压缩写法（不过 Armin 也说不确定模型是不是真以为没人看）。

反过来，只要告诉它代码有人要读，它就能写出人读得懂的代码：

  • Sean 用它写 Go，得到了几千行「可以接受」的代码（他只在 Go 上试过）。
  • 在人类写的代码库里，连这句都不用说，它会自己跟随周围代码的风格。

02 关键操作法则：告诉它“为什么”与“权衡取舍”

法则一：明确宏观目标，而非过早固化实现路径

先说清你最终想解决什么，而不是直接丢一份具体的技术规格。做法写死了，模型就只能照着做，没法按你的目标帮你找更合适的方案。

Sean 启动 Deckard 项目时，提示词里约一半篇幅在讲背景：

  • 想做一个自动藏起网页 AI 内容的本地程序或浏览器扩展；
  • 短期要找一个不让 MacBook 发烫、不耗光电池的检测模型；
  • 而且这是给自己用的。

法则二：留出发挥空间，避免错失最优解

自己的技术设想可以写，但要写成讨论的起点，而不是命令。

Sean 在提示词里把 EditLens 和 RoBERTa 只写成「我的猜测」，结尾还加了一句：如果你看到实现我目标的更好办法，告诉我，我们商量。

技术决策收益：如果不留探索空间会发生什么？

Sean 的判断是：当初如果写成一份明确的技术规格，就会错过后来用上的 native messaging 和 Gradient 模型。

这个项目是 Sean 和 Astra 一起做的：他负责拍板一批大方向，还能选自己不熟但更合适的语言（推理用 C++ 而不是 Python）；模型则提醒了他自己想不到的做法，比如用 native messaging 代替本地 HTTP。

法则三：明确“相对优先级”，明说哪些可以牺牲

工作里提技术需求，别把“少出 bug”、“可观测性”、“优雅融入现有代码”、“高性能”全列上，说它们都重要。

Sean 的做法是专门写一段话，讲清这几项谁先谁后，并明说哪几项他没那么在乎、可以拿去换别的。这样几个目标冲突时，模型才知道该让哪一项。

示意写法（本站推荐模板）
“这次最重要的是别引入 bug，其次是自然融入现有代码；可观测性保持现有水平即可；性能不是重点，为了前两项可以让出一些性能。”

法则四：警惕“XY 问题”

XY 问题是指：你真正想解决 X，却自以为答案是 Y，于是只问 Y。

  • 经典例子：有人问「怎么输出文件名的最后三个字符」，追问才知道他要的是扩展名，而扩展名不一定是三个字母（比如 .jpeg）。
  • 向专家看病的隐喻：现在的模型已经聪明到能对你的整体目标给出有用的意见；只给它具体技术规格、不给背景，就像去看病只问某种药怎么吃，医生也就没法帮你找更合适的治法。

03 完整例子：Sean 给 Deckard 写的提示词

Deckard 是 Sean 和 Astra 一起做的 Chrome 扩展，调用 Mac 上本地运行的小模型，自动标出网页里疑似 AI 写的文字。

  • Pangram：目前几乎唯一成熟的商业 AI 文本检测服务，EditLens 是它的模型；
  • Runpod：Sean 通过 MCP 接给模型用的远程算力，用来跑本地太热、太久、太慢的实验。

中英文提示词逐段对齐

English Original Prompt Sean Goedecke

Hello. You should have Runpod access via MCP (if not, tell me and I’ll fix it).

I have the long-term goal of building a local program or browser extension to automatically scan pages I load for AI content and hide it. I have the short-term goal of figuring out the best AI detection model I can run on my macbook without killing my battery or making it hot, and (relatedly) figuring out how to run the model most efficiently.

My guess is that Pangram’s EditLens 3B or the smaller Roberta model might be a good place to start, though they might require quantizing and will definitely require some work to make them run as efficiently as possible on my macbook.

I would like you to use my Runpod account to start answering these questions. Eventually we’ll move to doing things on this macbook pro, but my hope is that Runpod can help with some experiments that are too hot/long/slow to run locally.

You are a smart model; if you can see a better way to achieve my goals, please let me know and we’ll talk about it. Good luck.

中文对照翻译 对齐解析

你好。你应该可以通过 MCP 访问 Runpod（如果不行，告诉我，我去修）。

我的长期目标是开发一个本地程序或浏览器扩展，自动扫描我加载的网页中的 AI 生成内容并将其隐藏。 我的短期目标是找出最适合在我这台 MacBook 上运行的 AI 检测模型，要求不能让笔记本发烫或迅速耗尽电池，并且（与此相关地）搞清楚如何以最高效的方式运行该模型。

我的猜测是，Pangram 的 EditLens 3B 或更小一些的 RoBERTa 模型可能是一个不错的切入点，不过它们可能需要量化，而且肯定需要做一些工作才能尽可能高效在我的 MacBook 上跑起来。

我希望你使用我的 Runpod 账户开始探寻这些问题的答案。我们最终会把工作迁移到这台 MacBook Pro 上完成，但我希望 Runpod 能协助做一些在本地跑起来太热、太耗时或太慢的实验。

你是一个聪明的模型；如果你看到了实现我目标的更好途径，请告诉我，我们一起讨论。祝好运。

04 Deckard 最终给出的工程答案

这段提示词本质上问了两件事：选哪个模型，以及怎么在 MacBook 上跑得不发热、不耗电。最终 Deckard 的落地答案令人惊喜：

1. 怎么跑：Native Messaging 彻底取代本地 HTTP Daemon

模型提醒使用 Native Messaging，让 Chrome 扩展直接调用电脑上的模型程序，不用另开一个本地网页服务：

  • 按需启动与闲置关闭：用的时候才启动，5 分钟不用就自动关掉；
  • 极低内存足迹：运行时占 400MB–1.2GB 内存，大约相当于多开五六个浏览器标签页；
  • 硬件友好：Sean 没发现 MacBook Pro 发热或掉电（但也说换台机器可能不一样）。

2. 选哪个模型：放弃 EditLens，采纳 Gradient MLX 4-bit

没用最初猜的 EditLens，选了 Gradient 的 MLX 4-bit 版（压缩过、能在苹果电脑上高效跑的版本）：

对比维度 Gradient MLX 4-bit (Deckard 最终解) Pangram 商业云服务 (行业黄金标杆) 初始猜测 EditLens 3B (原始未量化)
AI 文字抓出率 ~52% (抓出过半) 99.66% (极致精准) 预估 ~68% (未剪裁)
误判率 (人判为AI) ~2.7% 0.004% (极低) 预估 ~1.5%
运行环境与网络 100% 本地运行，完全脱机 依赖云端 API 连网 本地运行困难，显存占用大
发热与功耗 极低（5分钟闲置自动关闭进程） 本机零发热（计算在云端） 高发热，风扇狂转并迅速耗电
个人使用实用性 足够：一篇文章标出几处就足以起疑 过剩：个人无需商业法庭级证据 不可用：严重拖垮日常续航

Sean 的实用主义权衡：一篇文章不用每句都抓到，标出几处就足够让人起疑；只是误判约 2%，单个标记不能当证据。这正是明确了“这是给自己用”才能达成的妥协方案！

06 附录：告诉 AI 为什么的标准化结构模版

在向前沿 Agent（如 GPT-6-Astra、Claude 3.7 Sonnet / Opus 等）发起复杂工程任务时，可直接参考以下三段式结构化模版：

Recommended Prompt Blueprint • 推荐提问模版
[1. 宏观意图与终极受众 (The Why & Audience)] “我的长期目标是解决 [X 业务痛点]，最终产物是给 [目标受众，如自己本地自用 / 生产团队多人维护] 运行的。” [2. 物理与工程硬约束 (Hard Constraints)] “短期内最核心的物理与工程限制是：[例如：不能让本地设备发热 / 内存峰值不能超过 1.5GB / 严格离线不可访问外网]。” [3. 技术设想与可证伪假设 (Hypothesis, Not Order)] “我目前的初步猜测是尝试使用 [技术方案 A 或 B]，但这只是起点。你有更适合此目标的替代方案吗？” [4. 相对优先级与牺牲项 (Trade-offs & Sacrifices)] “在本次实现中： - 优先级最高（绝不能牺牲）：[例如：零缺陷与清晰可读性] - 优先级次之：[例如：自然融入现有接口风格] - 可以让步牺牲的项：[例如：执行速度可以略慢，可以多占一点编译时间换取简单性]” [5. 反向赋权与协作邀请 (Collaborative Mandate)] “如果你看到实现我终极目标的更优雅架构，请明确指出并与我商量，不要受限于我最初的技术猜想。”
